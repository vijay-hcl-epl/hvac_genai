# HVAC Flap Actuator Demo Software Architecture

## 1. Architectural Style Selection and Justification

### Candidate Architectures Considered
- **Layered Architecture:** Separation of user interface, control logic, driver/IO, and hardware abstraction.
- **Component-Based Architecture:** Division into logical components (e.g., Command Handler, Flap Controller, Feedback Processor, LED Manager).
- **Monolithic Architecture:** Single-function block with all responsibilities handled in one main unit.
- **Event-Driven Architecture:** Functional units operate on events or messages (not explicitly required in requirements).

### Evaluation Against Criteria
- **System Complexity:** The system is moderately simple, with clear, non-concurrent operations (user commands, actuation, feedback, status LEDs). No need for multitasking.
- **Hardware Interaction:** Direct coordination with UART, ADC, motor driver, and LEDs, but all mapped predictably to clear software responsibilities.
- **Testability:** Requirements mandate modularity (SYS-REQ-043, SWE-REQ-041), favoring decomposition into testable units rather than a monolith.
- **Maintainability:** Modularity mandated (SYS-REQ-043), supporting clear unit separation and ease of change (e.g., separate user interface from control logic).
- **ASPICE Level-3:** Traceability, unit testability, separation of concerns, no hidden interfaces—all supported by a component-based architecture.

### Architecture Chosen: **Component-Based**
Component-based modular decomposition most closely addresses:
- Modularity (SYS-REQ-043)
- Clear test points (SWE-REQ-040, SWE-REQ-041)
- Explicit mapping and traceability to requirements
- Simplicity—no hidden cross-coupling or implicit state

### Rejected Alternatives
- **Monolithic:** Prevents modularity, hinders testability and long-term maintenance. Not in line with the requirements for modular, clear separation.
- **Layered:** Over-elaborate for small embedded demo; abstraction layering not required by system/software requirements.
- **Event-Driven:** Not merited, as requirements do not specify asynchronous operation or event/message queueing.

## 3. Software Units, Responsibilities, Interfaces

| Software Unit        | Responsibilities                                                        | Interfaces Provided          | Interfaces Used      |
|---------------------|-------------------------------------------------------------------------|------------------------------|----------------------|
| User Command Handler| - Accepts & validates UART commands (SWE-REQ-001/002/003)                | User Command API             | UART input/output    |
| Flap Position Controller| - Coordinates position targets, acts on valid commands, computes errors, invokes movement (SWE-REQ-004/005/006/007/008)| Position Control API | User Command Handler, Position Feedback Reader, Motor Controller|
| Motor Controller    | - Controls actuation signals, manages enabling/disabling, direction (SWE-REQ-009/010/011/012)| Motor Control API              | Flap Position Controller |
| Position Feedback Reader| - Reads ADC, computes position, validates range, filters input (SWE-REQ-013/014/015)| Position Feedback API      | ADC peripheral        |
| Status/LED Manager  | - Sets LEDs for position, error, power states; timing for updates (SWE-REQ-016/017)           | LED Control API                | Flap Position Controller |

## 4. Execution Model and Scheduling Policy Analysis
- No explicit execution model or scheduling policy is mandated by the requirements at this stage.
- The functional chain is simple, single-threaded, and driven only by valid user command receipt on UART.

## 5. Architectural Traceability
Each software unit maps directly to a logical theme of requirements (SWE.1).
- No new requirements introduced.
- No unmandated concurrency or scheduling included.
- No unrequired safety or cybersecurity logic imposed.

---
All architectural decisions and decomposition are strictly derived from the system and software requirements for the HVAC Flap Actuator Demo system (branch=new-b3). This architecture is fully ASPICE Level-3 capable for traceability, modularity, and testability.
