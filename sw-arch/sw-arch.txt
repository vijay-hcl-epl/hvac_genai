# 1.0 SWE.2 SOFTWARE ARCHITECTURE — HVAC FLAP ACTUATOR

## 1.1 Architecture Style Selection & Justification

### Candidate Styles Considered
- **Monolithic / Main-loop (Single Function Block)**
- **Layered Architecture (Interface-abstraction separation)**
- **Component-based (modular units with defined interfaces)**

### Evaluation
- **System complexity**: The system is simple, with discrete functional responsibilities; no dynamic tasking, OS, or concurrent scheduling. Component boundaries align with major abstractions only (I/O, Control Logic).
- **HW interaction**: Direct mapping to microcontroller peripherals (UART, GPIO/PWM, ADC). No abstraction needed beyond per-unit assignation.
- **Testability**: Modular structure at the function/unit level enables static and interface-level testing—especially for core logic and I/O.
- **Maintainability**: Layered/componentized units allow future extension (new sensor/motor, error logic) without design rupture.
- **ASPICE L3**: Component-based (unitized, testable, traceable, no invented behavior) satisfies L3 expectations while aligning tightly to SWE.1.

#### Style Decision
- **Selected:** Component-based (unitized abstraction: UART Interface, Position Feedback, Motor Actuation, Status Indication, Control Logic)
- **Rejected:**
  - Main-loop: Lacks modularity—a workaround for microcontroller projects, but not maintainable or ASPICE-suitable.
  - Layered: Overhead not justified—there are no cross-cutting platform services to separate (middleware, device drivers, etc).

## 1.2 SWE.2 Software Architecture Definition

### Execution Model
No explicit execution model or scheduling policy is mandated by the requirements at this stage. (SWE-REQ-033).

### Software Units, Responsibilities, Interfaces

#### Units and Responsibilities (Strictly Derived from SWE.1/REQs)
- **UART Command Handler**  
  - Responsibilities: Receive flap position commands, filter/validate numeric input, post valid commands to control logic.  
  - Interfaces Provided: UART RX interface (SWE-REQ-016).  
  - Interfaces Used: None (inputs data to control logic only).  
  - Trace: SWE-REQ-001, SWE-REQ-002, SWE-REQ-003

- **Position Feedback Handler**  
  - Responsibilities: Acquire ADC readings, map to logical position, flag out-of-range/error, provide current position to control logic.  
  - Interfaces Provided: Logical position output, status/error signal.  
  - Interfaces Used: ADC input peripheral.  
  - Trace: SWE-REQ-011, SWE-REQ-012, SWE-REQ-027

- **Flap Motor Actuation Unit**  
  - Responsibilities: Drive DC motor for flap via GPIO/PWM, support both directions, stop on command or error.  
  - Interfaces Provided: Motor control output (L298N driver interface).  
  - Interfaces Used: Control command from control logic, error from feedback.  
  - Trace: SWE-REQ-005, SWE-REQ-006, SWE-REQ-009, SWE-REQ-030

- **Status & Position Indicator Unit**  
  - Responsibilities: Drive status LED, indicate logical flap position using green LEDs, reflect state without patterns. 
  - Interfaces Provided: LED outputs.  
  - Interfaces Used: State from control logic.  
  - Trace: SWE-REQ-013, SWE-REQ-014, SWE-REQ-015

- **Control Logic & State Manager**  
  - Responsibilities: Orchestrate idle/wait, process valid commands, decide on actuation actions, issue control to actuator, update state, monitor error events, maintain system safety.  
  - Interfaces Provided: System state/status.  
  - Interfaces Used: Input from UART handler, Feedback handler, output to Actuator and LEDs.  
  - Trace: SWE-REQ-004, SWE-REQ-007, SWE-REQ-020, SWE-REQ-021, SWE-REQ-022, SWE-REQ-023, SWE-REQ-025

All responsibilities are mapped and justified *only* from SWE.1. NO invented or implied behaviors are included.

### Interfaces Between Software Units
- UART Handler ➔ Control Logic: command queue or function call
- Control Logic ➔ Motor Actuation: control signal (direction/stop)
- Control Logic ➔ Position Indicator: desired LED state
- Position Feedback ➔ Control Logic: current position/error
