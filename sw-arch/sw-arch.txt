# Software Architecture for HVAC Flap Actuator System

## 1. Candidate Architecture Styles

### Layered
- Provides separation between hardware abstraction, logic, and interfaces.
- Pros: Good maintainability, testability, traceability.
- Cons: May be overkill for simple, single-loop embedded control.

### Monolithic (“Superloop” Main)
- All logic in a single, clearly structured main loop calling functional blocks.
- Pros: Matches the simple state-driven, linear, single-responsibility nature described in requirements. Minimal overhead, maximum predictability.
- Cons: Less scalable for future extension to more features or concurrency.

### Component-based (Explicit MCU “Driver/Logic/UI” partition)
- Explicit components for each major I/O and logic, invoked from a shared controller.
- Pros: Modularization suitable for larger/distributed architectures, but not explicitly required in these requirements.
- Cons: Added complexity over monolithic for strictly single-function demonstrator.

## 3. Architecture Style Selection & Justification

**Chosen Style:**  
Monolithic (“Superloop” Main with clearly structured function calls and module boundaries).

**Justification:**  
- System and software requirements describe a single control path, simple I/O, no concurrent activity, and strictly linear/process demonstration responsibilities.
- Requirements explicitly note no asynchronous, multitasking, or complex scheduling needs.
- All hardware interactions are local and mapped 1:1 into the software logic.
- Modular structuring at the function/unit level inside a main loop supports maintainability and testability.
- Layered or component-based approaches are not mandated by requirements and would introduce avoidable complexity.

## 4. Architecture Definition

### 4.1 Software Units

| Software Unit            | Responsibilities                                                                              | Interfaces Provided       | Interfaces Used             |
|-------------------------|----------------------------------------------------------------------------------------------|--------------------------|-----------------------------|
| Main Control             | Initializes system, processes main control loop, coordinates unit interactions.               | Application Entry Point  | All below                   |
| UART Command Handler     | Receives/validates user commands, delivers numeric target to control logic.                   | UART Rx Decoder          | UART Peripheral, Main Ctrl  |
| Position Acquisition     | Reads potentiometer via ADC, maps raw value to logical position, validates range.             | Current Position Value   | ADC Peripheral, Main Ctrl   |
| Motor Controller         | Executes flap movement commands, direction, enable/disable, stops as required                 | Motor Control Signals    | GPIO, PWM, Main Ctrl        |
| LED Status Manager       | Controls power/status LED and position indication LEDs based on system/position state         | LED GPIO Control         | GPIO, Main Ctrl             |
| System State Manager     | Tracks current/target positions, command status, and safe system state.                       | Position/State Data      | Shared Data, Main Ctrl      |

### 4.2 High-level Architectural Diagram (Text Form)

```
             +-----------------+
             |  Main Control   |
             +--------+--------+
                      |
   +---------+--------+---------+----------+--------+
   |         |                  |          |        |
   v         v                  v          v        v
[UART]  [ADC:Pos.Acqu.]  [Motor Ctrl.] [LED Mgmt] [State Mgr]
   |         |                  |          |        |
   +---------+------------------+----------+--------+
                      |
               [Shared Data]
```

Legend:
- All data and control flow through "Main Control" in a sequential looping manner.
- Shared data (current/target pos, system state) is maintained in RAM.

### 4.3 Explicit Execution Model/Scheduling Policy

“No explicit execution model or scheduling policy is mandated by the requirements at this stage.”

- The super-loop/main-loop approach naturally fits the state-driven, event-driven system described.
- No timing, concurrency, or round-robin scheduling needs are found in requirements.
