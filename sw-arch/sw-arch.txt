# Software Architecture: HVAC Flap Actuator System (Branch: demo-43b)

## 1. Architecture Derivation and Style Evaluation

### Candidate Styles Considered
- **Monolithic**: All logic in a single control loop or function block/lightweight superloop.
- **Layered**: Separates interface, control logic, hardware abstraction, and low-level drivers.
- **Component-Based**: Segments by major domain function, with well-defined interfaces between components (e.g., Command Handler, Motor Control, Feedback Processor, Indication Controller).

### Evaluation Criteria
- **System Complexity**: Simple, single-actuator scope; no multitasking or dynamic allocation.
- **Hardware Interaction**: Requires explicit demarcation – UART, GPIO/PWM, ADC; isolated hardware domains.
- **Testability**: Must observe all functions via UART/LED; clear-state separation needed.
- **Maintainability**: System should be easy to extend to new feedback/indication strategies or alternate commands.
- **ASPICE Level-3**: Traceable, modular, transparent interfaces; separation of responsibilities without unneeded complexity.

### Selected Style & Justification
A **component-based, layered architecture** is chosen, combining clear logical separation (by domain responsibility) with a simple control and interface flow. This offers modularity (tracing to SWE.1), testability, and engineering clarity, avoiding the downsides of a flat monolith (poor traceability, hard to maintain) or a full deep-layered approach (overkill for scope).

## 3. Software Units, Responsibilities, and Interfaces

| Software Unit            | Responsibilities                                                                                                                   | Interfaces Provided                        | Interfaces Used                      |
|-------------------------|-------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------|--------------------------------------|
| User Command Handler    | Receive/validate UART commands; check allowed values                                                                               | Target position (to Position Ctrl Logic)    | UART RX                              |
| Position Control Logic  | Compare target/current; coordinate motor actuation; manage actuation states                                                        | Motor commands (to Motor Ctrl), LED update | Target/Current position from Feedback |
| Motor Control           | Drive motor via GPIO/PWM; enforce exclusive direction; safe-stop on error/target reached                                           | Hardware motor signals                     | Motor commands from Control Logic     |
| Feedback Acquisition & Processing | Acquire/sanitize ADC; map to position indices; filter signals; check validity                                      | Current position (to Control Logic/Ind)     | ADC input                            |
| Status/LED Indication   | Power/status and position LED control; update on changes                                                                           | Visual state                               | Position info from Ctrl/Feedback      |
| System Config/Data      | Store config (ADC ranges, state vars); provide shared access to position/command data                                              | Internal state                             | All                                  |

## 4. Interface and Execution Model Considerations
- Interfaces are function calls or logical message-passing within microcontroller code.
- Hardware-layer access (ADC, UART, GPIO) is strictly isolated within each hardware-facing unit.
- All state flows through System Config/Data.
- **No explicit execution model or scheduling policy is mandated by the requirements at this stage.** (Polling or event-driven dispatch is an implementation detail, not architecturally required or justified by SWE.1/requirements.)

## 5. Architecture Constraints & Traceability
- All defined units are directly traceable to one or more SWE.1 requirements (see user command, control, feedback, motor, LED, state/data units).
- No new requirements, behaviors, or side-effects are introduced.
- No safety/cybersecurity/diagnostics logic is present.
- No code, implementation algorithms, or detailed data shapes are included.

## 6. Change/Extension Implications
- Adding further positions/actuators: extend Feedback/Motor, update mapping/config unit.
- Changing user interface: replace/augment User Command Handler; rest unchanged.
- Introducing RTOS/concurrency: revisit only if justified by new requirements.
