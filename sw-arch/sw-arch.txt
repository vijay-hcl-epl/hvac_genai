# Software Architecture Specification – HVAC Flap Actuator

## 1.0 Introduction
This document defines the software architecture for the HVAC flap actuator system based strictly on the system (sys-reqs.txt) and software requirements (sw-reqs.txt) provided on branch new-b12.

All architectural decisions, units, responsibilities, and interface definitions are strictly traceable to requirements. No architectural mechanism, design, or execution model is introduced unless justified by an explicit requirement.

## 2.0 Candidate Architecture Styles
Based on requirements analysis, the following architectural styles were considered:

| Style              | Complexity | HW Interaction | Testability | Maintainability | ASPICE L3 |
|--------------------|------------|---------------|-------------|----------------|-----------|
| Monolithic         | LOW        | DIRECT        | GOOD        | BASIC          | OK        |
| Layered            | LOW-MED    | DIRECT        | GOOD        | MODERATE       | OK        |
| Component-based    | MED        | DIRECT        | GOOD        | GOOD           | OK        |

- **Monolithic:** All functionalities are in a single program unit. Simplicity, minimum overhead, but poor concern separation.
- **Layered:** Software structured in layers: Input, Control/Logic, Hardware Abstraction. Clear functional separation, easy to maintain, and supports ASPICE SWE.2/3 clarity.
- **Component-based:** Each major function (command handler, motor control, feedback, status indicator) as a discrete component/unit, interacting via clear interfaces; clarity and testability, moderate overhead for such a simple system.

## 3.0 Architectural Style Selection and Justification

### Selected Style: **Layered Architecture**

**Justification:**
- Requirements (SYS-REQ-057) explicitly mandate separation of concerns for maintainability and education.
- HW interfaces are simple and do not warrant heavy-weight modularization.
- Layered structure provides clear traceability and unit testing, meets the ASPICE L3 expectations for modularity/testability without introducing unnecessary artifacts.
- Overhead for stricter component-ization is not justified; monolithic does not satisfy the separation constraint.
- Fully justified by the requirements—no additional complexity introduced.

## 4.0 Software Units, Responsibilities, and Interfaces

### High-Level Architectural Diagram (Text-based)
```
[User UART Cmds]  --->  [Input Handler]
                                |
                                v
                    [Control Logic Unit]
                /          |            \
 [Motor Driver]   [Position Feedback]  [LED Status]
```
Legend:
- [Input Handler] handles UART, filtration, and one-command-at-a-time.
- [Control Logic Unit] processes positions, checks validity, manages state machine.
- [Motor Driver] unit for GPIO/PWM control, direction, enable/disable.
- [Position Feedback] unit for ADC acquisition, position mapping, monitoring.
- [LED Status] unit for status and position LEDs.

### Architecture Table
| Unit                  | Responsibilities                                                        | Interfaces Provided              | Interfaces Used                   |
|-----------------------|------------------------------------------------------------------------|----------------------------------|------------------------------------|
| Input Handler         | UART command acquisition/parsing, validation, one-at-a-time enforcement | Command Input API                | UART                              |
| Control Logic Unit    | Command execution, state tracking, validity checking, delegation        | PositionCtrl API, State API      | Command Input, MotorCtrl, Feedback, LEDCtl |
| Motor Driver          | GPIO/PWM output, direction, actuation, driver state                    | MotorCtrl API                    | Output GPIO/PWM                   |
| Position Feedback     | ADC acquisition, position mapping, range checks, noise rejection       | Feedback API                     | ADC input                         |
| LED Status            | Power/position LED control, fault indication                           | LEDCtl API                       | Output GPIO                       |

#### Interface Definitions:
- Command Input API: Receives validated, parsed user command.
- PositionCtrl API: Provides actuation requests to Motor Driver.
- State API: Provides status to outside (testing/manual verification).
- MotorCtrl API: Abstracts hardware actuation.
- Feedback API: Supplies current/last position; warns on errors.
- LEDCtl API: Controls/updates LEDs.

## 5.0 Execution Model & Scheduling
- There is **no explicit requirement** for a periodic, concurrent, or task-based execution model with scheduling.
- All requirements are compatible with a simple event-driven or polling main loop.
- **Explicit Statement:** _“No explicit execution model or scheduling policy is mandated by the requirements at this stage.”_

## 6.0 Traceability
All software units and interfaces are traceable to SWE.1 requirements. No additional requirements, safety, security, or behavioral assumptions are introduced. No unit-level algorithms or implementation details are included here. This architecture strictly fulfills the derived needs of the prototype HVAC flap actuator system as outlined in both system and software requirements.
