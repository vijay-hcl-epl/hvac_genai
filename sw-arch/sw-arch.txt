# 1.0 Introduction
The software architecture for the HVAC Flap Actuator system employs a modular, component-based style designed for traceability, separability, and clarity in educational demonstration contexts. The architecture enables explicit mapping to every functional, interface, behavioral, configuration, error handling, and testability requirement defined in the SWE.1 requirements document.

## 1.1 Style Decision and Alternatives
- Chosen Style: Modular/Component-based (strong separation by responsibility)
- Alternatives Considered: Monolithic (rejected – poor traceability/maintainability), Layered (rejected – unneeded additional abstraction)
- Rationale: Maximizes ASPICE traceability, supports single responsibility per unit, and ensures maintainability for demos.
- No architecture-level decision for scheduling, tasks, concurrency, or real-time partitioning is made (explicitly deferred).

- All unit interfaces are C functions or data structures. No messaging, queues, events, or implicit RTOS features are present.
- All interface calls are direct/static. No scheduling, polling, or concurrency model is introduced.

# 5.0 Architecture Constraints & Notes
- No RTOS/tasks/threads assumed or defined.
- All scheduling/execution policy is deferred to later phases.
- All units are stateless except where holding current or target position is mandatory.
- Designed for static, pedagogical demonstration and easy modification.

# 6.0 Requirements Tracing
Each unit interface/function provides direct traceability to at least one SWE.1 requirement.
No requirements are omitted, and all SWE.1 exclusions/restrictions are obeyed.

# 7.0 Glossary
- Unit: Coherent software module with one main responsibility
- ADC: Analog-to-Digital Converter (potentiometer interfacing)
- UART: Universal Asynchronous Receiver-Transmitter (PC user interface)
- GPIO: General Purpose I/O pin (motor and LED control)
