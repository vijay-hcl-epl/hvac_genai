# SOFTWARE ARCHITECTURE FOR HVAC FLAP ACTUATOR

## 1. Architecture Style Identification

**Candidate Styles:**
1. Layered design (Input, Logic, Output separation)
2. Component-based (distinct components for each major function)
3. Monolithic (all SW in a unified block without separation)

**Evaluation:**
- System Complexity: Low (single actuator, localized interaction, simple logic)
- Hardware Interaction: Multiple peripherals (UART, ADC, GPIO, PWM)
- Testability: Improve by clear separation of concerns
- Maintainability: Improve by modular assignment (per requirements)
- ASPICE L3: Requires SW units and explicit interfaces (not monolithic “blob”)
- Requirements: Explicitly call for "clear separation between input handling, control logic, feedback acquisition, and status/output indication" (SYS-REQ-047)

**Selected Style:**
> **Layered/component-based architecture with the following software units:**
> - Command Handler
> - Flap Controller (Core Logic)
> - Motor Control
> - Position Feedback
> - Status Indicator

**Justification:**  
This separation matches the requirements (SYS-REQ-047), maximizes testability/maintainability, keeps units small/traceable, and aligns with ASPICE L3 expectations. Monolithic style is rejected for lack of clarity/traceability/testability. Component style (one component per function) and “layered” are nearly equivalent at this scale.

## 2. Architecture Definition

### 2.1 Software Units and Responsibilities

| Software Unit         | Responsibilities                                                                              | Interfaces Provided            | Interfaces Used                |
|---------------------- |----------------------------------------------------------------------------------------------|-------------------------------|-------------------------------|
| Command Handler       | Receives UART commands, validates, forwards valid commands, ignores invalid ones              | CmdIn (valid command/none)    | UART                          |
| Position Feedback     | Reads ADC, maps to logical flap positions, detects out-of-range, provides position/valid flag | CurrentPosition, ValidFeedback| ADC; CalibrationData          |
| Flap Controller       | Receives commands & feedback, runs flap state machine, issues target/movement/order           | ControlOrder (move/stop)      | CmdIn, CurrentPosition, ValidFeedback |
| Motor Control         | Sets GPIO & PWM for motor enable/direction/stop, driven by Flap Controller                   | MotorStatus                   | ControlOrder                  |
| Status Indicator      | Sets LEDs per position/power, reflects current system state, supports feedback for test       | (none/LED states)             | CurrentPosition, MotorStatus  |

**Interfaces are strictly functions for data or control exchange, not hardware drivers. Drivers are at the “infrastructure layer” and not explicitly modeled here as units.**

### 2.2 High-Level Architecture Diagram (Text-Based)

```
┌───────────────────────────┐
│      Command Handler      │⇐─ UART
└───────┬───────────────┬───┘
        │               │
        │               │
        ▼               │
┌───────────────────┐   │
│ Position Feedback │   │
└──────┬────────────┘   │
       │                │
       ▼                │
┌───────────────────┐   │
│  Flap Controller  │◄──┘
└────┬──────────────┘
     │
     ▼
┌─────────────┐    ┌────────────────────┐
│Motor Control│    │  Status Indicator  │
└─────────────┘    └────────────────────┘

Dependencies:  
- Flap Controller: receives validated command (CmdIn), position info (CurrentPosition), validity (ValidFeedback)
- Motor Control: receives order (move/stop) from Flap Controller
- Status Indicator: driven by current position, power, movement (from Flap Controller or Position Feedback, as units choose)
```

### 2.3 Explicit Execution Model/Scheduling Mechanism

**Analysis:**  
No requirements mandate explicit execution model (no preemption, no periodic real-time tasks, no concurrency required). Per SWE-REQ-036:

> “...without introducing explicit timing or scheduling requirements.”

**Statement:**  
>No explicit execution model or scheduling policy is mandated by the requirements at this stage.

## 3. Architecture Constraints

- All structure and interfaces are derived from requirements
- No new requirements, system behavior, safety, or security logic introduced
- No architectural complexity (scheduling, OS, separation for safety) added, as not required
- No implementation, detailed algorithms, or code supplied; all unit-level decisions are left for SWE.3
- Maintains direct traceability to SWE.1 (software requirements), all requirements mapped
