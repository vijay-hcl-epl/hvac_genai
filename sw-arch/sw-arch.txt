# Software Architecture Document
## HVAC Flap Actuator System

### 1. Architecture Style Candidates & Evaluation

**Candidate Styles:**
- Monolithic (single block)
- Layered (logical separation by function/responsibility)
- Component-based (distinct interfacing modules)

**Evaluation Criteria:**
- **System Complexity**: System controls a single actuator with simple IO; low internal complexity.
- **Hardware Interaction**: All software units require direct, mapped hardware access.
- **Testability & Maintainability**: Modularity important for educational use and clarity (see SYS-REQ-045/SWE-REQ-045).
- **ASPICE Level-3 Compliance**: Requires clear, documented separation of responsibilities and testable interfaces.

**Choice & Rationale:**
- We select a **layered/component-based hybrid**:
  - SW units are logically defined and correspond to requirement groupings, each with identifiable interfaces.
  - Explicit layering is minimized due to flat system complexity; focus is on functional separation.

**Justification:**
- Direct mapping to requirement structure and behavioral splits (SWE-REQ-045, SWE-REQ-046, SYS-REQ-045).
- Layered monolith would obscure testability and traceability; pure component style adds unnecessary abstraction.
- Hybrid ensures maintainability and traceability with minimal overhead.

### 2. Architecture Definition

#### High-Level Architecture Diagram (text-based)

```
+------------------+
| User Command     |<------UART------+
| Handler Unit     |                 |
+------------------+                 |
         |                            |
         v                            |
+------------------+                  |
| Position Control |<-----+           |
| Logic Unit       |      |           |
+------------------+      |           |
         |                |           |
         v                |           |
+------------------+      |     +------------------+
| Motor Control    |<-----+-----| Feedback         |
| Unit             |           | Acquisition Unit  |
+------------------+           +------------------+
         |                                |
         v                                v
+------------------+               +------------------+
| Status/LED       | <------------ | System Config &  |
| Indication Unit  |               | Data Repository  |
+------------------+               +------------------+
```

#### Software Unit Breakdown & Interfaces

| Software Unit          | Responsibilities                                             | Interfaces Provided   | Interfaces Used        |
|------------------------|-------------------------------------------------------------|----------------------|-----------------------|
| User Command Handler   | Receives UART input; parses and validates target commands.   | Command API          | UART                  |
| Position Control Logic | Compares desired vs. actual, sequences actuation; holds/idle.| Move/hold/stop API   | Feedback API, Command |
| Motor Control          | Drives GPIO/PWM to actuator motor per control logic.         | Motor HW API         | Control API           |
| Feedback Acquisition   | Reads ADC, maps/validates position, flags faults.            | Feedback API         | ADC                   |
| Status/LED Indication  | Updates LEDs to reflect state and flap position.             | Indication API       | Control, Feedback     |
| System Config/Data     | Holds static configuration, logical flap mapping.            | Config/Mapping API   | All units             |

#### Additional Analysis
- No explicit execution model or scheduling policy is mandated by the requirements at this stage. All interfaces/processes must assume sequential (single context) execution by default.
- All timing, concurrency, and scheduling needs are explicitly excluded (see SWE-REQ-050, SWE-REQ-051).

### 3. Traceability to SWE.1 Requirements
- Each unit and interface reflects explicit groupings and trace references (see documentation table above) according to SWE requirements.
- No new requirements, safety/cyber logic, or behavioral changes introduced.

### 4. Constraints
- Module decomposition is logical for traceability; no code-level split is prescribed.
- All interface and data boundary details shall be refined in SWE.3.
