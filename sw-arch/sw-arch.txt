# Software Architecture for HVAC Flap Actuator System

## 1. Architecture Style Selection

### Candidates Considered
- Layered
- Component-Based/Modular
- Monolithic (Static Single-Loop/Main-Event)

### Evaluation
- System complexity, hardware interaction, testability, maintainability, and ASPICE Level-3 compatibility were the primary criteria.
- Requirements clearly indicate a simple, MCU-local, sequential logic system, with all hardware interfacing direct from the microcontroller.
- No requirements for multitasking, externalization, plug-in, or network effects.

### Selected Architecture
- **Monolithic Static Fore-Loop with Clearly Separated Modules** (single-threaded, main loop calls all units in a deterministic order)
- **Justification:**
  - Minimal system complexity, direct hardware interaction
  - Testable via modular function/unit boundaries
  - No need for concurrency, service abstraction, or complexity of a layered/component system
  - Fully meets ASPICE compositional and traceability structure
  - No requirements support or justify more complex architectural styles

## 2. Software Units & Responsibilities

| Software Unit                | Responsibilities                                                                                      | Interfaces Provided                 | Interfaces Used                    |
|------------------------------|------------------------------------------------------------------------------------------------------|-------------------------------------|-------------------------------------|
| Main Application Control     | System initialization, main loop sequencing, command/result dispatch                                 | Application Entry/Initialization    | All below units                    |
| UART Command Handler         | Receive, parse, validate UART commands; provide target position input                                | Target position value, status flags | UART peripheral, Main Control      |
| Flap Movement Controller     | Compare current/target positions, decide/command motor action, issue stop                            | Motor enable/dir, move/stop cmd     | Position State, Motor Controller   |
| Motor Driver Controller      | Actual GPIO/PWM control for motor driver based on commands from Flap Movement Controller             | Motor drive signals                 | MCU GPIO/PWM HW, Movement Ctrl     |
| Position Feedback Processor  | Read ADC, map/calibrate ADC to logical position, detect validity                                     | Current flap position, validity     | ADC peripheral                     |
| LED Status Driver            | Set status/position LEDs based on application state and position                                     | LED drive signals                   | MCU GPIO HW                        |
| Configuration/Calibration    | Store ADC thresholds, ranges, and system config                                                     | Config data to all units            | None (read-only for other modules) |
| Error & Safe State Handler   | Detect/handle invalid ADC, invalid command, enforce safe motor/LED states if any invalidity detected | Motor stop, safe state flags        | All above (signals only)           |

## 4. Explicit Scheduling & Execution Model

No explicit execution model or scheduling policy is mandated by the requirements at this stage. The main loop sequentially invokes each module’s processing “step” each cycle (UART → validation → logic → hardware I/O → feedback → indicators).

## 5. Architecture Constraints & Notes
- Traceable to SWE.1 requirements
- No new requirements introduced
- No system behavior changed
- No safety/cybersecurity logic added (none required by requirements)
- No implementation or unit-level algorithms
- All interfaces are logical/module-level, not runtime-separated

## 6. Architectural Traceability
- Architecture strictly supports and is derived from SYS-REQ and SWE-REQ identified in the requirements.
- No mechanisms, patterns, or code introduced that are not justified by requirements.
