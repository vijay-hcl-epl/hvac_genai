# 1.0 Architecture Style Evaluation and Decision

## Candidate Architectures Considered
1. Layered Architecture
2. Component-Based (Modular) Architecture
3. Monolithic Architecture

### Evaluation
- **System Complexity:** The system is moderately complex and must support educational clarity and maintainability. All logic centers around a single actuator with no concurrency or multi-device scaling.
- **Hardware Interaction:** Multiple hardware interfaces (UART, ADC, GPIO, PWM/Timer).
- **Testability:** Important to allow isolated validation (process, logic, I/O, indication).
- **Maintainability:** System must be modifiable for demonstration/extension.
- **ASPICE Level-3:** Explicit modularity, distinct separation of logic, I/O, and error handling are required for traceability and compliance.

#### Rationale
- **Monolithic:** Simple, but hinders traceability, clarity, and maintainability; not compliant with ASPICE Level-3.
- **Layered:** Reasonable, but would introduce artificial layering without significant communication/protocol abstraction.
- **Component-Based (Modular):** Most naturally supports clear mapping of software requirements and system functions to explicit software units/modules; best for testability, traceability, and educational needs.

**Chosen Architecture Style:**
- **Component-Based Modular Software Architecture**
- **Justification:** Directly traceable to requirements. Provides clarity, modularity, and maintainability. Easiest for demonstration and supports ASPICE Level-3 process objectives.

# 2.0 Software Units, Responsibilities, and Interfaces

## Logical Software Units
| Unit Name               | Main Responsibilities                                                                                          | Interfaces Provided            | Interfaces Used                |
|------------------------|--------------------------------------------------------------------------------------------------------------|-------------------------------|-------------------------------|
| CommandHandler         | - Receive and validate UART commands\n- Filter/parse/dispatch position commands                              | Command API                   | UART, FlapControlLogic        |
| FlapControlLogic       | - Compare current/target position\n- Decide movement direction, start/stop\n- Safeguard limits               | Flap Control API               | PositionFeedback, MotorDriver |
| PositionFeedback       | - Sample ADC\n- Map ADC to logical position\n- Validate readings, range-check                                  | Position API                   | ADC                           |
| MotorDriver            | - Set GPIO for motor output\n- Manage PWM/enable signals\n- Enforce movement boundaries/set motor state      | Motor Driver API               | GPIO, PWM                     |
| StatusIndicator        | - Update status/position LEDs according to state\n- Ensure exclusive green LED indicator                      | Status API                     | GPIO                          |
| ErrorHandler           | - Handle invalid command/ADC/motor error cases\n- Idle/stop as fallback\n- Route error feedback if needed    | Error API                      | All units (callback if reqd)  |
| UART                   | - Abstract UART receive handler\n- Deliver RX data events                                 | UART API                  | Hardware UART                 |
| ADC                    | - Abstract ADC sampling\n- Provide readings on request                                  | ADC API                   | Hardware ADC                  |
| GPIO                   | - Abstract GPIO pin set/clear functions                                  | GPIO API                  | Hardware GPIO                 |


# 3.0 Interface Overview

- **All communication is via static invocation (no messages/queues).**
- Data flows: UART → CommandHandler → FlapControlLogic → MotorDriver & StatusIndicator, with feedback from PositionFeedback.
- ErrorHandler accessible from any unit.
- UART, ADC, GPIO abstract hardware details.

# 5.0 Execution Model/Scheduling
No explicit execution model or scheduling policy is mandated by the requirements at this stage. All event handling is assumed to be top-level cyclic or interrupt-driven by drivers, as is typical for STM32 MCU demonstration environments. Requirements explicitly exclude multi-command, multitask, or explicit periodic scheduling.

# 6.0 Justification of Architectural Boundaries
- Each unit aligns with clear software requirements (see mapping below)
- No new requirements; purely modularization for clarity and demonstration per ASPICE
- All interfaces are synchronous, direct, and do not require RTOS, queues, or scheduling abstraction
- No safety, cybersecurity, or implementation-specific logic is introduced
