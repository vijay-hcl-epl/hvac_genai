# Software Architecture for HVAC Flap Actuator System

## 1. Architecture Style Selection and Evaluation

**Candidate Styles:**
- Monolithic
- Layered
- Component-based / Modular

**Evaluation:**
| Style        | System Complexity | Hardware Interaction | Testability | Maintainability | ASPICE Level-3 | Comments |
|-------------|------------------|---------------------|-------------|----------------|----------------|----------|
| Monolithic  | Simple, but inflexible | Direct           | Poor        | Poor           | Poor           | Not easily modifiable, difficult for demo/education |
| Layered     | Flexible, can be overkill| Good separation | Good        | Good           | Good           | Unneeded abstraction (only 1 MCU, 1 actuator, 1 control path) |
| Component-based | Clear separation | Direct            | Excellent   | Excellent      | Excellent      | Best matches separation-of-concerns, traceability, demo needs |

**Style Selected:** Component-based / Modular

**Justification:**
- System requirements (SYS-REQ-052, SYS-REQ-053) and software requirements explicitly require clear separation of responsibilities for maintainability, modifiability, and educational/demo use.
- Single microcontroller and actuator allow simple, explicit interface design with no need for complex scheduling, layers, or runtime abstraction.
- ASPICE Level-3 expects modularity, traceability, and ease of test; component style directly maps requirements and is easy to verify.

## 2. Architectural Definition

### Software Units & Responsibilities

| Software Unit        | Responsibilities                                            | Interfaces Provided               | Interfaces Used               |
|---------------------|------------------------------------------------------------|-----------------------------------|-------------------------------|
| CommandHandler      | Receive/validate UART user commands, set target position    | UART command parser               | UART (rx)                     |
| FlapControlLogic    | Compare current/target pos., drive logic for movement      | Flap position management          | CommandHandler, PositionFeedback, MotorDriver, StatusIndicator |
| MotorDriver         | GPIO/PWM for motor dir/enable; enable/disable motor        | Motor direction and enable control| GPIO, PWM                     |
| PositionFeedback    | Acquire/process ADC, map raw to logical position           | Current position output           | ADC                           |
| StatusIndicator     | LED control: power/position, update on change              | LED status interface              | GPIO                          |
| ErrorHandler        | Safe-state handling for invalid input/feedback             | Error trigger & reporting         | System calls, StatusIndicator |

### Execution Model/Scheduling Analysis

No explicit execution model or scheduling policy is mandated by the requirements at this stage. All interaction is driven by user UART commands and direct state-based logic, without concurrency or periodic tasking need.

### Architecture Constraints
- Architecture is strictly traceable to SWE.1 requirements (see mapping table below).
- No new requirements introduced; does not alter system behavior, does not add safety or cybersecurity logic, no implementation or code details, and no unit-level algorithms.
