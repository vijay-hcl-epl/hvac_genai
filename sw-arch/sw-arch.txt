# HVAC Flap Actuator ECU: Software Architecture (SWE.2)

## 1. Architecture Style Selection

Candidate Styles Considered:
- Layered
- Component-based
- Monolithic

**Evaluation and Selection:**
- The system and software requirements (see SWE-REQ-023, 036) expressly demand separation of concerns for modularity and testability. Multiple distinct functionality domains are present: command parsing, actuation, feedback acquisition, status indication, diagnostics.
- Hardware adaptation and testability both favor distinct, loosely-coupled blocks.
- ASPICE L3 expects justifiable architectural structuring and explicit traceability.

**Decision:**
- Selected: "Component-based architecture." Each major functional area (as derived from requirements) is implemented as an explicit software unit. (TRACE: SWE-REQ-023, 036)
- Rejected: "Layered" (No requirement for stack/hierarchy or forced abstraction). "Monolithic" (Rejected due to maintainability and testability needs in SWE.1).


## 2. Architecture Definition

**Execution Model:**
No explicit execution model or scheduling policy is mandated by the requirements at this stage.

**Software Units (with SWE.1 traceability):**

1. Command Handler  
  - SWE-REQ-001, 002, 012, 024, 035
2. Flap Motor Control  
  - SWE-REQ-003, 005, 006, 014, 028
3. Position Sensor Processing  
  - SWE-REQ-007, 008, 013
4. Status Indication (LED)  
  - SWE-REQ-009, 010, 015, 027
5. State & Error Manager  
  - SWE-REQ-011, 017, 018, 019, 020, 021, 022, 023, 026, 029
6. Config/Data Manager  
  - SWE-REQ-023, 024, 025, 033, 034, 036
7. Diagnostic Interface  
  - SWE-REQ-035

All responsibilities and interfaces are derived strictly from SWE.1 requirements. No additional mechanisms, behaviors, or implementation algorithms are present.

### (B) Architecture Table

| Software Unit          | Responsibilities                                              | Interfaces Provided                              | Interfaces Used                     |
|-----------------------|--------------------------------------------------------------|--------------------------------------------------|-------------------------------------|
| Command Handler        | Parse/validate UART cmds, dispatch to State Manager           | Parsed command API                               | UART, State Manager, Config/Data    |
| Flap Motor Control     | DC motor actuation per target, stop on fault/target reached  | Motor control API                                | State Manager, Position Sensing     |
| Position Sensor Proc.  | Acquire sensor via ADC, convert to flap position             | Position getter API                              | ADC, Config/Data                    |
| Status Indication      | Drive LEDs for all operating states/errors                   | LED status control                               | State Manager, Config/Data          |
| State & Error Manager  | System state machine, error monitoring, event coordination   | State/transition/status notification             | Command Handler, Motor Ctrl, Status |
| Config/Data Manager    | Maintain system configs & dynamic data                       | Config/data getter/setter                        | All                                 |
| Diagnostic Interface   | Accept/trigger diagnostics, expose status                    | Diagnostic commands/status API                   | UART, All main units                |


## 4. Constraints and Strict Adherence
- All functional boundaries, units, and interfaces have been mapped directly from SWE.1 (see table above for explicit traces).
- No functional, timing, safety, or diagnostic enhancements beyond requirements scope.
- No implementation details; no code; no unit-level algorithms.
- No invented requirements.
