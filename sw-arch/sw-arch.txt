1.0 Software Architecture for HVAC Flap Actuator
================================================

This document defines the software architecture, derived exclusively from documented requirements in sys-reqs/sys-reqs.txt and sw-reqs/sw-reqs.txt (branch hvdemo-142b). No functionality, assumptions, or interfaces are invented. All structural/architectural decisions trace directly to requirements. No code, algorithms, safety/security, or diagnostics are included, in accordance with workflow rules.

------------------------------------------------
2.0 Architecture Style Selection (SWE.2.A)
------------------------------------------------
Candidate styles evaluated:

- Monolithic: All logic in one software entity.
- Layered: Separation of application logic, hardware abstraction, and device drivers.
- Component-based: Discrete software units for command handling, flap control, feedback acquisition, and indication.

Evaluation:
- System complexity is low (single actuator, single user command, simple feedback).
- Direct hardware interaction via UART, ADC, GPIO, and PWM required (SWE-REQ-019...SWE-REQ-022).
- ASPICE expects separation to ensure testability (SWE-REQ-044, SYS-REQ-041), maintainability, and traceability.

Selection: Component-based architecture.

Justification:
- Layered is rejected as no multi-layered abstraction is needed for this hardware and functional partitioning (SWE-REQ-023: no other interfaces, SWE-REQ-040: resource constraints).
- Monolithic is rejected as it hinders testability/modularity (SWE-REQ-044, SYS-REQ-041).
- Component-based is justified to enable testability (SWE-REQ-044), interface clarity (SWE-REQ-019 to -022), and precise functional assignment.
