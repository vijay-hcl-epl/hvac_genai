# Software Architecture for HVAC Flap Actuator System

## 1. Architecture Style Selection and Justification

### Candidate Styles Considered
1. **Layered Architecture**
   - Modularizes by device drivers, control logic, and application layer.
   - Pros: Separation, testability.
   - Cons: Complex for simple system.
2. **Component-Based Architecture**
   - Functional blocks for each main role/component.
   - Pros: Responsibility separation, maintainability, ASPICE alignment, clear mapping to requirements.
   - Cons: None significant for this scale.
3. **Monolithic Architecture**
   - All logic in a single block.
   - Pros: Simplicity.
   - Cons: Poor maintainability, testability, traceability (not suitable for ASPICE).

### Evaluation and Selection
Requirement analysis (not assumptions):
- Explicit demands for modularity and separation (SYS-REQ-053, SWE-REQ-048).
- Traceability and testability (SWE-REQ-043 to 045, SYS-REQ-055 to 057).
- Simple hardware and no concurrency requirements.

**Selected Style: Component-Based Architecture**
- Provides modular, maintainable structure.
- Enables clear traceability from SWE.1 requirements to software units.
- Supports ASPICE Level-3 rigor.

## 2. Software Units, Responsibilities, Interfaces

| Software Unit           | Responsibilities                                                               | Interfaces Provided         | Interfaces Used                         |
|------------------------|--------------------------------------------------------------------------------|-----------------------------|------------------------------------------|
| Command Handler        | Accept and validate UART commands; convert to target positions                  | Position Command API        | UART Driver                              |
| Motor Control Logic    | Compare actual/target positions; command movement, direction, stop              | Motor Control API           | ADC/Feedback Logic, Motor Driver         |
| Position Feedback Logic| Read potentiometer (ADC); map to flap position; check for error                 | Position Feedback API       | ADC Driver                               |
| LED Status Indication  | Control LEDs for power/status/position                                         | LED Indication API          | GPIO Driver, Motor/Position Logic        |
| UART Driver            | UART peripheral access, IRQ or polling                                         | UART char RX/TX             | Hardware UART Registers                  |
| ADC Driver             | ADC channel read abstraction                                                    | ADC read API                | Hardware ADC Registers                   |
| Motor Driver           | GPIO/PWM abstraction for motor (enable/direction)                              | Motor enable/dir control    | GPIO Driver, Hardware Pins               |
| GPIO Driver            | Provide GPIO pin control for motor/LEDs                                        | GPIO API                    | Hardware GPIO Registers                  |

## 3. High-Level Architecture Diagram (Text-Based)

```
[UART Driver] <---> [Command Handler] <---------+
                                                |
[ADC Driver] <---> [Position Feedback Logic] <--+
                                                |
[Motor Driver] <--- [Motor Control Logic] <-----+
                                                |
[GPIO Driver] <--- [LED Status Indication] <----+
```
- Each block is a clear software unit (as per ASPICE, SWE-REQ-048, SYS-REQ-053).
- All hardware access is through drivers, used only by logic units.

## 4. Scheduling & Execution Model

**No explicit execution model or scheduling policy is mandated by the requirements at this stage.**
- Event-driven loop or simple cooperative polling suffices.
- No multitasking/concurrency/RTOS is required or allowed unless later justified by requirements.

## 5. Additional Architecture Constraints (per Requirements)
- No new requirements introduced.
- No implementation/code/algorithm details here; unit details are deferred to design (SWE.3).
- Safety/cybersecurity/diagnostics, dynamic reconfiguration beyond requirements are not present.
- All interfaces/unit boundaries exist solely to satisfy allocated requirements and traceability.

## 6. Traceability
- All units and interfaces are traceable to SWE.1 requirements.
  - Command Handler: SWE-REQ-001–005
  - Motor Control Logic: SWE-REQ-006–013
  - Position Feedback Logic: SWE-REQ-014–017
  - LED Status Indication: SWE-REQ-018–020
  - All drivers: SWE-REQ-021–024, and indirectly for HW management
