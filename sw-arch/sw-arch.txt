## Traceability: All decisions below explicitly traced to SWE.1 (Software Requirements)

---

## ARCHITECTURE STYLE SELECTION

### Candidate Styles
1. Layered Architecture
2. Component-Based Architecture
3. Monolithic Architecture

#### Evaluation Criteria (per ASPICE L3 and project context)

| Style               | System Complexity | HW Interaction Needs | Testability | Maintainability     | ASPICE L3 Compliance    |
|---------------------|------------------|---------------------|-------------|---------------------|-------------------------|
| Layered             | Handles moderate complexity. May be overkill for simple direct-control needs. | Easy to segregate HW abstraction. | High – can test layers independently. | Good; changes in one layer isolated. | Strong, if layering justifiable. |
| Component-Based     | Ideal for high modularity; breaks down by HW/control/logical function. | Clear HW/component boundary. | High – component-level test feasible. | Strong, but adds interface overhead. | Excellent if requirements support strong modular boundaries. |
| Monolithic          | Direct, simplest for tightly-coupled logic. | No explicit separation; fastest for coupling. | Less so – all logic tangled. | Poor; hard to refactor/extend. | Minimal; generally not favored. |

### Selection
- Requirements (see SWE-REQ-019, SWE-REQ-032) mandate modularity and platform abstraction, allowing position mapping, motor control, and command parsing to be updated independently.
- Direct monolithic is not justifiable; maintainability and modularity explicitly needed.
- Layered vs. Component-Based: Component-based yields clearer mapping to the independent axes (command, control, feedback, interface abstraction) required.

**Selected Style**: Component-Based Architecture
**Rejected Styles**:
- Layered: Not chosen due to limited layering in such a simple direct-control embedded system; actual "layers" become trivial wrappers.
- Monolithic: Not acceptable; violates modular/maintainable structure per SWE-REQ-032, SWE-REQ-019.

## ARCHITECTURE DEFINITION

### Software Units (with Responsibility & Traces)

- **Command Parser**  
  Parses incoming UART bytes. 
  [Traces: SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-015, SWE-REQ-022]

- **Flap Control Logic**  
  Decides if/when movement is necessary, mediates between commanded and current position.  
  [Traces: SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-023, SWE-REQ-024, SWE-REQ-031]

- **Motor Driver**  
  Sets PWM/GPIO outputs.  
  [Traces: SWE-REQ-007, SWE-REQ-008, SWE-REQ-016, SWE-REQ-025, SWE-REQ-036, SWE-REQ-038]

- **Feedback Processor**  
  Reads ADC, validates sample, translates to logical positions.  
  [Traces: SWE-REQ-010, SWE-REQ-011, SWE-REQ-017, SWE-REQ-027, SWE-REQ-028, SWE-REQ-030]

- **LED Status Handler**  
  Activates power/position LEDs, ensures only 1 green LED ON, only on true event.  
  [Traces: SWE-REQ-012, SWE-REQ-013, SWE-REQ-014, SWE-REQ-018, SWE-REQ-021, SWE-REQ-039]

- **System Startup/Initialization**  
  One-off peripheral/variable init and power-on logic.  
  [Traces: SWE-REQ-020]

### Interfaces Between Units

- Command Parser -> Flap Control Logic: delivers validated user commands (target position)
- Feedback Processor <-> Flap Control Logic: provides current mapped position; receives requests to update
- Flap Control Logic -> Motor Driver: issues movement commands (direction/enable/disable)
- Flap Control Logic -> LED Status Handler: triggers status indication update (only on state/event)
- System Startup/Initialization -> all units: triggers configuration/init method

### Execution Model
No explicit execution model or scheduling policy is mandated by the requirements at this stage. [SWE-REQ-034, SWE-REQ-026]

|-------------------------|---------------------------------------------------------------|-------------------------------|--------------------------------------|

| Feedback Processor      | Acquire/interpret ADC, validate position                     | Feedback acquisition, mapping | ADC Device, Flap Logic               |
| LED Status Handler      | Drive power/position LEDs, 1-hot indication, safe status      | State indication abstraction  | Flap Logic, Feedback                 |
| System Startup/Init     | One-time peripheral/var setup, initial state set              | Initialization                | All units (initialization)           |
