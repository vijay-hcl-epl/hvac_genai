# Software Architecture for HVAC Flap Actuator System

## 1. Architecture Style Selection

### Candidate Architecture Styles Considered
- Layered Architecture
- Component-based Architecture
- Monolithic (Procedural) Architecture

### Evaluation
- **Layered Architecture:** Provides separation (I/O, logic, drivers), promotes maintainability/modularity, suitable for testability, maps well to ASPICE modularity, and supports future extensions. Slightly heavier than pure monolithic but justified by requirements for modularity and clear separation of concerns (see SYS-REQ-053, SYS-REQ-054).
- **Component-based Architecture:** Would define clear component boundaries, but the system does not have multiple independent, complex components—most functionality is closely coupled.
- **Monolithic Architecture:** Minimum overhead. However, it does not satisfy explicit requirements for modularity and separation of functions (see SYS-REQ-053, SWE-REQ-054).

### Chosen Style and Justification
**Layered Architecture** is selected. It directly addresses system requirements for modularity, maintainability, and clarity (see SYS-REQ-053/054, SWE-REQ-054) and aligns with ASPICE Level 3 expectations for separation of concerns without undue complexity.

## 3. Software Units, Responsibilities, Interfaces

| Software Unit         | Responsibilities                                             | Interfaces Provided                      | Interfaces Used                     |
|----------------------|--------------------------------------------------------------|------------------------------------------|-------------------------------------|
| Command Processor    | Parses UART commands, validates, and updates target position | Command API (to Control Logic)           | UART Driver                         |
| Control Logic        | Compares current/target, actuates motor, manages state      | Control API (to Motor/LED/Feedback)      | Command Processor, Feedback Mapper  |
| Feedback Mapper      | Maps ADC readings to discrete positions                     | Feedback API (to Control Logic)          | ADC Driver                          |
| Motor Driver         | Low-level GPIO/PWM to drive DC motor                        | Motor Control API                       | GPIO, PWM HW                        |
| LED Driver           | Manages status and position LEDs                            | LED Control API                         | GPIO HW                             |
| UART Driver          | Low-level RX/TX, exposes data to Command Processor          | UART API                                | MCU UART HW                         |
| ADC Driver           | Low-level analog acquisition for position feedback          | ADC API                                 | MCU ADC HW                          |


## 4. Explicit Execution Model/Scheduling
Based strictly on the requirements:
- No periodic/cyclic control, real-time OS, or explicit multitasking is mandated.
- User commands processed as events; continuous/periodic position checking is implementation detail but not prescribed by requirements.
- If executed in foreground/background, must be implementation-neutral at architecture level.

**Statement:**
"No explicit execution model or scheduling policy is mandated by the requirements at this stage."

## 5. Architecture Constraints
- Architecture is strictly traceable to SWE.1 requirements; unit responsibilities and interfaces map to functional and modular decomposition required by the software requirements.
- No new requirements, no functional changes, no invented scheduling, safety, or cybersecurity mechanisms beyond requirements.
- No code or detailed algorithms are included here.
