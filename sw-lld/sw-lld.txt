# Software Low-Level Design (SWE.3) for HVAC Flap Actuator

This document provides a complete low-level design for each software unit named in the software architecture. It adheres strictly to ASPICE L3 and your organizational rules. Each section uses the mandatory structure below—absolutely no architecture modification, new units, code snippets, or test content is introduced.

## Software Units:
- Command Processor
- Control Logic
- Feedback Mapper
- Motor Driver
- LED Driver
- UART Driver
- ADC Driver


---

## Software Unit: Command Processor

1. Responsibilities
- Parses received UART data and converts to numeric command.
- Validates command against supported positions.
- Updates target position in shared state if valid.
- Does NOT directly drive hardware or actuate motor.
- Does NOT acknowledge or reply to invalid commands (see SWE-REQ-004).

2. Internal Data Design
- `received_command`: Temporary storage for parsed UART value.
- `command_valid` (bool): Sets after command parsing/validation.

3. State Machine (if applicable)
- States: IDLE, RECEIVED_COMMAND, VALIDATED, INVALID_COMMAND.
- Events: UART RX complete, Parse error, Validation success/fail.
- Transitions: 
    - IDLE → RECEIVED_COMMAND (on UART RX)
    - RECEIVED_COMMAND → VALIDATED (on successful parse)
    - RECEIVED_COMMAND → INVALID_COMMAND (on parse fail)
    - VALIDATED → IDLE, INVALID_COMMAND → IDLE on process complete.
- No persistent state except while handling command.

4. Algorithms and Control Flow
- On UART RX event:
    1. Parse received bytes.
    2. If parse succeeds and value is in position table: set `command_valid = true` and update target position.
    3. Else, set `command_valid = false`. No outbound response.
- Pseudocode:
    - receive_uart() → parse → if valid: update_target(), else: ignore.

5. Interfaces (APIs)
- Provides: `process_u_command(data)`: Accepts UART buffer, returns status.
- Requires: `set_target_position(pos)` from Control Logic; `get_position_map()` from Feedback Mapper.

6. Error Handling
- Ignores malformed/invalid commands (SWE-REQ-003, SWE-REQ-040).
- No error is propagated externally for invalid commands.

7. Resource and Timing Considerations
- Triggered by UART RX event.
- Quick validation and update logic.
- Not re-entrant; expects sequential command processing.

8. Traceability to SWE Requirements
- SWE-REQ-001, 002, 003, 004, 040; interfaces to Control Logic (SWE-REQ-024, 025).

## Software Unit: Control Logic

1. Responsibilities
- Evaluates current flap position vs. target.
- Initiates/terminates motor actuation.
- Updates status for use by LED Driver.
- Does NOT directly parse commands, read ADC, or toggle GPIO.

2. Internal Data Design
- `target_position` (int, from Command Processor)
- `current_position` (int, from Feedback Mapper)
- `state`: IDLE, MOVING, AT_TARGET, ERROR
- Config: none (beyond position mapping supplied)

3. State Machine
- States: IDLE (await command), MOVING (drive motor), AT_TARGET, ERROR
- Events: command_valid, position_change, error_detected
- Entry/exit:
    - IDLE on startup or after reaching/holding position
    - MOVING after a new valid command
    - AT_TARGET after reaching final destination
    - ERROR on irrecoverable sensor/motor error

4. Algorithms and Control Flow
- On valid command: compare `target_position` to `current_position`
- If not equal: command Motor Driver to move toward `target_position` (choice of direction)
- On each ADC update: check for arrival at target. If arrived – stop Motor Driver and update status.
- If position is out of bounds or can't be reached: enter ERROR; halt movement.

5. Interfaces (APIs)
- Provides: `evaluate_position()` (called on new command or feedback update). Returns control actions.
- Requires: `get_current_position()` (Feedback Mapper), `actuate_motor(direction)` (Motor Driver), `set_led_status(state)` (LED Driver)

6. Error Handling
- If target unreachable or feedback invalid: stop motor, set status to ERROR

7. Resource and Timing Considerations
- Event-driven (by command or position change)
- Brief execution on event
- Not re-entrant but tolerant to fast sequential events

8. Traceability to SWE Requirements
- SWE-REQ-005, 006, 007, 008, 013, 042; interfaces to Motor/LED/Feedback (SWE-REQ-025, 027)

## Software Unit: Feedback Mapper

1. Responsibilities
- Converts ADC readings to logical position index.
- Validates raw ADC feedback against mapping/thresholds.
- Supplies position and validity state to Control Logic.
- Does NOT initiate ADC acquisition or control motor.

2. Internal Data Design
- `adc_value` (latest ADC sample)
- `position_mapping[]`: Static ADC ranges for each position
- `current_position` (int)
- `valid_feedback` (bool)

3. State Machine
- No explicit state machine; single-shot conversion logic per acquisition.
- Control flow: on ADC update, update mapping and validity flags.

4. Algorithms and Control Flow
- On ADC update:
    1. Map value to the corresponding discrete position via static mapping.
    2. If out of defined range: set `valid_feedback = false`, else update `current_position`, set `valid_feedback = true`.

5. Interfaces (APIs)
- Provides: `map_adc_to_position(adc_val)`, `is_feedback_valid()`
- Requires: `get_adc_value()` (ADC Driver)

6. Error Handling
- If ADC value is out-of-bounds: `valid_feedback = false`, reported to Control Logic (SWE-REQ-041, 042)

7. Resource and Timing Considerations
- Called event-driven per ADC update
- Minimal/quick processing, low resource

8. Traceability to SWE Requirements
- SWE-REQ-016, 017, 018, 019, 037, 041

## Software Unit: Motor Driver

1. Responsibilities
- Drives GPIO/PWM to control DC motor direction and enable/disable.
- Stops motor on command or on error signal.
- Does NOT evaluate position or validate commands.

2. Internal Data Design
- `motor_enable` (bool), `motor_direction` (enum)
- GPIO/PWM pins (abstracted, not enumerated here)

3. State Machine
- States: OFF, RUN_CW, RUN_CCW
- Events: enable/disable, change direction
- Entry/exit: always passes through OFF when changing direction

4. Algorithms and Control Flow
- On `actuate_motor(dir)`:
    - If enable & direction change needed: disable, set direction, enable
- On `stop_motor()`: disable outputs

5. Interfaces (APIs)
- Provides: `actuate_motor(direction)`, `stop_motor()`
- Requires: GPIO/PWM hardware interface

6. Error Handling
- On error from Control Logic: stop motor, report status if requested

7. Resource and Timing Considerations
- Direct, blocking operations; never re-entrant

8. Traceability to SWE Requirements
- SWE-REQ-011, 012, 013, 014, 015, 025

## Software Unit: LED Driver

1. Responsibilities
- Controls status and position indicator LEDs per Control Logic commands.
- Ensures at most one green (position) LED on at a time.
- Does NOT interpret control logic, only acts as instructed.

2. Internal Data Design
- `status_led_state`, `position_led_states[]` (one per position)

3. State Machine
- No explicit state machine: immediate action per command

4. Algorithms and Control Flow
- On `set_led_status(state)`: evaluate input state, update hardware outputs (abstracted)

5. Interfaces (APIs)
- Provides: `set_led_status(state)`
- Requires: GPIO hardware interface

6. Error Handling
- Ignores redundant/invalid states safely

7. Resource and Timing Considerations
- Called event-driven by Control Logic; no long processing

8. Traceability to SWE Requirements
- SWE-REQ-020, 021, 022, 023, 027, 032, 033, 051

## Software Unit: UART Driver

1. Responsibilities
- Low-level RX/TX handling for UART bus
- Buffers data; provides completed command to Command Processor
- Does NOT decode or interpret messages

2. Internal Data Design
- `rx_buffer[]`, `tx_buffer[]`, buffer pointers

3. State Machine
- RX/TX FSM as required by UART hardware abstraction

4. Algorithms and Control Flow
- RX complete interrupt: populate buffer, signal Command Processor

5. Interfaces (APIs)
- Provides: `uart_rx_complete(data)` event/reference
- Requires: MCU UART HW interface

6. Error Handling
- On framing/overrun: drop data, signal error status (internally only)

7. Resource and Timing Considerations
- HW-driven; not re-entrant

8. Traceability to SWE Requirements
- SWE-REQ-024, 050

---

## Software Unit: ADC Driver

1. Responsibilities
- Performs analog conversion on specified channel
- Provides result to Feedback Mapper
- Does NOT interpret meaning of value

2. Internal Data Design
- `latest_adc_val`, channel config

3. State Machine
- Simple: IDLE, CONVERTING; interrupt-driven

4. Algorithms and Control Flow
- On trigger: start conversion, post value to Feedback Mapper

5. Interfaces (APIs)
- Provides: `get_adc_value()`
- Requires: MCU ADC HW interface

6. Error Handling
- On hardware error: provide out-of-range value, signal invalid

7. Resource and Timing Considerations
- HW-driven; fast completion

8. Traceability to SWE Requirements
- SWE-REQ-026, 037
