## Software Unit: User Command Handler
### 1. Responsibilities
- Accept and validate command packets via UART (SWE-REQ-001, SWE-REQ-002, SWE-REQ-003)
- Forward valid requests for further processing (SWE-REQ-004)
- Reject invalid/malformed/out-of-range commands (SWE-REQ-003, SWE-REQ-032)
- RESP EXCLUDES: Does not interpret the meaning of positions, does not engage in position control, does not actuate hardware directly

### 2. Internal Data Design
- Command input buffer (static array/queue, size fixed)
- State: `last_valid_command`, `error_count`
- Config: command format definition, input timeout, min/max allowed positions

### 3. State Machine
- [States: IDLE, RECEIVING_COMMAND, VALIDATING, REJECT, FORWARD]
- Events: UART RX interrupt, buffer complete, timeout, validation failed/success
- Simple transition diagram, single active command at a time

### 4. Algorithms/Control Flow
- Upon UART data RX → buffer input
- On buffer full/command delimiter → validate syntax/semantics
- If valid: store to `last_valid_command`, forward to next unit
- If invalid: increment `error_count`, send error resp UART, remain in IDLE

### 5. Interfaces
- Provided: `parse_user_command(const char *uart_data)` → `CMD_VALID`/`CMD_INVALID`
- Required: `uart_receive()`, `uart_send_response(const char*)`

### 6. Error Handling
- Input buffer overflow → discard input, halt parsing, log/count error
- Malformed/unknown command → error response, no effect on downstream

### 7. Resource and Timing
- Invoked by UART RX event or command completion only
- Bounded parse time (< max UART frame time)
- Not reentrant

### 8. Traceability
- SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004, SWE-REQ-032
- Maps to Software Unit: User Command Handler

## Software Unit: Flap Position Controller
### 1. Responsibilities
- Analyze valid position/setpoint commands (SWE-REQ-004, SWE-REQ-005)
- Compare target/actual positions, determine error (SWE-REQ-005, SWE-REQ-006)
- Command/stop motor as required (SWE-REQ-007, SWE-REQ-008)
- ERROR: Does not handle low-level actuation, does not directly interpret sensor ADC/range, does not decode UART

### 2. Internal Data Design
- Variables: `target_position`, `actual_position`, `position_error`
- Config: acceptable range from calibration
- Persistent state: `movement_status` (MOVING, IDLE), `last_cmd_time`

### 3. State Machine
- States: IDLE, MOVING_TO_TARGET, ARRIVED, ERROR, HOLDING
- Events: New valid setpoint, actual position update, arrival detected

### 4. Algorithms/Control Flow
1. On valid command, update `target_position`.
2. Compare `actual_position` (from Position Feedback Reader)
3. If (difference > threshold): instruct Motor Controller (dir/en)
4. If (difference <= threshold): send stop to Motor Controller, enter HOLD
5. On error → send error downstream

### 5. Interfaces
- Provided: `set_flap_target(uint16_t position)`, `notify_position_update(uint16_t)`
- Required: `Motor Controller` (`set_motor_state`), `Position Feedback Reader` (`get_position`)

### 6. Error Handling
- If `actual_position` out of bounds → error to Status/LED, stop Motor
- Loss of feedback signal → error state

### 7. Resource/Timing
- Invoked by command arrival or periodic/feedback change
- Bounded iteration (no loops), single task only
- Not reentrant

### 8. Traceability
- SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-008
- Software Unit: Flap Position Controller

## Software Unit: Motor Controller
### 1. Responsibilities
- Issue motor drive enable/disable, set direction (SWE-REQ-009, SWE-REQ-010, SWE-REQ-011)
- Ensures no conflicting drive signals (SWE-REQ-012)
- EXCLUDE: Does not interpret commands, no state/position knowledge, does not filter ADC

### 2. Internal Data Design
- Control lines state (FWD/REV/EN as bools)
- Config constants: GPIO pin IDs
- Internal: `motor_active`, `last_direction`

### 3. State Machine
- States: IDLE, FORWARD, REVERSE
- Events: set_motor_state() calls, stop

### 4. Algorithms/Control Flow
- On command: set direction pins, enable pin
- On stop: clear enable
- Protect against both directions simultaneously

### 5. Interfaces
- Provided: `set_motor_state(enum DIR, bool enable)`
- Required: Output GPIO abstraction

### 6. Error Handling
- Concurrent direction = error, disable drive
- Invalid signals = safe off

### 7. Resource and Timing
- Command-based, no periodic activity
- Minimal latency required

### 8. Traceability
- SWE-REQ-009, SWE-REQ-010, SWE-REQ-011, SWE-REQ-012
- Software Unit: Motor Controller

## Software Unit: Position Feedback Reader
### 1. Responsibilities
- Read ADC, convert to logical position (SWE-REQ-013, SWE-REQ-014)
- Filter/average ADC as needed (SWE-REQ-015)
- Determine out-of-range conditions (SWE-REQ-033)
- EXCLUDE: Does not interpret user intent, does not trigger actuation

### 2. Internal Data Design
- Raw ADC buffer (fixed length)
- Variables: `filtered_adc`, `logical_position`
- Config: ADC channel, scaling factors, filters

### 3. State Machine
- [No explicit state machine; purely transactional]

### 4. Algorithms/Control Flow
- On acquisition: sample ADC, apply averaging/filter
- Bound clamp to valid physical range

### 5. Interfaces
- Provided: `get_position()` → returns logical_position
- Required: ADC hardware abstraction

### 6. Error Handling
- ADC out-of-range → error reported
- Unreliable input → last known safe

### 7. Resource and Timing
- Invoked during controller cycles or explicit poll
- Deterministic (no dynamic allocation)

### 8. Traceability
- SWE-REQ-013, SWE-REQ-014, SWE-REQ-015, SWE-REQ-033
- Software Unit: Position Feedback Reader

## Software Unit: Status/LED Manager
### 1. Responsibilities
- Control/status LEDs for: power, error, position (SWE-REQ-016, SWE-REQ-017)
- Timely updates after system status/position change
- EXCLUDE: Does not modify state, interpret commands, or handle logic

### 2. Internal Data Design
- Variables: `led_status[]`
- Timing: `last_led_update`, LED priority
- Config: LED pin IDs

### 3. State Machine
- [No explicit state machine; status driven]

### 4. Algorithms/Control Flow
- On status/position change → update appropriate LED
- Manage minimum refresh interval

### 5. Interfaces
- Provided: `set_led_status(enum led, bool on)`
- Required: GPIO abstraction

### 6. Error Handling
- Invalid status/position → error LED on
- Communication/driver fail → fallback default LED pattern

### 7. Resource and Timing
- Invoked on system status change
- Latency <500ms as requirement

### 8. Traceability
- SWE-REQ-016, SWE-REQ-017, SWE-REQ-041
- Software Unit: Status/LED Manager
