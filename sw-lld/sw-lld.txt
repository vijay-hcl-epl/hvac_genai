# Software Low Level Design (SWE.3) – HVAC Flap Actuator

## Introduction
This document details the Software Low Level Design for the HVAC Flap Actuator, as derived from:
- Software Requirements: sw-reqs/sw-reqs.txt (demo-43c)
- Software Architecture: sw-arch/sw-arch.txt (demo-43c)

All design elements are strictly traceable to Software Requirements (SWE.1). No new units, architecture, scheduling, or implementation code are present. Design targets MISRA C, no dynamic allocation.

---

## Software Unit: User Command Handler

### 1. Responsibilities
- Receives user commands through UART.
- Validates commands against allowed protocol.
- Forwards valid target position to Position Control Logic.
- Explicitly does NOT perform actuator/motor control, position calculation, or LED signaling.

### 2. Internal Data Design
- Internal buffer for received UART command (fixed, e.g., uint8_t rx_buffer[8])
- Command decode state (enum: IDLE, RECEIVING, ERROR, VALIDATED)
- Parsed target position/temp variable

### 3. State Machine
- States: IDLE, RECEIVING, VALIDATED, ERROR
- Events: UART RX Complete, Protocol Error, Valid Command, External Reset
- Transitions: 
  - IDLE → RECEIVING (on first byte)
  - RECEIVING → VALIDATED (full valid command)
  - RECEIVING → ERROR (protocol violation)
  - ERROR → IDLE (reset/timeout)
- Entry/Exit: Entry to ERROR triggers command ignore.

### 4. Algorithms and Control Flow
- On UART RX: accumulate bytes. If protocol valid, parse for position.
- On error or excess length: discard, set ERROR.
- On valid: forward target position, set VALIDATED.

### 5. Interfaces (APIs)
- void cmd_handler_rx_byte(uint8_t byte): called from UART ISR
- int cmd_handler_get_target(int* pos): returns valid target position if available
- void cmd_handler_reset(void): resets state on error

### 6. Error Handling
- Protocol error: ignore, set ERROR state, request status indication.
- Buffer overflow: reset state, log error if telemetry/debug enabled.

### 7. Resource and Timing Considerations
- Event-driven by user input; not re-entrant (single UART transfer at a time)
- Execution per byte rx or completed command (~few cycles)

### 8. Traceability to SWE Requirements
- SWE-REQ-001, 002, 003, 016, 027

## Software Unit: Position Control Logic

### 1. Responsibilities
- Receives validated target from Command Handler.
- Compares current position to target, determines movement direction.
- Forwards motion commands to Motor Control.
- Does NOT handle direct motor signals, UART, LED.

### 2. Internal Data Design
- Target position (int)
- Current position (int; updated from feedback unit)
- Movement state (enum: IDLE, MOVING_FWD, MOVING_REV, HOLD, ERROR)
- Tolerance/threshold for position match

### 3. State Machine
- States: IDLE, MOVING_FWD, MOVING_REV, HOLD, ERROR
- Events: New Target, Position Update, Motion Complete, Position Error
- Transitions: 
  - IDLE ↔ MOVING_FWD/REV (target ≠ current)
  - MOVING → HOLD (target == position within threshold)
  - Any → ERROR (invalid pos)

### 4. Algorithms and Control Flow
- On new target, compare and signal direction.
- Continue to monitor position until match.
- On error (out of bounds), set ERROR.

### 5. Interfaces (APIs)
- void ctrl_logic_set_target(int pos)
- void ctrl_logic_update_feedback(int pos)
- int ctrl_logic_get_state(void)
- void ctrl_logic_reset(void)

### 6. Error Handling
- Out-of-range: signal ERROR, halt movement
- Oscillation/no progress: limit retries, go ERROR

### 7. Resource and Timing Considerations
- Invoked on new target or position feedback updates
- Not re-entrant; single state machine per system

### 8. Traceability to SWE Requirements
- SWE-REQ-004, 005, 006, 007, 021, 022, 026, 028, 034

## Software Unit: Motor Control Unit

### 1. Responsibilities
- Drives/controls H-bridge outputs (forward/reverse/enable) per logic signals
- Disables drive at end positions or on errors
- No command parsing, feedback processing, or LEDs

### 2. Internal Data Design
- Output state (enum: DISABLED, FWD, REV)
- End-stop/limit detection flag
- Error status (bool)

### 3. State Machine
- Simple state: DISABLED, FWD, REV
- Switch on control logic input or error

### 4. Algorithms and Control Flow
- When movement requested: enable corresponding output
- When done/error/limit: disable all outputs

### 5. Interfaces (APIs)
- void motor_control_move(enum dir)
- void motor_control_stop(void)
- int motor_control_status(void)
- void motor_control_fault(void)

### 6. Error Handling
- On end-stop or motor fault: disable drive, assert error status

### 7. Resource and Timing Considerations
- Driven only by Position Control Logic; not re-entrant
- Pin setting cost only

### 8. Traceability to SWE Requirements
- SWE-REQ-008, 009, 010, 018, 023, 029

## Software Unit: Feedback Acquisition & Processing

### 1. Responsibilities
- Acquire analog sensor value from ADC
- Map ADC value to logical flap position
- Provide feedback to Position Control Unit
- No UART, motor/LED outputs

### 2. Internal Data Design
- ADC reading (uint16_t)
- Position mapping table (const struct [])
- Calibration constants
- Validity/status flag

### 3. State Machine
- No complex machine; event-driven conversion + mapping

### 4. Algorithms and Control Flow
- On acquisition: read ADC, map to logical position via lookup/interpolation
- Validate range; set error status if out of range

### 5. Interfaces (APIs)
- void feedback_acq_start(void)
- int feedback_acq_get_position(void)
- int feedback_acq_status(void)

### 6. Error Handling
- Out-of-range or hardware fault: status = error; trigger system error handling

### 7. Resource and Timing Considerations
- Triggered periodically/event from main loop

### 8. Traceability to SWE Requirements
- SWE-REQ-011, 012, 013, 017, 024, 025, 028

## Software Unit: Status/LED Indication

### 1. Responsibilities
- Drive/refresh system status/position LEDs based on control logic and error flags
- No command, position, or motor logic

### 2. Internal Data Design
- LED output table (const/un), error/position status (bitfield)

### 3. State Machine
- No explicit state, only update on change/event

### 4. Algorithms and Control Flow
- LED pattern based on input system state, flap position, and error

### 5. Interfaces (APIs)
- void led_indication_update(int pos, int error)
- void led_indication_error(void)

### 6. Error Handling
- On error: display pattern, may blink, per system policy

### 7. Resource and Timing Considerations
- Invoked on system state/error change; no timing dependencies

### 8. Traceability to SWE Requirements
- SWE-REQ-014, 015, 019, 023, 028, 029, 033
