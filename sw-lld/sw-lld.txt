# Software Low Level Design (SWE.3) — HVAC Flap Actuator

## 1. User Command Interface Layer

### 1. Responsibilities
Responsible for:
- Receiving UART commands for target flap position (SWE-REQ-001)
- Validating UART commands against allowed positions (SWE-REQ-002, 003)
- Filtering out invalid, out-of-range, or malformed commands; no error is returned (SWE-REQ-003)
- Securing/validating UART data prior to use (SWE-REQ-004)
Explicitly not responsible for:
- Motor/position logic
- Error reporting beyond internal discard

### 2. Internal Data Design
- Buffer for incoming UART bytes (fixed size, static)
- Parsed command index variable
- Command valid flag (boolean)
- Hardcoded valid command list/position indices

### 3. State Machine
- No explicit state machine; operates as event-driven parser/validator
- Main states: Waiting for complete command, command ready, command invalid

### 4. Algorithms and Control Flow
1. Receive UART data (interrupt or polling input)
2. Buffer until end-of-command detected
3. Parse buffer to position index
   - If valid index: set command ready flag, update index
   - If invalid: clear command, set error flag (no external error report)
4. Output: API to get latest valid command (+valid/invalid status)

### 5. Interfaces (Unit-Level APIs)
- Provide: `get_user_command()` → (index, valid flag)
- Require: `uart_receive_byte()` (HW abstraction)

### 6. Error Handling Design
- Out-of-range, malformed, or incomplete commands are ignored
- Buffer overflow: buffer resets, nothing processed
- Never enters error loop, always recovers

### 7. Resource and Timing Considerations
- Invoked by UART RX event
- Non-blocking; statically allocated buffer
- No dynamic allocation; no timing delay
- Not reentrant (assumed single command sequence at a time)

### 8. Traceability
- SWE-REQ-001, 002, 003, 004, 022, 035
- Unit: User Command Interface Layer

## 2. Flap Control Logic Layer

### 1. Responsibilities
Responsible for:
- Comparing current and target positions (SWE-REQ-005)
- Initiating motor movement sequences (SWE-REQ-006 to 008)
- Sequencing, debounce of position, safe state transitions (SWE-REQ-009)
- Stopping motor on arrival, holding idle, error/fault logic
- Commanding status outputs (LED, error reports)
Not responsible for:
- UART parsing, ADC input, direct motor/LED drive

### 2. Internal Data Design
- Target and current position variables (static, integer index)
- Motor requested/active status
- Debounce/stability counters, last N ADC samples (ring buffer)
- Error/state flags (idle, moving, fault)

### 3. State Machine
- States: Idle, Moving, Arrived, Error
- Events: Valid command received, target reached, input error, timeout/fault
- Transition Table:
    - Idle → Moving (command valid & target ≠ current)
    - Moving → Arrived (target reached)
    - Moving → Error (stuck/fault)
    - Error → Idle (reset/clear)

### 4. Algorithms and Control Flow
- On valid command:
  - If out-of-range: ignore
  - If target ≠ current, and no active error:
    - Debounce/verify position feedback
    - Activate motor command (to interface layer)
    - Monitor feedback: when position = target, deactivate motor
    - If stuck beyond timeout, enter Error state, deactivate motor, light fault LED
  - If command = current, do nothing. Block spurious repeats

### 5. Interfaces (Unit-Level APIs)
- Provide: `control_flap(target_index)`, `flap_state_query()`
- Require: `get_user_command()` (interface), `get_position_feedback()`, `motor_drive_request()`

### 6. Error Handling Design
- Invalid commands ignored, no system effect
- Feedback error (unreachable/stuck): enter Error state, halt motor
- System always forced to Idle or Error (never undefined)

### 7. Resource and Timing Considerations
- Invoked on event from interface layer or polling
- Duty: movement time bounded; statically defined counters/delays
- Non-reentrant (monolithic flow per operation)

### 8. Traceability
- SWE-REQ-005, 006, 007, 008, 009, 031, 037
- Unit: Flap Control Logic Layer

## 3. Position Feedback Processing

### 1. Responsibilities
Responsible for:
- Acquiring ADC input
- Mapping ADC value to position index (SWE-REQ-014, 015, 016)
- Validating ADC value range; reporting faults (SWE-REQ-017)
Not responsible for control or output logic (motor/LED)

### 2. Internal Data Design
- ADC raw value (static)
- Calibrated thresholds table (hardcoded, no runtime change)
- Position index (last determined)
- Fault/out-of-range flags

### 3. State Machine
- No full state machine; explicit states: Valid, Out of Range, Fault

### 4. Algorithms and Control Flow
- Read ADC
- Compare to threshold table[mapping]
- If within range, assign position index
- If out-of-range, set error/fault flag, report to control logic

### 5. Interfaces (Unit-Level APIs)
- Provide: `get_position_feedback()` → (index, valid, fault)
- Require: `adc_read_raw()` (HW abstraction)

### 6. Error Handling Design
- ADC value out of bounds: set fault, report up, retain last known good unless hard fault
- Fault state flagged to control logic

### 7. Resource and Timing Considerations
- Called synchronously from control logic
- No blocking; static variable only, single read at a time

### 8. Traceability
- SWE-REQ-014, 015, 016, 017, 023, 041
- Unit: Position Feedback Processing

## 4. Motor & Indicator Interface

### 1. Responsibilities
Responsible for:
- Driving GPIOs for DC motor: direction, enable/disable (SWE-REQ-010–013, 018–021)
- Controlling all status/power/position LEDs
Not responsible for: logic decision (only for acting on requests)

### 2. Internal Data Design
- Output state registers (static)
- LED status variables
- Motor last commanded state (direction, enabled)
- Fault indicator flag

### 3. State Machine
- No full state machine; direct drive outputs per request
- Indicator: Explicit Fault/Error state (distinct LED pattern)

### 4. Algorithms and Control Flow
- On command:
  - Set/clear output bits for direction/enable as requested
  - Only one direction signal active at once
  - LED: ensure only one position LED on at a time
  - On fault, activate error LED sequence
- Reset all on power-up or error cleared

### 5. Interfaces (Unit-Level APIs)
- Provide: `motor_drive_request(direction, enable)`, `set_led_state(pos_idx, error_flag)`
- Require: digital write APIs for GPIO (hardware abstraction)

### 6. Error Handling Design
- Prevent illegal output states (e.g., both directions)
- Fault/abnormal command: deactivate all, set error LED

### 7. Resource and Timing Considerations
- Called as needed (event, poll, command)
- No dynamic allocation, all static variables

### 8. Traceability
- SWE-REQ-010, 011, 012, 013, 018, 019, 020, 021, 024, 025, 035, 036, 037
- Unit: Motor & Indicator Interface
