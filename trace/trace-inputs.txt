# 1.0 System Overview
The HVAC Flap Actuator system is a microcontroller-based prototype intended for learning and process demonstration. Its purpose is to electrically move and hold an air flap in discrete positions for automotive HVAC using a DC motor, potentiometer position feedback, UART-based user commands, and LED indicators. All control occurs on-board, with no vehicle network link. Correctness, usability, and clarity are prioritized over production-grade complexity.

# 2.0 Flap Position Control Requirements
SYS-REQ-001: The system shall allow a user to select a target flap position via UART command.
SYS-REQ-002: The system shall compare the current flap position with the target position at all times.
SYS-REQ-003: The system shall move the flap toward the target position when a new valid target command is received.
SYS-REQ-004: The system shall stop the motor once the flap reaches the commanded target position.
SYS-REQ-005: The system shall hold the flap at its target position after movement is complete.
SYS-REQ-006 [Implied]: The system shall define and store exact ADC value ranges representing each discrete flap position.
SYS-REQ-007 [Implied]: The system shall not require a homing sequence at startup.

# 3.0 Motor Control Requirements
SYS-REQ-008: The system shall drive the motor in the direction required to reach the target flap position.
SYS-REQ-009: The system shall control motor direction using dedicated GPIO pins.
SYS-REQ-010: The system shall enable and disable the motor via GPIO or PWM signal.
SYS-REQ-011: The system shall turn the motor off as soon as the flap reaches the target position.
SYS-REQ-012 [Implied]: The system shall prevent simultaneous activation of both motor directions.

# 4.0 Position Feedback Acquisition and Processing
SYS-REQ-013: The system shall acquire position feedback from a potentiometer connected to an ADC channel.
SYS-REQ-014: The system shall sample the ADC at intervals sufficient to detect position changes promptly.
SYS-REQ-015: The system shall map ADC readings to logical position indices (0 through 5) using pre-defined value ranges.
SYS-REQ-016 [Implied]: The system shall ignore ADC values outside the defined potentiometer range and not move the motor in those cases.

# 5.0 User Command Interface Requirements
SYS-REQ-017: The system shall receive user commands via a UART serial interface.
SYS-REQ-018: Each command shall specify a numeric target position in the allowed range (0–5).
SYS-REQ-019: The system shall validate the received command as a legal flap position command.
SYS-REQ-020: The system shall ignore invalid or out-of-range commands and not respond to the user in such cases.

# 6.0 Status Indication Requirements
SYS-REQ-021: The system shall energize a dedicated power/status LED as long as it is powered and initialized.
SYS-REQ-022: The system shall indicate the current detected flap position by activating exactly one corresponding green LED.
SYS-REQ-023: Only one green LED shall be ON at any given time to indicate the flap position.
SYS-REQ-024 [Implied]: LED indications shall update promptly if the detected position changes.

# 7.0 System Behavioral Requirements
SYS-REQ-025: On power-up, the system shall initialize all peripherals (ADC, UART, PWM, GPIO).
SYS-REQ-026: On power-up, the system shall ensure the motor is off.
SYS-REQ-027: On power-up, the system shall read the potentiometer to determine the current flap position.
SYS-REQ-028: The system shall remain idle, waiting for valid user command, when no new input arrives.
SYS-REQ-029: The system shall proceed to move the flap towards a target when a valid command is received.
SYS-REQ-030: When the flap is at the target position, the system shall keep the motor off until further user command.
SYS-REQ-031: Invalid input or operational exceptions (e.g., ADC out of range) shall be handled by stopping the actuator and not moving the flap.

# 8.0 System Interface Requirements
SYS-REQ-032: The system shall interact with a PC over UART for command input only.
SYS-REQ-033: The system shall drive the DC motor through a motor driver module (L298N) via GPIO and/or PWM outputs.
SYS-REQ-034: The system shall receive flap position feedback via an ADC channel connected to a potentiometer.
SYS-REQ-035: The system shall drive each LED via a dedicated GPIO output.

# 9.0 Constraints and Assumptions
SYS-REQ-036: Only a single flap and single DC motor are controlled.
SYS-REQ-037: Only one user command is processed at a time; no command queueing.
SYS-REQ-038: No dynamic or in-field calibration is required; flap position mapping is software-fixed.
SYS-REQ-039: No CAN, LIN, or vehicle-wide bus is present or used.
SYS-REQ-040: The hardware and all connections are assumed functional for normal operation.

# 10.0 Non-Functional Requirements
## 10.1 Responsiveness Expectations
SYS-REQ-041: The system shall process user commands and move the flap promptly (perceived as nearly instantaneous response).
SYS-REQ-042 [Implied]: No guaranteed timing or deadlines are imposed beyond practical responsiveness.

## 10.2 Error Handling and Edge Cases
SYS-REQ-043: Invalid UART commands shall be ignored safely with no side-effects.
SYS-REQ-044: ADC values outside the valid range shall disable the motor until a valid range is detected.
SYS-REQ-045 [Implied]: No extensive diagnostics or error reporting is implemented.

## 10.3 Resource Constraints
SYS-REQ-046: The implementation shall avoid dynamic memory allocation.
SYS-REQ-047: The solution shall have predictable, bounded runtime behavior appropriate for a microcontroller.

## 10.4 Maintainability and Modularity
SYS-REQ-048: The code and configuration shall be clear, modular, and easy for engineers to understand or modify.

## 10.5 Testability
SYS-REQ-049: All system functions shall be observable via LED status or UART-controlled actuation.
SYS-REQ-050: The system shall support manual and script-based testing through UART commands and LED/motor observation.

# Architecture-Relevant Considerations Derived from System Requirements
- All core system behaviors are sequential and command/response oriented; no requirement for multitasking or concurrent execution exists.
- UART, ADC, and GPIO/PWM control are each isolated functional domains, simplifying modularization.
- No requirement for advanced network or diagnostics simplifies the overall control and communication complexity.
- Expandability would require additional interfaces, but the current system restricts scope to a single actuator, single channel.
- Requirements avoid any execution or scheduling assumptions: event-driven or polling are both allowable (implementation detail).
- System is highly observable by design (for learning), requiring explicit traceable mapping per requirement and simple interface cross-communication only.

# Software Requirements for HVAC Flap Actuator System

## 1. Overview
The following software requirements are derived strictly from the system-level requirements (sys-reqs.txt) for the HVAC Flap Actuator. All requirements are clear, atomic, testable, and free from architectural details. Each requirement is traced to one or more system requirements (SYS-REQ-XXX).

## 2. Functional Requirements

SWE-REQ-001: The software shall receive flap position commands as single-byte values (0–5) via UART. [SYS-REQ-001, SYS-REQ-017, SYS-REQ-018]

SWE-REQ-002: The software shall validate each received UART command is within the allowed values 0–5. [SYS-REQ-019]

SWE-REQ-003: The software shall, upon receiving a valid command, store the new target position and initiate movement if the current position does not match the target. [SYS-REQ-002, SYS-REQ-003, SYS-REQ-005]

SWE-REQ-004: The software shall read the flap position periodically from the potentiometer using the ADC. [SYS-REQ-013, SYS-REQ-014, SYS-REQ-015]

SWE-REQ-005: The software shall map ADC readings to indices 0–5 according to fixed lookup ranges. [SYS-REQ-015, SYS-REQ-038]

SWE-REQ-006: The software shall drive GPIO pins to set the DC motor direction as required to move the flap toward the target position. [SYS-REQ-008, SYS-REQ-009, SYS-REQ-033]

SWE-REQ-007: The software shall use PWM or GPIO to enable/disable the DC motor as needed. [SYS-REQ-010, SYS-REQ-011, SYS-REQ-033]

SWE-REQ-008: The software shall stop the motor when the current position matches the target position or ADC value is out of range. [SYS-REQ-004, SYS-REQ-016, SYS-REQ-031, SYS-REQ-044]

SWE-REQ-009: The software shall indicate the current flap position by turning on exactly one green LED linked to the detected position. [SYS-REQ-022, SYS-REQ-023]

SWE-REQ-010: The software shall turn the power/status LED ON when system initialization is complete. [SYS-REQ-021]

SWE-REQ-011: The software shall handle invalid (out-of-range) UART commands by ignoring them without any motor or indicator action. [SYS-REQ-020, SYS-REQ-043]

SWE-REQ-012: The software shall update status LEDs promptly if the detected position changes. [SYS-REQ-024]

SWE-REQ-013: The software shall initialize all MCU peripherals (ADC, UART, GPIO, PWM) at power-up. [SYS-REQ-025, SYS-REQ-026]

SWE-REQ-014: The software shall ensure the motor is off immediately on startup. [SYS-REQ-026]

SWE-REQ-015: The software shall store all configuration/calibration values (position ADC ranges, pin assignments) as source code constants. [SYS-REQ-038]

SWE-REQ-016: The software shall process only one user command at a time (no queuing). [SYS-REQ-037]

SWE-REQ-017: The software shall not use dynamic memory allocation. [SYS-REQ-046]

SWE-REQ-018: The software shall support testability through UART command execution and visual feedback. [SYS-REQ-049, SYS-REQ-050]

## 3. Non-Functional Requirements

SWE-REQ-019: The software shall be written in C, suitable for STM32Cube IDE, and conforming to MISRA-C style. [Platform Spec]

SWE-REQ-020: The software structure and logic shall be modular and clearly commented for maintainability. [SYS-REQ-048]

SWE-REQ-021: The software shall avoid direct manipulation of scheduling, timing, or execution model. [SYS-REQ-042]

SWE-REQ-022: All functions shall complete in bounded time, suitable for the targeted microcontroller. [SYS-REQ-047]

## 4. Exclusions and Out-of-Scope

SWE-REQ-023: The software shall not implement CAN/LIN bus communication or UDS diagnostics. [SYS-REQ-039, SYS-REQ-016]

SWE-REQ-024: The software does not implement timeout detection or safety-critical logic beyond what is described here. [SYS-REQ-045]

# End of Software Requirements

# Software Architecture for HVAC Flap Actuator System

## 1. Introduction
This document presents the high-level software architecture for the HVAC Flap Actuator, derived from the system and software requirements (sys-reqs.txt, sw-reqs.txt). The design enables maintainability, traceability, and independent verification.

## 2. Architecture Style and Rationale
- The architecture uses a layered/component-based model to maximize modularity, testability, and mapping to ASPICE.
- Core system responsibilities (command parsing, position acquisition, actuation, feedback, and indication) are isolated in independent software units.
- Scheduler/execution model is not prescribed; event-driven or polling may be used.

## 3. High-Level Diagram (Textual)
```
+-----------------------------+
|       User Command Parser   |
+-------------+---+-----------+
              | UART RX
              v
+-------------+--------------+
|      Position Control      |
+------+------+-------------+
       |      | ADC Read
       v      v
  Feedback  Motor Control
 Acquisition    |
   |           |
   +----+------+------+
        |             |
        v             v
   Status Indication  |
        |         System Data/Config
```

## 4. Software Units and Responsibilities

### 4.1 User Command Parser
- Receives and parses UART data
- Validates command values (0–5)
- Forwards valid position requests

### 4.2 Position Control Logic
- Compares commanded target position with actual
- Initiates movement via Motor Control
- Holds state when at target
- Invokes Feedback Acquisition

### 4.3 Motor Control
- Enables/disables motor (PWM/GPIO)
- Sets direction
- Stops on target match or error

### 4.4 Feedback Acquisition
- Reads ADC value from potentiometer
- Maps ADC to logical positions (0–5)
- Filters out-of-range readings

### 4.5 Status Indication
- Drives power LED
- Indicates current position using green LEDs
- Only one position LED active at a time

### 4.6 System Config/Data
- Stores calibration ranges, pin configs
- No dynamic calibration; all values are static

## 5. Data Flow and Interfaces
- UART RX → User Command Parser
- User Command Parser → Position Control
- Position Control ↔ Feedback Acquisition (invoked/read)
- Position Control → Motor Control (move/stop)
- Position Control → Status Indication (LED update)
- All modules access System Config/Data as needed

## 6. Rationale, Exclusions, and Non-Functional Coverage
- No requirement for multi-actuator support (single instance)
- No CAN/LIN/UDS or network external interface
- No RTOS, watchdog, or advanced error handling mandated
- Each block can be unit tested in isolation or via integration

## 7. Mapping and Traceability
- User Command Parser (SWE-REQ-001, SWE-REQ-002, SWE-REQ-011)
- Position Control (SWE-REQ-003, SWE-REQ-004, SWE-REQ-005, SWE-REQ-008)
- Motor Control (SWE-REQ-006, SWE-REQ-007, SWE-REQ-014)
- Feedback Acquisition (SWE-REQ-004, SWE-REQ-005, SWE-REQ-008)
- Status Indication (SWE-REQ-009, SWE-REQ-010, SWE-REQ-012)
- System Config/Data (SWE-REQ-015, SWE-REQ-017, SWE-REQ-020)
- All modules respect SWE-REQ-018, SWE-REQ-019, SWE-REQ-021, SWE-REQ-022

## 8. No Architectural or Scheduling Mandates
- The architecture does not introduce OS, foreground/background, or interrupt-driven logic unless stated in requirements
- Polling or event-driven dispatch is implementation detail

# Software Low Level Design (LLD) for HVAC Flap Actuator

## 1. Introduction
This LLD document translates the software architecture and requirements for HVAC flap actuator into C-code-ready component/module details for STM32 using STM32Cube IDE and HAL drivers. Architecture, scheduling, and RTOS choices are left undefined; LLD is implementation-agnostic where possible.

## 2. Module Breakdown

### 2.1 User Command Parser (user_cmd.c/.h)
- Function: void UART_UserCmd_ReceiveHandler(uint8_t rxValue)
- Validates 0–5, ignores others
- Stores targetPos (volatile uint8_t)
- Static inline map for validation
- No command buffer/queue

### 2.2 Position Control Logic (pos_ctrl.c/.h)
- Function: void POSCTRL_HandleTargetMove(void)
- Compares currPos vs. targetPos
- Invokes Motor_Control_SetDirection (if needed)
- Invokes Feedback_Adc_Read
- Entry/exit criteria: target achieved, ADC valid, error

### 2.3 Motor Control (motor_ctrl.c/.h)
- Function: void Motor_Control_SetDirection(dir)
- Function: void Motor_Control_Enable(bool enable)
- Uses HAL_GPIO, PWM for enable
- Safety interlock to prevent both directions at once

### 2.4 Feedback Acquisition (feedback_adc.c/.h)
- Function: uint16_t Feedback_Adc_Read(void)
- Maps ADC value to index (0–5); returns -1 if invalid
- Lookup table for ADC–pos

### 2.5 Status Indication (status_led.c/.h)
- Function: void LED_UpdatePosition(uint8_t pos)
- Only one active; static pin map
- void LED_SetPower(bool on)

### 2.6 System Config/Data (system_cfg.h)
- Defines: ADC threshold table, pin assignments, constants
- No runtime update

## 3. Data Structures
- typedef struct {
    uint8_t targetPos;
    uint8_t currPos;
    bool motorEnabled;
    ...
  } HVAC_FlapCtrlHandle_t;
- All global state static to file/module

## 4. Function Prototypes
- All functions modelled to block until completion (where applicable)
- No dynamic allocation
- No RTOS dependencies

## 5. Interfaces and Dependencies
- STM32 HAL: UART, GPIO, ADC, TIM (PWM)
- Module-to-module interaction via header APIs only
