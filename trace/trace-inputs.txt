1.0 System Overview
------------------
The HVAC flap actuator system is designed to control the position of a single air flap in a vehicle's HVAC (Heating, Ventilation, and Air Conditioning) subsystem. The position is actuated by a DC motor, measured by a potentiometer, and commanded by a user from a PC via UART. The system provides visual feedback via LEDs on a microcontroller board. No networking or advanced diagnostics are included. This is a prototype and not a production-grade system.

2.0 Flap Position Control
-------------------------
SYS-REQ-001: The system SHALL move the HVAC flap to the user-commanded discrete position (0–5) upon receiving a valid command over UART.
SYS-REQ-002: The system SHALL keep the HVAC flap stationary when no new valid command is received.
SYS-REQ-003: The system SHALL maintain the flap position within its corresponding ADC range for the commanded position.
SYS-REQ-004: [Implied] The system SHALL not overshoot or oscillate between positions during normal operation.

3.0 Motor Control
-----------------
SYS-REQ-005: The system SHALL control the motor to rotate clockwise or anti-clockwise in order to reach the target flap position.
SYS-REQ-006: The system SHALL stop the motor once the measured flap position matches the target position.
SYS-REQ-007: [Implied] The motor SHALL be turned OFF during system initialization and whenever an invalid command, invalid input, or ADC out-of-range condition occurs.

4.0 Position Feedback Acquisition & Processing
---------------------------------------------
SYS-REQ-008: The system SHALL acquire the flap position via an analog potentiometer connected to an ADC channel.
SYS-REQ-009: The system SHALL map acquired ADC values to the logical flap positions (0–5) according to fixed, defined ranges.
SYS-REQ-010: If the ADC value is outside all defined ranges, the system SHALL stop the motor and not attempt to move it until the value is valid.

5.0 User Command Interface
-------------------------
SYS-REQ-011: The system SHALL receive flap target position commands via UART as simple numeric values (0–5).
SYS-REQ-012: Any received UART command outside the range 0–5 SHALL be ignored, and the system SHALL NOT respond or acknowledge it.
SYS-REQ-013: [Implied] The system SHALL process only one user command at a time.

6.0 Status Indication
---------------------
SYS-REQ-014: The system SHALL illuminate a dedicated LED to indicate when system power is ON.
SYS-REQ-015: The system SHALL illuminate, at any time, at most one green LED corresponding to the current logical flap position (0–5).
SYS-REQ-016: [Implied] The status indication SHALL be updated promptly to reflect the current flap position.

7.0 System Behavior
-------------------
SYS-REQ-017: On power-up, the system SHALL initialize peripherals (ADC, UART, GPIO, PWM) and ensure the motor is OFF.
SYS-REQ-018: On power-up, the system SHALL read the potentiometer to determine the initial flap position and set the appropriate position LED.
SYS-REQ-019: In idle state, the system SHALL wait for valid user input via UART.
SYS-REQ-020: Upon a valid movement command, the system SHALL move the flap and stop the motor when the target position is reached.
SYS-REQ-021: If an invalid command is received, the system SHALL ignore it and SHALL NOT change state or indicate an error.
SYS-REQ-022: [Implied] During motor movement toward a target, the system SHALL continue to monitor the ADC for position feedback.

8.0 Interfaces
--------------
SYS-REQ-023: The system SHALL use UART for receiving user position commands.
SYS-REQ-024: The system SHALL use an ADC channel for flap position feedback.
SYS-REQ-025: The system SHALL use GPIO pins to drive the motor and LED.
SYS-REQ-026: The system SHALL use PWM, if available, for motor enable and speed control.
SYS-REQ-027: [Implied] The system SHALL NOT implement communication over CAN, LIN, or other vehicle networks.

9.0 Constraints & Assumptions
------------------------------
SYS-REQ-028: The system SHALL assume a fixed calibration between potentiometer ADC values and flap positions as defined in software.
SYS-REQ-029: Only one HVAC flap and one user command stream SHALL be supported.
SYS-REQ-030: [Implied] The system SHALL assume hardware is functioning correctly during normal operation.

10.0 Non-Functional Requirements
-------------------------------
10.1 Responsiveness
SYS-REQ-031: The system SHALL process received UART commands and update the flap position promptly enough to feel responsive to a human user.

10.2 Error Handling & Edge Cases
SYS-REQ-032: If the ADC position feedback is not within any valid range, the system SHALL stop the motor and hold its last position until a valid input is available.
SYS-REQ-033: The system SHALL NOT crash or hang if the motor fails to reach the command target position.

10.3 Resource Constraints
SYS-REQ-034: The system SHALL operate without using dynamic memory allocation.
SYS-REQ-035: The system SHALL use only required resources on the STM32F407G-DISC1 hardware platform.

10.4 Maintainability & Modularity
SYS-REQ-036: The system SHALL structure functionality such that command handling, motor control, feedback acquisition, and status indication can be tested and maintained separately.

10.5 Testability
SYS-REQ-037: The system SHALL be testable by sending commands from a PC, observing motor position, and checking LED status.


Architecture-Relevant Considerations Derived from System Requirements
--------------------------------------------------------------------
- Concurrency: All interactions (command input, motor movement, feedback acquisition, status update) can be handled sequentially in simple prototyping; concurrency may only be required if true parallel handling is introduced in the future.
- Interaction complexity: System interactions are simple, driven by single commands, with direct feedback and indication; minimal cross-coupling or state management is present.
- Control complexity: Only direct movement to target, input-to-action processing, and safeties for out-of-range or invalid input are required. No advanced strategies or error recovery.
- Expandability: The modularity requirements permit future addition of network interfaces, multiple flap actuators, or advanced error diagnostics
[END OF REQUIREMENTS]

- HW interaction: All cross-unit hardware accesses are simple, direct (UART, GPIO, ADC, PWM). (SWE-REQ-019, SWE-REQ-020, SWE-REQ-021)

- ASPICE L3: Requires traceability, low inter-unit coupling, and clarity of interfaces.

-- Decisions --
Layered architecture is preferred: it allows clear separation between low-level HW interaction (drivers), application logic (flap/motor handling), and user interaction, maximizing maintainability and testability in line with SWE.1 without introducing unnecessary overhead for this simple system.

- Layered: Selected for clarity, modularity, and ease of independent test (SWE-REQ-036, SWE-REQ-037), even for this simple system.
- Component-based: Not adopted as there's little need for dynamic discovery or late binding—overhead unjustified by current requirements.
- Monolithic: Rejected due to maintainability/testability constraints in requirements (SWE-REQ-036, SWE-REQ-037).

LOW LEVEL DESIGN PER SOFTWARE UNIT
======================================================

------------------------------------------------------
Software Unit: User Command Handler (UCH)
------------------------------------------------------

1. Responsibilities
- Handles parse of UART RX into numeric command (0–5); discards invalid/out-of-range.
- Does not handle system state, movement, or hardware control.

2. Internal Data Design
- Command buffer (static, fixed size)
- parse_result (enum: CMD_OK, CMD_OUT_OF_RANGE, CMD_INVALID)
- new_command (bool), command_val (uint8_t 0–5)

3. State Machine
- None; operates stateless per input event. Each input handled independently. Flow: check buffer → parse/validate → issue result.

4. Algorithms & Control Flow
- On UART RX:
  1. Copy ASCII byte(s) to buffer
  2. Parse integer
  3. If 0 ≤ integer ≤ 5: set parse_result = CMD_OK; new_command = TRUE
     Else: set parse_result = CMD_OUT_OF_RANGE; discard
  4. Only one valid command in process; queue others

5. Interfaces (APIs)
- Provided: get_valid_command() → (uint8_t val, bool valid)
- Required: UART read (async, non-blocking)

6. Error Handling
- Ignores buffer overruns; discards malformed/invalid out of range
- No error response or feedback downstream

7. Resource & Timing Considerations
- Only invoked upon UART RX; no cyclic polling
- WCET: <5ms/command parse
- Not re-entrant (static buffer)

8. Traceability
- SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-025, SWE-REQ-018

------------------------------------------------------
Software Unit: Application Logic (APPL)
------------------------------------------------------

1. Responsibilities
- Handles command sequencing, state tracking, flap move sequence; coordinates units (MC, FA, SI)
- Does not handle UART input parsing, ADC sampling, or direct motor/LED control

2. Internal Data Design
- curr_flap_pos (0–5), target_flap_pos (0–5)
- active_command (struct: pos, status), in_progress (bool)
- attempt_counter, timeout_counter

3. State Machine
States:
  - IDLE: Await command
  - MOVING: Flap moving toward command
  - BUSY: Movement complete; updating status
  - ERROR: ADC OOR / Timeout
Events:
  - Valid command, ADC OOR, position reached, timeout
Transitions:
  - IDLE→MOVING: Valid command
  - MOVING→BUSY: Flap within range
  - MOVING→ERROR: ADC OOR or timeout
  - BUSY→IDLE: Status update complete
  - ERROR→IDLE: User command
Actions:
  - On each transition, invoke MC/SI/FA APIs

4. Algorithms & Control Flow
- On valid command:
  1. Set target_pos; in_progress = TRUE
  2. While not reached and attempts < MAX_ATTEMPTS:
     a. Query FA for position
     b. Command MC (dir/enable)
     c. If OOR, abort, set ERROR
     d. If timeout: abort, set ERROR
  3. On completion, update SI LEDs
  4. Return to IDLE

5. Interfaces (APIs)
- Provided: process_command(uint8_t cmd), tick(), get_state()
- Required: MC (move(stop/start, dir), status), FA (get_pos, is_oor), SI (led_update)

6. Error Handling
- ADC out-of-range: command MC to stop, enter ERROR, await next command
- Timeout: same as above
- Fail-silent (no assert, no reset)

7. Resource & Timing Considerations
- Invoked per command; tick() to process state/timeout
- WCET: Movement ~50ms per iteration; overall <100ms perceived response
- Not re-entrant; static data

8. Traceability
- SWE-REQ-003, SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-008, SWE-REQ-026, SWE-REQ-027

------------------------------------------------------
Software Unit: Motor Controller (MC)
------------------------------------------------------

1. Responsibilities
- Generates GPIO/PWM for motor drive; executes APPL commands (dir, enable/disable)
- Does not handle flap logic, state, or ADC

2. Internal Data Design
- state (enum: OFF, FWD, REV)
- output_config (struct, pins)

3. State Machine
- None; direct response to APPL calls

4. Algorithms & Control Flow
- On move(dir):
  1. Set GPIO/PWM per dir
  2. Set state (FWD/REV)
- On stop():
  1. Clear enable
  2. Set state OFF

5. Interfaces (APIs)
- Provided: move(dir), stop()
- Required: GPIO/PWM HAL

6. Error Handling
- On HAL error: report error to APPL; enter OFF

7. Resource & Timing Considerations
- WCET: <2ms per API call
- Not re-entrant

8. Traceability
- SWE-REQ-009, SWE-REQ-010, SWE-REQ-011, SWE-REQ-020, SWE-REQ-036

------------------------------------------------------
Software Unit: Feedback Acquisition (FA)
------------------------------------------------------

1. Responsibilities
- Samples ADC; maps value to flap position number; flags OOR
- Does not hold state or control units

2. Internal Data Design
- adc_val (uint16_t), last_pos (0–5), mapping_table (const)
- oor_flag (bool)

3. State Machine
- None; stateless per read invocation

4. Algorithms & Control Flow
- On get_pos():
  1. Read ADC
  2. Lookup table: map ADC to pos
  3. If out of mapped range: set oor_flag

5. Interfaces (APIs)
- Provided: get_pos() → (pos, oor), is_oor()
- Required: ADC HAL

6. Error Handling
- If ADC/HAL error: set oor_flag, report up

7. Resource & Timing Considerations
- WCET: <2ms/read
- Not re-entrant

8. Traceability
- SWE-REQ-012, SWE-REQ-013, SWE-REQ-014, SWE-REQ-019, SWE-REQ-031

------------------------------------------------------
Software Unit: Status Indicator (SI)
------------------------------------------------------

1. Responsibilities
- Sets GPIO for position and power LEDs according to flap position, power state
- Does not compute state, parse inputs, or read ADC

2. Internal Data Design
- led_pins (const)
- curr_led (0–5), power_led (bool)

3. State Machine
- None; invoked by APPL

4. Algorithms & Control Flow
- On led_update():
  1. Set all LEDs OFF
  2. Set curr_led ON
  3. Set power_led ON per system state

5. Interfaces (APIs)
- Provided: led_update(pos, power)
- Required: GPIO HAL

6. Error Handling
- If GPIO error: ignore (silent fail)

7. Resource & Timing Considerations
- WCET: <1ms per call
- Not re-entrant

8. Traceability
- SWE-REQ-015, SWE-REQ-016, SWE-REQ-017, SWE-REQ-021

#include "uch.h"
#include <ctype.h>
static uch_cmd_ctx_t g_uch_cmd_ctx = {0};
void uch_init(uch_cmd_ctx_t* ctx) {
    ctx->buffer = 0;
    ctx->parse_result = CMD_INVALID;
    ctx->new_command = false;
    ctx->command_val = 0;
}

void uch_uart_rx_handler(uch_cmd_ctx_t* ctx, uint8_t ascii_byte) {
    if (isdigit(ascii_byte)) {
        uint8_t val = ascii_byte - '0';
        if (val >= FLAP_POS_MIN && val <= FLAP_POS_MAX) {
            ctx->parse_result = CMD_OK;
            ctx->new_command = true;
            ctx->command_val = val;
            ctx->buffer = val;
        } else {
            ctx->parse_result = CMD_OUT_OF_RANGE;
        }
    } else {
        ctx->parse_result = CMD_INVALID;
    }
}

bool uch_get_valid_command(uint8_t* val) {
    if (g_uch_cmd_ctx.new_command) {
        *val = g_uch_cmd_ctx.command_val;
        g_uch_cmd_ctx.new_command = false;
        return true;
    }
    return false;
}

static appl_state_t appl_state = APPL_IDLE;
static uint8_t curr_flap_pos = FLAP_POS_MIN;
static uint8_t target_flap_pos = FLAP_POS_MIN;
static uint8_t attempt_counter = 0;
#define MAX_ATTEMPTS 10
void appl_init(void) {
    appl_state = APPL_IDLE;
    curr_flap_pos = fa_get_pos();
    si_led_update(curr_flap_pos, true);
}
void appl_process_command(uint8_t cmd) {
    if (appl_state != APPL_IDLE) return;
    if (cmd < FLAP_POS_MIN || cmd > FLAP_POS_MAX) return;
    target_flap_pos = cmd;
    attempt_counter = 0;
    appl_state = APPL_MOVING;
    mc_move((target_flap_pos > curr_flap_pos) ? 1 : -1);
}
void appl_tick(void) {
    uint8_t pos = fa_get_pos();
    if (appl_state == APPL_MOVING) {
        attempt_counter++;
        if (fa_is_oor() || attempt_counter > MAX_ATTEMPTS) {
            mc_stop();
            appl_state = APPL_ERROR;
            si_led_update(curr_flap_pos, true);
            return;
        }
        if (pos == target_flap_pos) {
            mc_stop();
            curr_flap_pos = pos;
            appl_state = APPL_BUSY;
            si_led_update(curr_flap_pos, true);
            return;
        }
    } else if (appl_state == APPL_BUSY) {
        appl_state = APPL_IDLE;
    } else if (appl_state == APPL_ERROR) {
        // Wait for new command
    }
}
appl_state_t appl_get_state(void) {
    return appl_state;
}
