1.0 System Overview
------------------------------------
The HVAC Flap Actuator system is a microcontroller-based prototype that controls the position of an automotive HVAC air flap via a DC motor based on user commands received over UART. Position feedback is provided via a potentiometer, and system status is indicated with LEDs. The system demonstrates embedded control concepts in a learning context; production vehicle integration is not in scope.

2.0 Flap Position Control Requirements
------------------------------------
SYS-REQ-001: The system shall allow the user to select a target flap position using UART commands.
SYS-REQ-002: The system shall move the flap to the target position specified by the user command.
SYS-REQ-003: The system shall compare the current and target flap positions to determine if further action is needed.
SYS-REQ-004: The system shall command the motor to hold the flap at the target position once reached.
SYS-REQ-005: The system shall support at least six discrete flap positions, as mapped by ADC values (0–5).
[Implied] SYS-REQ-006: The system shall treat ADC value-to-flap-position mapping as fixed and defined in software, with no dynamic calibration required.
[Implied] SYS-REQ-007: The system shall not attempt to move the flap if the current position matches the command.

3.0 Motor Control Requirements
------------------------------------
SYS-REQ-008: The system shall control motor direction (clockwise/anti-clockwise) via dedicated GPIO outputs.
SYS-REQ-009: The system shall enable or disable motor drive using a PWM or GPIO signal.
SYS-REQ-010: The system shall stop the motor when the flap reaches the commanded position.
SYS-REQ-011: The system shall stop the motor if an ADC reading indicates an out-of-range value.
[Implied] SYS-REQ-012: The system shall ensure no PWM or enable signal is active on power-up or initialization.

4.0 Position Feedback Acquisition and Processing
------------------------------------
SYS-REQ-013: The system shall acquire potentiometer feedback using an ADC channel.
SYS-REQ-014: The system shall process ADC values to determine logical flap position (0–5) using predefined ranges embedded in software.
SYS-REQ-015: The system shall continuously monitor the flap position while powered on.
[Implied] SYS-REQ-016: The system shall tolerate ADC values just outside boundary ranges without causing uncontrolled behavior.

5.0 User Command Interface Requirements
------------------------------------
SYS-REQ-017: The system shall accept UART commands consisting of single-byte values representing discrete flap positions (0–5).
SYS-REQ-018: The system shall ignore any UART command outside the valid range (0–5). No acknowledgment or error is required.
SYS-REQ-019: The system shall not respond on UART or generate output beyond position control.
[Implied] SYS-REQ-020: The system shall validate incoming data to ensure only valid commands influence system behavior.

6.0 Status Indication Requirements
------------------------------------
SYS-REQ-021: The system shall turn on a dedicated LED to indicate system power-on status.
SYS-REQ-022: The system shall indicate the current flap position using multiple LEDs, with only one position LED active at any time.
SYS-REQ-023: The system shall update flap position LEDs in response to both power-up state and successful position changes.
[Implied] SYS-REQ-024: The system shall ensure simple, non-overlapping LED logic (no blinking or multiplexing required).

7.0 System Behavioral Requirements
------------------------------------
SYS-REQ-025: On power-up, the system shall initialize all peripherals (ADC, UART, GPIO, PWM) before accepting user input.
SYS-REQ-026: The system shall ensure the motor is not active at startup.
SYS-REQ-027: The system shall read and display the current flap position during initialization.
SYS-REQ-028: The system shall remain idle (waiting for command) when no input is present.
SYS-REQ-029: The system shall ignore any invalid command and maintain the current state.
SYS-REQ-030: The system shall clearly separate state transitions: power-up/init, idle, moving, and holding position.
[Implied] SYS-REQ-031: Explicit state management (state machines) is not mandatory but system behavior shall be predictable and follow the described logic.

8.0 System Interface Requirements
------------------------------------
SYS-REQ-032: The system shall use UART for user command input.
SYS-REQ-033: The system shall use GPIO/PWM for motor driver control.
SYS-REQ-034: The system shall use an ADC channel for potentiometer input.
SYS-REQ-035: The system shall use GPIO outputs for controlling status LEDs.
[Implied] SYS-REQ-036: The system shall not interface with CAN, LIN, or other vehicle networks.

9.0 Constraints and Assumptions
------------------------------------
SYS-REQ-037: Only one flap actuator shall be controlled by the system.
SYS-REQ-038: Only one user command shall be processed at a time.
SYS-REQ-039: The system shall assume connected hardware conforms to design expectations.
SYS-REQ-040: All calibration data (ADC to position mapping) shall be fixed in code.
[Implied] SYS-REQ-041: No homing sequence is required at startup.
[Implied] SYS-REQ-042: No dynamic hardware reconfiguration shall be performed at runtime.

10.0 Non-Functional Requirements
------------------------------------
10.1 Responsiveness Expectations
SYS-REQ-043: The system shall process UART commands and actuate the flap such that it feels responsive to a human user (within a short, user-perceivable delay).
[Implied] SYS-REQ-044: No real-time guarantees or fixed timeouts are required, unless added for demonstration/test purposes.

10.2 Error Handling and Edge Cases
SYS-REQ-045: The system shall safely ignore invalid UART commands.
SYS-REQ-046: The system shall stop the motor if ADC values are out of range.
[Implied] SYS-REQ-047: No automatic diagnostics or error reporting is required; hardware is assumed functional.

10.3 Resource Constraints
SYS-REQ-048: The system shall be implemented simply to prioritize understandability and bounded resource usage.
SYS-REQ-049: No dynamic memory allocation shall be used.
SYS-REQ-050: The executable image shall run on STM32F407G-DISC1 with typical configuration.

10.4 Maintainability and Modularity
SYS-REQ-051: The system shall separate motor control, feedback acquisition, command interface, and indication logic for understandability and maintainability.

10.5 Testability
SYS-REQ-052: System observability shall be assured via LED state and UART communication.
SYS-REQ-053: System shall be testable using manual or script-based UART command injection and observation of physical outputs.
[Implied] SYS-REQ-054: No automated test framework integration is required.

HVAC Flap Actuator Software Architecture
========================================

1. Architecture Style Selection & Justification
------------------------------------------------
Candidate styles: Monolithic, Layered, Component-based

Evaluation:
- System complexity is low (single actuator, no multitasking)
- Explicit requirements call for separation/modularity: SYS-REQ-051
- Maintainability and testability are important
- All hardware interaction via microcontroller peripherals (GPIO, ADC, UART, PWM)
- No real-time, concurrent, or scheduling requirements

Decision:
Layered/component-based hybrid is selected, with clear separation for:
- User Command Handling
- Flap Position Control
- Motor Control
- Feedback Acquisition
- Status Indication

This follows the explicit maintainability requirement and ASPICE L3 traceability. Monolithic approach would not satisfy the modularity requirement. Full component-based is excessive for current system complexity. The selected style is justified because it is both simple and extensible.

2. Architectural Units and Responsibilities
--------------------------------------------
| Software Unit                | Responsibilities                                            | Interfaces Provided            | Interfaces Used             |
|------------------------------|------------------------------------------------------------|-------------------------------|-----------------------------|
| User Command Handler         | Parse/validate UART commands, issue target position updates | Command parser, API to Flap   | UART RX, Flap Position API  |
| Flap Position Control        | State logic: idle, move, hold; target/curr pos compare     | Movement logic API            | Motor Control, Feedback API |
| Motor Control Unit           | Drive motor per commands, stop on position/limits          | Motor driver API              | GPIO/PWM, Flap Ctrl API     |
| Position Feedback Handling   | Read ADC, extract logical position, provide to control     | Position Provider API         | ADC, Flap Ctrl API          |
| Status Indication Handler    | Reflect power/position state via LEDs                      | LED update API                | Flap Position, GPIO         |
| Hardware Interface Drivers   | Low-level access to UART/GPIO/ADC/PWM                      | Peripheral driver APIs        | STM32 HAL / Direct HW       |

4. Scheduling & Execution Model
--------------------------------
No explicit execution or scheduling model is mandated by requirements. The control loop may be event-driven (on UART command) or in a simple polling loop (as proven/testable), with no concurrency or preemption.

5. Traceability & Constraints
-----------------------------
- All units trace directly to software/system requirements (see SYS-REQ-051, non-functional and interface requirements)
- No safety/security logic added, no dynamic allocation, no multitasking
- No changes to specified system state logic or interfaces

6. Further Notes
-----------------
- The architecture is easily extendable if more actuators or sophisticated indication/diagnostics are required in the future.
- No additional non-mandated mechanisms have been introduced.
- No detailed design or code included (SWE.3 responsibility)
