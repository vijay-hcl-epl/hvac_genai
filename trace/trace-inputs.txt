1.0 System Overview
The HVAC flap actuator system controls the position of the air distribution flap in a climate control system based on user or system commands. It ensures accurate positioning, feedback, and safe operation within defined constraints.

2.0 Flap Position Control
SYS-REQ-001: The system SHALL allow setting the flap position to any target position within the defined operational range.
SYS-REQ-002: The system SHALL restrict flap movement to within the minimum and maximum allowed positions.
SYS-REQ-003: The system SHALL confirm when the commanded flap position is reached within a defined tolerance window.
SYS-REQ-004: The system SHALL disregard position commands outside the valid position range and report them as invalid input.

3.0 Motor Control
SYS-REQ-005: The system SHALL command the actuator motor to move the flap toward the target position when a valid command is received.
SYS-REQ-006: The system SHALL stop the actuator motor when the target position is reached or an error condition is detected.
SYS-REQ-007: The system SHALL prevent continuous motor actuation in the case of mechanical blockage or detected stall.
[Implied] The system SHALL operate the motor in response to received position commands only.

4.0 Position Feedback Acquisition & Processing
SYS-REQ-008: The system SHALL acquire real-time feedback from a position sensor to determine current flap position.
SYS-REQ-009: The system SHALL process position sensor data and validate it against plausibility thresholds.
SYS-REQ-010: The system SHALL detect and report sensor faults (e.g., open/short circuit, out-of-range data).

5.0 User Command Interface
SYS-REQ-011: The system SHALL provide an interface for external entities to send flap position commands.
SYS-REQ-012: The system SHALL acknowledge valid commands received via this interface.
SYS-REQ-013: The system SHALL indicate receipt and status of invalid, out-of-range, or malformed commands.

6.0 Status Indication
SYS-REQ-014: The system SHALL provide a visible or digital status indicator for flap position, error, and operational state.
SYS-REQ-015: The system SHALL indicate the presence of errors or faults to the user or higher-level system.

7.0 System Behavior
SYS-REQ-016: On power-up, the system SHALL initialize all interfaces, calibrate/stow the flap if required, and enter idle state.
SYS-REQ-017: When idle, the system SHALL not actuate the motor unless a new, valid position command is received.
SYS-REQ-018: During normal operation, the system SHALL move the flap to the target position and provide real-time status.
SYS-REQ-019: Upon reaching the target, the system SHALL transition to a steady-state and cease actuation.
SYS-REQ-020: The system SHALL detect and reject invalid or conflicting input conditions, e.g., overlapping commands.

8.0 Interfaces

SYS-REQ-022: The system SHALL interface with an actuator driver circuit to control motor direction and power.
SYS-REQ-023: The system SHALL interface with an analog-to-digital converter (ADC) for position sensor data acquisition.
SYS-REQ-024: The system SHALL manage status and error indication via dedicated or multiplexed LEDs.

9.0 Constraints & Assumptions

SYS-REQ-026: The system operational voltage and current SHALL remain within thresholds defined by component limits.
SYS-REQ-027: The system SHALL tolerate short power interruptions and resume to last safe/known state on power restoration.

# 1.0 Architecture Style Selection

### Candidate Styles Evaluated
- Layered
- Component-Based (Module/Unit with clear interfaces)
- Monolithic

### Evaluation Against Needs
- **System Complexity:** Minimal; actuator logic is sequential, with clear input/output boundaries.
- **HW Interaction Needs:** Multiple MCU internal peripherals (ADC, PWM/CCU6, GPIOs, UART) with strong boundaries between command processing, sensor feedback, and actuator output. HW mapping arguments favor a component-based or layered style.
- **Testability:** Highest if software is modularized; grouping user interface, control kernel, and output drivers separately … matches ASPICE expectations.
- **Maintainability:** Easier with clear separation (component-based or layered). Monolithic would reduce maintainability and testability.
- **ASPICE L3:** Expects software architecture (SWE.2) to justify modularization, clear interfaces, and traceability to requirements (SWE.1). Modularity is needed.

### Selection & Justification
- **Selected Approach:** Component-Based / Modular (each logical responsibility as a separate software unit with explicit interfaces)
- **Rejected:**
  - **Monolithic:** Would not support ASPICE L3 or maintainability.
  - **Strict Layered:** Over-detailed for such a simple embedded actuator. Our architecture will permit layers-de-facto by strict module separation, but is not enforcing OSI-like stacks.

# 2.0 Software Architecture Definition (SWE.2)

## 2.1 Overview
The software is partitioned into discrete units each fulfilling an identifiable, traceable responsibility tied to SWE.1 requirements. Units communicate only via explicit interfaces – no global state (except for minimal cross-unit status needed for correct actuator function). All hardware-related information (registers, signals, constraints) is based exclusively on information present in the cited TLE985x documents (see above—no invention of electrical characteristics/values).

## 2.2 Software Units / Responsibilities / Interfaces

### 1. **User Command Interface Unit**
- Responsibilities: Receives UART commands, decodes requested position, validates user input against supported positions.
- Provided interfaces: user_command_received(command)
- Used interfaces: None (initial input source)
- Requirements: SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-014

### 2. **Flap Position Control Kernel**
- Responsibilities: Core logic – compares requested position to actual (from feedback), determines if motor movement is needed, issues actuation requests.
- Provided interfaces: request_move_to(position)
- Used interfaces: get_actual_position() from Feedback Acquisition; actuate_motor(direction, enable) from Output Driver
- Requirements: SWE-REQ-004, SWE-REQ-005, SWE-REQ-021

### 3. **Feedback Acquisition Unit**
- Responsibilities: Reads ADC potentiometer channel, converts ADC to position, validates range.
- Provided interfaces: get_actual_position() => position, get_adc_value()
- Used interfaces: None (hardware ADC)
- Requirements: SWE-REQ-009, SWE-REQ-010, SWE-REQ-011, SWE-REQ-015

### 4. **Motor Driver Output Unit**
- Responsibilities: Direct GPIO and PWM/CCU6 configuration, output for motor enable/disable and direction; react to control kernel requests.
- Provided interfaces: actuate_motor(direction, enable)
- Used interfaces: None (HW access)
- Requirements: SWE-REQ-006, SWE-REQ-007, SWE-REQ-008, SWE-REQ-016

### 5. **Status Indicator Output Unit**
- Responsibilities: Drives GPIO or HS switch for Power/Position LEDs following position changes; reflects system state per requirements.
- Provided interfaces: update_leds(position)
- Used interfaces: None
- Requirements: SWE-REQ-012, SWE-REQ-013, SWE-REQ-017

### 6. **System Initialization/Reset Unit**
- Responsibilities: On power-up, initialize all peripherals (UART, GPIO, CCU6/PWM, ADC); ensure all outputs in safe state.
- Provided interfaces: initialize_system()
- Used interfaces: None
- Requirements: SWE-REQ-018, SWE-REQ-019, SWE-REQ-020

### 7. **Error Management Unit**
- Responsibilities: Detects/handles out-of-range ADC, input errors, mechanical/electrical motor faults, disables actuator when needed.
- Provided interfaces: handle_input_error(), handle_feedback_error(type), handle_motor_fault()
- Used interfaces: None (watches signals)
- Requirements: SWE-REQ-011, SWE-REQ-022, SWE-REQ-026, SWE-REQ-027, SWE-REQ-028

### 8. **Configuration/Data Definition Unit**
- Responsibilities: Stores/calibrates position ranges, channel assignments, unaffected by run-time state.
- Provided interfaces: get_position_limits()
- Used interfaces: None
- Requirements: SWE-REQ-023, SWE-REQ-024, SWE-REQ-025

Software Unit: User Command IF
---------------------------------------------------
1. Responsibilities
   - Handles: Parse and validate user position commands via UART/LIN, issue ACK/NACK, detect invalid/corrupt/malformed commands.
   - Does not handle: decoding non-position commands, LIN protocol error-recovery (delegated to hardware), scheduling.
2. Internal Data Design
   - Variables: cmd_buffer[8], uint8_t cmd_value, uint8_t status_code
   - Structs: uart_rx_packet, lin_rx_frame
   - Config/State: UartLinMode (compile-time), error_count
3. State Machine
   - Idle: waiting for new frame/packet
   - Decoding: validating & extracting user command
   - Ack/Nack: responding with status
   - Fault: if protocol malformed; stays until error cleared
4. Algorithms & Control Flow
   - Wait for RX complete
   - Validate (framing/parity/CRC, value in range 0–5)
   - If valid: issue command event, send ACK
   - If invalid: block/ignore, increment error_count, send NACK
   - Never reset chip on malformed command
5. Interfaces (APIs)
   - Provided: CommandReceived(cmd: uint8_t), ErrorAck(), StatusMsg()
   - Required: UART_RxISR, LIN_RxISR
   - Params: cmd_value (0–5), status_code (OK/ERR)
   - Error reporting: error_return()
6. Error Handling
   - On malformed/invalid: increment error_count, send NACK
   - Hardware/frame-level error: rely on hardware autobaud/timeout
7. Resource & Timing Considerations
   - Invoked from RX ISR or polling loop
   - WCET: <<1ms typical (@ 20MHz core, per datasheet)
   - No reentrancy constraints (single RX at a time)
8. Traceability
   - SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-019, SWE-REQ-020, SWE-REQ-021, SWE-REQ-040

Software Unit: Flap Control Logic
---------------------------------------------------
1. Responsibilities
   - Handles: Flap position logic, bridge motor command generation, transition to Safe State, system idle management, error monitoring.
   - Does not handle: direct hardware access (delegated to IF units), scheduling.
2. Internal Data Design
   - Variables: uint8_t pos_target, uint8_t pos_actual, FlapControlState (Idle, Moving, Safe, Error)
   - Calibration: ADC threshold table[6] flash/NVM
   - Structs: FlapCmdMsg, FlapStatusMsg
3. State Machine
   - Idle: pos_actual == pos_target, no movement
   - Moving: actuating motor to target (monitored ADC)
   - Safe: on error (latched)
   - Error: persistent fault or manual abort
   - Transitions:
       • Idle→Moving: user cmd; Moving→Idle: reached target;
       • Any→Safe/Error: detected fault
4. Algorithms & Control Flow
   - On cmd: check validity, compare pos_actual to pos_target
   - If not equal: drive required direction
   - Continuously monitor ADC & error flags
   - On any error: abort movement, enter Safe
   - On complete: stop motor, notify status
5. Interfaces (APIs)
   - Provided: FlapMoveTo(pos: uint8_t), FlapGetStatus()
   - Required: MotorCmd(direction: enum), ADCRead(), ErrorHandler()
   - Params: pos_target (0–5), FlapStatusMsg
   - Error: FlapErrorEvent()
6. Error Handling
   - If motor/ADC HW fault, or impossible pos: assert error, enter Safe
7. Resource & Timing
   - Invoked on new cmd, ADC update, or error event
   - WCET: <<2ms (ADC latency as per datasheet 29.9.1)
   - Not reentrant (only one active command)
8. Traceability
   - SWE-REQ-005, 006, 007, 010, 011, 013, 014, 022–026, 031
