1.0 System Overview
The HVAC Flap Actuator system is a microcontroller-based prototype designed to control an air flap using a DC motor, providing discrete position control for air distribution in an HVAC system. Position feedback is via a potentiometer read by an ADC, and user commands are received over UART. Visual feedback is provided using LEDs. All operations are local; no vehicle network interfaces are present.

2.0 Flap Position Control
SYS-REQ-001: The system SHALL accept user commands to set the HVAC flap to one of six discrete positions (0 to 5).
SYS-REQ-002: The system SHALL move the flap to the commanded position if the command is valid.
SYS-REQ-003: The system SHALL stop the motor once the target position is reached.
SYS-REQ-004: The system SHALL ignore invalid position commands (i.e., commands not corresponding to positions 0–5).
SYS-REQ-005: The mapping of ADC values to positions SHALL be defined in software.
[Implied] The system SHALL not act on simultaneous contradictory commands (by accepting only one command at a time).

3.0 Motor Control
SYS-REQ-006: The system SHALL control the motor direction based on the required flap movement (clockwise or anti-clockwise).
SYS-REQ-007: The system SHALL switch off (disable) the motor when the target position is reached or an error/invalid state is detected.
SYS-REQ-008: Motor start and stop SHALL be managed via GPIO and PWM as appropriate.
[Implied] The system SHALL ensure the flap is only moved upon receipt of a valid command.

4.0 Position Feedback Acquisition & Processing
SYS-REQ-009: The system SHALL read flap position using the potentiometer connected to an ADC channel.
SYS-REQ-010: The system SHALL process and map ADC readings to discrete flap positions (0–5).
SYS-REQ-011: The system SHALL stop the motor if ADC values fall outside the valid range.
[Implied] The system SHALL periodically acquire and update position feedback.

5.0 User Command Interface
SYS-REQ-012: The system SHALL receive user commands via UART.
SYS-REQ-013: The system SHALL accept only numeric commands within the allowed range (0–5).
SYS-REQ-014: The system SHALL not transmit acknowledgments or errors for invalid commands.
[Implied] Commands from only one user/source SHALL be supported at a time.

6.0 Status Indication
SYS-REQ-015: The system SHALL turn on a dedicated power/status LED when the system is powered up.
SYS-REQ-016: The system SHALL illuminate a green LED corresponding to the current flap position so that only one position LED is ON at any time.
[Implied] LED indication SHALL update if the flap position changes as a result of a command or at power-up.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)
SYS-REQ-017: On power-up, the system SHALL initialize all peripherals (ADC, UART, GPIO, PWM), leave the motor OFF, read current flap position, turn the status LED ON, and illuminate the correct position LED.
SYS-REQ-018: While idle (no user command), the system SHALL monitor UART for commands and flap position for feedback indication.
SYS-REQ-019: When moving to a new position, the system SHALL update position indication and switch off the motor once the position is achieved.
SYS-REQ-020: If an invalid command is received, the system SHALL ignore it and continue normal operation.
[Implied] System states SHALL be managed according to this behavioral logic.

8.0 Interfaces (UART, motor driver, ADC, LEDs)
SYS-REQ-021: The system SHALL communicate with a PC/user via UART for command input.
SYS-REQ-022: The system SHALL interface with the motor driver (L298N) for motor actuation using GPIO and PWM.
SYS-REQ-023: The system SHALL use an ADC channel for flap position feedback from the potentiometer.
SYS-REQ-024: The system SHALL use GPIOs to control all status and position LEDs.
[Implied] Each interface SHALL be initialized and monitored for correct operation upon system start.

9.0 Constraints & Assumptions
SYS-REQ-025: The system SHALL operate as a single-flap, single-user, local controller only.
SYS-REQ-026: Calibration/position-mapping values SHALL be fixed in software; no self-learning or run-time calibration is required.
SYS-REQ-027: The system SHALL not assume perfect hardware; invalid readings must be handled as specified; advanced diagnostics are not required.
[Implied] The hardware setup (motor, gears, potentiometer) is mechanically correct.

10.0 Non-Functional Requirements
10.1 Responsiveness
SYS-REQ-028: The system SHALL process UART commands and update position/LED indication with responsiveness suitable for interactive manual testing (typically < 1 second per action, but no strict timing).

10.2 Error Handling & Edge Cases
SYS-REQ-029: The system SHALL stop the motor for any out-of-range ADC readings or unrecognized position commands.
SYS-REQ-030: The system SHALL not hang or crash if the commanded position cannot be achieved (e.g., due to hardware limits or potentiometer fault).

10.3 Resource Constraints
SYS-REQ-031: The system SHALL operate within the memory, I/O, and processing power available on the STM32F407-Discovery platform.

10.4 Maintainability & Modularity
SYS-REQ-032: Code and configuration values for positions, calibration, interfaces, and state indication SHALL be separated and well-documented for ease of change.

10.5 Testability
SYS-REQ-033: The system SHALL support testability via user command input (UART), observable motor behavior, and LED output.
[Implied] Manual/script-based testing SHALL be feasible using listed interfaces and behaviors.

Architecture-Relevant Considerations Derived from System Requirements

- Concurrency: Only implicit, low-level concurrency (e.g., interrupt-driven UART/ADC) is suggested; the system logic itself is single-command-at-a-time, with simple event handling.
- Interaction Complexity: The system has low interaction complexity; user commands are one-at-a-time, and control/feedback interfaces are direct.
- Control Complexity: The control logic is straightforward with stateful behavior tracked via software variables and simple status indication.
- Expandability: The system could be extended to support more positions or features, but is explicitly single-flap, single-user, no networking as per requirements.

1.0 Software Scope & Responsibility

The software implements flap position control, motor management, feedback acquisition, command handling, and status indication for a single-flap HVAC actuator on an STM32F407 MCU.
Responsibilities include interpreting UART commands, controlling motor/LEDs via GPIO/PWM, reading ADC input for flap position, mapping analog feedback, and managing simple event-driven behaviors per the system requirements.

2.0 Software Functional Requirements

2.1 User Commands
SWE-REQ-001: The software SHALL interpret and decode user commands received over UART to select a discrete flap position in the range 0 through 5. [SYS-REQ-001, SYS-REQ-012, SYS-REQ-013]
SWE-REQ-002: The software SHALL ignore and reject any UART command that does not represent a valid integer value in the range 0–5. [SYS-REQ-004, SYS-REQ-013, SYS-REQ-020]
SWE-REQ-003: The software SHALL accept only one user command at a time, and SHALL complete processing before accepting a new command. [Implied: SYS-REQ-001, SYS-REQ-012]
[Implied] No support for multiple or simultaneous command origins is provided.

2.2 Flap Control
SWE-REQ-004: The software SHALL check the decoded command and initiate flap repositioning only if a valid new position is requested. [SYS-REQ-002, SYS-REQ-018, SYS-REQ-019]
SWE-REQ-005: The software SHALL stop the flap repositioning operation as soon as the new target position is achieved. [SYS-REQ-003, SYS-REQ-019]
[Implied] When at target, no further movement command SHALL be issued.

2.3 Motor Control
SWE-REQ-006: The software SHALL control motor driver outputs to rotate in the direction needed for flap repositioning (clockwise or anti-clockwise). [SYS-REQ-006]
SWE-REQ-007: The software SHALL immediately disable motor driver outputs when the target position is reached or when an error/invalid state is detected. [SYS-REQ-007, SYS-REQ-011, SYS-REQ-029]
SWE-REQ-008: The software SHALL execute all motor enable/disable and direction controls via logical access to GPIO and PWM outputs only. [SYS-REQ-008, SYS-REQ-022]
[Implied] The flap is only actuated in response to valid commands.

2.4 Feedback Processing
SWE-REQ-009: The software SHALL acquire flap position feedback by reading the assigned ADC channel attached to the potentiometer. [SYS-REQ-009, SYS-REQ-023]
SWE-REQ-010: The software SHALL process the ADC value to determine and map it to a discrete flap position (0–5) using a software-defined mapping table or logic. [SYS-REQ-005, SYS-REQ-010]
SWE-REQ-011: The software SHALL immediately stop the motor and set an error state if the ADC reading falls outside valid, calibrated boundaries. [SYS-REQ-011, SYS-REQ-027, SYS-REQ-029]
SWE-REQ-012: The software SHALL update current position tracking and provide for recalculation after ADC sampling or command-based movement. [SYS-REQ-019]
[Implied] Feedback SHALL be updated each time new data is sampled or position changes.

2.5 Status Indication
SWE-REQ-013: The software SHALL drive a dedicated status/power LED via GPIO as soon as software initialization is complete. [SYS-REQ-015, SYS-REQ-017]
SWE-REQ-014: The software SHALL illuminate only the one position LED (of six) corresponding to the present flap position at any given time. [SYS-REQ-016]
SWE-REQ-015: The software SHALL update LED indication (status and position) on any position change or at system power-up. [SYS-REQ-016, SYS-REQ-017, SYS-REQ-019]
[Implied] LED outputs reflect internally tracked position, not raw ADC state.

3.0 Software Interface Requirements

SWE-REQ-016: The software SHALL receive ASCII-encoded user commands over a logical UART interface for input only. [SYS-REQ-012, SYS-REQ-021]
SWE-REQ-017: The software SHALL control the DC motor via logical GPIO and PWM signals connected to a standard H-bridge motor driver. [SYS-REQ-008, SYS-REQ-022]
SWE-REQ-018: The software SHALL acquire flap position feedback by initiating ADC conversions on the assigned MCU ADC channel. [SYS-REQ-009, SYS-REQ-023]
SWE-REQ-019: The software SHALL control dedicated status and position indicator LEDs via GPIO outputs. [SYS-REQ-015, SYS-REQ-016, SYS-REQ-024]
[Implied] All interface initialization and monitoring is software-driven, hardware-agnostic.

4.0 Software Behavioral Requirements

SWE-REQ-020: The software SHALL perform initialization of all peripherals (GPIO, ADC, UART, PWM) upon power-up and before entering main operation. [SYS-REQ-017, SYS-REQ-024]
SWE-REQ-021: On startup, the software SHALL determine current flap position using ADC feedback, enable status LED, and reflect position via position LEDs without actuating the motor. [SYS-REQ-017]
SWE-REQ-022: During normal operation, if no user command is received, the software SHALL monitor UART for commands and update position feedback and indication. [SYS-REQ-018]
SWE-REQ-023: The software SHALL process each user command to drive the flap as required and stop movement upon reaching the requested position. [SYS-REQ-002, SYS-REQ-003, SYS-REQ-019]
SWE-REQ-024: The software SHALL ignore all invalid commands and continue to operate in its current mode. [SYS-REQ-020]
[Implied] Control flow is event/data-driven, not cyclic or fixed-order/schedule.

5.0 Software Data & Configuration

SWE-REQ-025: The software SHALL implement a mapping table or equivalent algorithm to translate ADC readings to discrete positions (0–5), using fixed, calibration values. [SYS-REQ-005, SYS-REQ-026]
SWE-REQ-026: All configuration values (position thresholds, GPIO/channel mappings, etc.) SHALL be implemented in modular, maintainable structures for ease of future change. [SYS-REQ-032]
[Implied] There SHALL be no auto-calibration, nor dynamic learning of mapping values at runtime.

6.0 Software Error Handling

SWE-REQ-027: For any error detected (invalid ADC value, unachievable position, communication error), the software SHALL immediately disable the motor and ignore further movement requests until valid conditions return. [SYS-REQ-007, SYS-REQ-011, SYS-REQ-027, SYS-REQ-029, SYS-REQ-030]
SWE-REQ-028: Invalid UART inputs SHALL be ignored, and no error or acknowledgment SHALL be returned to the sender. [SYS-REQ-014, SYS-REQ-020]
SWE-REQ-029: The software SHALL never crash or deadlock due to any invalid input or unexpected state. [SYS-REQ-030]
[Implied] The error handling strategy is to fail-safe and continue monitoring for valid recovery events.

7.0 Performance & Responsiveness

SWE-REQ-030: The software SHALL process each user command and update indicators in a time frame suitable for interactive testing, typically within one second per action, as observed externally. [SYS-REQ-028]
[Implied] No fixed cycle time, OS task, or polling/interrupt servicing model is imposed.

8.0 Resource Constraints

SWE-REQ-031: The software SHALL execute within the available code flash, RAM, I/O pins, and CPU performance limits of the STM32F407-Discovery board. [SYS-REQ-031]
[Implied] Resource quotas SHALL be enforced by design, not at run-time.

9.0 Testability

SWE-REQ-032: The software SHALL support functional verification by providing observable changes in motor motion, UART command acceptance/rejection, and LED outputs as visible indicators. [SYS-REQ-033]
[Implied] No built-in self-test or explicit test stub logic is implemented beyond the defined observable behaviors.

10.0 Implied Requirements

[Implied] Each coded module SHALL be structured, maintainable, and well-documented to support future changes as per SYS-REQ-032.
[Implied] No advanced diagnostics, networking, multi-user capability, or run-time reconfiguration is present per baseline system assumptions.

# HVAC Flap Actuator — Software Architecture (SWE.2)

**Scope:**
This architecture is derived exclusively from the supplied system and software requirements for the HVAC Flap Actuator application (branch: demojun-10a).

---

## 1. ARCHITECTURE STYLE SELECTION

### Candidate Styles Considered
- Layered (Presentation, Application, Hardware Abstraction)
- Component-Based (distinct modules for each function or interface)
- Monolithic (single-block with functional separation only through code structure)
- Service-Oriented / Microkernel (not suitable; out of scope per SYS/SWE.1)

### Evaluation

| Style            | System Complexity | HW Interaction | Testability       | Maintainability   | ASPICE L3 Fit           |
|------------------|------------------|----------------|-------------------|-------------------|-------------------------|
| Layered          | Moderate         | Good           | Good              | Good              | Well-suited             |
| Component-Based  | Moderate         | Very Good      | Very Good         | Very Good         | Well-suited             |
| Monolithic       | Simple           | Acceptable     | Limited           | Poor              | Not preferred           |
| Service/Micro    | Excessive        | Overkill       | Unneeded          | Overengineered    | Not justified           |

### Style Decision
**Selected:**  
**Component-based architecture** (justified below).

**Rational & Justification:**  
- System and SWE.1 both require clear interface abstraction (UART, GPIO/PWM, ADC, LEDs) with direct traceability to functional decomposition (SWE-REQ-016 thru SWE-REQ-019); these are best modularized as components.
- Testability and maintainability increased via explicit interface separation.
- System complexity is low—layered is possible, but a flat component model achieves the modularity and traceability sought by SWE.1/ASPICE.
- Monolithic design explicitly rejected for long-term maintainability and traceability reasons.
- Service/microkernel not justified due to simplicity and lack of dynamic or distributed requirements.

---

- User command input triggers `Command Manager`.
- `Command Manager` invokes `Flap Control Coordinator` to process and direct operations.
- `Flap Control Coordinator` orchestrates:
    - Motor actions via `Motor Control`
    - ADC feedback via `Feedback Processing`
    - LED indications via `LED Management`
- All external HW accesses handled via dedicated driver interfaces.
