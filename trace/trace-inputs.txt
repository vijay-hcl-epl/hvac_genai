1.0 System Overview  
The HVAC Flap Actuator is responsible for controlling the position of an air flow regulating flap based on received commands, providing feedback on flap status, and interacting over defined automotive interfaces.

2.0 Flap Position Control  
SYS-REQ-001: The system SHALL move the flap to the target position command received from the control unit or user interface within specified tolerance.  
SYS-REQ-002: The system SHALL reject or report commands outside the valid physical range of the flap actuator.

3.0 Motor Control  
SYS-REQ-003: The system SHALL control the DC motor to move the flap towards the target position.  
SYS-REQ-004: The system SHALL stop the motor when the target position is reached or on detection of a fault.

4.0 Position Feedback Acquisition & Processing  
SYS-REQ-005: The system SHALL acquire the current position of the flap via a position sensor.  
SYS-REQ-006: The system SHALL process the sensor signal to determine the actual flap position within ±2° accuracy.

5.0 User Command Interface  
SYS-REQ-007: The system SHALL support reception of position commands via UART.  
SYS-REQ-008: The system SHALL validate received commands for range and format before accepting.

6.0 Status Indication  
SYS-REQ-009: The system SHALL provide visual status indication using LEDs for the following states: power-up, idle, active movement, target reached, error/fault.  
[Implied]: Distinct LED statuses for each system state.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)  
SYS-REQ-010: On power-up, the system SHALL initialize, self-check, and indicate readiness via LED.  
SYS-REQ-011: In idle state, the system SHALL conserve power and monitor for incoming commands.  
SYS-REQ-012: On target reached, the system SHALL stop all motion, indicate status, and send feedback.  
SYS-REQ-013: On invalid input, the system SHALL ignore the command and indicate error status.  
[Implied]: System returns to idle after motion completes or if an error occurs.

8.0 Interfaces (UART, motor driver, ADC, LEDs)  
SYS-REQ-014: The system SHALL expose a UART interface for command and status communication.  
SYS-REQ-015: The system SHALL interface with a motor driver to actuate the DC motor.  
SYS-REQ-016: The system SHALL use an ADC to read analog position signals.  
SYS-REQ-017: The system SHALL use GPIOs for LED status indication.

9.0 Constraints & Assumptions  
SYS-REQ-018: The system SHALL operate within 8V–16V DC vehicle supply voltage.  
SYS-REQ-019: The system SHALL support flap positions between 0% (fully closed) and 100% (fully open).

10.0 Non-Functional Requirements

  10.1 Responsiveness  
  SYS-REQ-020: The system SHALL achieve commanded flap position within 500ms under normal conditions.

  10.2 Error Handling & Edge Cases  
  SYS-REQ-021: The system SHALL detect and report sensor failures, motor faults, and invalid commands within 50ms of occurrence.

  10.3 Resource Constraints  
  SYS-REQ-022: The system SHALL execute all control and feedback functions using <= 128KB Flash and <= 16KB RAM.

  10.4 Maintainability & Modularity  
  SYS-REQ-023: The system SHALL structure software to separate command parsing, motor control, sensor processing, and status indication.

  10.5 Testability  
  SYS-REQ-024: The system SHALL support diagnostic commands for testing all interfaces and error conditions.

---

Architecture-Relevant Considerations Derived from System Requirements

- Concurrency: No explicit concurrency mandated by requirements; however, simultaneous acquisition of commands and feedback/update may introduce parallelism.
- Interaction Complexity: Moderate, with defined command processing, feedback, and multiple states.
- Control Complexity: State-based behaviors covering power-up, idle, movement, target reached, invalid input, and errors.
- Expandability: Clear separation of interfaces and state logic allow for potential integration with additional communication protocols or extended diagnostics in future variants.

1.0 Software Scope & Responsibility
The software embedded in the HVAC Flap Actuator ECU implements all logic to receive user commands, control the flap position via DC motor based on feedback from a position sensor, handle motor actuation, manage validation and feedback, and visually indicate status using LEDs. The software abstracts hardware-specific drivers and exposes logical interfaces needed for integration in the vehicle. It covers startup, normal operation, error states, and all command interaction; it does not set any tasking/scheduling policy, or cyclic/periodic mechanisms beyond what is mandated by system requirements.

# HVAC Flap Actuator ECU: Software Architecture (SWE.2)

## 1. Architecture Style Selection

Candidate Styles Considered:
- Layered
- Component-based
- Monolithic

**Evaluation and Selection:**
- The system and software requirements (see SWE-REQ-023, 036) expressly demand separation of concerns for modularity and testability. Multiple distinct functionality domains are present: command parsing, actuation, feedback acquisition, status indication, diagnostics.
- Hardware adaptation and testability both favor distinct, loosely-coupled blocks.
- ASPICE L3 expects justifiable architectural structuring and explicit traceability.

**Decision:**
- Selected: "Component-based architecture." Each major functional area (as derived from requirements) is implemented as an explicit software unit. (TRACE: SWE-REQ-023, 036)
- Rejected: "Layered" (No requirement for stack/hierarchy or forced abstraction). "Monolithic" (Rejected due to maintainability and testability needs in SWE.1).


## 2. Architecture Definition

**Execution Model:**
No explicit execution model or scheduling policy is mandated by the requirements at this stage.

  - SWE-REQ-003, 005, 006, 014, 028

  - SWE-REQ-007, 008, 013

  - SWE-REQ-009, 010, 015, 027

# HVAC Flap Actuator ECU: Low-Level Design (SWE.3)

## Conventions
- Target Language: MISRA-style Embedded C (NO dynamic memory allocation)
- Each Software Unit directly maps to architecture and SWE.1 (requirements trace shown)
- No code, no scheduling/tasking, no invented responsibilities, fully requirement-traceable

================================================================================

### 1. Software Unit: Command Handler

1. Responsibilities
   - Handles: parsing and validating UART commands, dispatches to State Manager
   - Does not handle: direct actuation, status assessment, hardware specifics

2. Internal Data Design
   - `LastCmd` (struct holding command details, validity, range)
   - `CommandBuffer[FIXED_LEN]`
   - No dynamic allocation; fixed buffer sizes only

3. State Machine
   - State: None (stateless, event-driven calls per input)
   - Flow: Upon UART RX event → validate packet → update LastCmd → dispatch

4. Algorithms & Control Flow
   - On UART RX: parse bytes, check CRC/range, update LastCmd; if valid, notify State Manager; else, flag error

5. Interfaces (APIs)
   - Provided: `HandleUARTCommand(const uint8_t* Buf, size_t Len)`
   - Required: `NotifyCmdToStateMgr(const CommandStruct*)`
   - Params: Input buffer, returns status/error code

6. Error Handling
   - Invalid/Out-of-range → returns error, sets error flag, notifies State Manager

7. Resource & Timing Considerations
   - Invoked on UART RX event only
   - WCET: <5ms
   - Not re-entrant (single-command-at-a-time model)

8. Traceability
   - SWE-REQ-001, SWE-REQ-002, SWE-REQ-012, SWE-REQ-024, SWE-REQ-035

--------------------------------------------------------------------------------

### 2. Software Unit: Flap Motor Control

1. Responsibilities
   - Handles: commanding DC motor for flap, monitors target, stops on fault
   - Does not handle: command parsing, system state transitions

2. Internal Data Design
   - `TargetPosition` (uint8_t: 0-100), `CurrentPosition` (uint8_t), `MotorStatus` (enum)
   - `ActuationInProgress` (bool)

3. State Machine
   - States: Idle, Actuating, Stopped, Fault
   - Events: Start Request, TargetReached, FaultDetected, Stop Request
   - Transitions: Idle→Actuating (start), Actuating→Stopped (on target/fault)

4. Algorithms & Control Flow
   - On Start: check bounds, drive motor, poll position
   - On Target/Fault: stop motor, notify State Manager

5. Interfaces (APIs)
   - Provided: `ControlFlapMotor(uint8_t TargetPosition)`
   - Required: `GetCurrentPosition()`, `ReportMotorStatus()`
   - Params: Target pos, returns status

6. Error Handling
   - Faults → stop, set error, notify State Manager

7. Resource & Timing Considerations
   - Periodic invocation until target/fault
   - WCET: 10ms per invocation
   - Not re-entrant

8. Traceability
   - SWE-REQ-003, SWE-REQ-005, SWE-REQ-006, SWE-REQ-014, SWE-REQ-028

--------------------------------------------------------------------------------

### 3. Software Unit: Position Sensor Processing

1. Responsibilities
   - Handles: ADC reading, convert to angle, provides to Flap/Mgr
   - Does not handle: direct motor control, system state

2. Internal Data Design
   - `RawAdcValue` (uint16_t), `LastPositionDeg` (float, fixed-point for C)

3. State Machine
   - State: None (conversion function)

4. Algorithms & Control Flow
   - ADC read → convert (scaling) → update LastPositionDeg

5. Interfaces (APIs)
   - Provided: `GetFlapPosition(void)`
   - Required: `ReadADC(void)`
   - Returns: position, diagnostic status

6. Error Handling
   - Bad ADC → set error flag

7. Resource & Timing Considerations
   - Invoked by Flap Motor/State Manager/Diagnostics
   - WCET: 3ms
   - Thread-safe if required

8. Traceability
   - SWE-REQ-007, SWE-REQ-008, SWE-REQ-013

--------------------------------------------------------------------------------

### 4. Software Unit: Status Indication (LED)

1. Responsibilities
   - Handles: Drives LEDs according to state/error
   - Does not handle: state transitions, error analysis

2. Internal Data Design
   - `LedState` (enum), `PatternBuffer[N]` (if req’d per state)

3. State Machine
   - States: PowerUp, Idle, Active, TargetReached, Error
   - Events: State change, error indication

4. Algorithms & Control Flow
   - On state/error updates: set buffer, drive GPIO

5. Interfaces (APIs)
   - Provided: `SetLedState(LedState)`
   - Required: `DrvGpioSet(uint8_t led, bool on)`

6. Error Handling
   - LED driver errors → escalate to State Manager

7. Resource & Timing Considerations
   - On state changes only
   - WCET: 1ms
   - Not re-entrant

8. Traceability
   - SWE-REQ-009, SWE-REQ-010, SWE-REQ-015, SWE-REQ-027

--------------------------------------------------------------------------------

### 5. Software Unit: State & Error Manager

1. Responsibilities
   - Handles: All system state transitions, error monitoring, event coordination
   - Does not handle: low-level device I/O, direct command parsing

2. Internal Data Design
   - `SysState` (enum), `ErrorFlags` (bitfield), `LastTransition` (struct)

3. State Machine
   - States: PowerUp, Idle, Active, TargetReached, Error
   - Events: Init, CommandRx, ValidTarget, Fault, Reset
   - Complete state/event matrix – all transitions as derived

4. Algorithms & Control Flow
   - On event: evaluate transition, update SysState, notify

5. Interfaces (APIs)
   - Provided: `NotifyEvent(EventType, EventData)`
   - Required: APIs from Command Handler, Flap Motor, LED, Diagnostics

6. Error Handling
   - Persistent faults → Safe idle, set error message

7. Resource & Timing Considerations
   - Invoked on each software event
   - WCET: 3ms
   - Not re-entrant

8. Traceability
   - SWE-REQ-011, SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-020, SWE-REQ-021, SWE-REQ-022, SWE-REQ-023, SWE-REQ-026, SWE-REQ-029

--------------------------------------------------------------------------------

### 6. Software Unit: Config/Data Manager

1. Responsibilities
   - Handles: Provides configuration, dynamic software data to other units
   - Does not handle: processing, status, state

2. Internal Data Design
   - All config tables (read-only), variable store (flap position, errors...)

3. State Machine
   - State: None (getter/setter only)

4. Algorithms & Control Flow
   - Get/Set ops for config/data (bounds checked)

5. Interfaces (APIs)
   - Provided: `GetConfig(key)`, `SetConfig(key,value)`
   - Required: None

6. Error Handling
   - Data bounds, illegal keys → error code

7. Resource & Timing Considerations
   - Typically called by State Manager/Flap Motor
   - WCET: <1ms
   - Thread-safe if required

8. Traceability
   - SWE-REQ-023, SWE-REQ-024, SWE-REQ-025, SWE-REQ-033, SWE-REQ-034, SWE-REQ-036

--------------------------------------------------------------------------------

### 7. Software Unit: Diagnostic Interface

1. Responsibilities
   - Handles: Accepts/dispatches diagnostic/test commands; monitors/report status
   - Does not handle: normal operation, state transitions

2. Internal Data Design
   - `DiagStatus` (struct), `DiagCmdBuffer` (fixed size)

3. State Machine
   - State: None (event-driven on command/test)

4. Algorithms & Control Flow
   - On diag command RX: parse, verify; call unit under test; marshal response

5. Interfaces (APIs)
   - Provided: `RunDiagCommand(DiagCmdType, params)`
   - Required: APIs from all main units

6. Error Handling
   - Invalid command → error code in response

7. Resource & Timing Considerations
   - Only on diag/test
   - WCET: <3ms
   - Not re-entrant

8. Traceability
   - SWE-REQ-035
