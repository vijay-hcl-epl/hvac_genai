1.0 System Overview
SYS-REQ-001 The system SHALL control a single HVAC air flap actuator for air direction/mixing, as commanded by the user.
SYS-REQ-002 The system SHALL operate as a standalone prototype on a microcontroller platform and not interface with any vehicle networks. [Implied]

2.0 Flap Position Control
SYS-REQ-003 The system SHALL move the flap to the position commanded by the user.
SYS-REQ-004 The system SHALL support discrete flap positions as defined (positions 0 to 5).
SYS-REQ-005 The system SHALL stop the motor when the target position is reached.
SYS-REQ-006 If an invalid target position is commanded, the motor SHALL remain stopped. [Implied]

3.0 Motor Control
SYS-REQ-007 The system SHALL control a DC motor to modify the flap position using GPIO pins and PWM.
SYS-REQ-008 The system SHALL support both clockwise and anti-clockwise motor operation.
SYS-REQ-009 The system SHALL stop the motor at the target position or if an ADC error is detected (e.g., out-of-range value). [Implied]

4.0 Position Feedback Acquisition & Processing
SYS-REQ-010 The system SHALL acquire the flap position using a potentiometer connected to an ADC channel.
SYS-REQ-011 The system SHALL map ADC readings to logical flap positions (0 to 5) based on fixed well-defined ADC ranges.
SYS-REQ-012 The system SHALL continuously monitor the flap position during operation. [Implied]

5.0 User Command Interface
SYS-REQ-013 The system SHALL receive user flap position commands via UART as simple numeric values.
SYS-REQ-014 The system SHALL process each received UART command promptly after reception.
SYS-REQ-015 The system SHALL ignore any invalid UART commands without producing an acknowledgment or error response.

6.0 Status Indication
SYS-REQ-016 The system SHALL use a dedicated power/status LED to indicate system power-on state.
SYS-REQ-017 The system SHALL use up to 6 green LEDs to indicate the current logical flap position (at most 1 green LED illuminated at any time).
SYS-REQ-018 LED behavior SHALL always directly reflect the actual system and flap status (no flashing or patterns).

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)
SYS-REQ-019 On power-up, the system SHALL initialize all peripherals (ADC, UART, GPIO, PWM), ensure the motor is OFF, and read the current flap position.
SYS-REQ-020 At start-up, the system SHALL turn on the power/status LED and set green position LEDs according to the initial detected flap position.
SYS-REQ-021 The system SHALL wait in an idle state for user commands.
SYS-REQ-022 Upon valid command, the system SHALL move the flap towards the target position and indicate this with the corresponding LED.
SYS-REQ-023 If a received command is invalid, the system SHALL remain in the current state and ignore the input. [Implied]

8.0 Interfaces (UART, motor driver, ADC, LEDs)
SYS-REQ-024 The system SHALL use UART for PC-to-microcontroller command input only.
SYS-REQ-025 The system SHALL use GPIO and PWM to drive the DC motor via the motor driver module (L298N).
SYS-REQ-026 The system SHALL use ADC to sample the potentiometer for position feedback.
SYS-REQ-027 The system SHALL use GPIO to control the power and position-indicating LEDs.

9.0 Constraints & Assumptions
SYS-REQ-028 The system SHALL only control a single flap and a single DC motor.
SYS-REQ-029 Only one user command SHALL be processed at a time.
SYS-REQ-030 ADC position calibration ranges SHALL be fixed in software (no dynamic calibration/self-learning).
SYS-REQ-031 The system SHALL assume hardware is functional unless proven otherwise by error input (e.g., out-of-range ADC). [Implied]

10.2 Error Handling & Edge Cases
SYS-REQ-033 The system SHALL stop the motor if a position command is outside expected range or if an ADC value is out of the defined calibration bands.
SYS-REQ-034 The system SHALL handle error events by ensuring the motor is off and the system state is safe. [Implied]

10.3 Resource Constraints
SYS-REQ-036 The system SHALL operate without dynamic memory allocation and within the microcontroller’s resources.

SYS-REQ-037 The requirements and logic SHALL be clear and sufficient for modular software design and future maintenance. [Implied]

# 1.0 SWE.2 SOFTWARE ARCHITECTURE — HVAC FLAP ACTUATOR

## 1.1 Architecture Style Selection & Justification

### Candidate Styles Considered
- **Monolithic / Main-loop (Single Function Block)**
- **Layered Architecture (Interface-abstraction separation)**
- **Component-based (modular units with defined interfaces)**

### Evaluation
- **System complexity**: The system is simple, with discrete functional responsibilities; no dynamic tasking, OS, or concurrent scheduling. Component boundaries align with major abstractions only (I/O, Control Logic).
- **HW interaction**: Direct mapping to microcontroller peripherals (UART, GPIO/PWM, ADC). No abstraction needed beyond per-unit assignation.
- **Testability**: Modular structure at the function/unit level enables static and interface-level testing—especially for core logic and I/O.
- **Maintainability**: Layered/componentized units allow future extension (new sensor/motor, error logic) without design rupture.
- **ASPICE L3**: Component-based (unitized, testable, traceable, no invented behavior) satisfies L3 expectations while aligning tightly to SWE.1.

#### Style Decision
- **Selected:** Component-based (unitized abstraction: UART Interface, Position Feedback, Motor Actuation, Status Indication, Control Logic)
- **Rejected:**
  - Main-loop: Lacks modularity—a workaround for microcontroller projects, but not maintainable or ASPICE-suitable.
  - Layered: Overhead not justified—there are no cross-cutting platform services to separate (middleware, device drivers, etc).

### Execution Model
No explicit execution model or scheduling policy is mandated by the requirements at this stage. (SWE-REQ-033).

For each software unit defined in SWE.2, the following template and rules are strictly adhered to. No units, interfaces, or behaviors are introduced beyond those specified in SWE.1 and SWE.2. Software Unit: UART Command Handler

1. Responsibilities  
   - Handles reception and validation of position commands over UART (SWE-REQ-001, SWE-REQ-002, SWE-REQ-003). 
   - Forwards validated commands to Control Logic.
   - Does not handle command queuing, timing, or error response output beyond ignoring invalid input.

2. Internal Data Design  
   - Input buffer: static char[] for UART RX.  
   - Validated input: static int for command value (0-5).
   - Receive state (IDLE, RECEIVING, COMPLETE/INVALID).

3. State Machine  
   - States: IDLE (waiting), RECEIVING (accumulating chars), VALIDATING (checking input), COMPLETE (valid, signal main), INVALID (ignore).
   - Events: UART RX, End-of-line/Receive complete, Out-of-range, Error.
   - Actions: Move from IDLE to RECEIVING on RX, accumulate data, validate on EOL; valid moves to COMPLETE, invalid to INVALID (then back to IDLE).

4. Algorithms & Control Flow  
   - On RX event: Read char, append if digit (max 1 char - single digit 0-5), signal EOL or buffer full.
   - If completed: Parse input, check range (0-5). If valid, forward to control logic; If invalid, clear buffer, return to IDLE.

5. Interfaces (APIs)  
   - Provided: uart_rx_handler(void* param) — receives UART input, triggers internal FSM.
   - Required: send_cmd_to_control_logic(int position).

6. Error Handling  
   - Invalid UART or out-of-range: Discard, return to idle. No error output generated.

7. Resource & Timing Considerations  
   - Invoked on each UART RX event; typical processing <100μs per char; no reentrancy needed; all state static.

8. Traceability  
   - SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-016, SWE-REQ-028

======================================================================

Software Unit: Position Feedback Handler

1. Responsibilities
   - Handles ADC sampling. Maps value to [0-5] position. Flags error if out-of-range.
   - Provides logical position, error status to control logic.
   - Does not handle calibration storage (uses only constant data).

2. Internal Data Design
   - Static uint16_t adc_sample; static int logical_position (0-5 or -1 if invalid).
   - Const struct with calibration table: {min, max} per position.
   - Error flag: ADC_FAULT, boolean.

3. State Machine
   - States: IDLE (wait poll), SAMPLING (acquire ADC), MAPPING (lookup), OK (valid), FAULT (flag error).
   - Events: Poll trigger, ADC completion, out-of-range.
   - Actions: Sample ADC, check against calibration, set position/error, return to IDLE.
   - If value not in any calibrated range: set FAULT, position = -1.

4. Algorithms & Control Flow
   - When poll triggered: Read ADC, for each calibration slot check min ≤ sample ≤ max; if match, position=N. None: FAULT.
   - Signal position/error to control logic each time.

5. Interfaces (APIs)
   - Provided: get_flap_position(void) → int; get_adc_fault(void) → bool.
   - Required: adc_read(void).

6. Error Handling
   - If no match in calibration table: set error, position invalid.
   - All outputs default to safety if error.

7. Resource & Timing Considerations
   - Runs per periodic poll (typ. 10 ms or on demand).  < 20μs per acquisition. Not reentrant.

8. Traceability
   - SWE-REQ-011, SWE-REQ-012, SWE-REQ-024, SWE-REQ-027, SWE-REQ-018
