# System Requirements Specification – HVAC Flap Actuator

## 1.0 System Overview
The system is a simple prototype HVAC air flap actuator, demonstrating control over vent airflow direction/mix in a vehicle. It electrically operates a single flap between discrete positions using a DC motor. The system features direct user control via UART, feedback through potentiometer and LEDs, is implemented on a microcontroller (STM32F407G-DISC1), and is intended for education and process demonstration—not automotive production.

---
## 2.0 Flap Position Control Requirements
SYS-REQ-001: The system shall allow the user to command a target flap position using numeric UART input.
SYS-REQ-002: The system shall compare the current flap position to the target position.
SYS-REQ-003: The system shall move the flap to the commanded position.
SYS-REQ-004: The system shall stop the flap motor once the requested position is reached.
SYS-REQ-005: The system shall support at least six discrete flap positions (example: 0 to 5).
SYS-REQ-006: The system shall ensure only valid positions can be targeted.
SYS-REQ-007: [Implied] The system shall continuously monitor the current flap position while the flap is moving.
SYS-REQ-008: [Implied] The system shall prevent movement beyond the minimum or maximum flap position.

---
## 3.0 Motor Control Requirements
SYS-REQ-009: The system shall control motor direction (clockwise/counter-clockwise) via GPIO per position request.
SYS-REQ-010: The system shall enable the motor to move only when a new valid command is received.
SYS-REQ-011: The system shall disable and stop the motor immediately when the target position is reached.
SYS-REQ-012: The motor shall be OFF by default on system startup.
SYS-REQ-013: [Implied] The system shall prevent the motor from running indefinitely in case of persistent invalid feedback.
SYS-REQ-014: [Implied] PWM-based speed control of the motor shall be adjustable in software, but speed value is not a requirement in this prototype.

---
## 4.0 Position Feedback Acquisition and Processing
SYS-REQ-015: The system shall acquire analog feedback from a potentiometer mechanically linked to the flap.
SYS-REQ-016: The potentiometer signal shall be connected to an ADC channel.
SYS-REQ-017: The system shall map ADC values to discrete logical flap positions, as defined in software calibration data.
SYS-REQ-018: The system shall define fixed ADC ranges for each logical flap position in software.
SYS-REQ-019: [Implied] The system shall ignore transient noise/spikes in potentiometer readings that may occur during steady (idle) state.
SYS-REQ-020: [Implied] If an ADC reading is out-of-range, the system shall immediately stop the motor and maintain last-known-safe position.

---
## 5.0 User Command Interface Requirements
SYS-REQ-021: The system shall receive user commands as numeric UART input representing desired flap positions.
SYS-REQ-022: The system shall validate user commands against the range of supported flap positions.
SYS-REQ-023: The system shall ignore and not act on invalid UART commands.
SYS-REQ-024: The system shall not send acknowledgment or error response for invalid commands.
SYS-REQ-025: [Implied] The system shall accept only one command at a time and not queue multiple commands.

---
## 6.0 Status Indication Requirements
SYS-REQ-026: The system shall indicate power status via a dedicated LED.
SYS-REQ-027: The system shall indicate the current detected flap position via green LEDs, ensuring only one position LED is ON at a time.
SYS-REQ-028: The LED indication shall be clear, unambiguous, and map 1:1 to the currently detected position.
SYS-REQ-029: [Implied] LEDs shall update immediately after the flap changes position.
SYS-REQ-030: [Implied] The system shall ensure no LEDs (except the power LED) are lit if position cannot be determined due to sensor fault.

---
## 7.0 System Behavioral Requirements
SYS-REQ-031: The system shall initialize all peripherals (ADC, UART, GPIO, PWM) on startup.
SYS-REQ-032: On power-up, the system shall read the current position using the potentiometer and update LEDs.
SYS-REQ-033: By default after reset, the system shall not move the motor unless/until a valid command is received.
SYS-REQ-034: The system shall transition to idle state and maintain current position after a target is reached.
SYS-REQ-035: The system shall ignore invalid (out-of-range) UART commands during any state.
SYS-REQ-036: [Implied] The system shall survive power cycling or reset and resume normal operation from the detected flap position.
SYS-REQ-037: [Implied] The system shall not require a homing sequence for this prototype.

---
## 8.0 System Interface Requirements
SYS-REQ-038: The system shall provide a UART interface for receiving user commands from a PC.
SYS-REQ-039: The system shall interface with a DC motor through a motor driver (L298N or equivalent) using GPIO and PWM.
SYS-REQ-040: The system shall receive analog input from a potentiometer via an ADC channel.
SYS-REQ-041: The system shall provide digital outputs for driving position LEDs and a power LED.
SYS-REQ-042: [Implied] The system shall not require or support any vehicle network (e.g., CAN, LIN) communication for this prototype.

---
## 9.0 Constraints and Assumptions
SYS-REQ-043: Only a single flap shall be controlled.
SYS-REQ-044: Only one DC motor shall be present and controlled.
SYS-REQ-045: Only one user command shall be processed at a time; parallel commands are not supported.
SYS-REQ-046: The microcontroller hardware is assumed to operate correctly; hardware diagnostics are not required.
SYS-REQ-047: ADC position calibration is static—no dynamic calibration or self-learning is required.
SYS-REQ-048: No real-time constraints or deadlines are defined—responsiveness is on a human time scale.
SYS-REQ-049: [Implied] System software shall be simple and understandable for demonstration and educational use.

---
## 10.0 Non-Functional Requirements
### 10.1 Responsiveness Expectations
SYS-REQ-050: The system shall feel responsive for interactive human testing—UART commands shall be processed shortly after receipt.

### 10.2 Error Handling and Edge Cases
SYS-REQ-051: The system shall ignore invalid UART commands and not affect the current state or position.
SYS-REQ-052: If ADC values are outside all valid ranges, the system shall halt the motor and not attempt to move the flap until readings return valid.
SYS-REQ-053: The system shall not crash if the target position cannot be attained.
SYS-REQ-054: No timeout or advanced diagnostics are required.

### 10.3 Resource Constraints
SYS-REQ-055: The system shall not use dynamic memory allocation.
SYS-REQ-056: System software shall be lightweight, predictable, and bounded in resource usage.

### 10.4 Maintainability and Modularity
SYS-REQ-057: The system shall ensure separation of concerns in software organization (input handling, position control, feedback, motor drive, and status indication).
SYS-REQ-058: The system shall be written for clarity and ease of understanding for learning/demo purposes.

### 10.5 Testability
SYS-REQ-059: The system shall allow observation of correct behavior through visible indicators (LEDs) and command responses (flap movement).
SYS-REQ-060: The system shall support manual and script-based testing via UART.

---

# Architecture-Relevant Considerations Derived from System Requirements
- The system’s responsibilities are simple and sequential; no concurrent tasks are involved or required.
- All interfaces are direct and local (UART, GPIO, ADC, LEDs), with no external network protocols.
- System control is simple, driven by a “command-react” paradigm: wait for command, act, indicate.
- Functional expansion (e.g., more positions, diagnostics, flap types) could be added by updating calibration data or interface logic, but not required.
- No execution timing or scheduling models are described or required by the system requirements.
- The system is explicitly kept simple for education and maintainability, with no over-engineering or unnecessary complexity.

# Software Architecture Specification – HVAC Flap Actuator

## 1.0 Introduction
This document defines the software architecture for the HVAC flap actuator system based strictly on the system (sys-reqs.txt) and software requirements (sw-reqs.txt) provided on branch new-b12.

All architectural decisions, units, responsibilities, and interface definitions are strictly traceable to requirements. No architectural mechanism, design, or execution model is introduced unless justified by an explicit requirement.

## 2.0 Candidate Architecture Styles
Based on requirements analysis, the following architectural styles were considered:

| Style              | Complexity | HW Interaction | Testability | Maintainability | ASPICE L3 |
|--------------------|------------|---------------|-------------|----------------|-----------|
| Monolithic         | LOW        | DIRECT        | GOOD        | BASIC          | OK        |
| Layered            | LOW-MED    | DIRECT        | GOOD        | MODERATE       | OK        |
| Component-based    | MED        | DIRECT        | GOOD        | GOOD           | OK        |

- **Monolithic:** All functionalities are in a single program unit. Simplicity, minimum overhead, but poor concern separation.
- **Layered:** Software structured in layers: Input, Control/Logic, Hardware Abstraction. Clear functional separation, easy to maintain, and supports ASPICE SWE.2/3 clarity.
- **Component-based:** Each major function (command handler, motor control, feedback, status indicator) as a discrete component/unit, interacting via clear interfaces; clarity and testability, moderate overhead for such a simple system.

## 3.0 Architectural Style Selection and Justification

### Selected Style: **Layered Architecture**

**Justification:**
- Requirements (SYS-REQ-057) explicitly mandate separation of concerns for maintainability and education.
- HW interfaces are simple and do not warrant heavy-weight modularization.
- Layered structure provides clear traceability and unit testing, meets the ASPICE L3 expectations for modularity/testability without introducing unnecessary artifacts.
- Overhead for stricter component-ization is not justified; monolithic does not satisfy the separation constraint.
- Fully justified by the requirements—no additional complexity introduced.

## 4.0 Software Units, Responsibilities, and Interfaces

### High-Level Architectural Diagram (Text-based)
```
[User UART Cmds]  --->  [Input Handler]
                                |
                                v
                    [Control Logic Unit]
                /          |            \
 [Motor Driver]   [Position Feedback]  [LED Status]
```
Legend:
- [Input Handler] handles UART, filtration, and one-command-at-a-time.
- [Control Logic Unit] processes positions, checks validity, manages state machine.
- [Motor Driver] unit for GPIO/PWM control, direction, enable/disable.
- [Position Feedback] unit for ADC acquisition, position mapping, monitoring.
- [LED Status] unit for status and position LEDs.

### Architecture Table
| Unit                  | Responsibilities                                                        | Interfaces Provided              | Interfaces Used                   |
|-----------------------|------------------------------------------------------------------------|----------------------------------|------------------------------------|
| Input Handler         | UART command acquisition/parsing, validation, one-at-a-time enforcement | Command Input API                | UART                              |
| Control Logic Unit    | Command execution, state tracking, validity checking, delegation        | PositionCtrl API, State API      | Command Input, MotorCtrl, Feedback, LEDCtl |
| Motor Driver          | GPIO/PWM output, direction, actuation, driver state                    | MotorCtrl API                    | Output GPIO/PWM                   |
| Position Feedback     | ADC acquisition, position mapping, range checks, noise rejection       | Feedback API                     | ADC input                         |
| LED Status            | Power/position LED control, fault indication                           | LEDCtl API                       | Output GPIO                       |

#### Interface Definitions:
- Command Input API: Receives validated, parsed user command.
- PositionCtrl API: Provides actuation requests to Motor Driver.
- State API: Provides status to outside (testing/manual verification).
- MotorCtrl API: Abstracts hardware actuation.
- Feedback API: Supplies current/last position; warns on errors.
- LEDCtl API: Controls/updates LEDs.

# Software Low Level Design – HVAC Flap Actuator

## Introduction
This Software Low Level Design (LLD) document delivers the design for all software units of the HVAC flap actuator software per ASPICE SWE.3. LLD is strictly traceable to the SWE.1 and SWE.2 requirements and does not introduce new software units, does not change the software architecture, and refrains from specifying execution/scheduling logic (see architectural and requirements documents for rationale and units).

All software logic is assumed to be implemented in C (MISRA-compliant; no dynamic allocation). No code, no register-level, hardware, test case, or schematic content is provided.

## Software Units

---

## Software Unit: Input Handler
### 1. Responsibilities
- Responsible for receiving UART user commands, parsing numeric input, validating allowable range (0..5), and enforcing one-command-at-a-time.
- Explicitly does NOT: interpret positions, control motor/LEDs/feedback directly, or process queued/multiple commands.

### 2. Internal Data Design
- command_buffer[CMD_BUF_SIZE]: circular/static buffer for UART bytes
- parsed_cmd: integer, latest parsed user command
- cmd_pending: boolean, true if new valid command is ready
- uart_rx_status: error/valid state code

### 3. State Machine
- No explicit state machine; control flow is linear event-driven: wait for byte, accumulate, parse, flag pending command.

### 4. Algorithms and Control Flow
- On UART RX event: accumulate byte(s) in buffer. On end-of-command, parse as integer.
- If parsed value in 0..5: set parsed_cmd, set cmd_pending.
- Else: ignore, clear buffer and do not flag command.
- Never queue more than one command.

### 5. Interfaces
- Provides: Command Input API (get_pending_command, clear_pending)
- Uses: UART hardware receive
- Parameters: None (besides passed buffer refs)
- Error reporting: Returns status code (OK/NO_CMD/ERR_RANGE)

### 6. Error Handling
- Invalid commands are detected, ignored, and buffer cleared. No UART response; status is not reported to user.
- Buffer overflows are prevented via static size, excess incoming bytes before termination char are dropped.

### 7. Resource and Timing Considerations
- Event-driven: called from UART RX or polled in main.
- Very short, bounded execution time. Non-reentrant; single context.

### 8. Traceability to SWE Requirements
- SWE-REQ-001, 002, 003, 004, 005, 026, 040
- Software Unit: Input Handler

---

## Software Unit: Control Logic Unit
### 1. Responsibilities
- Responsible for interpreting user commands, tracking target/current position, validating position, delegating actuation/LED/output, and holding state.
- Does NOT: directly parse UART, drive hardware, or fetch ADC data.

### 2. Internal Data Design
- current_position: uint8, 0..5
- target_position: int8, -1 if idle/none
- command_active: boolean
- movement_in_progress: boolean

### 3. State Machine
- States: IDLE, MOVING
- Events: New valid command, feedback position == target, feedback error.
- Transitions:
    - IDLE -> MOVING on valid (current != target) command
    - MOVING -> IDLE on arrival at target
    - MOVING -> IDLE on error/invalid feedback

### 4. Algorithms and Control Flow
- On get_pending_command(): If cmd valid, set target, activate command.
- If target != current: request motor move, set MOVING.
- When feedback == target: deactivate command, set IDLE.
- On out-of-range feedback: abort movement, remain in IDLE.

### 5. Interfaces
- Provides: PositionCtrl API (set_target_position, cancel_movement), State API (get_current_status)
- Uses: Command Input API, MotorCtrl API, Feedback API, LEDCtl API
- Parameters: position integers
- Error reporting: status enum returned (e.g. MOVEMENT_DONE, ERROR)

### 6. Error Handling
- Invalid feedback positions result in movement cancel and holding safe state.
- If target unattainable, transitions to IDLE, no further movement attempted until new valid command.

### 7. Resource and Timing Considerations
- Runs on external trigger or command event; not periodic.
- Fast, bounded by hardware interactions. Not reentrant.

### 8. Traceability to SWE Requirements
- SWE-REQ-006, 007, 008, 009, 010, 011, 032, 033, 034, 041, 042, 043
- Software Unit: Control Logic Unit

---

## Software Unit: Motor Driver
### 1. Responsibilities
- Responsible for actuating motor HW (via GPIO/PWM), direction control, enable/disable.
- Does NOT: decide when to start/stop, evaluate positions, handle user commands.

### 2. Internal Data Design
- motor_enable: boolean
- motor_direction: enum (FORWARD/REVERSE)
- Optional: pwm_duty_cycle (uint8) if used

### 3. State Machine
- No explicit multi-state; simply on/off + direction. Motor is always off except during valid actuation.

### 4. Algorithms and Control Flow
- On activate: set GPIOs for direction, enable output; if PWM, set duty.
- On stop: disable output, reset GPIOs.

### 5. Interfaces
- Provides: MotorCtrl API (start, stop, set_dir, set_pwm)
- Uses: Output GPIO/PWM driver
- Parameters: direction, enable
- Error reporting: simple return if command not valid due to unsafe mode

### 6. Error Handling
- On error (from Control Logic): disables HW output, safe state.

### 7. Resource and Timing Considerations
- Short, atomic calls. Never reentrant. HW driver ops are bounded.

### 8. Traceability to SWE Requirements
- SWE-REQ-012, 013, 014, 015, 016, 017, 028, 041, 047, 048
- Software Unit: Motor Driver

---

## Software Unit: Position Feedback
### 1. Responsibilities
- Acquires ADC readings, maps to discrete positions, detects out-of-range, removes noise.
- Does NOT: command/move actuators or determine target.

### 2. Internal Data Design
- adc_raw_value: uint16
- logical_position: uint8 (0..5, or INVALID)
- calibration_constants: struct (min, max, thresholds)
- last_valid_position: uint8

### 3. State Machine
- No explicit; on each sample, computes position and flags errors if out of bounds.

### 4. Algorithms and Control Flow
- On ADC event: apply calibration and thresholds. If within valid range, update logical_position.
- If out-of-range, set INVALID, notify via Feedback API.

### 5. Interfaces
- Provides: Feedback API (get_current_position, is_valid)
- Uses: ADC driver
- Parameters: ADC value(s)
- Error reporting: VALID/INVALID enum

### 6. Error Handling
- Out-of-range disables further actuation (by notifying control logic), holds last safe position.
- No filtering needed beyond thresholding for noise.

### 7. Resource and Timing Considerations
- Regularly called on ADC conversion or polling. Not reentrant.

### 8. Traceability to SWE Requirements
- SWE-REQ-018, 019, 020, 021, 037, 038, 039, 041, 042
- Software Unit: Position Feedback

---

## Software Unit: LED Status
### 1. Responsibilities
- Controls power and position indication LEDs. Reflects status for testability and user visible status.
- Does NOT: process commands, interpret feedback, or drive actuators.

### 2. Internal Data Design
- led_states: struct (power: bool, position_leds[6]: bool)

### 3. State Machine
- No explicit; updates reflect instant state reported by control/feedback.

### 4. Algorithms and Control Flow
- On notification, sets power LED on/off; updates one-hot encoding for position LEDs per positioned feedback, blanks on error/undefined.

### 5. Interfaces
- Provides: LEDCtl API (set_power, set_position, clear_all)
- Uses: GPIO driver
- Parameters: LED selection/state
- Error reporting: none (called on valid state only)

### 6. Error Handling
- If position INVALID, blanks all LEDs except power.

### 7. Resource and Timing Considerations
- Short GPIO write cycles, atomic, non-reentrant.

### 8. Traceability to SWE Requirements
- SWE-REQ-022, 023, 024, 025, 029, 050
- Software Unit: LED Status

---

- No new units added; strictly aligned with architecture.
- No code, scheduler, hardware register, or test content present.
- All elements strictly map to architectural and SWE.1 requirements.
