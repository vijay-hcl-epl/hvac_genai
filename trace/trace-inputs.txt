# 1.0 System Overview
The HVAC flap actuator system enables user control of an air flap’s position using a DC motor, mechanical feedback via a potentiometer, and system interaction via UART and status LEDs, implemented on a microcontroller for a proof-of-concept demonstration.

# 2.0 Flap Position Control
SYS-REQ-001: The system SHALL allow the user to command the flap position using numeric values corresponding to discrete positions via the UART interface.
SYS-REQ-002: The system SHALL control the flap to move to the user-requested position.
SYS-REQ-003: The system SHALL cease motor actuation once the target flap position is attained as measured by the feedback mechanism.
SYS-REQ-004: The system SHALL ignore any command specifying an unsupported flap position.

# 3.0 Motor Control
SYS-REQ-005: The system SHALL drive the DC motor in either clockwise or anti-clockwise direction to reach the commanded position, based on the relative current and target positions.
SYS-REQ-006: The system SHALL use GPIOs for motor direction control and PWM for motor enable operation.
SYS-REQ-007: The motor SHALL stop operation upon reaching the valid target position or upon detecting invalid feedback values.

# 4.0 Position Feedback Acquisition & Processing
SYS-REQ-008: The system SHALL use ADC readings from the potentiometer to determine the instantaneous flap position.
SYS-REQ-009: The mapping from ADC readings to logical flap positions SHALL be defined in software.
SYS-REQ-010: The system SHALL periodically update the measured position against the command input to guide actuation.

# 5.0 User Command Interface
SYS-REQ-011: The system SHALL receive single-byte numeric commands representing target positions via UART from a PC.
SYS-REQ-012: The system SHALL process only the latest command received and ignore extra buffered commands.
SYS-REQ-013: The system SHALL take no further action and not acknowledge invalid or unsupported commands.

# 6.0 Status Indication
SYS-REQ-014: The system SHALL drive one status LED to indicate system power/initialization state.
SYS-REQ-015: The system SHALL drive a set of green LEDs, with at most one ON at any time, to indicate the current detected flap position.
SYS-REQ-016: Status LEDs SHALL change state only in response to valid system state transitions (power-up, position change, fault detected).

# 7.0 System Behavior (power-up, idle, normal, target reached, invalid input)
SYS-REQ-017: Upon power-up, the system SHALL initialize all required peripherals (ADC, UART, GPIOs, PWM, LEDs), set the power/status LED ON, and ensure the motor is OFF.
SYS-REQ-018: The system SHALL read and indicate the current flap position immediately after initialization.
SYS-REQ-019: While idle, the system SHALL monitor the UART interface for valid user commands and monitor feedback.
SYS-REQ-020: Target reaching SHALL be confirmed by correlating feedback position to the command; otherwise, actuation SHALL persist or cease if an error is detected.

# 8.0 Interfaces (UART, motor driver, ADC, LEDs)
SYS-REQ-021: The system SHALL support UART communication with an external device for command input.
SYS-REQ-022: The system SHALL output motor driver control signals via GPIO and PWM channels only.
SYS-REQ-023: The system SHALL acquire potentiometer readings through a designated ADC channel.
SYS-REQ-024: The system SHALL control onboard LEDs connected via GPIO outputs.

# 9.0 Constraints & Assumptions
SYS-REQ-025: The system SHALL assume only one user command is handled at a time.
SYS-REQ-026: The system SHALL assume fixed and pre-configured ADC ranges for all supported flap positions. [Implied]
SYS-REQ-027: No requirement for dynamic calibration, self-learning, or diagnostics is imposed. [Implied]
SYS-REQ-028: Hardware and external connections are assumed operational (wiring, LEDs, motor, potentiometer, UART adapter). [Implied]

# 10.0 Non-Functional Requirements
## 10.1 Responsiveness
SYS-REQ-029: The system SHALL respond to a valid UART command by initiating flap movement within a timeframe perceived as responsive by a human user.
## 10.2 Error Handling & Edge Cases
SYS-REQ-030: The system SHALL stop the motor if ADC feedback readings fall outside the expected range.
## 10.3 Resource Constraints
SYS-REQ-031: The system SHALL avoid dynamic memory allocation and operate within microcontroller resource limits.
## 10.4 Maintainability & Modularity
SYS-REQ-032: The system’s software SHALL be organized to allow independent update of position mapping, motor control, and command parsing logic. [Implied]
## 10.5 Testability
SYS-REQ-033: The system SHALL permit position command testing using UART and feedback validation with physical LEDs and flap movement observation. [Implied]

# Architecture-Relevant Considerations Derived from System Requirements
- Concurrency: The system is essentially sequential, with no explicitly required concurrent operations but may check inputs and feedback in quick succession.
- Interaction Complexity: Interaction is low—commands, feedback, and control all remain local, direct, and simple.
- Control Complexity: Position control logic is straightforward with atomic state transitions based on user input and sensor feedback.
- Expandability: While core operation is for a single actuator and user, modular requirements allow future expansion (adding new positions or additional actuators, etc.).

# SOFTWARE ARCHITECTURE (SWE.2) – HVAC Flap Actuator
## Traceability: All decisions below explicitly traced to SWE.1 (Software Requirements)

## ARCHITECTURE STYLE SELECTION

### Candidate Styles
1. Layered Architecture
2. Component-Based Architecture
3. Monolithic Architecture

#### Evaluation Criteria (per ASPICE L3 and project context)

| Style               | System Complexity | HW Interaction Needs | Testability | Maintainability     | ASPICE L3 Compliance    |
|---------------------|------------------|---------------------|-------------|---------------------|-------------------------|
| Layered             | Handles moderate complexity. May be overkill for simple direct-control needs. | Easy to segregate HW abstraction. | High – can test layers independently. | Good; changes in one layer isolated. | Strong, if layering justifiable. |
| Component-Based     | Ideal for high modularity; breaks down by HW/control/logical function. | Clear HW/component boundary. | High – component-level test feasible. | Strong, but adds interface overhead. | Excellent if requirements support strong modular boundaries. |
| Monolithic          | Direct, simplest for tightly-coupled logic. | No explicit separation; fastest for coupling. | Less so – all logic tangled. | Poor; hard to refactor/extend. | Minimal; generally not favored. |

### Selection
- Requirements (see SWE-REQ-019, SWE-REQ-032) mandate modularity and platform abstraction, allowing position mapping, motor control, and command parsing to be updated independently.
- Direct monolithic is not justifiable; maintainability and modularity explicitly needed.
- Layered vs. Component-Based: Component-based yields clearer mapping to the independent axes (command, control, feedback, interface abstraction) required.

**Selected Style**: Component-Based Architecture
**Rejected Styles**:
- Layered: Not chosen due to limited layering in such a simple direct-control embedded system; actual "layers" become trivial wrappers.
- Monolithic: Not acceptable; violates modular/maintainable structure per SWE-REQ-032, SWE-REQ-019.

## ARCHITECTURE DEFINITION

### Software Units (with Responsibility & Traces)

- **Command Parser**  
  Parses incoming UART bytes. 
  [Traces: SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-015, SWE-REQ-022]

- **Flap Control Logic**  
  Decides if/when movement is necessary, mediates between commanded and current position.  
  [Traces: SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-023, SWE-REQ-024, SWE-REQ-031]

- **Motor Driver**  
  Sets PWM/GPIO outputs.  
  [Traces: SWE-REQ-007, SWE-REQ-008, SWE-REQ-016, SWE-REQ-025, SWE-REQ-036, SWE-REQ-038]

- **Feedback Processor**  
  Reads ADC, validates sample, translates to logical positions.  
  [Traces: SWE-REQ-010, SWE-REQ-011, SWE-REQ-017, SWE-REQ-027, SWE-REQ-028, SWE-REQ-030]

- **LED Status Handler**  
  Activates power/position LEDs, ensures only 1 green LED ON, only on true event.  
  [Traces: SWE-REQ-012, SWE-REQ-013, SWE-REQ-014, SWE-REQ-018, SWE-REQ-021, SWE-REQ-039]

- **System Startup/Initialization**  
  One-off peripheral/variable init and power-on logic.  
  [Traces: SWE-REQ-020]

### Interfaces Between Units

- Command Parser -> Flap Control Logic: delivers validated user commands (target position)
- Feedback Processor <-> Flap Control Logic: provides current mapped position; receives requests to update
- Flap Control Logic -> Motor Driver: issues movement commands (direction/enable/disable)
- Flap Control Logic -> LED Status Handler: triggers status indication update (only on state/event)
- System Startup/Initialization -> all units: triggers configuration/init method

### Execution Model
No explicit execution model or scheduling policy is mandated by the requirements at this stage. [SWE-REQ-034, SWE-REQ-026]
