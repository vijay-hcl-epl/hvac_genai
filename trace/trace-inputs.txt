1.0 System Overview

The HVAC flap actuator system is a microcontroller-based solution designed to control the position of an air mixing flap, commonly used in automotive HVAC systems. The system facilitates user-specified positioning of the flap for air distribution or mixing purposes. Flap movement is electrically driven via a DC motor, and real-time position feedback is acquired using a potentiometer read by an ADC. User commands are accepted over UART, and clear visual feedback is provided by LEDs. This system is for prototypical, non-production (proof-of-concept) demonstration purposes only.

2.0 Flap Position Control

SYS-REQ-001: The system SHALL allow the flap to be set to any discrete target position defined by configuration (e.g., 0–5).
SYS-REQ-002: The system SHALL move the flap to the user-commanded target position using the DC motor.
SYS-REQ-003: The system SHALL stop the motor once the target position is reached.
SYS-REQ-004: The system SHALL ignore commands for positions outside the defined range.
SYS-REQ-005: The system SHALL process only one user command at a time. [Implied]

3.0 Motor Control

SYS-REQ-006: The system SHALL control motor direction (clockwise/anti-clockwise) via GPIOs as required to reach the target position.
SYS-REQ-007: The system SHALL be capable of turning the motor ON and OFF using the motor driver enable (PWM or equivalent).
SYS-REQ-008: The system SHALL keep the motor OFF at power-up/init until a valid movement command is received or current position is assessed.
SYS-REQ-009: The system SHALL stop the motor if ADC feedback is outside defined valid range. [Implied]

4.0 Position Feedback Acquisition & Processing

SYS-REQ-010: The system SHALL acquire the flap’s actual position via an ADC channel connected to the potentiometer.
SYS-REQ-011: The system SHALL map ADC readings to the logical positions (e.g., 0 to 5) using pre-configured fixed calibration values.
SYS-REQ-012: The system SHALL allow software modification of the ADC-to-position mapping for calibration purposes.
SYS-REQ-013: The system SHALL update actual flap position indication continuously, at a rate sufficient for human-perceptible responsiveness.

5.0 User Command Interface

SYS-REQ-014: The system SHALL accept target position commands as single numeric values over UART from a PC or similar host.
SYS-REQ-015: The system SHALL not acknowledge or respond to valid or invalid commands for this prototype. [Implied]
SYS-REQ-016: The system SHALL ignore and take no action on any UART command outside the valid position range.

6.0 Status Indication

SYS-REQ-017: The system SHALL illuminate a dedicated status LED when power is ON.
SYS-REQ-018: The system SHALL indicate the actual flap position by illuminating at most one green LED corresponding to the current logical position.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)

SYS-REQ-019: On power-up, the system SHALL initialize all peripherals (ADC, UART, GPIO, PWM) before beginning normal operation.
SYS-REQ-020: On power-up, the system SHALL leave the motor OFF until after reading the initial flap position.
SYS-REQ-021: In idle, the system SHALL wait for a new user command.
SYS-REQ-022: If an invalid command is received, the system SHALL ignore and take no action.
SYS-REQ-023: If the target is reached during movement, the system SHALL stop the motor and maintain position indication.

8.0 Interfaces (UART, motor driver, ADC, LEDs)

SYS-REQ-024: The system SHALL use UART for user command input.
SYS-REQ-025: The system SHALL use an ADC channel for position sensing.
SYS-REQ-026: The system SHALL use GPIOs for motor direction and LED control.
SYS-REQ-027: The system SHALL use PWM (timer-based) for motor driver enable/speed control.

9.0 Constraints & Assumptions

SYS-REQ-028: The system SHALL make no assumptions about the timing or spacing of UART commands. [Implied]
SYS-REQ-029: The system SHALL be limited to one flap, one motor, and one potentiometer.
SYS-REQ-030: The system assumes correct calibration and hardware setup for this prototype. [Implied]

10.0 Non-Functional Requirements

10.1 Responsiveness
SYS-REQ-031: The system SHALL process user commands and update flap position indication with human-perceptible responsiveness (sub-second typical latency).
10.2 Error Handling & Edge Cases
SYS-REQ-032: The system SHALL safely ignore out-of-range ADC readings and stop the motor if such readings are detected.
SYS-REQ-033: The system SHALL not crash nor require a reset in the case of any invalid UART input or ADC edge-case. [Implied]

Concurrency:No explicit concurrency is required; all operations can occur sequentially, as only one command is handled at a time. Some peripheral activities (e.g. UART RX, ADC sampling) may be handled through interrupts or polling, but requirements do not mandate concurrency.

Expandability: The requirements are written to be extendable for additional features (e.g., different position counts, error reporting) without changing core structure, but the current system supports only the documented minimal feature set.

SOFTWARE ARCHITECTURE (SWE.2)
HVAC FLAP ACTUATOR
========================

1. ARCHITECTURE STYLE SELECTION
------------------------------
Candidate Styles:
- Monolithic
- Layered
- Component-based

Evaluation Criteria:
- System Complexity: Simple state-driven behavior, limited hardware peripherals, no advanced error handling/control
- HW Interaction: Direct, one-to-one (no sharing or multiplexing)
- Testability: Direct test-injection (UART) & observable outputs (LEDs)
- Maintainability: Mostly static logic, configuration via software constants
- ASPICE L3 compatibility: Clear allocation of responsibilities needed

Style Analyses:
A) Monolithic: Acceptable for simple apps, but reduces clarity and modularity for ASPICE.
B) Component-based: Adds unnecessary coupling and indirection; limited benefit given lack of independently-replaceable features/behaviors at this scale.
C) Layered: Offers logical separation (e.g. Command I/F, Flap Logic, Motor Driver, I/O Abstraction), matches natural boundary lines from SWE.1, and supports clear test points.

Selected: LAYERED ARCHITECTURE
- Layers:
  1. Application (Flap Logic)
  2. Command Interface (UART handler)
  3. Hardware Abstraction (Motor Driver, ADC, LEDs)
- Justification: Balanced modularity/testability required for ASPICE/L3; simple enough for system size; every layer's boundaries trace to clusters of SWE.1 requirements.
- Other styles rejected for lack of clarity/structure, or unnecessary complexity.

2. ARCHITECTURE DEFINITION
-----------------------------

SOFTWARE UNITS & RESPONSIBILITIES

1) Command Handler (UART Processor)
- Parses single-byte UART commands [SWE-REQ-001,002]
- Decides/ignores command per range [SWE-REQ-002,032]

2) Position Manager
- Maintains/configures logical (0–5) position mapping [SWE-REQ-013,014,028]
- Issues movement requests
- Determines if command can proceed (idle, busy) [SWE-REQ-003,012]

3) Flap Control Logic
- Moves flap to target using Position Manager [SWE-REQ-005,007,024]
- Controls state transitions (idle, moving, target reached, error)
- Stops motor if out-of-range feedback [SWE-REQ-008,025,031,043]
- Enforces single-command-at-a-time [SWE-REQ-003,012]
- No corrective actions beyond stop/ignore

4) Motor Driver Abstraction
- Drives motor ON/OFF, sets direction & PWM [SWE-REQ-006,007,011,020]
- Ensures motor OFF at startup/idle [SWE-REQ-008,009]

5) Position Feedback Acquisition
- Reads ADC, applies mapped calibration [SWE-REQ-013,029]
- Performs error/out-of-range checks [SWE-REQ-008,031]

6) Status Indicator Controller
- Updates Status LED [SWE-REQ-015]
- Sets one-of-N green LEDs for position [SWE-REQ-016]

INTERFACES:
- Command Handler <-> Position Manager: valid/invalid command, busy state
- Flap Control Logic <-> Motor Driver: start/stop/dir
- Flap Control Logic <-> Position Feedback: read current actual
- Position Feedback <-> Position Manager: update logical position
- Status Indicator <-> Position Manager/Feedback: current position indication

Execution Model:
No explicit execution model or scheduling policy is mandated by the requirements at this stage.

SOFTWARE LOW-LEVEL DESIGN (SWE.3)
HVAC FLAP ACTUATOR
=======================

Note: This document details the low-level design of software units in strict accordance with the defined architecture. No new software units, system-level features, or scheduling mechanisms were introduced. All design elements are MISRA-style embedded C compliant, static only (no dynamic allocation).

-----------------------------------------------------------------------------
Software Unit: Command Handler (UART Processor)
-----------------------------------------------------------------------------
1. Responsibilities
   - Handles UART RX for target position commands, invokes command validation, filters out-of-range/invalid input, and signals busy state.
   - Does not handle hardware resource init or scheduling.

2. Internal Data Design
   - UART RX buffer[1]: unsigned 8-bit
   - Command in-progress flag: boolean
   - Invalid command counter: unsigned 8-bit (optional, static, for error tracking)

3. State Machine
   - States: IDLE (waiting RX), BUSY (command being processed)
   - Events: UART RX complete, valid command detected, invalid command detected, handler signals "busy"
   - Transitions: IDLE→BUSY on valid command, BUSY→IDLE after command finish, IDLE remains if invalid command

4. Algorithms & Control Flow
   - On UART RX interrupt or poll: read byte. If not in "busy", check if value within allowed position range. If valid, signal to Position Manager and set "busy". If invalid, increment error counter; remain in IDLE.

5. Interfaces (APIs)
   Provided:
     - validate_and_dispatch(uint8_t cmd): returns ACCEPTED/IGNORED/BUSY
   Required:
     - UART_read_byte()
     - PositionManager_command(uint8_t pos)

6. Error Handling
   - Silently ignore invalid input (per SWE-REQ-032).
   - Do not enter or clear busy unless command fully handled.

7. Resource & Timing Considerations
   - Invoked on UART RX or equivalent event loop
   - WCET per command: <<1 ms
   - Always re-entrant for idle RX; blocked for "busy" state

8. Traceability
   - SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004, SWE-REQ-017, SWE-REQ-026, SWE-REQ-032

-----------------------------------------------------------------------------
Software Unit: Position Manager
-----------------------------------------------------------------------------
1. Responsibilities
   - Handles position mapping (ADC→logical), command gating, position update/config,
   - Issues move requests to Flap Control; blocks commands when "busy" per design.
   - Does not handle physical movement, only logical coordination.

2. Internal Data Design
   - CurrentPosition: uint8_t (0-5)
   - TargetPosition: uint8_t (0-5)
   - isBusy: boolean
   - PositionTable[6]: ADC value mapping (static const)

3. State Machine
   - States: IDLE, WAIT_FOR_MOVE, BUSY
   - Events: New valid command, move finished, ADC update, busy set/clear
   - Transitions: IDLE→WAIT, WAIT→BUSY on move-req, BUSY→IDLE when done

4. Algorithms & Control Flow
   - On new command from Command Handler: Check isBusy==false, check range, set TargetPosition, flag as busy, notify FlapControl
   - Debounce or ignore redundant/duplicate commands

5. Interfaces (APIs)
   Provided:
     - PositionManager_command(uint8_t pos): returns ACCEPTED/BUSY
     - get_CurrentPosition(): returns uint8_t
   Required:
     - FlapControl_request(uint8_t target)
     - PositionFeedback_get()

6. Error Handling
   - Ignores out-of-range and "busy" commands
   - Resets isBusy after error or normal completion

7. Resource & Timing Considerations
   - Only one operation in progress
   - Memory footprint: PositionTable[6] + flags
   - Not re-entrant

8. Traceability
   - SWE-REQ-003, SWE-REQ-012, SWE-REQ-013, SWE-REQ-014, SWE-REQ-028

-----------------------------------------------------------------------------
Software Unit: Flap Control Logic
-----------------------------------------------------------------------------
1. Responsibilities
   - Coordinates flap movement state, commands Motor Driver, checks limits/errors, ensures single motion at a time. No corrective actions except stop/ignore.

2. Internal Data Design
   - CurrentState: enum {IDLE, MOVING, TARGET_REACHED, ERROR}
   - LastError: uint8_t/enum (optional, static only)

3. State Machine
   - States: IDLE, MOVING, TARGET_REACHED, ERROR
   - Events: Command received, position reached, error detected
   - Transitions: per command/state model—see requirements section 4

4. Algorithms & Control Flow
   - On move request: Check current vs. target, calculate direction, enable motor, poll Position Feedback. If error detected or on completion, send stop, update state.

5. Interfaces (APIs)
   Provided:
     - FlapControl_request(uint8_t target)
     - stop()
   Required:
     - MotorDriver_start(uint8_t dir)
     - MotorDriver_stop()
     - PositionFeedback_get()

6. Error Handling
   - Send stop to Motor Driver on error or completion
   - No retries or advanced recovery

7. Resource & Timing Considerations
   - One move at a time
   - Not re-entrant
   - Per-move WCET: <200 ms typical

8. Traceability
   - SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-008, SWE-REQ-025, SWE-REQ-031, SWE-REQ-043

-----------------------------------------------------------------------------
Software Unit: Motor Driver Abstraction
-----------------------------------------------------------------------------
1. Responsibilities
   - Maps move/start/stop commands to hardware: GPIO for direction, PWM for enable, ensures OFF at startup

2. Internal Data Design
   - MotorState: {ON, OFF}
   - Direction: {OPEN, CLOSE}
   - PWMValue: uint8_t (static only)

3. State Machine
   - States: ON, OFF
   - Events: Start, Stop
   - Transitions: direct mapping; none if started while already ON

4. Algorithms & Control Flow
   - On start: Set GPIO direction, PWM enable=ON
   - On stop: PWM=OFF
   - On boot: PWM=OFF

5. Interfaces (APIs)
   Provided:
     - MotorDriver_start(dir)
     - MotorDriver_stop()
   Required:

7. Resource & Timing Considerations
   - Maps directly to hardware

8. Traceability
   - SWE-REQ-006, SWE-REQ-007, SWE-REQ-008, SWE-REQ-009, SWE-REQ-011, SWE-REQ-020

Software Unit: Position Feedback Acquisition
-----------------------------------------------------------------------------
1. Responsibilities
   - Reads ADC, calibrates mapped value to logic position, error-check for out-of-range, only static calibration

   - On request: Read ADC, lookup/match against CalibTable, range-check, output logical position else flag error

5. Interfaces (APIs)
   Provided:
     - PositionFeedback_get(): returns (uint8_t pos, status_t ok)
   Required:
     - ADC_read()

6. Error Handling
   - If out-of-range, report status=error, current position invalid

7. Resource & Timing Considerations
   - Invoked as needed by logic
   - WCET <<1 ms per call
   - Always state-free/static

8. Traceability
   - SWE-REQ-013, SWE-REQ-014, SWE-REQ-029

Software Unit: Status Indicator Controller
-----------------------------------------------------------------------------
1. Responsibilities
   - Updates power/status/green position LEDs, only one green LED active at a time, reflects last known valid position

2. Internal Data Design
   - LEDState: {ON, OFF} per channel
   - LastKnownPos: uint8_t (0-5)

3. State Machine
   - None (table-driven output set)

4. Algorithms & Control Flow
   - On position/status update: turn ON corresponding LED, all others OFF; on power ON, power/status LED ON

5. Interfaces (APIs)
   Provided:
     - StatusLED_set(uint8_t pos)

     - None (hardware mapping only)

   - Fail-safe: on error, no green LEDs ON, status LED blinking (if HW supported)

###### FILE: code/src/command_handler.c ######
#include "command_handler.h"
#include "position_manager.h"
#include "uart_drv.h"
static volatile uint8_t uart_rx_buf = 0;
static volatile uint8_t command_in_progress = 0;
static uint8_t invalid_cmd_count = 0;
// UART RX ISR or poll calls this
CmdStatus_t validate_and_dispatch(uint8_t cmd) {
    if (command_in_progress) return CMD_BUSY;
    if ((cmd < 0) || (cmd > 5)) {
        invalid_cmd_count++;
        return CMD_IGNORED;
    }
    command_in_progress = 1;
    if (PositionManager_command(cmd) == POSMGR_ACCEPTED) {
        command_in_progress = 0;
        return CMD_ACCEPTED;
    } else {
        command_in_progress = 0;
        return CMD_BUSY;
    }
}
void command_handler_init(void) {
    uart_rx_buf = 0;
    command_in_progress = 0;
    invalid_cmd_count = 0;
}

static uint8_t target = 0;
void FlapControl_request(uint8_t tgt) {
    target = tgt;
    current_state = FLAP_MOVING;
    uint8_t actual;
    Status_t ok;
    position_feedback_get(&actual, &ok);
    if (ok && actual != target) {
        int8_t direction = (target > actual) ? 1 : -1;
        MotorDriver_start(direction);
        // pseudo loop: in real code use timer/task, here only logic
        do {
            position_feedback_get(&actual, &ok);
        } while (ok && actual != target);
        MotorDriver_stop();
        current_state = FLAP_TARGET_REACHED;
    } else if (!ok) {
        MotorDriver_stop();
        current_state = FLAP_ERROR;
    }
}

    current_state = FLAP_IDLE;
}

static const uint16_t HIGH = 2500;
void position_feedback_get(uint8_t *pos, Status_t *status) {
    uint16_t adc = 0; // TODO: Implement ADC_read for STM32F4
    // Map ADC to logical position
    *pos = 0xFF;
    *status = STATUS_ERROR;
    for (uint8_t i = 0; i < NUM_POSITIONS; ++i) {
        if (adc == CalibTable[i]) {
            *pos = i;
            *status = STATUS_OK;
            return;
        }
    }
    if (adc < LOW || adc > HIGH) {
        *status = STATUS_ERROR;
        return;
    }
}
