SYS-REQ-001: The system SHALL control the position of an HVAC flap actuator as commanded by the user via a defined interface.
SYS-REQ-002: The system SHALL provide real-time feedback of flap position to the user interface.
SYS-REQ-003: The system SHALL operate using power supplied via the primary system supply voltage.
[Implied]

SYS-REQ-004: The system SHALL accept user input to command the flap position between fully closed and fully open.
SYS-REQ-005: The system SHALL adjust the flap position to match the user command within the physical limits of actuator travel.
SYS-REQ-006: The system SHALL prevent motion beyond physical flap limits.
[Implied]

3.0 Motor Control

SYS-REQ-007: The system SHALL control the actuator motor to increase, decrease, or maintain the flap position.
SYS-REQ-008: The system SHALL disengage the motor when the requested flap position matches the feedback position within allowable tolerance.

SYS-REQ-010: The system SHALL acquire flap position feedback via an analog or digital sensor.

SYS-REQ-012: The system SHALL detect sensor faults (out-of-range or missing signals).
[Implied]

SYS-REQ-014: The system SHALL acknowledge receipt of valid commands.

6.0 Status Indication

SYS-REQ-016: The system SHALL indicate flap position and system status (e.g., movement, target reached, error, idle) via external LEDs or other defined means.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)

SYS-REQ-017: On power-up, the system SHALL initialize all internal variables, outputs, and state indication.
SYS-REQ-018: When idle, the system SHALL minimize power consumption and maintain feedback monitoring.
SYS-REQ-019: When a valid target is reached, the system SHALL maintain flap position and indicate "target reached" status.
SYS-REQ-020: Upon invalid input, the system SHALL not initiate motion and SHALL provide a clear indication of input error.

SYS-REQ-021: The system SHALL support communication via UART for receiving commands and/or providing status.
SYS-REQ-022: The system SHALL interface with the actuator motor driver.

SYS-REQ-024: The system SHALL control LEDs for status indication.

SYS-REQ-026: The actuator position sensor is assumed to be calibrated and linear within the usable range.

- Interaction Complexity: Interfaces are discrete and modular, with clearly defined points (UART, motor driver, ADC, LED), suggesting manageable interaction complexity.

It interprets user requests, processes sensor data, commands motor actuation, manages diagnostics, and coordinates system outputs within the context of an MCU (ADC, GPIO, UART, LEDs, timers). The software does not modify system-level requirements or physical system constraints, but implements, in a modular and testable way, the logic, interface management and data processing specified at the system level.

HVAC Flap Actuator — Software Architecture (SWE.2)
============================

----------------------------
ARCHITECTURE STYLE SELECTION
----------------------------

Candidate Styles Considered:
1. Monolithic (all logic in a single unit)
2. Layered (separation: application logic, platform abstractions, I/O/HW)
3. Component-based (larger modules with clear interfaces)

Evaluation:
- System complexity is low, with logical separation between user command handling, actuator/motor control, feedback acquisition, and status indication (SWE-REQ-001, SWE-REQ-005, SWE-REQ-011, SWE-REQ-013).
- HW interaction is clearly defined at the interface level (SWE-REQ-016, SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-020).
- Testability and maintainability are explicitly demanded (SWE-REQ-020, SWE-REQ-028, SWE-REQ-037).
- ASPICE L3 requires clear unit boundaries and interfaces, not monolithic.

Selection: Layered Architecture
- The layered style allows modular implementation and separation of core logic from platform hardware interfaces, while keeping units at a maintainable granularity for ASPICE alignment.

Rejection Rationale:
- Monolithic: Rejected—requirements demand clear separation and modularity for verification and test.
- Component-based: Overly complex for current requirements, as it would partition further than traceable responsibilities warrant.

----------------------------
SOFTWARE ARCHITECTURE DEFINITION
----------------------------

Software Units & Responsibilities:

1. Command Handler
   - Responsibilities: Interpret and validate user commands (SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004). Reject and acknowledge input.
   - Interfaces Provided: Command interface.
   - Interfaces Used: System State Manager, Status Indicator.

2. Flap Control Logic
   - Responsibilities: Calculate target position, enforce limits, idle/active transitions (SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-023, SWE-REQ-025).
   - Interfaces Provided: Target position command.
   - Interfaces Used: Command Handler, Motor Driver Interface, Position Feedback Processor.

3. Motor Driver Interface
   - Responsibilities: Command motor direction, enable/disable, fault feedback. No direct hardware layer logic. (SWE-REQ-008, SWE-REQ-009, SWE-REQ-010, SWE-REQ-018)
   - Interfaces Provided: Motor control API.
   - Interfaces Used: Flap Control Logic.

4. Position Feedback Processor
   - Responsibilities: Acquire/process position sensor data, validate signal, provide current position (SWE-REQ-011, SWE-REQ-012, SWE-REQ-017).
   - Interfaces Provided: Position data, error notification.
   - Interfaces Used: Flap Control Logic, System State Manager.

5. Status Indicator
   - Responsibilities: Manage LEDs or indicator output for system status, target reached, error (SWE-REQ-013, SWE-REQ-014, SWE-REQ-015, SWE-REQ-019).
   - Interfaces Provided: Status output API.
   - Interfaces Used: System State Manager.

6. System State Manager
   - Responsibilities: System-level state transitions: power-up init, idle, active, error (SWE-REQ-021, SWE-REQ-022, SWE-REQ-024, SWE-REQ-025, SWE-REQ-031).
   - Interfaces Provided: State transition API.
   - Interfaces Used: All units needing status/state.

7. HW Abstraction Layer (HAL)
   - Responsibilities: Platform abstraction for UART/ADC/GPIO (SWE-REQ-016, SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-020). No logic beyond interface definition.
   - Interfaces Provided: Hardware APIs for UART, ADC, GPIO/LEDs.
   - Interfaces Used: Motor Driver Interface, Position Feedback Processor, Status Indicator.

1. Introduction
----------------------------------------------------------------------
This document specifies the System Qualification Test Specification (SYS.5) for the HVAC flap actuator system. Test cases aim to validate each mapped System Requirement (SYS-REQ-xxx) through observable system-level behavior. Only end-to-end, integrated, hardware-in-the-loop tests are included. No unit, integration, safety, cybersecurity, or internal software/RTOS validation is covered unless explicitly required by SYS requirements.

----------------------------------------------------------------------
2. Test Cases
----------------------------------------------------------------------

----------------------------------------------------------------------
1) Power-Up & Initialization
----------------------------------------------------------------------

Test Case ID: SYS-TC-001
Mapped Req ID(s): SYS-REQ-017, SYS-REQ-003
Objective: Verify that the system powers up, initializes all variables, outputs, and enters idle state with motor OFF and correct status indication.
Preconditions: System powered OFF
Test Inputs: Power ON event
Test Steps:
 1. Apply primary supply voltage to the system.
 2. Observe status LEDs during/after startup.
 3. Monitor UART for initialization message (if applicable).
Expected Results:
 - Motor remains OFF throughout initialization
 - All internal variables initialized (observable via status report/UART or other diagnostic output)
 - LEDs indicate system ready/idle as per requirements
Pass/Fail Criteria: All expected results are observed. No unintended motion or error indication occurs.

Test Case ID: SYS-TC-002
Mapped Req ID(s): SYS-REQ-010, SYS-REQ-011
Objective: Verify initial flap position detection upon power-up.
Preconditions: Flap in known physical position, System powered OFF
Test Inputs: Power ON event
Test Steps:
 1. Set flap to known reference (e.g., fully closed)
 2. Power ON system
 3. Observe system-diagnosed initial position (via UART/status LED)
Expected Results:
 - System accurately detects current flap position within described tolerance
 - Position LED or output reflects detected position
Pass/Fail Criteria: Flap position is detected and reported within ±3% accuracy; no error/fault is flagged.

----------------------------------------------------------------------
2) Valid Flap Position Commands
----------------------------------------------------------------------

Test Case ID: SYS-TC-003
Mapped Req ID(s): SYS-REQ-004, SYS-REQ-013, SYS-REQ-021
Objective: Verify system accepts all valid user position commands (positions 0-5) via UART and actuates flap to corresponding positions.
Preconditions: Power ON, idle state, flap in any valid position
Test Inputs: UART commands for each supported position (0–5)
Test Steps:
 1. Issue command for each position sequentially
 2. Observe movement, direction, and final resting position
 3. Observe status/position LED after each move
Expected Results:
 - For each command, motor moves flap to requested position without overshoot
 - LEDs/status signal matches target
Pass/Fail Criteria: For all commands, position is reached without overshoot, correct status indication is given, and no error is signaled.

Test Case ID: SYS-TC-004
Mapped Req ID(s): SYS-REQ-005, SYS-REQ-006
Objective: Verify system enforces physical flap limits and prevents out-of-range movement.
Preconditions: Flap at/extremely near endpoint, power ON
Test Inputs: UART command for out-of-range/overtravel position
Test Steps:
 1. Command position below minimum or above maximum
 2. Observe system response (motor, LEDs, status)
Expected Results:
 - Motor does not move beyond the defined physical limits
 - System rejects improper commands
 - Error/invalid input is indicated
Pass/Fail Criteria: No movement outside limits, error is indicated, system overall remains stable.

----------------------------------------------------------------------
3) Invalid & Boundary Conditions
----------------------------------------------------------------------

Test Case ID: SYS-TC-005
Mapped Req ID(s): SYS-REQ-015, SYS-REQ-021, SYS-REQ-028
Objective: Verify response to invalid UART inputs, out-of-range position commands, communication/ADC faults during operation.
Preconditions: Power ON, idle state
Test Inputs: Invalid UART data, out-of-range position, corrupted ADC input
Test Steps:
 1. Send malformed command (bad checksum/format)
 2. Issue out-of-range command
 3. Manually inject out-of-range ADC value (if feasible)
 4. Issue command during motion
Expected Results:
 - System rejects invalid commands and provides clear indication (e.g., error LED/status)
 - No uncommanded motion occurs
 - System remains stable, does not lock or reset
Pass/Fail Criteria: All errors are detected and indicated; valid functions are unaffected, no reset or crash occurs.

----------------------------------------------------------------------

----------------------------------------------------------------------

Mapped Req ID(s): SYS-REQ-002, SYS-REQ-011, SYS-REQ-012
Objective: Verify continuous position feedback acquisition, correct mapping to reported position, and handling of sensor faults.
Preconditions: Power ON, flap at arbitrary position
Test Inputs: Physical movement of flap; sensor fault injection (if feasible)
Test Steps:
 1. Move flap manually (if possible) and monitor system output
 2. Simulate/induce sensor out-of-range or disconnect
Expected Results:
 - Position reported by system tracks physical movement within accuracy spec
 - Sensor faults are detected and indicated
Pass/Fail Criteria: Position feedback is continuous and correct; sensor faults are reliably flagged with system indication.

----------------------------------------------------------------------

Test Case ID: SYS-TC-007
Mapped Req ID(s): SYS-REQ-007, SYS-REQ-008, SYS-REQ-009

Preconditions: Power ON, flap at rest
Test Inputs: Valid position commands, fault injection (stall/short/open)
Test Steps:
 1. Command movement to new position
 2. Observe direction, start, and stop
 3. Induce motor fault (if feasible)
Expected Results:
