1.0 System Overview 

The HVAC Flap Actuator System is a microcontroller-based prototype designed to move an air-control flap to discrete positions as commanded by a user through UART. The system controls a DC motor, acquires position feedback via a potentiometer using an ADC, and reports its status through LEDs.

2.0 Flap Position Control

SYS-REQ-001: The system SHALL allow the user to command the flap to any supported discrete position via UART.
SYS-REQ-002: The system SHALL move the flap only to the commanded positions defined in the requirements.
SYS-REQ-003: The system SHALL stop the motor upon reaching the target position.
SYS-REQ-004: The system SHALL ignore commands outside the supported position range. [Implied]

3.0 Motor Control

SYS-REQ-005: The system SHALL drive the DC motor in both clockwise and anti-clockwise directions as required to reach the target flap position.
SYS-REQ-006: The system SHALL control motor operation using GPIO and PWM signals.
SYS-REQ-007: The system SHALL ensure the motor is off when not actively moving the flap.

4.0 Position Feedback Acquisition & Processing

SYS-REQ-008: The system SHALL acquire position feedback using an ADC connected to the potentiometer.
SYS-REQ-009: The system SHALL map ADC values to logical flap positions (e.g., 0–5) according to defined software ranges.
SYS-REQ-010: The system SHALL continuously monitor actual flap position while powered on.
SYS-REQ-011: The system SHALL stop the motor if the ADC value is out of valid range. [Implied]

5.0 User Command Interface

SYS-REQ-012: The system SHALL receive user target position commands via UART as single numeric values.
SYS-REQ-013: The system SHALL ignore invalid or malformed UART commands. [Implied]

6.0 Status Indication

SYS-REQ-014: The system SHALL use one LED to indicate power status.
SYS-REQ-015: The system SHALL indicate the current flap position using up to one green LED at a time.
SYS-REQ-016: The system SHALL update the green LED indication upon position changes.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)

SYS-REQ-017: On power-up, the system SHALL initialize all required peripherals (ADC, UART, GPIO, PWM).
SYS-REQ-018: On power-up, the system SHALL ensure the motor is off.
SYS-REQ-019: On power-up, the system SHALL sample the current flap position from the potentiometer.
SYS-REQ-020: The system SHALL remain idle, with no actuator motion, until a valid user command is received.
SYS-REQ-021: Upon receiving an invalid command, the system SHALL maintain its previous state and take no action.

8.0 Interfaces (UART, motor driver, ADC, LEDs)

SYS-REQ-022: The system SHALL use UART for receiving position commands from a connected PC.
SYS-REQ-023: The system SHALL use ADC to measure potentiometer feedback for position acquisition.
SYS-REQ-024: The system SHALL use GPIO and PWM to command the motor driver.
SYS-REQ-025: The system SHALL use GPIO pins to control the power and position LEDs.

9.0 Constraints & Assumptions

SYS-REQ-026: The system SHALL operate a single flap using a single motor and a single potentiometer.
SYS-REQ-027: The system SHALL not communicate on any vehicle network such as CAN or LIN. [Implied]
SYS-REQ-028: The system SHALL assume hardware is functional and calibrated. [Implied]
SYS-REQ-029: User commands are non-concurrent and processed sequentially. [Implied]

10.0 Non-Functional Requirements
10.1 Responsiveness
SYS-REQ-030: The system SHALL process valid UART commands promptly with human-perceivable responsiveness.
10.2 Error Handling & Edge Cases
SYS-REQ-031: The system SHALL stop the motor if position feedback cannot be reliably acquired or mapped. [Implied]
SYS-REQ-032: The system SHALL ignore errors in UART communication or ADC measurement, provided safety is not compromised.
10.3 Resource Constraints
SYS-REQ-033: The system SHALL not require dynamic memory allocation at runtime.
10.4 Maintainability & Modularity
SYS-REQ-034: The system SHALL modularize functionality such that command handling, position monitoring, and indication may be independently tested. [Implied]
10.5 Testability
SYS-REQ-035: The system SHALL be testable via UART commands, LED feedback, and motor movement observable by a human or script. [Implied]

Architecture-Relevant Considerations Derived from System Requirements

Concurrency: Minimal concurrency is required, as only one command is processed at a time and no parallel motor actions occur. Data acquisition and actuation may be realized sequentially.
Interaction Complexity: Interaction is simple; input (UART) maps to motor actuation and LED output, with feedback acquired via ADC. No bidirectional or network communication is present.
Control Complexity: Position mapping, discrete position support, motor control, and error handling are straightforward; no hierarchical or distributed control.
Expandability: The architecture is easily expandable to more flap positions or additional interface types (e.g., CAN) with clear requirements separation, provided atomicity and safety are maintained.

1.0 Software Scope & Responsibility

The software for the HVAC Flap Actuator System implements user-driven control of an air flap via a DC motor, processing commands received over UART and using ADC-derived feedback from a potentiometer for precise positioning. The software is responsible for interpreting user commands, actuating the motor, acquiring position feedback, indicating status, handling errors, and ensuring bounded and robust operation on an MCU with ADC, GPIO, UART, and timer/PWM capability.

2.0 Software Functional Requirements

2.1 User Commands

SWE-REQ-001: The software SHALL interpret any UART command corresponding to a discrete supported position and initiate flap actuation to that position. [SYS-REQ-001, SYS-REQ-012, SYS-REQ-002]
SWE-REQ-002: The software SHALL ignore user commands received over UART which request positions outside the valid supported range. [SYS-REQ-004]
SWE-REQ-003: The software SHALL ignore malformed or non-numeric commands on UART. [SYS-REQ-013]
SWE-REQ-004: The software SHALL process only one command at a time; commands SHALL NOT preempt ongoing movement. [SYS-REQ-029] [Implied]

2.2 Flap Control

SWE-REQ-005: The software SHALL convert valid user position requests into target positions and command the motor accordingly. [SYS-REQ-001, SYS-REQ-009]
SWE-REQ-006: The software SHALL ensure the flap moves only between defined, discrete positions as mapped in the application. [SYS-REQ-002, SYS-REQ-009]
SWE-REQ-007: The software SHALL initiate stopping of the motor when the flap reaches the commanded position. [SYS-REQ-003]

2.3 Motor Control

SWE-REQ-008: The software SHALL command the motor for both directions as required by position targets. [SYS-REQ-005, SYS-REQ-006]
SWE-REQ-009: The software SHALL generate appropriate logical signals (PWM and GPIO) to start and stop the motor as per movement needs. [SYS-REQ-006]
SWE-REQ-010: The software SHALL ensure no logical signal is sent to keep the motor running except when movement is required. [SYS-REQ-007]

2.4 Feedback Processing

SWE-REQ-011: The software SHALL read ADC input from the position feedback potentiometer on demand whenever flap movement or target check is required. [SYS-REQ-008, SYS-REQ-019, SYS-REQ-010]
SWE-REQ-012: The software SHALL map ADC values to discrete logical flap positions using software-configured bounds and tolerances. [SYS-REQ-009]

2.5 Status Indication

SWE-REQ-014: The software SHALL activate a power-status LED upon power-up initialization. [SYS-REQ-014, SYS-REQ-017]
SWE-REQ-015: The software SHALL control a single position-indicating green LED to match the most recent known flap position. [SYS-REQ-015, SYS-REQ-016]
SWE-REQ-016: The software SHALL update LED status each time the designated flap position changes as per user command and feedback. [SYS-REQ-016]

# HVAC Flap Actuator Software Architecture (ASPICE SWE.2)

## 1. Architecture Style Selection

### Candidate Styles Considered
- **Layered**: Separates I/O, application logic, and hardware abstraction for modularity.
- **Component-Based**: Allocates responsibilities to independent components with defined interfaces (often used for larger or distributed systems).
- **Monolithic**: Combines all logic into a single software block with minimal logical separation.

### Evaluation
- **System Complexity**: Low; only one main control flow, minimal parallelism, all peripheral interaction local.
- **HW Interaction Needs**: UART, ADC, GPIO, PWM; well-mapped with clear abstraction.
- **Testability**: Test points are defined at interfaces (UART handler, position monitoring, LED logic).
- **Maintainability**: Modularity is useful for change, as additional flap positions or interfaces may be added.
- **ASPICE L3**: Requires traceable, modular architecture, clear unit boundaries, explicit interfaces and responsibilities, and rationale for style choices.

### Selection 
- **Adopted Style: Layered**: 
    - Cleanly separates hardware abstraction (drivers), application logic (main control state machine), and I/O (command, feedback, indication).
    - Facilitates testability (per-unit test points via UART/LED), maintainability, and direct mapping to requirements.
- **Rejected Styles**:
    - **Component-Based**: Rejected due to system scale (single actuator, no distribution, no optional local execution).
    - **Monolithic**: Lacks maintainability and testability required by ASPICE and requirements (SWE-REQ-034, SWE-REQ-035, SWE-REQ-039).

## 2. Architecture Definition

### Software Units and Responsibilities

1. **UART Command Handler**
   - Decodes/validates incoming UART commands (SWE-REQ-001, SWE-REQ-003, SWE-REQ-017).
   - Passes valid target position to control logic.
   - Ignores spurious/invalid/malformed commands (SWE-REQ-002, SWE-REQ-003).

2. **Application Logic (Flap Actuator Controller)**
   - Sequencing and arbitration unit: receives position requests, manages target state, and controls the actuation sequence (SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-021, SWE-REQ-024).
   - Performs state machine for position control, enforces single-command processing (SWE-REQ-004, SWE-REQ-025).
   
3. **Motor Control Unit**
   - Receives actuation requests from controller, drives motor via PWM/GPIO as per command (SWE-REQ-008, SWE-REQ-009, SWE-REQ-010, SWE-REQ-019).
   - Responsible for direction, start/stop, and compliance with target/stop conditions.

4. **Position Monitoring Unit**
   - Acquires ADC and maintains logical/current/target positions (SWE-REQ-011, SWE-REQ-012, SWE-REQ-013, SWE-REQ-018, SWE-REQ-029).
   - Performs out-of-range detection, error flagging, position-to-LED mapping (SWE-REQ-013, SWE-REQ-032).

5. **LED Indication (Status and Position)**
   - Powers up and controls LEDs for power/position feedback (SWE-REQ-014, SWE-REQ-015, SWE-REQ-016, SWE-REQ-020).
   - Provides visual test/verification points (SWE-REQ-039).

6. **System Initialization**
   - One-time setup: initialize drivers, clear error state, acquire initial position (SWE-REQ-021, SWE-REQ-022).

### Interfaces Between Units
- **UART Command Handler ↔ Controller**: Delivers parsed/validated position requests.
- **Controller ↔ Motor Control**: Commands motor movement/stopping.
- **Controller ↔ Position Monitoring**: Requests current position/feedback, receives position or error.
- **Controller ↔ LED Indication**: Issues display/feedback update commands.
- **System Initialization ↔ All Units**: Startup sequencing.

### Execution Model:
No explicit execution model or scheduling policy is mandated by the requirements at this stage.
