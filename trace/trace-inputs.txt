1.0 System Overview
SYS-REQ-001: The system shall control an HVAC air flap actuator using a microcontroller, a DC motor for positioning, a potentiometer for position feedback, and provide a user interface via UART for demonstration and learning purposes.

2.0 Flap Position Control Requirements
SYS-REQ-002: The system shall allow the user to command the flap to any of the predefined discrete positions via UART.
SYS-REQ-003: The system shall move the flap to the user-requested target position.
SYS-REQ-004: The system shall continuously compare the current flap position to the requested target.
SYS-REQ-005: The system shall stop the motor once the flap reaches the requested target position.
SYS-REQ-006: The system shall hold the flap at the target position after it is reached.
SYS-REQ-007 [Implied]: The system shall prevent the flap from overshooting the requested position for all valid commanded positions.

3.0 Motor Control Requirements
SYS-REQ-008: The system shall control motor rotation direction via GPIO to achieve the proper flap movement.
SYS-REQ-009: The system shall enable the motor when movement towards the target is required.
SYS-REQ-010: The system shall disable the motor when the flap is at the requested position.
SYS-REQ-011: The system shall stop the motor if the potentiometer feedback is out of the expected valid range.
SYS-REQ-012 [Implied]: The system shall avoid unintentional or spurious motor activation when no target change occurs.

4.0 Position Feedback Acquisition and Processing
SYS-REQ-013: The system shall acquire flap position feedback from a rotary potentiometer through an ADC channel.
SYS-REQ-014: The system shall define fixed ADC ranges that map to each logical flap position (e.g., 0–5).
SYS-REQ-015: The system shall process ADC readings and determine the current logical flap position from potentiometer feedback.
SYS-REQ-016: If an ADC reading falls outside all defined flap positions, the system shall treat the position as invalid.
SYS-REQ-017 [Implied]: The system shall reject ADC values not mapped to any legal position and trigger a safe state.

5.0 User Command Interface Requirements
SYS-REQ-018: The system shall accept user position commands via UART, with each command mapped to a valid flap position number (0–5).
SYS-REQ-019: The system shall validate received UART commands for correctness and supported range.
SYS-REQ-020: The system shall ignore invalid or out-of-range UART commands without acknowledgment or error response.
SYS-REQ-021 [Implied]: The system shall not change target position or activate the motor for ignored/invalid commands.

SYS-REQ-023: The system shall use green LEDs to indicate the current logical flap position; at most one green LED shall be ON at any time.
SYS-REQ-024: The system shall update the LEDs to reflect current position immediately upon status change.
SYS-REQ-025 [Implied]: The system shall provide clear visual feedback for all valid positions; invalid or undefined states shall result in no green position LEDs being ON.

7.0 System Behavioral Requirements
SYS-REQ-026: On power-up, the system shall initialize all necessary peripherals (ADC, UART, GPIO, PWM).
SYS-REQ-027: On power-up, the system shall ensure the motor is OFF.

SYS-REQ-031: Upon reaching the target position, the system shall stop the motor and update LEDs to reflect the new position.
SYS-REQ-032: The system shall ignore invalid user commands gracefully, leaving system state unchanged.
SYS-REQ-033 [Implied]: The system shall not require or perform a homing/calibration sequence at startup.
SYS-REQ-034 [Implied]: The system shall maintain predictable and bounded state transitions between operating states (start, idle, moving, target-reached).

8.0 System Interface Requirements
SYS-REQ-035: The system shall communicate with a user PC via a UART interface for command input.
SYS-REQ-036: The system shall interface with the DC motor through a motor driver using GPIO and PWM signals.
SYS-REQ-037: The system shall obtain position feedback from a potentiometer via an ADC interface.
SYS-REQ-038: The system shall use GPIO pins to control multiple LEDs for status indication.
SYS-REQ-039 [Implied]: The system shall not interact with external automotive networks such as CAN or LIN.

# Software Architecture for HVAC Flap Actuator System

## 1. Architecture Style Selection and Evaluation

**Candidate Styles:**
- Monolithic
- Layered
- Component-based / Modular

**Evaluation:**
| Style        | System Complexity | Hardware Interaction | Testability | Maintainability | ASPICE Level-3 | Comments |
|-------------|------------------|---------------------|-------------|----------------|----------------|----------|
| Monolithic  | Simple, but inflexible | Direct           | Poor        | Poor           | Poor           | Not easily modifiable, difficult for demo/education |
| Layered     | Flexible, can be overkill| Good separation | Good        | Good           | Good           | Unneeded abstraction (only 1 MCU, 1 actuator, 1 control path) |
| Component-based | Clear separation | Direct            | Excellent   | Excellent      | Excellent      | Best matches separation-of-concerns, traceability, demo needs |

**Style Selected:** Component-based / Modular

**Justification:**
- System requirements (SYS-REQ-052, SYS-REQ-053) and software requirements explicitly require clear separation of responsibilities for maintainability, modifiability, and educational/demo use.
- Single microcontroller and actuator allow simple, explicit interface design with no need for complex scheduling, layers, or runtime abstraction.

# Software Low-Level Design (SWE.3) for HVAC Flap Actuator

## Software Unit: CommandHandler

### 1. Responsibilities
- Responsible for receiving UART bytes and command frames from the user interface.
- Parses received UART data into complete command frames.
- Verifies checksum (if any), parses, and validates command data.
- Maps validated user commands to target position requests.
- Issues command events to FlapControlLogic.
- Explicitly does NOT: process ADC data, control the motor, update LEDs, or manage system state.

### 2. Internal Data Design
- UART receive buffer (fixed length, statically allocated, e.g. uint8_t rx_buf[N]).
- Command frame assembly state (current byte count, pointer/index).
- Parsed command structure (enum or struct for decoded position).
- Flag/variable for command validity.

### 3. State Machine
- No explicit state machine, but uses staged command assembly and validation:
  - WAIT_FOR_START
  - ASSEMBLE_BYTES
  - VALIDATE_FRAME
  - READY_TO_DISPATCH
- Transitions: Reception of start byte, byte count increments, end/validate, dispatch or discard.

### 4. Algorithms and Control Flow
1. On UART byte received:
   - If WAIT_FOR_START, check for start-of-frame, else ignore.
   - In ASSEMBLE_BYTES, append byte, update index.
   - If frame complete: Validate length/checksum.
      - If valid: Set READY_TO_DISPATCH, extract position.
      - If invalid: discard buffer/reset.
2. On READY_TO_DISPATCH:
   - Issue event to FlapControlLogic with decoded position.
   - Reset buffer/flags.
3. Ignore and discard invalid or out-of-range commands.

### 5. Interfaces (APIs)
- Public:
  - void CommandHandler_UART_ByteReceived(uint8_t byte);
  - void CommandHandler_Init(void);
- Provided Events:
  - void CommandHandler_OnFrameDecoded(enum FlapPosition pos);
- Required:
  - None directly; FlapControlLogic consumes events.

### 6. Error Handling
- Invalid command frame: buffer reset, event not raised.
- Out-of-range position: ignored, system state not changed.
- No error acknowledgment sent to user as per requirements.

### 7. Resource and Timing Considerations
- Invoked by UART RX interrupt or polling event.
- All functions are stateless per call. Uses static buffers only.
- Not reentrant; must be guarded if used with true interrupts.
- Latency dominated by UART frame arrival.

### 8. Traceability to SWE Requirements
- Implements: SWE-REQ-001, 002, 003, 004, 005, 026, 044, 052, 053

## Software Unit: FlapControlLogic

### 1. Responsibilities
- Receives command events (target position requests) from CommandHandler.
- Determines necessary flap movement.
- Issues motor control commands.
- Tracks current and target position.
- Requests position feedback update.
- Reports status changes to StatusIndicator.
- Explicitly does NOT: handle UART, ADC, direct GPIO, or timer/RTOS management.

### 2. Internal Data Design
- Variables for current and target position (enum FlapPosition current, target).
- Movement state (IDLE, MOVING, REACHED).
- Last command validity status.
- Timestamps or tick-count for debounce/transition if needed (static, no timer dependency).

### 3. State Machine
- STATES: IDLE, MOVING, REACHED, ERROR_SAFE
- EVENTS: Command event, Position update, Motor stop, Error detected
- TRANSITIONS:
  - IDLE -> MOVING: Valid user command received
  - MOVING -> REACHED: PositionFeedback = target
  - MOVING -> ERROR_SAFE: PositionFeedback invalid
  - ERROR_SAFE -> IDLE: Recover after safe condition

### 4. Algorithms and Control Flow
1. On command event:
   - If command valid & != current, set target, set MOVING.
   - Else: Ignore.
2. On MOVING:
   - Request PositionFeedback update.
   - Compare: if feedback < target, issue MOTOR_FWD.
     if feedback > target, issue MOTOR_REV.
     if feedback == target, issue MOTOR_STOP.
3. On error (invalid feedback):
   - Enter ERROR_SAFE. Stop motor, notify ErrorHandler.

### 5. Interfaces (APIs)
- Public:
  - void FlapControlLogic_OnCommand(enum FlapPosition target);
  - void FlapControlLogic_OnFeedback(enum FlapPosition position);
- Required:
  - MotorDriver control, PositionFeedback, StatusIndicator

### 6. Error Handling
- Invalid command: ignored.
- Invalid feedback: transition to ERROR_SAFE.
- On ERROR_SAFE: system blocks new commands until recovery.

### 7. Resource and Timing Considerations
- Event-driven by UART and feedback.
- No persistent timers, no concurrency.
- All buffers/vars statically allocated. Not re-entrant.

### 8. Traceability to SWE Requirements
- Implements: SWE-REQ-006, 007, 008, 009, 010, 032, 033, 034, 035, 036, 037, 039, 048, 051, 052, 053

## Software Unit: MotorDriver

### 1. Responsibilities
- Receives direction and enable/disable commands from FlapControlLogic.
- Drives the GPIO and/or PWM pins to control DC motor rotation.
- Reports motor status as needed.
- Explicitly does NOT: decide position, interpret UART commands, or manage feedback.

### 2. Internal Data Design
- Motor direction variable (enum MotorDirection dir).
- Enable flag.
- Static GPIO pin config struct(s).

### 3. State Machine
- No explicit state machine. Driven directly by API invocations; current enable/direction defines implicit "state".

### 4. Algorithms and Control Flow
- On enable/disable: Set GPIO to energize or de-energize motor.
- On direction change: Set direction pins.
- On stop: De-energize all pins.

### 5. Interfaces (APIs)
- Public:
  - void MotorDriver_SetDirection(enum MotorDirection dir);
  - void MotorDriver_Enable(bool en);
  - void MotorDriver_Stop(void);
- Required: None except GPIO low-level drivers.

### 6. Error Handling
- Invalid direction: do not actuate pins.
- Redundant enable: idempotent.
- All errors are fail-safe; motor is disabled on error.

### 7. Resource and Timing Considerations
- Only driven by FlapControlLogic. No concurrency.
- Stateless between invocations except last set direction/enable.
- Not reentrant. All variables static/single-threaded.

### 8. Traceability to SWE Requirements
- Implements: SWE-REQ-011, 012, 013, 014, 015, 028, 050, 051

## Software Unit: PositionFeedback

### 1. Responsibilities
- Acquires ADC value from potentiometer.
- Maps ADC value to discrete flap position.
- Signals validity of value.
- Explicitly does NOT: issue commands, control the motor, parse UART, or handle errors beyond feedback.

### 2. Internal Data Design
- Last sampled ADC value (uint16_t adcVal).
- Complete static map of ADC ranges to flap positions.
- Variable for valid/invalid (bool feedbackValid).
- Configuration constants for range bounds (const static arrays).

### 3. State Machine
- No explicit state machine, single-shot on request/report.

### 4. Algorithms and Control Flow
- On sample request:
   - Trigger ADC read, acquire value.
   - For each map entry: if adcVal in range, set corresponding enum FlapPosition.
   - If no match, set feedbackValid = false.
   - Report to logic (FlapControlLogic).

### 5. Interfaces (APIs)
- Public:
  - void PositionFeedback_Sample(void);
  - enum FlapPosition PositionFeedback_GetPosition(void);
  - bool PositionFeedback_IsValid(void);
- Required:
  - ADC driver; FlapControlLogic consumer.

### 6. Error Handling
- Out-of-range or invalid ADC: feedbackValid = false, triggers safe-state (FlapControlLogic).
- No retries or fallback.

### 7. Resource and Timing Considerations
- Triggered by FlapControlLogic on demand.
- All buffers/config statically allocated.
- All code atomic per invocation; not reentrant.

### 8. Traceability to SWE Requirements
- Implements: SWE-REQ-016, 017, 018, 019, 020, 027, 040, 041, 042, 043

## Software Unit: StatusIndicator

### 1. Responsibilities
- Drives GPIO to control status LED and green position LEDs.
- Updates LED status based on flap state/position.
- Ensures only one position LED is ON at a time.
- Explicitly does NOT: determine flap position, parse commands, interact with ADC or UART, report errors.

### 2. Internal Data Design
- Current state of LEDs (bitfield or struct, static).
- Mapping: position to LED pins (static array).
- Power LED state flag.
- Last known flap position variable.

### 3. State Machine
- No state machine. Duty is event-driven by API calls.

### 4. Algorithms and Control Flow
- On LED update:
   - Set power LED on if system up.
   - Set single position LED ON per request, all others OFF.
   - If invalid/undefined: all position LEDs OFF.

### 5. Interfaces (APIs)
- Public:
  - void StatusIndicator_Update(enum FlapPosition pos, bool powerOn);
- Required: None except GPIO low-level drivers.

### 6. Error Handling
- Invalid position: all position LEDs OFF.
- Redundant updates: idempotent.

### 7. Resource and Timing Considerations
- Event-driven by FlapControlLogic.
- No concurrency; all state is static.
- Not reentrant by design.

### 8. Traceability to SWE Requirements
- Implements: SWE-REQ-021, 022, 023, 024, 025, 029, 052, 053

## Software Unit: ErrorHandler

### 1. Responsibilities
- Handles software-detected error or unexpected input/feedback.
- Enforces safe-state (stopping motor, clearing outputs).
- Signals error condition to LEDs (via StatusIndicator).
- Optionally logs internal error (reserved for demo/extension).
- Explicitly does NOT: parse commands, read UART/ADC, interpret flap position.

### 2. Internal Data Design
- Static variable for last error code.
- Error status flag.
- Lookup/table for error type to safe action.

### 3. State Machine
- STATES: NORMAL, ERROR_SAFE
- EVENTS: error_detected, clear_error
- TRANSITIONS: NORMAL -> ERROR_SAFE, ERROR_SAFE -> NORMAL

### 4. Algorithms and Control Flow
- On error trigger: store code, set ERROR_SAFE, disable motor, call StatusIndicator for fault LED output.
- On error clear: reset state.

### 5. Interfaces (APIs)
- Public:
  - void ErrorHandler_Trigger(enum ErrorType code);
  - void ErrorHandler_Clear(void);
- Required:
  - StatusIndicator_Update for error indication.

### 6. Error Handling
- All errors set system to safe-state.
- Only explicit clear recovers.

### 7. Resource and Timing Considerations
- Event-driven, never periodic.
- Not reentrant. Static state only.

- Implements: SWE-REQ-044, 045, 046, 047
