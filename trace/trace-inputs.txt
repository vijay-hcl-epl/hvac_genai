====================================================
1.0 System Overview
====================================================
The HVAC Flap Actuator System is an embedded prototype intended to demonstrate a simplified automotive air distribution actuator subsystem for educational and process demonstration purposes. The system comprises a DC motor-driven air flap, a position feedback potentiometer, green status LEDs, and a microcontroller. User commands are received over UART, and visual feedback is provided via LEDs. The principal aim is to control air flap position reliably and provide observable system states for learning, specifying clear, testable software requirements, and demonstrating compliance with ASPICE level 3 processes.

====================================================
2.0 Flap Position Control Requirements
====================================================
SYS-REQ-001: The system shall accept user commands representing target flap positions via the UART interface.
SYS-REQ-002: The system shall continuously compare the current position of the flap to the requested target position.
SYS-REQ-003: The system shall activate the motor to move the flap toward the requested position when a valid command is received.
SYS-REQ-004: The system shall stop the motor once the flap reaches the requested position within the defined tolerance.
SYS-REQ-005: The system shall monitor the flap's physical position and initiate corrective action if the target position drifts.
SYS-REQ-006: The system shall reject and ignore user commands specifying positions outside the allowed range (0-5).
SYS-REQ-007: The system shall hold the flap in its final position after reaching the target.
SYS-REQ-008: The system shall not require a homing or calibration sequence upon power-up. [Implied]

====================================================
3.0 Motor Control Requirements
====================================================
SYS-REQ-009: The system shall enable the DC motor only when the flap must be moved to a new position.
SYS-REQ-010: The system shall control the direction of the DC motor based on whether the target position is greater or less than the current position.
SYS-REQ-011: The system shall use dedicated GPIO outputs to control motor direction and enable/disable signals.
SYS-REQ-012: The system shall stop (disable) the motor immediately after the target position is reached.
SYS-REQ-013: The system shall not attempt to drive the motor if an error, such as out-of-range feedback, is detected.
SYS-REQ-014: The system shall ensure that only one direction signal is asserted at any time to prevent conflicting drive.
SYS-REQ-015: The system shall keep the motor disabled (OFF) after power-up and during idle states.

====================================================
4.0 Position Feedback Acquisition and Processing
====================================================
SYS-REQ-016: The system shall acquire the analog voltage from the flap-position potentiometer using an ADC input channel.
SYS-REQ-017: The system shall map ADC readings to discretized logical positions (0-5), corresponding to physical flap positions.
SYS-REQ-018: The system shall define ADC value ranges that partition the potentiometer output into the supported logical positions.
SYS-REQ-019: The system shall periodically sample the position feedback signal to detect changes.
SYS-REQ-020: The system shall detect and flag potentiometer/ADC readings outside the expected range as errors.
SYS-REQ-021: The system shall never accept ADC values that do not correspond to a valid logical position. [Implied]

====================================================
5.0 User Command Interface Requirements
====================================================
SYS-REQ-022: The system shall receive user commands through UART as simple unsigned integers corresponding to defined flap positions (0-5).
SYS-REQ-023: The system shall validate received commands and only act upon those corresponding to valid logical positions.
SYS-REQ-024: The system shall ignore commands that do not represent valid positions without generating error responses.
SYS-REQ-025: The system shall not require acknowledgment of either valid or invalid commands. [Implied]

====================================================
6.0 Status Indication Requirements
====================================================
SYS-REQ-026: The system shall use a dedicated status LED to indicate system power is ON.
SYS-REQ-027: The system shall use a set of green LEDs to indicate the current flap position, with no more than one green LED ON at a time.
SYS-REQ-028: The system shall update LED outputs promptly whenever the position changes.
SYS-REQ-029: The system shall maintain clear and simple LED behavior per the requirements, with no elaborate visual patterns. [Implied]

====================================================
7.0 System Behavioral Requirements
====================================================
SYS-REQ-030: On power-up or reset, the system shall initialize all hardware and software components (UART, ADC, GPIO, PWM, LEDs, etc.).
SYS-REQ-031: On power-up, the motor shall remain OFF until a valid user command is received.
SYS-REQ-032: The system shall read and display the detected current flap position on power-up.
SYS-REQ-033: While idle, the system shall wait for user command input.
SYS-REQ-034: The system shall handle invalid user command input gracefully by ignoring such input.
SYS-REQ-035: During normal operation, the system shall execute movement to the requested flap position and indicate the result via LEDs.
SYS-REQ-036: If the target position is reached, the system shall transition to a holding state with the motor OFF.
SYS-REQ-037: The system shall never crash or exhibit undefined behavior if continuous invalid commands are received. [Implied]
SYS-REQ-038: The system shall disable the motor if ADC input is outside the valid range. [Implied]

====================================================
8.0 System Interface Requirements
====================================================
SYS-REQ-039: The system shall use UART as the sole external command interface for user input.
SYS-REQ-040: The system shall use PWM-controlled GPIO to enable or disable the motor driver.
SYS-REQ-041: The system shall use dedicated GPIO pins for motor direction control and LED control.
SYS-REQ-042: The system shall connect the position feedback potentiometer to an ADC channel of the microcontroller.
SYS-REQ-043: The system shall provide all position and status feedback solely through the status and green LEDs. [Implied]

====================================================
9.0 Constraints and Assumptions
====================================================
SYS-REQ-044: The system shall control only one actuator flap and one DC motor.
SYS-REQ-045: The system shall process one user command at a time.
SYS-REQ-046: The system shall not implement communication over CAN or LIN or external vehicle networks.
SYS-REQ-047: System calibration values shall be fixed in software for all logical positions, with no runtime modification.
SYS-REQ-048: The system shall operate under the assumption that all hardware components are functioning correctly. [Implied]

====================================================
10.0 Non-Functional Requirements
====================================================
10.1 Responsiveness Expectations
SYS-REQ-049: The system shall respond to user commands in a manner that feels instantaneous to a human operator, within practical prototype limits.
10.2 Error Handling and Edge Cases
SYS-REQ-050: The system shall stop the motor if ADC values indicate an out-of-range or fault condition, and shall ignore invalid UART commands.
10.3 Resource Constraints
SYS-REQ-051: The system shall avoid unnecessary or resource-intensive computations, and utilize lightweight code suitable for an embedded learning application.
10.4 Maintainability and Modularity
SYS-REQ-052: The system shall separate functional blocks (command handling, motor control, feedback processing, LED indication) within the software to simplify understanding and modification for learning purposes.
10.5 Testability
SYS-REQ-053: The system shall ensure all functions (flap movement, command handling, indication) are observable either via UART or LED indicators, for both manual and script-based test execution.

====================================================
Architecture-Relevant Considerations Derived from System Requirements
====================================================
- This system does not require concurrent real-time multitasking; state machine or sequential control is sufficient.
- All command inputs and actuation are local; there is no networked/external system integration.
- System responsibilities are simple: receive command, validate, drive actuation, provide status.
- Code must remain scalable for possible future extension, but over-engineering is unnecessary.
- Visual and command interfaces are explicit; the architecture must keep UI feedback and motor control logically separated.
- Software structure must facilitate easy understanding, demonstration, and modification for instructional use.

# 1.0 Software Scope and Responsibility

The software for the HVAC Flap Actuator System executes on a microcontroller and is responsible for:
- Receiving user commands representing target flap positions via UART
- Validating and interpreting user commands
- Determining and signaling the correct motor actions required to achieve the requested flap position
- Acquiring, interpreting, and mapping position feedback from a potentiometer using an ADC
- Reporting system and actuator status using LEDs
- Ensuring safe handling of invalid inputs and error conditions
- Operating in a predictable, efficient, and testable manner per system requirements without making architectural or execution model assumptions

# 2.0 Software Functional Requirements

## 2.1 User Command Handling

- SWE-REQ-001: The software shall receive and interpret user commands for flap position targets via UART. (SYS-REQ-001, SYS-REQ-022, SYS-REQ-039)
- SWE-REQ-002: The software shall validate received user commands and only process those corresponding to flap positions 0–5. (SYS-REQ-006, SYS-REQ-023)
- SWE-REQ-003: The software shall ignore any user command outside the allowed flap position range (0–5). (SYS-REQ-006, SYS-REQ-024)
- SWE-REQ-004: The software shall not require acknowledgment for either valid or invalid commands. [Implied] (SYS-REQ-025)

## 2.2 Flap Position Control Logic

- SWE-REQ-007: The software shall activate the appropriate motor drive direction based on whether the target is greater than or less than the current position. (SYS-REQ-010)
- SWE-REQ-008: The software shall stop the motor when the requested position is reached within the defined tolerance. (SYS-REQ-004, SYS-REQ-012)
- SWE-REQ-009: The software shall maintain the flap in its last reached position after achieving the target. (SYS-REQ-007)
- SWE-REQ-010: The software shall monitor the flap's physical position and, if drift is detected, re-initiate movement to correct position. (SYS-REQ-005)
- SWE-REQ-011: The software shall ensure the flap actuator only controls a single actuator and motor. (SYS-REQ-044)
- SWE-REQ-012: The software shall process only one user command at a time. (SYS-REQ-045)
- SWE-REQ-013: The software shall not require a homing or calibration sequence upon power-up. [Implied] (SYS-REQ-008)

## 2.3 Motor Control Logic

====================================================
SOFTWARE ARCHITECTURE: HVAC FLAP ACTUATOR SYSTEM
====================================================

1.0 Candidate Architecture Styles and Evaluation
----------------------------------------------------
Three candidate architecture styles are considered based on the SWE.1 and SYS-REQ-X requirements:

A) Monolithic Block Architecture
- Simple main-loop single source file or module
- Pros: Easiest to understand, minimal overhead, simple prototype
- Cons: Extremely poor maintainability, very limited scalability, not compliant with ASPICE Level 3 which demands logical decomposition and traceability; does not support separation of testable software units
- Evaluation: Rejected due to lack of maintainability, limited testability, does not enable modularity constraints (SYS-REQ-052), and not suitable for ASPICE Level 3.

B) Layered Architecture (Classic 3-Layer)
- Application Layer (logic, state machine), Services Layer (driver abstraction), Hardware Abstraction Layer
- Pros: Good maintainability, testability, and clear separation of hardware interaction; enables mapping to future projects/extensions
- Cons: More complexity than is needed for this simple system; slightly more overhead
- Evaluation: Acceptable, but adds unnecessary abstraction for a single actuator system. System requirements do not specify portable software or hardware independence, and layered drivers not demanded.

C) Component-Based, Logical Modular Software Structure
- Each major SW function (command handler, position feedback, motor driver, status indication, error handling) is separate software unit
- Pros: Fully supports modularity explicitly required (SYS-REQ-052, SWE-REQ-057); supports simple mapping, testability, and clear responsibilities; easy for educational expansion/testing; matches ASPICE Level 3 for traceable modules and responsibilities
- Cons: Slightly more complex than pure monolith but much lower complexity than layered; matches instructional/learning system intent
- Evaluation: Best fit. All requirements for logical separation, maintainability, ease of understanding (SYS-REQ-052), testability (SYS-REQ-053/ SWE-REQ-053), and hardware interaction are satisfied without introducing unnecessary overhead.

Conclusion: The Component-Based modular software structure is selected. No explicit execution model (RTOS, timer, scheduler) is required by requirements, so none is chosen. The architecture will consist of logical software units mapped to requirements; implementation mechanism (super-loop, event-driven, etc.) is deferred.

---
2.0 Architecture Decisions and Justification
----------------------------------------------------
Selected Architecture: Logical, Component-Based Software Modularity

Justification:
- Explicit support for modularity/demonstration per (SYS-REQ-052/ SWE-REQ-057)
- Clear mapping of SWE.1 requirements to SW units responsible for each major function
- Supports maintainability, ease of change (SYS-REQ-052), separation of concerns, and testability (SYS-REQ-053, SWE-REQ-053/054)
- Traceable to ASPICE L3 by clear mapping of requirements to units
- No requirements indicate the need for an explicit execution model/scheduler (see below)
