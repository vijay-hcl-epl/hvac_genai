## 1.0 System Overview
- **SYS-REQ-001:** The system SHALL control a single HVAC air flap, allowing a user to select discrete positions via UART command input.
- **SYS-REQ-002:** The system SHALL provide feedback regarding flap position and system status using LEDs.
- **SYS-REQ-003:** The system SHALL monitor air flap position using a potentiometer connected to an ADC input.
- **SYS-REQ-004:** The system SHALL interface with a DC motor driver to move the flap to commanded positions.

---

## 2.0 Flap Position Control
- **SYS-REQ-005:** The system SHALL move the HVAC flap to the user-commanded target position when a valid command is received.
- **SYS-REQ-006:** The system SHALL define and use a fixed mapping of ADC value ranges to each logical flap position (positions 0, 1, 2, 3, 4, 5).
- **SYS-REQ-007:** The system SHALL prevent the flap from moving beyond the minimum and maximum supported positions. [Implied]
- **SYS-REQ-008:** The system SHALL stop the motor and hold the flap position once the target position is reached.

---

## 3.0 Motor Control
- **SYS-REQ-009:** The system SHALL control the direction of flap movement using GPIO signals to the motor driver to rotate the motor clockwise or anti-clockwise.
- **SYS-REQ-010:** The system SHALL enable or disable the DC motor using a PWM output.
- **SYS-REQ-011:** The system SHALL ensure that the motor is stopped (no drive commands output) upon system power-up and initialization.

---

## 4.0 Position Feedback Acquisition & Processing
- **SYS-REQ-012:** The system SHALL acquire the current flap position by sampling the potentiometer through an ADC input channel.
- **SYS-REQ-013:** The system SHALL process the ADC value to determine and update the logical flap position.
- **SYS-REQ-014:** The system SHALL continuously monitor the flap position during active movement and when idle. [Implied]

---

## 5.0 User Command Interface
- **SYS-REQ-015:** The system SHALL receive flap position commands as single-byte (e.g., values 0–5) over UART.
- **SYS-REQ-016:** The system SHALL interpret only commands within the defined range as valid; commands outside this range SHALL be classified as invalid.
- **SYS-REQ-017:** The system SHALL ignore invalid UART commands without providing acknowledgment or error response.

---

## 6.0 Status Indication
- **SYS-REQ-018:** The system SHALL use a dedicated LED to indicate system power-on status.
- **SYS-REQ-019:** The system SHALL provide flap position status by illuminating only the LED corresponding to the current logical position; at most, one position indicator LED SHALL be active at any given time.

---

## 7.0 System Behavior (power-up, idle, normal, target reached, invalid input)
- **SYS-REQ-020:** Upon power-up, the system SHALL initialize all required peripherals (ADC, UART, GPIO, PWM) prior to any control actions.
- **SYS-REQ-021:** Upon power-up, the system SHALL determine and indicate the current flap position before accepting user commands.
- **SYS-REQ-022:** In idle state (awaiting commands), the system SHALL maintain the flap at the last valid position and update current position indication accordingly.
- **SYS-REQ-023:** Upon receiving a valid command, the system SHALL move the flap from its current to the commanded position and then enter a target-reached (holding) state.
- **SYS-REQ-024:** Upon receiving an invalid command, the system SHALL maintain current position and status indication; no action SHALL be taken.
- **SYS-REQ-025:** If an ADC value is detected outside valid range, the system SHALL stop the motor and disregard further movement commands until the value returns within range.

---

## 8.0 Interfaces (UART, motor driver, ADC, LEDs)
- **SYS-REQ-026:** The system SHALL use a UART interface for receiving external user commands.
- **SYS-REQ-027:** The system SHALL use ADC hardware to read potentiometer position feedback.
- **SYS-REQ-028:** The system SHALL use GPIO and PWM outputs to control the DC motor via the motor driver interface.
- **SYS-REQ-029:** The system SHALL use dedicated GPIO outputs to control system and position indicator LEDs.

---

## 9.0 Constraints & Assumptions
- **SYS-REQ-030:** The system SHALL assume only one user, one flap actuator, and one user command is to be processed at a time.
- **SYS-REQ-031:** The system SHALL assume that hardware components (motor, potentiometer, LEDs, driver) are operating within functional limits. [Implied]
- **SYS-REQ-032:** The system SHALL NOT perform calibration or self-learning activities during operation; position mapping is statically defined. [Implied]

---

# HVAC Flap Actuator Software Architecture (SWE.2)

## 1. Candidate Architecture Styles & Evaluation

**Considered:**
- **Monolithic:** Simple main loop, all logic in one block. Fails ASPICE L3 modularity, poor separation of concerns. ❌
- **Layered:** Stacks device driver, control, and interface logic in layers. Modular, but excessive for direct, simple job.
- **Component-Based:** Modest number of logically separated units aligned to SWE.1/SYS-REQ feature boundaries. ✅

### Evaluation (Traced to SWE.1/SYS-REQ)
- **System complexity:** Single actuator, atomic (SWE-REQ-003, SYS-REQ-030); simple direct flows.
- **HW interaction:** All mapped to dedicated MCUs, clear API boundaries (SWE-REQ-017-020).
- **Testability:** Unit isolation, each function testable (SWE-REQ-040-042, SYS-REQ-040-041).
- **Maintainability:** Logical separation of commands, control, I/O (SWE-REQ-039).
- **ASPICE L3:** Modular, clearly scoped interfaces, per SYS-REQ-039, SWE-REQ-042.

**Selected:** Component-Based Architecture (modular functional units per SWE.1 functions)
**Rejected:**
- Monolithic - fails modular/testable criteria.
- Strict Layered - more structured than needed, with minimal logical separation.

## 2. Software Architecture Definition

### 2.1 Software Units & Responsibilities

- **Command Handler**
  - SWE-REQ-001, SWE-REQ-002, SWE-REQ-003
  - Accepts/validates UART input, interfaces UART driver, passes valid commands
- **Position Control**
  - SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-025
  - Maintains state of commanded/actual flap position, initiates motor actions
- **Motor Driver Interface**
  - SWE-REQ-008, SWE-REQ-009, SWE-REQ-019
  - Converts position changes to GPIO/PWM for DC motor via driver
- **ADC Interface**
  - SWE-REQ-011, SWE-REQ-012, SWE-REQ-018
  - Periodically (or on request) samples position feedback
- **LED Status Indicator**
  - SWE-REQ-014, SWE-REQ-015, SWE-REQ-020
  - Updates power/position LEDs per status/position
- **Error Handling**
  - SWE-REQ-013, SWE-REQ-026, SWE-REQ-027, SWE-REQ-032, SWE-REQ-033
  - Triggers/handles motor stop, safe idle, ignores/flags invalid state

### 2.2 Interfaces Between Units

- Command Handler => Position Control (valid command input, triggers position update)
- Position Control <=> Motor Driver Interface (commands to start/stop/hold/position, feedback)
- Position Control <=> ADC Interface (position queries, sample results)
- Position Control => LED Status Indicator (notify position/state changes)
- Error Handling <=> All Units (propagate/act-on error states)

# SOFTWARE LOW LEVEL DESIGN (SWE.3) – HVAC Flap Actuator

## Traceable to SWE.1 and SWE.2, APRILDEMO-17B

### Introduction
This document provides the detailed Low Level Design (LLD) for each software unit of the HVAC Flap Actuator, as defined in the SWE.2 (sw-arch.txt) and tracing directly to SWE.1 (sw-reqs.txt). No architecture changes, unit additions, code generation, or scheduling are described. All structures target MISRA-compliant embedded C with only static data allocation.

----

## 1. Software Unit: Command Handler

### 1. Responsibilities
- Handles: Receiving UART input, basic command validation, passing only valid flap-position commands for processing.
- Does not handle: Any diagnostic output, error escalation beyond rejection/ignore of bad commands.

### 2. Internal Data Design
- Internal buffer for command character(s) (static, fixed-size, no allocation).
- Variable for last received command, validity flag.

### 3. State Machine
- States: IDLE, RECEIVING, VALIDATING, READY (command available or not)
- Events: UART RX event, buffer full, parse complete, bad/ignored command
- Transitions: On RX –> RECEIVING. On complete –> VALIDATING. If valid –> READY. If invalid –> IDLE (buffer cleared).

### 4. Algorithms & Control Flow
- Wait for UART RX event
- Store data to buffer (up to static size)
- On command delimiter or buffer-full: validate as position (0–5)
- If valid, pass to Position Control; else, clear buffer
- No output/ack for invalid input

### 5. Interfaces (APIs)
- Provided: get_valid_command(): returns latest valid position or ‘NONE’ if not available
- Required: UART peripheral RX interface
- Error: Only sets internal state; no reporting

### 6. Error Handling
- Ignores bad UART data, framing/parity errors; no error output (per SWE-REQ-032/004)
- Buffer overflow resets to IDLE; no retries

### 7. Resource & Timing Considerations
- Static buffer, non-reentrant
- Executed on UART RX event; no busy polling
- Very short WCET (<1ms per RX)

### 8. Traceability
- SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004, SWE-REQ-017, SWE-REQ-032

----

## 2. Software Unit: Position Control

### 1. Responsibilities
- Handles: Maintain and update requested vs actual flap position; initiate/complete commanded movements
- Does not handle: Motor bit-level/PWM, ADC hardware access, error signaling beyond passing out-of-range to Error Handler

### 2. Internal Data Design
- Static variables for current position, target position, last command, movement state
- Static configuration: position map (logical<->ADC), comparator window

### 3. State Machine
- States: IDLE (holding), WAIT_COMMAND, MOVING, COMPLETED, ERROR_HOLD
- Events: valid command from Command Handler, target=actual, move done, error

### 4. Algorithms & Control Flow
- On valid command:
    - If within range & not busy, set target position
    - If ADC actual ≈ target (tolerance): no move, go to COMPLETED
    - Else: activate Motor Driver IF, update movement state
    - Track ADC until target reached (with hysteresis)
- If out-of-range ADC: transition to ERROR_HOLD

### 5. Interfaces (APIs)
- Provided: set_target(position), get_state()
- Required: get_current_position() from ADC IF; drive_motor(target) from Motor Driver IF; notify_LED(status)

### 6. Error Handling
- If ADC invalid or out-of-range, invokes Error Handling unit
- Ignores new commands until prior sequence complete or error cleared

### 7. Resource & Timing Considerations
- No dynamic allocation; all control variables static
- Not re-entrant, single-command active at a time
- Typical WCET per event: <2 ms

### 8. Traceability
- SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-025, SWE-REQ-024, SWE-REQ-028, SWE-REQ-029, SWE-REQ-031

----

## 3. Software Unit: Motor Driver Interface

### 1. Responsibilities
- Handles: Drive DC motor (via MCU IO/PWM) to move flap; issue stop/drive/hold logic as control requests
- Does not handle: High-level positioning logic or error analysis

### 2. Internal Data Design
- Static variables: command queue (max size 1–2), motor enable/disable state, current drive direction
- Static config: motor PWM params, IO pin mapping

### 3. State Machine
- States: IDLE, DRIVING, STOPPED
- Events: drive request, stop command, fault/event

### 4. Algorithms & Control Flow
- On drive_motor(target):
    - Set direction and PWM according to Position Control's directive
    - Assert/clear drive/stops via IO
    - On stop: clear enables, set STOPPED

### 5. Interfaces (APIs)
- Provided: drive_motor(position), stop_motor()
- Required: GPIO/PWM control access, position/stop from Position Control
- Error: Reports hardware error up to Error Handler only

### 6. Error Handling
- On hardware error/disconnect, set STOPPED; invokes Error Handling unit
- On out-of-range request, ignores

### 7. Resource & Timing Considerations
- All config static; no dynamic variable use
- Not re-entrant, sequential commands
- WCET per drive: <1 ms (API call), actuation time is physical

### 8. Traceability
- SWE-REQ-008, SWE-REQ-009, SWE-REQ-019, SWE-REQ-037, SWE-REQ-038

----

## 4. Software Unit: ADC Interface

### 1. Responsibilities
- Handles: Poll or receive command to sample analog flap position sensor and return mapped logical position
- Does not handle: Mechanical/physical sensor analysis

### 2. Internal Data Design
- Static variable: last ADC result, last logical position
- Static config: table (ADC-value <-> logical position), valid range min/max

### 3. State Machine
- States: IDLE, SAMPLING, NEW_SAMPLE
- Events: sample request, complete, out-of-range detected

### 4. Algorithms & Control Flow
- On request:
    - Start ADC conversion, store result
    - Map result to logical position/bin/static table
    - Mark new sample available
    - If out-of-range, flag error

### 5. Interfaces (APIs)
- Provided: get_current_position(), is_valid()
- Required: ADC peripheral access, config

### 6. Error Handling
- On out-of-range result: set error, inform Error Handler

### 7. Resource & Timing Considerations
- Static only, no allocation
- Not re-entrant, sample-on-request or periodic
- WCET per sample: <0.5ms (excl. ADC HW latency)

### 8. Traceability
- SWE-REQ-011, SWE-REQ-012, SWE-REQ-013, SWE-REQ-018, SWE-REQ-029, SWE-REQ-031

----

## 5. Software Unit: LED Status Indicator

### 1. Responsibilities
- Handles: Updates system status and position LEDs on state/command events
- Does not handle: Any logic except direct LED mapping

### 2. Internal Data Design
- Static bitmap/variable per LED (power/state/position)
- Static pin mapping config

### 3. State Machine
- States: IDLE, UPDATE_REQUIRED, DISPLAYING
- Events: power-on, movement, completed

### 4. Algorithms & Control Flow
- On notify_LED(status):
    - Update LED bitmap/state per flap position
    - Write to GPIO outputs for new pattern
    - Only one position LED enabled; power always on if powered

### 5. Interfaces (APIs)
- Provided: notify_LED(state)
- Required: GPIO output access, pin config

### 6. Error Handling
- On illegal state/input, set all LEDs to error-indication pattern (defined in config)

### 7. Resource & Timing Considerations
- All data static, single bitmap per change
- Not re-entrant, event-driven
- WCET: <0.1ms

### 8. Traceability
- SWE-REQ-014, SWE-REQ-015, SWE-REQ-016, SWE-REQ-020, SWE-REQ-029

----

## 6. Software Unit: Error Handling

### 1. Responsibilities
- Handles: Detects errors (ADC out-of-range, invalid command, hardware/logic failures); forces system into known-safe idle, clears requests
- Does not handle: Recovery/auto-retry or escalation beyond halting system

### 2. Internal Data Design
- Static variables: error flag/status
- Static signature for last detected error code

### 3. State Machine
- States: NORMAL, FAULT
- Events: error detected, error clear

### 4. Algorithms & Control Flow
- On error detected:
    - Set error state, clear command/action requests
    - Notify affected units (LEDs -> error pattern; Driver -> STOPPED)
    - Block further movement/commands until clear

### 5. Interfaces (APIs)
- Provided: report_error(code), get_error_status()
- Required: interfaces to all units (state, error notification)

### 6. Error Handling
- Only one level: on first error, transitions to FAULT, disables all actuators
- No retries; must be cleared by system reset or other (not in scope)

### 7. Resource & Timing Considerations
- All static data; never re-entrant
- Invoked by error event from any unit
- WCET per error: <0.5ms

### 8. Traceability
- SWE-REQ-013, SWE-REQ-026, SWE-REQ-027, SWE-REQ-032, SWE-REQ-033, SWE-REQ-034
