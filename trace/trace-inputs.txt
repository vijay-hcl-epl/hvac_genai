# 1.0 System Overview

The HVAC flap actuator system is a microcontroller-based control unit that commands the position of an air distribution flap, as typically found in automotive HVAC (Heating, Ventilation, and Air Conditioning) systems. The purpose of the system is to allow a user to remotely select a flap position (via UART), actuate a DC motor to achieve the desired position (measured using a potentiometer/ADC feedback), and visually indicate system and position status using LEDs. The system represents a prototype for demonstrating embedded software development processes.

# 2.0 Flap Position Control Requirements

## Target Position Selection
- SYS-REQ-001: The system shall accept user commands via UART to specify a target flap position.
- SYS-REQ-002: The system shall support discrete flap positions from 0 (fully closed) to 5 (fully open).

## Position Comparison
- SYS-REQ-003: The system shall determine if the current flap position matches the user-requested target position using ADC feedback.

## Achieving and Holding Flap Positions
- SYS-REQ-004: The system shall command the DC motor to adjust the flap position when a new valid target is received.
- SYS-REQ-005: The system shall stop the motor once the target position is achieved.
- SYS-REQ-006: The system shall maintain the flap in the achieved position until a new valid target is received or power is cycled.

- SYS-REQ-007: [Implied] The system shall ignore commands for positions outside of the defined 0-5 range.

# 3.0 Motor Control Requirements

## Motor Direction Control
- SYS-REQ-008: The system shall control the motor direction using GPIO outputs to the motor driver to move the flap toward the requested position.

## Motor Enable/Disable Behavior
- SYS-REQ-009: The system shall enable the motor via PWM only to move the flap toward a new position and disable the motor when no movement is required.

## Motor Stopping Conditions
- SYS-REQ-010: The system shall stop motor movement immediately when the target position is reached, or if an out-of-range potentiometer/ADC value is detected.

# 4.0 Position Feedback Acquisition and Processing

## Potentiometer Signal Acquisition
- SYS-REQ-011: The system shall acquire flap position feedback from a potentiometer connected to an ADC channel.

## ADC Usage
- SYS-REQ-012: The system shall configure and use the ADC peripheral to sample the potentiometer voltage at a periodic rate sufficient for responsive position updates [Implied].

## Mapping ADC Values to Logical Flap Positions
- SYS-REQ-013: The system shall map ADC values to one of six discrete logical flap positions (0-5), based on predefined ADC ranges.
- SYS-REQ-014: The system shall treat ADC values outside the calibrated range as invalid.

# 5.0 User Command Interface Requirements

## UART-Based User Commands
- SYS-REQ-015: The system shall provide a UART-based user command interface for receiving flap position requests.

## Command Validation
- SYS-REQ-016: The system shall validate that received commands correspond to supported flap position values 0–5.
- SYS-REQ-017: The system shall take no action in response to an invalid command; no error response or acknowledgment is required.

## Handling of Invalid Commands
- SYS-REQ-018: [Implied] The system shall safely ignore out-of-range and malformed UART commands.

# 6.0 Status Indication Requirements

## Power/Status Indication
- SYS-REQ-019: The system shall turn on a dedicated power/status LED in response to successful system initialization and continued operation.

## Flap Position Indication using LEDs
- SYS-REQ-020: The system shall use up to six green LEDs to indicate the current logical flap position (0–5), illuminating only the LED corresponding to the active position.
- SYS-REQ-021: At most one green LED shall be illuminated at any time.
- SYS-REQ-022: [Implied] Status indication logic shall update within a user-noticeable period following position changes.

# 7.0 System Behavioral Requirements

## Power-Up and Initialization
- SYS-REQ-023: On power-up, the system shall initialize all required peripherals: ADC, UART, GPIO, and PWM.
- SYS-REQ-024: On power-up, the system shall read the potentiometer and indicate the detected position via LEDs.
- SYS-REQ-025: On power-up, the motor shall remain off unless a movement command is subsequently received.

## Idle Operation
- SYS-REQ-026: The system shall operate in an idle state awaiting valid user commands.
## Normal Operation
- SYS-REQ-027: During movement, the system shall drive the motor toward the requested target position.
- SYS-REQ-028: When the target position is reached, the system shall stop the motor and indicate the new position via LEDs.

## Target Position Reached
- SYS-REQ-029: The system shall generate no additional movement commands unless a new valid target position is requested.

## Invalid Input Handling
- SYS-REQ-030: If an invalid UART command is received, the system shall ignore it and remain in the current state.
- SYS-REQ-031: If ADC feedback is out-of-range, the system shall stop the motor immediately and ignore further move commands until valid feedback is restored.

# 8.0 System Interface Requirements

## UART Interface
- SYS-REQ-032: The system shall receive user commands over a serial UART interface connected to a PC.

## Motor Driver Interface
- SYS-REQ-033: The system shall control the external L298N motor driver via two GPIO pins for direction and a timer PWM output for enable/speed.

## Potentiometer / ADC Interface
- SYS-REQ-034: The system shall read flap position feedback from a potentiometer connected to a signal ADC channel.

## LED Outputs
- SYS-REQ-035: The system shall provide output signals to discrete status and position LEDs.

# 9.0 Constraints and Assumptions

- SYS-REQ-036: Only one flap and one DC motor shall be controlled by the system.
- SYS-REQ-037: Only one user command shall be processed at a time.
- SYS-REQ-038: The system shall assume correct hardware operation (no diagnostics required).
- SYS-REQ-039: The system shall use fixed, pre-configured ADC ranges for position mapping, without support for dynamic calibration or learning.
- SYS-REQ-040: All system logic shall focus on software process demonstration and learning value over production robustness.

# 10.0 Non-Functional Requirements

## 10.1 Responsiveness Expectations
- SYS-REQ-041: The system shall respond to user UART commands and update position/status LEDs with observable responsiveness (i.e., within a period perceptible to a human user).
- SYS-REQ-042: [Implied] The system shall not specify fixed real-time deadlines unless explicitly stated elsewhere in requirements.

## 10.2 Error Handling and Edge Cases
- SYS-REQ-043: The system shall handle invalid UART commands by ignoring them and maintaining safe behavior.
- SYS-REQ-044: The system shall stop the motor in case ADC returns values outside calibrated position ranges.
- SYS-REQ-045: [Implied] The system shall avoid lock-ups or crashes due to unresponsive hardware or unexpected operating conditions.

## 10.3 Resource Constraints
- SYS-REQ-046: The system shall be implemented as a lightweight process suitable for an entry-level STM32 microcontroller without dynamic memory allocation.
## 10.4 Maintainability and Modularity
- SYS-REQ-047: The system requirements, interfaces, and behaviors shall be clearly separated for ease of understanding and modification.

## 10.5 Testability
- SYS-REQ-048: The system shall support external functional testing through UART command input and visual inspection of motor and LED outputs.
- SYS-REQ-049: [Implied] The requirements shall be verifiable through manual or script-based test procedures, without need for automated HIL/SIL test environments.

# Architecture-Relevant Considerations Derived from System Requirements

- The system is inherently single-threaded with no explicit need for concurrency due to its simple, single-flap control logic and user-command-driven operation.
- All external interactions (UART, potentiometer/ADC, motor driver, LEDs) are direct and local, with no networking or distributed requirements.
- Control complexity is limited; logic is centered on user command interpretation, position movement, and visual indication.
- The system is designed to be highly expandable for additional learning objectives (e.g., more positions, alternate indication methods), but is intentionally kept simple for process clarity.
- No recommendation is made regarding execution models, scheduling, or OS/RTOS selection by these requirements.

# 1.0 Architecture Overview
The HVAC flap actuator software is best realized with a component-based architecture. This decision is justified below and followed by a clear breakdown of software units, their responsibilities, and inter-unit interfaces. All content and decisions are strictly traceable to SWE.1 software requirements and source system requirements.

## 1.1 Candidate Architecture Styles
- **Monolithic**: All logic in a main loop, direct hardware access in-line. Simple, but impedes testability/modifiability for ASPICE Level 3 and does not separate concerns.
- **Layered**: HAL/driver, logic, and interface-management layers. Good for separation, but over-structured for the scale/complexity required by the current requirements.
- **Component-based**: Domain components each own a cohesive behavioral responsibility, with explicit interfaces. Matches SWE.1 separation and testability needs, avoid unnecessary layering, and is directly traceable.

## 1.2 Evaluation and Selection
- **System Complexity**: Low-moderate. Requirements separation (command parsing, feedback, control, indication) justifies modularization, but not deep layering.
- **Hardware Interaction**: All hardware mapped 1:1 to modules. No peripheral sharing, OS, RTOS, timing, or concurrency issues required. ADC/UART events are handled locally per module.
- **Testability & Maintainability**: Component separation enables unit verification (UART, logic, indication, feedback, driver). Replaceable units improve future maintainability and process demonstration.
- **ASPICE Level 3**: Explicitly supports interface traceability, requirement-to-component mapping, architectural rationale (no hidden legacy).

**Decision**: A component-based architecture is selected. It delivers the required separation and traceability for maintainability/testing without the overengineering of a deep layered solution. Mono-style is rejected due to poor maintainability. Layered is rejected as unnecessary for the simplicity and size of this application.

# 2.0 Architecture Definition
## 2.1 High-Level Block Diagram (Text)

[UART Handler] <--> [Command Dispatcher] <--> [Flap Control Logic] <--> [Motor Driver]
                                    \
                                     \---> [Feedback Processor (ADC)]
                                     \---> [Indication Handler (LEDs, Status)]

**Data Flows:**
- UART Handler receives commands and forwards to the command dispatcher
- Dispatcher routes commands and manages state
- Control logic directs motor driver and queries ADC feedback
- Indication handler updates LEDs per state and status

## 2.2 Software Unit Table
| Software Unit             | Responsibilities                                                                                 | Interfaces Provided                     | Interfaces Used                                  |
|--------------------------|-------------------------------------------------------------------------------------------------|------------------------------------------|--------------------------------------------------|
| UART Handler             | Receive UART data, validate framing, forward valid commands                                      | UART message dispatch                    | UART hardware                                   |
| Command Dispatcher       | Manage received commands, invoke logic units based on command/state                             | Command distribution                     | UART Handler, Control Logic, Feedback Processor   |
| Flap Control Logic       | Compare target/current, initiate movement, enforce position rules                               | Flap/motor state change, position status | Command Dispatcher, Feedback Processor, Motor Driver |
| Motor Driver             | Manage GPIO/PWM to actuate DC motor as instructed by Flap Control Logic                        | Motor control                            | Flap Control Logic, GPIO/PWM hardware             |

| Indication Handler       | Update power/status LED, indicate current position via discrete LEDs                            | System and user indication               | Flap Control Logic, Command Dispatcher, GPIOs     |

# 3.0 Execution Model and Scheduling Comments
No explicit execution model or scheduling policy is mandated by the requirements at this stage. The architecture and interfaces are agnostic regarding super-loop, polling, or event/callback invocation. Timing/concurrency aspects are intentionally excluded as not justified in SWE.1 or system requirements.

# 4.0 Architectural Constraints
- All design decisions and interfaces are traced to SWE.1 requirements and their system requirement sources only.
- No new requirements, system behavior changes, or implementation details are introduced.
- No safety, diagnostics, or cybersecurity features/mechanisms have been added.
- This model provides clear separation of concerns to support ASPICE Level-3 process and testability, but is process-purposed—not a fieldable product framework.

# 1.0 HVAC Flap Actuator - Software Low-Level Design (SWE.3)

## 1. Architectural Context
Design is strictly based on the component-based structure defined in the software architecture document. SWE.3 units:
1. UART Handler
2. Command Dispatcher
3. Flap Control Logic
4. Motor Driver
5. Feedback Processor (ADC)
6. Indication Handler

All architectural boundaries, responsibilities, and interfaces are kept intact. No new units, no changes to the high-level interfaces or architectural allocation.

---

## 2. Detailed Design by Software Unit

### Software Unit: UART Handler

#### 1. Responsibilities
- Receive UART bytes.
- Validate framing and command delimitation.
- Accumulate/parse new command frames.
- Forward valid position commands to Command Dispatcher.
**Does NOT:**
- Act on parsed commands.
- Validate command semantics beyond UART format/syntax.

#### 2. Internal Data Design
- Receive buffer (fixed size, circular or linear with overflow discard)
- State variable: parse state (IDLE, RECEIVING, FRAME_COMPLETE, ERROR)
- Config: UART baud/config parameters (static)

#### 3. State Machine
States: IDLE, RECEIVING, FRAME_COMPLETE, ERROR
- On RX interrupt or poll, accumulate bytes into buffer.
- If frame delimiter or timeout: set FRAME_COMPLETE or ERROR accordingly.
- On FRAME_COMPLETE: prepare to forward.

#### 4. Algorithms and Control Flow
- On RX event:
  1. If in IDLE, begin frame when start delimiter seen.
  2. On byte, append if below buffer limit.
  3. If delimiter: mark complete; else if overflow/error: ERROR.
  4. On completion, forward buffer as new command.

#### 5. Interfaces (APIs)
- void UART_Handler_RxISR(uint8_t byte)
- int UART_Handler_GetParsedCommand(uint8_t* buf, size_t* len)  // returns frame, resets state
Requires:
- Calls CommandDispatcher_ReceiveCommand(...)

#### 6. Error Handling
- Invalid framing, overflow, or timeout clears/flags error state, resets buffer.
- All output filtered to be well-formed for dispatcher.

#### 7. Resource and Timing Considerations
- Expected: interrupt-on-RX or polled-read.
- Bounded buffer, static allocation.
- Not re-entrant (one command at a time parse).

#### 8. Traceability
- SWE-REQ-001, SWE-REQ-018, SWE-REQ-032, SWE-REQ-035
- Unit: UART Handler

---

### Software Unit: Command Dispatcher

#### 1. Responsibilities
- Receive parsed commands
- Validate semantic content (legal position, format)
- Debounce/ignore out-of-range or malformed commands
- Route valid requests to Flap Control Logic
**Does NOT:**
- Interact with hardware directly

#### 2. Internal Data Design
- Current valid command buffer (pos, length, validity)
- Error flags for last command

#### 3. State Machine
No explicit state machine, uses procedural validation:
- On new command: parse, check position, set validity/error.

#### 4. Algorithms and Control Flow
- On command received:
  1. Parse command into position/int.
  2. If in range 0–5: mark valid, forward.
  3. Else: flag error; do NOT forward.

#### 5. Interfaces (APIs)
- int CommandDispatcher_ReceiveCommand(const uint8_t* data, size_t len)
- int CommandDispatcher_GetNextTarget(int* pos_out)
- void CommandDispatcher_NotifyIdle(void)
Requires:
- Calls FlapControl_SetTargetPosition(...)

#### 6. Error Handling
- Malformed/out-of-range position: ignore, flag error, do not propagate.
- Multiple malformed commands do not disrupt state.

#### 7. Resource and Timing Considerations
- Event-driven: reacts to handler above, non-periodic.
- Bounded memory, no dynamic allocation.
- Not re-entrant (single command context).

#### 8. Traceability
- SWE-REQ-002, SWE-REQ-003, SWE-REQ-018, SWE-REQ-032, SWE-REQ-035
- Unit: Command Dispatcher

---

### Software Unit: Flap Control Logic

#### 1. Responsibilities
- Receive valid new target position requests
- Acquire current position via Feedback Processor
- Command Motor Driver to achieve target
- Enforce no redundant move to same position
- Indicate position changes to Indication Handler
**Does NOT:**
- Process ADC raw data
- Control hardware directly

#### 2. Internal Data Design
- Target position (int: 0–5)
- Actual position (int: 0–5)
- Move state: IDLE, MOVING, ERROR, COMPLETE
- Error flag(s): position error

#### 3. State Machine
States: IDLE, MOVING, ERROR, COMPLETE
Events: New target, feedback update, error/fault, motor done
Transitions:
- IDLE→MOVING (valid new position ≠ actual)
- MOVING→COMPLETE (target achieved)
- MOVING→ERROR (fault/invalid feedback)
- ERROR→IDLE (fault clear, valid feedback)

#### 4. Algorithms and Control Flow
- New request:
  1. If target != actual: invoke motor, set MOVING.
  2. Poll/monitor feedback; when match: stop motor, set COMPLETE, update LED.
  3. On ADC/motor error: set ERROR, stop all motion.

#### 5. Interfaces (APIs)
- int FlapControl_SetTargetPosition(int pos)
- int FlapControl_FeedbackUpdate(int pos, int is_valid)
- int FlapControl_Service(void)
Requires:
- Calls MotorDriver_SetState(...), IndicationHandler_Update(...), FeedbackProcessor_GetPosition(...)

#### 6. Error Handling
- If feedback invalid: halt, set error state.
- All errors drive LEDs/status handler.

#### 7. Resource and Timing Considerations
- Invoked by event/command.
- No internal recursion or re-entrancy required.

#### 8. Traceability
- SWE-REQ-004–007, SWE-REQ-012, SWE-REQ-025, SWE-REQ-026, SWE-REQ-028
- Unit: Flap Control Logic

---

### Software Unit: Motor Driver

#### 1. Responsibilities
- Receive movement directive from Flap Control Logic
- Drive GPIO and PWM to activate/deactivate motor
- Enforce movement duration, enable/disable cycles
**Does NOT:**
- Choose new positions
- Interpret ADC or UART data

#### 2. Internal Data Design
- Motor enable flag
- Direction variable
- PWM duty config (constant)

#### 3. State Machine
No explicit state machine; single-action interface per call.
- Action: ON/OFF, DIRECTION, PWM ENABLE

#### 4. Algorithms and Control Flow
- On set state:
  1. Set/clear enable.
  2. Set direction as commanded.
  3. Apply (static) PWM duty.

#### 5. Interfaces (APIs)
- int MotorDriver_SetState(int enable, int direction)
- int MotorDriver_Stop(void)
Requires:
- Calls GPIO/PWM drivers (abstracted)

#### 6. Error Handling
- If called with invalid args: disables.
- On hardware error: returns error to control logic.

#### 7. Resource and Timing Considerations
- Invoked as required by flap control.
- Static data only.
- No re-entrancy (gate via flap logic).

#### 8. Traceability
- SWE-REQ-008–010, SWE-REQ-020, SWE-REQ-023
- Unit: Motor Driver

---

### Software Unit: Feedback Processor (ADC)

#### 1. Responsibilities
- Sample ADC on request
- Map ADC value to flap position
- Validate ADC range, report errors
**Does NOT:**
- Command movement

#### 2. Internal Data Design
- ADC sample buffer (static size)
- Calibration constants: range per position
- State: last known position, is_valid

#### 3. State Machine
No explicit state machine; event-driven/acquire-on-demand.
- If sample in range: output logical position.
- If out-of-range: flag error.

#### 4. Algorithms and Control Flow
- On acquire:
  1. Start/complete ADC read.
  2. Map numeric value to range.
  3. Flag error if out of position limits.

#### 5. Interfaces (APIs)
- int FeedbackProcessor_GetPosition(int* pos_out)
- int FeedbackProcessor_CheckValid(void)
Requires:
- Calls ADC driver

#### 6. Error Handling
- Out-of-range: returns invalid/flag error; caller disables movement.
- Hardware timeout: propagate error.

#### 7. Resource and Timing Considerations
- Static buffer only.
- Per-request or periodic sample, driven by caller.
- Not re-entrant.

#### 8. Traceability
- SWE-REQ-011–013, SWE-REQ-019, SWE-REQ-029–031, SWE-REQ-033
- Unit: Feedback Processor (ADC)

---

### Software Unit: Indication Handler

#### 1. Responsibilities
- Drive system status LED
- Indicate current flap position via LEDs
- Update indicators on event
**Does NOT:**
- Decide what/when to indicate
- Interact with user commands or ADC

#### 2. Internal Data Design
- LED state bitmap (6 bits for position, 1 for status)
- Status code variable

#### 3. State Machine
No explicit state machine; direct-update model.

#### 4. Algorithms and Control Flow
- On update event:
  1. Set correct LED outputs as requested.
  2. Only one position LED set at any time.
  3. Status LED per health/init/error request.

#### 5. Interfaces (APIs)
- int IndicationHandler_Update(int position, int status_code)
- void IndicationHandler_AllOff(void)
Requires:
- Calls GPIO driver (LEDs)

#### 6. Error Handling
- Hardware errors not reported, but status LED can display error state from logic.
