1.0 System Overview

The HVAC Flap Actuator System is a microcontroller-based embedded system designed for educational and demonstration use. Its primary function is to actuate an air flap (commonly found in automotive HVAC systems) to discrete positions as commanded by a user. The system moves the flap using a DC motor, senses position with a potentiometer via an ADC, takes user commands over UART, and provides feedback using LEDs. The purpose is to demonstrate and learn embedded software processes and not for deployment in automotive production environments.

2.0 Flap Position Control Requirements

SYS-REQ-001: The system shall allow the user to select a target flap position via UART command input.
SYS-REQ-002: The system shall compare the current flap position with the commanded target position.
SYS-REQ-003: The system shall command the flap to move toward the target position when there is a difference between current and target position.
SYS-REQ-004: The system shall stop the flap movement when the target position is reached.
SYS-REQ-005: The system shall monitor the current flap position continuously while the flap is moving.
SYS-REQ-006: The flap shall support at least six discrete positions (e.g., 0–5).
SYS-REQ-007: The mapping between ADC values and flap positions shall be configurable in software.
[Implied] SYS-REQ-008: The system shall clamp the commanded target position to the valid range if out-of-range values are provided.

3.0 Motor Control Requirements

SYS-REQ-009: The system shall control the DC motor to rotate in both clockwise and anti-clockwise directions.
SYS-REQ-010: The system shall use digital outputs (GPIO) for controlling the motor direction.
SYS-REQ-011: The system shall enable or disable the motor as required for positioning.
SYS-REQ-012: The system shall stop the motor when the flap has reached the commanded position.
[Implied] SYS-REQ-013: The system shall stop the motor if the potentiometer/ADC feedback value is out of expected range.

4.0 Position Feedback Acquisition and Processing

SYS-REQ-014: The system shall acquire the current flap position using an ADC channel connected to the potentiometer.
SYS-REQ-015: The system shall process ADC readings and map them to logical flap positions defined in software.
SYS-REQ-016: The system shall support fixed, pre-configured ADC-to-position mappings. 
[Implied] SYS-REQ-017: The system shall ignore dynamic calibration or self-learning of ADC ranges.

5.0 User Command Interface Requirements

SYS-REQ-018: The system shall receive user commands for target position selection via a UART interface.
SYS-REQ-019: The system shall accept only valid integer commands mapped to the supported flap positions.
SYS-REQ-020: The system shall ignore and safely reject invalid commands (outside range, non-numeric).
SYS-REQ-021: The system shall not transmit acknowledgments or errors for invalid commands.
SYS-REQ-022: The UART commands should be processed shortly after being received.
[Implied] SYS-REQ-023: The system shall support single command-at-a-time operation (no command queue).

6.0 Status Indication Requirements

SYS-REQ-024: The system shall use at least one LED to indicate power or system status (e.g., always ON when powered).
SYS-REQ-025: The system shall use a set of LEDs to indicate the current flap position.
SYS-REQ-026: Only one position-indicating LED shall be ON at any time; all others shall be OFF.
SYS-REQ-027: Status indication via LEDs shall be simple, clear, and free of complex patterns.

7.0 System Behavioral Requirements

SYS-REQ-028: On power-up, the system shall initialize all peripherals: ADC, UART, GPIO, and PWM.
SYS-REQ-029: On power-up, the system shall ensure the motor is stopped and not energized.
SYS-REQ-030: On power-up, the system shall read the potentiometer and display the detected flap position on LEDs.
SYS-REQ-031: When no user command is present, the system shall remain idle and hold flap position.
SYS-REQ-032: When a valid user command is received, the system shall transition to normal operation and move the flap.
SYS-REQ-033: Once the target position is reached, the system shall stop the motor and indicate the position on LEDs.
SYS-REQ-034: If invalid user input is received, the system shall ignore it and continue safe operation.
[Implied] SYS-REQ-035: The system shall not require a homing sequence at startup.

8.0 System Interface Requirements

SYS-REQ-036: The system shall implement UART as the interface for user command input.
SYS-REQ-037: The system shall implement digital control outputs to drive the DC motor via a compatible motor driver.
SYS-REQ-038: The system shall implement one ADC channel as the interface for potentiometer position feedback.
SYS-REQ-039: The system shall use GPIO output signals for LED control.
[Implied] SYS-REQ-040: The system shall support PWM timer output for motor enable or speed control, even if full variable speed is not required.

9.0 Constraints and Assumptions

SYS-REQ-041: Only one flap actuator and one DC motor are present and controlled.
SYS-REQ-042: Only one command at a time will be handled; command queuing is not required.
SYS-REQ-043: The system operates locally and does not utilize any vehicle network communication (e.g., CAN, LIN).
SYS-REQ-044: Potentiometer ADC ranges are considered fixed for the duration of use and defined in configuration.
SYS-REQ-045: Hardware is assumed to function correctly during operation (no advanced diagnostics needed).
[Implied] SYS-REQ-046: The system shall avoid dynamic memory allocation in software.

10.0 Non-Functional Requirements

10.1 Responsiveness Expectations
SYS-REQ-047: The user should observe that commands are acted on promptly, with minimal perceivable delay.
[Implied] SYS-REQ-048: No hard real-time deadlines are specified unless stated in requirements; responsiveness must feel adequate to a human user.

10.2 Error Handling and Edge Cases
SYS-REQ-049: The system shall stop the motor and avoid movement if ADC feedback is out of expected range.
SYS-REQ-050: The system shall continue safe operation if the motor fails to reach the requested position (no retry or timeout is strictly required).
SYS-REQ-051: Invalid UART commands shall be ignored safely.

10.3 Resource Constraints
SYS-REQ-052: The system software shall be lightweight and operate within the memory and compute limits of the target microcontroller.
SYS-REQ-053: The system shall avoid unbounded loops or waiting.

10.4 Maintainability and Modularity
SYS-REQ-054: The system’s software design shall support a clear separation between key functional modules (e.g., motor control, feedback processing, command handling, indication).
SYS-REQ-055: The system design and requirements shall facilitate future maintainability and ease of understanding for learners.

10.5 Testability
SYS-REQ-056: Observability for all key behaviors shall be provided via LEDs and UART interface.
SYS-REQ-057: The system shall support both manual and script-based testing through UART command input and visual LED feedback.


ARCHITECTURE-RELEVANT CONSIDERATIONS DERIVED FROM SYSTEM REQUIREMENTS

- The system is simple, with no need for concurrency or complex interleaving of unrelated tasks.
- All external interactions (UART, LEDs, ADC, Motor Driver) are direct and synchronous from the microcontroller.
- Control flow is simple: one command at a time, one flap, no parallel activities.
- There are minimal expandability requirements (single actuator; local-only control).
- The system does not require a defined execution or scheduling model, nor does it require an RTOS.
- Testing, maintainability, and separation of concerns should be visible and traceable in the software design.

The HVAC Flap Actuator Software executes on a microcontroller and is responsible for receiving user commands via UART, processing flap position feedback from a potentiometer (via ADC), driving a DC motor through GPIOs, and providing status indication via LEDs. The software translates user commands into discrete flap positions, manages motor and feedback interaction, and ensures robust operation within the system's educational and demonstration context—all without architectural or execution model assumptions.

# Software Architecture for HVAC Flap Actuator System

## 1. Architecture Styles Considered

- **Monolithic**: All functionality implemented in a single large block with direct hardware interactions.
- **Layered**: Separation between hardware abstraction, application logic, and interfaces.
- **Component-Based**: Organized as discrete software units/modules each with a clear responsibility and explicit interfaces.

### Evaluation Against Criteria
| Criteria             | Monolithic         | Layered               | Component-Based      |
|---------------------|-------------------|-----------------------|---------------------|
| System Complexity   | Low-Moderate      | Moderate              | Low-Moderate (for this system)|
| Hardware Interaction| Direct            | Wrapper/Isolated      | Explicit Interfaces |
| Testability         | Poor/Fair         | Good                  | Excellent           |
| Maintainability     | Poor/Fair         | Good                  | Excellent           |
| ASPICE Compliance   | Weak              | Good                  | Strong              |

**Justification:**
Given ASPICE Level-3 expectations (traceability, modularity, testability, maintainability) and explicit requirements (e.g., SYS-REQ-054, SYS-REQ-055 for clear module separation), a **Component-Based Architecture** is selected. This ensures feature separation, supporting educational/review needs, and matches the indicated (non-layered, non-monolithic) philosophy from system/software requirements.

### Unit Arrangement
- User input reaches the Command Handler via the UART Interface.
- Command Handler interprets and validates input, passing actions to Position Control.
- Position Control compares states, orchestrates feedback/motor/LEDs.
- Motor Control provides abstracted access to driver (GPIO/PWM), ensuring safety and state per requirements.
- Feedback Handling abstracts ADC/position mapping.
- LED Indicate Unit drives power/status and position LEDs.

## Software Unit: UART Interface

1. Responsibilities
- Responsible for initializing and managing UART hardware, receiving user input (target flap position commands) and providing a raw command to the Command Handler.
- Not responsible for interpreting, parsing, or validating the meaning/content of received commands.

2. Internal Data Design
- UART RX buffer (fixed-size, statically allocated)
- Flags for RX completion/error/overflow (single-command at a time logic enforced)

3. State Machine
- No explicit state machine. RX events trigger callback/flag, data is serviced by Command Handler.

4. Algorithms and Control Flow
- On RX interrupt or polling, store incoming byte(s) until termination (e.g. newline or max length).
- On receive completion, raise RX-complete flag.
- Ignore data if previous command not yet consumed (enforce single-command-at-a-time).
- RX buffer is cleared on consumption by Command Handler.

5. Interfaces (APIs)
- Public: `UART_Init(void)`, `UART_ReadCmd(buffer,len)`, `UART_ClearBuffer(void)`
- Required: Hardware UART driver (no software scheduling).
- Error reporting: Overflow flag, RX error/timeout flag (cleared on Command Handler read).

6. Error Handling
- Input overruns set overflow flag and clear buffer.
- Protocol errors (framing, parity, etc.) set error flag; no retries or echoes.
- Only deliver data if command buffer is valid/complete and no errors occurred.

7. Resource and Timing Considerations
- Event-driven (on RX interrupt or polling).
- Non-reentrant (single buffer, not thread-safe).
- Worst-case: one full buffer service per valid RX event.

8. Traceability to SWE Requirements: SWE-REQ-001, SWE-REQ-020, SWE-REQ-042

---

## Software Unit: Command Handler Unit

1. Responsibilities
- Parse, validate, and filter user commands received from UART Interface.
- Only accepts integer commands within valid flap range; all others rejected silently.
- Not responsible for hardware access, position calculation, or system state management.

2. Internal Data Design
- Internal variable for parsed target position (integer)
- Validity flag, error state
- Config parameter: valid flap position range (min/max)

3. State Machine
- No explicit state machine.
- Control flow is command-driven: on valid command, triggers event to Position Control.

4. Algorithms and Control Flow
- On new UART command: parse string to integer.
- Validate: check in-range, integer format.
- If valid, update target position and notify Position Control Unit.
- If invalid, discard, clear buffer, and set error flag (no user indication).

5. Interfaces (APIs)
- Public: `CMD_ParseAndValidate(input)`, `CMD_GetTargetPosition(void)`, `CMD_Consume(void)`
- Required: UART Interface, Position Control Unit API (callback/event).

6. Error Handling
- Invalid string, out-of-range, or unparseable: discard and reset.
- On any error, set error state (for observability/testing).
- No response or error message sent to user.

7. Resource and Timing Considerations
- Event-driven by UART Interface.
- Not re-entrant (statics used for command-in-progress).
- Executed once per valid command input.

8. Traceability: SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004, SWE-REQ-005, SWE-REQ-034, SWE-REQ-042, SWE-REQ-043

---

## Software Unit: Position Control Unit

1. Responsibilities
- Main orchestrator: receives target position, checks current flap position (from Feedback), decides movement and safety actions, invokes Motor and LED units.
- Does not directly access UART or hardware drivers; relies on sub-unit APIs.

2. Internal Data Design
- Internal state: current flap position, target flap position
- Command valid/active flag
- Configurable: permitted position range, thresholds

3. State Machine
- States: Idle, MoveRequest, Error
- Events: ValidCommandReceived, PositionReached, FeedbackError
- Transitions: Idle->MoveRequest (command), MoveRequest->Idle (target reached), Any->Error (feedback out-of-range)
- Entry/exit actions: On Error, stop motor, indicate idle; On PositionReached, disable motor.

4. Algorithms and Control Flow
- On command: compare current position vs target.
- If different, determine direction, invoke Motor Control for required movement.
- Continuously check feedback until match or error.
- If position out of range or feedback invalid, enter Error state (motor off, error-indicate LED via LED unit).
- Clamp target position if needed.

5. Interfaces (APIs)
- Public: `POS_SetTarget(int tgt)`, `POS_Process(void)`, `POS_OnFeedbackUpdate(int pos)`
- Requires: Motor Control Unit, Feedback Handling Unit, LED Indicate Unit

6. Error Handling
- If feedback invalid, stop motor, set error state.
- Ignore and idle on no/invalid command.

7. Resource and Timing Considerations
- Invoked per command, feedback update, or timer tick (non-scheduled, as per architecture).
- Non-reentrant; maintains state internally.
- Worst-case: One command and feedback update at a time.

8. Traceability: SWE-REQ-006, SWE-REQ-007, SWE-REQ-008, SWE-REQ-009, SWE-REQ-010, SWE-REQ-025, SWE-REQ-026, SWE-REQ-027, SWE-REQ-028, SWE-REQ-029, SWE-REQ-033, SWE-REQ-035, SWE-REQ-037, SWE-REQ-039

---

## Software Unit: Motor Control Unit

1. Responsibilities
- Accept movement commands from Position Control and apply to output signals (direction, enable) for DC motor driver.
- Provides motor on/off, direction, stop upon position match or error.
- Not responsible for safety logic or direct user command reception.

2. Internal Data Design
- Output signal state variables: direction, enable
- Config: GPIO/PWM mapping (static), enable polarity

3. State Machine
- No explicit state machine.
- Control consists of discrete signal outputs based on position delta and enable condition.

4. Algorithms and Control Flow
- On command: set motor direction, assert enable, update outputs.
- On stop or error: de-assert enable, clear outputs.
- PWM control for enable as required (no dynamic allocation).
- All outputs atomic, no timed pulses or ramping logic.

5. Interfaces (APIs)
- Public: `MOTOR_SetDirection(enum dir)`, `MOTOR_Enable(bool)`, `MOTOR_Stop(void)`
- Required: Position Control Unit calls.

6. Error Handling
- On invalid input, reject and disable motor (safe off).
- Redundant stop if any contract broken.

7. Resource and Timing Considerations
- Invoked on Position Control command change.
- Not re-entrant; statics for output control.

8. Traceability: SWE-REQ-011, SWE-REQ-012, SWE-REQ-013, SWE-REQ-022, SWE-REQ-024, SWE-REQ-035, SWE-REQ-039, SWE-REQ-040

---

## Software Unit: Feedback Handling Unit

1. Responsibilities
- Acquire analog feedback (ADC), apply mapping to discrete position, check valid range, report to Position Control.
- Not responsible for state management, only for signal processing and conversion.

2. Internal Data Design
- ADC raw value buffer
- Discrete position output
- Static config: ADC-to-position mapping, valid threshold ranges
- Error flag for out-of-range

3. State Machine
- No explicit state machine. Triggered by timer/ADC complete event.

4. Algorithms and Control Flow
- On read: sample ADC, map value to position using static table.
- Check range, set error if value out-of-bounds.
- Provide current position via API.

5. Interfaces (APIs)
- Public: `FEEDBACK_ReadPosition(void)`, `FEEDBACK_IsValid(void)`
- Required: ADC hardware driver

6. Error Handling
- Out-of-range triggers error flag; reports error to Position Control.
- Never returns unvalidated data.

7. Resource and Timing Considerations
- Event-driven or periodic (not scheduled here).
- Not re-entrant.

8. Traceability: SWE-REQ-014, SWE-REQ-015, SWE-REQ-016, SWE-REQ-021, SWE-REQ-032, SWE-REQ-033, SWE-REQ-035

---

## Software Unit: LED Indicate Unit

1. Responsibilities
- Provide power/status LED and position-indicate LED control.
- Each command/request from Position Control results in atomic LED update (only one position LED is ON at a time).

2. Internal Data Design
- LED output state variables
- Config: LED-to-position mapping, polarity

3. State Machine
- No explicit state machine; atomic update per request.

4. Algorithms and Control Flow
- On command: turn OFF all position LEDs, set power/status LED ON, set only indicated position LED ON.
- On error: may set error-indicate LED as required for safe state.
- Update only on change (minimize flicker).

5. Interfaces (APIs)
- Public: `LED_SetPosition(int pos)`, `LED_SetStatus(enum status)`
- Required: Position Control Unit

6. Error Handling
- If position invalid, clear all position LEDs and keep status LED amber (for error/idle).
- Never drives more than one position LED at once.

7. Resource and Timing Considerations
- Invoked by Position Control 'on change.'
- Not re-entrant.

8. Traceability: SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-023, SWE-REQ-035, SWE-REQ-042
