# 1.0 System Overview
The HVAC Flap Actuator system is a microcontroller-based prototype intended for learning and process demonstration. Its purpose is to electrically move and hold an air flap in discrete positions for automotive HVAC using a DC motor, potentiometer position feedback, UART-based user commands, and LED indicators. All control occurs on-board, with no vehicle network link. Correctness, usability, and clarity are prioritized over production-grade complexity.

# 2.0 Flap Position Control Requirements
SYS-REQ-001: The system shall allow a user to select a target flap position via UART command.
SYS-REQ-002: The system shall compare the current flap position with the target position at all times.
SYS-REQ-003: The system shall move the flap toward the target position when a new valid target command is received.
SYS-REQ-004: The system shall stop the motor once the flap reaches the commanded target position.
SYS-REQ-005: The system shall hold the flap at its target position after movement is complete.
SYS-REQ-006 [Implied]: The system shall define and store exact ADC value ranges representing each discrete flap position.
SYS-REQ-007 [Implied]: The system shall not require a homing sequence at startup.

# 3.0 Motor Control Requirements
SYS-REQ-008: The system shall drive the motor in the direction required to reach the target flap position.
SYS-REQ-009: The system shall control motor direction using dedicated GPIO pins.
SYS-REQ-010: The system shall enable and disable the motor via GPIO or PWM signal.
SYS-REQ-011: The system shall turn the motor off as soon as the flap reaches the target position.
SYS-REQ-012 [Implied]: The system shall prevent simultaneous activation of both motor directions.

# 4.0 Position Feedback Acquisition and Processing
SYS-REQ-013: The system shall acquire position feedback from a potentiometer connected to an ADC channel.
SYS-REQ-014: The system shall sample the ADC at intervals sufficient to detect position changes promptly.
SYS-REQ-015: The system shall map ADC readings to logical position indices (0 through 5) using pre-defined value ranges.
SYS-REQ-016 [Implied]: The system shall ignore ADC values outside the defined potentiometer range and not move the motor in those cases.

# 5.0 User Command Interface Requirements
SYS-REQ-017: The system shall receive user commands via a UART serial interface.
SYS-REQ-018: Each command shall specify a numeric target position in the allowed range (0–5).
SYS-REQ-019: The system shall validate the received command as a legal flap position command.
SYS-REQ-020: The system shall ignore invalid or out-of-range commands and not respond to the user in such cases.

# 6.0 Status Indication Requirements
SYS-REQ-021: The system shall energize a dedicated power/status LED as long as it is powered and initialized.
SYS-REQ-022: The system shall indicate the current detected flap position by activating exactly one corresponding green LED.
SYS-REQ-023: Only one green LED shall be ON at any given time to indicate the flap position.
SYS-REQ-024 [Implied]: LED indications shall update promptly if the detected position changes.

# 7.0 System Behavioral Requirements
SYS-REQ-025: On power-up, the system shall initialize all peripherals (ADC, UART, PWM, GPIO).
SYS-REQ-026: On power-up, the system shall ensure the motor is off.
SYS-REQ-027: On power-up, the system shall read the potentiometer to determine the current flap position.
SYS-REQ-028: The system shall remain idle, waiting for valid user command, when no new input arrives.
SYS-REQ-029: The system shall proceed to move the flap towards a target when a valid command is received.
SYS-REQ-030: When the flap is at the target position, the system shall keep the motor off until further user command.
SYS-REQ-031: Invalid input or operational exceptions (e.g., ADC out of range) shall be handled by stopping the actuator and not moving the flap.

# 8.0 System Interface Requirements
SYS-REQ-032: The system shall interact with a PC over UART for command input only.
SYS-REQ-033: The system shall drive the DC motor through a motor driver module (L298N) via GPIO and/or PWM outputs.
SYS-REQ-034: The system shall receive flap position feedback via an ADC channel connected to a potentiometer.
SYS-REQ-035: The system shall drive each LED via a dedicated GPIO output.

# 9.0 Constraints and Assumptions
SYS-REQ-036: Only a single flap and single DC motor are controlled.
SYS-REQ-037: Only one user command is processed at a time; no command queueing.
SYS-REQ-038: No dynamic or in-field calibration is required; flap position mapping is software-fixed.
SYS-REQ-039: No CAN, LIN, or vehicle-wide bus is present or used.
SYS-REQ-040: The hardware and all connections are assumed functional for normal operation.

# 10.0 Non-Functional Requirements
## 10.1 Responsiveness Expectations
SYS-REQ-041: The system shall process user commands and move the flap promptly (perceived as nearly instantaneous response).
SYS-REQ-042 [Implied]: No guaranteed timing or deadlines are imposed beyond practical responsiveness.

## 10.2 Error Handling and Edge Cases
SYS-REQ-043: Invalid UART commands shall be ignored safely with no side-effects.
SYS-REQ-044: ADC values outside the valid range shall disable the motor until a valid range is detected.
SYS-REQ-045 [Implied]: No extensive diagnostics or error reporting is implemented.

## 10.3 Resource Constraints
SYS-REQ-046: The implementation shall avoid dynamic memory allocation.
SYS-REQ-047: The solution shall have predictable, bounded runtime behavior appropriate for a microcontroller.

## 10.4 Maintainability and Modularity
SYS-REQ-048: The code and configuration shall be clear, modular, and easy for engineers to understand or modify.

## 10.5 Testability
SYS-REQ-049: All system functions shall be observable via LED status or UART-controlled actuation.
SYS-REQ-050: The system shall support manual and script-based testing through UART commands and LED/motor observation.

# Architecture-Relevant Considerations Derived from System Requirements
- All core system behaviors are sequential and command/response oriented; no requirement for multitasking or concurrent execution exists.
- UART, ADC, and GPIO/PWM control are each isolated functional domains, simplifying modularization.
- No requirement for advanced network or diagnostics simplifies the overall control and communication complexity.
- Expandability would require additional interfaces, but the current system restricts scope to a single actuator, single channel.
- Requirements avoid any execution or scheduling assumptions: event-driven or polling are both allowable (implementation detail).
- System is highly observable by design (for learning), requiring explicit traceable mapping per requirement and simple interface cross-communication only.

# 1.0 Software Scope and Responsibility
The software for the HVAC Flap Actuator System is responsible for interpreting user commands received over UART to control a DC motor-driven air flap. The software translates discrete user requests into actuator movement, acquires feedback via ADC from a potentiometer, and drives position and status LEDs to indicate system state. Its primary responsibilities are:
- Receiving and validating user commands
- Mapping target positions to ADC ranges
- Controlling the DC motor via GPIO/PWM to reach and maintain target positions
- Processing potentiometer feedback
- Providing feedback/observability to the user through LEDs
- Ensuring predictable, bounded, and observable behavior on a microcontroller

# Software Architecture: HVAC Flap Actuator System (Branch: demo-43b)

## 1. Architecture Derivation and Style Evaluation

### Candidate Styles Considered
- **Monolithic**: All logic in a single control loop or function block/lightweight superloop.
- **Layered**: Separates interface, control logic, hardware abstraction, and low-level drivers.
- **Component-Based**: Segments by major domain function, with well-defined interfaces between components (e.g., Command Handler, Motor Control, Feedback Processor, Indication Controller).

### Evaluation Criteria
- **System Complexity**: Simple, single-actuator scope; no multitasking or dynamic allocation.
- **Hardware Interaction**: Requires explicit demarcation – UART, GPIO/PWM, ADC; isolated hardware domains.
- **Testability**: Must observe all functions via UART/LED; clear-state separation needed.
- **Maintainability**: System should be easy to extend to new feedback/indication strategies or alternate commands.
- **ASPICE Level-3**: Traceable, modular, transparent interfaces; separation of responsibilities without unneeded complexity.

### Selected Style & Justification
A **component-based, layered architecture** is chosen, combining clear logical separation (by domain responsibility) with a simple control and interface flow. This offers modularity (tracing to SWE.1), testability, and engineering clarity, avoiding the downsides of a flat monolith (poor traceability, hard to maintain) or a full deep-layered approach (overkill for scope).

# Software Low Level Design (SWE.3): HVAC Flap Actuator System

---
Each section strictly follows ASPICE SWE.3 and the provided architecture. No new units, no architecture/scheduling changes, and no C code is present. MISRA embedded C assumptions, no dynamic allocation.

## Software Unit: User Command Handler

### 1. Responsibilities
- Receives position commands via UART, validates command syntax and range (SWE-REQ-001, SWE-REQ-002)
- Reports valid/invalid status to control logic
- Excludes: Does NOT process command queuing, scheduling, or interpret command context; does not execute actuator or low-level motor logic

### 2. Internal Data Design
- `last_cmd_position` (uint8_t): Stores most recent valid command position [0..5]
- `cmd_valid` (bool): Flag indicating validity of current UART command
- No persistent/dynamic data
- Configuration: position min/max constants

### 3. State Machine
- States: WAIT_CMD, VALIDATE
- Events: UART RX, Data Ready
- Transitions: WAIT_CMD→VALIDATE (on UART RX); VALIDATE→WAIT_CMD (on validation complete)
- Entry: WAIT_CMD (power-on)
- Exit: on valid command, notifies Position Control Logic

### 4. Algorithms and Control Flow
- On UART RX:
  - Parse input
  - Check for valid numeric [0..5]
  - If valid: update `last_cmd_position`, set `cmd_valid`=true
  - Else: set `cmd_valid`=false
- Hand over valid (position, status) to Position Control Logic

### 5. Interfaces (APIs)
- Provided:
  - `get_last_cmd_position(void) -> uint8_t`
  - `is_cmd_valid(void) -> bool`
- Required:
  - `uart_receive(buffer, len)` (from UART HW/driver)
- Error: Return/copy zeros or error flag if UART signal loss

### 6. Error Handling
- Ignore commands outside [0..5] (SWE-REQ-003, SWE-REQ-033)
- On UART framing/parity error: ignore
- Invalid: set `cmd_valid`=false

### 7. Resource/Timing
- Invoked on UART interrupt or polling
- WCE: < 1ms/command
- Not re-entrant (single-command design)

### 8. Traceability
- SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004, SWE-REQ-033

---

## Software Unit: Position Control Logic

### 1. Responsibilities
- Compares `last_cmd_position` to feedback position
- Requests movement or idle to Motor Ctrl Logic
- Manages actuation state
- Excludes: no direct hardware access; no command parsing

### 2. Internal Data Design
- `target_position` (uint8_t, set by User Cmd Handler)
- `current_position` (uint8_t, from Feedback Acquisition)
- `moving_status` (bool)

### 3. State Machine
- States: IDLE, MOVING
- Events: New Command, At Target, Error
- Transitions: IDLE→MOVING (on new valid command && not at target)
                 MOVING→IDLE (on reaching target or invalid)
- No entry/exit logic beyond setting/clearing `moving_status`

### 4. Algorithms and Control Flow
- If `cmd_valid` & `target_position` != `current_position`: 
  - Trigger move (call Motor Control)
  - Update `moving_status`
- If at target: 
  - Request Motor Ctrl to stop
  - Update LEDs (Status/Indication)

### 5. Interfaces (APIs)
- Provided:
  - `position_ctrl_step(void)`
  - `get_moving_status(void)`
- Required:
  - `get_last_cmd_position` (User Command Handler)
  - `get_current_position` (Feedback Acquisition)
  - `motor_control_move(dir)` (Motor Control)
- Error: On error or no valid feedback, requests stop

### 6. Error Handling
- Ignores command unless `cmd_valid`
- On loss of feedback: issues safe stop
- Never issues simultaneous conflicting commands

### 7. Resource/Timing
- Invoked on command/feedback update
- WCE: < 2ms
- Not re-entrant

### 8. Traceability
- SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-008, SWE-REQ-029

---

## Software Unit: Motor Control

### 1. Responsibilities
- Drives GPIO/PWM pins for motor direct/enable
- Guarantees no simultaneous forward/reverse
- Excludes: Does not parse/apply logic for state, position, or user commands

### 2. Internal Data Design
- `motor_direction` (enum: FWD/REV/OFF)
- `motor_enabled` (bool)
- `hw_error_flag` (bool)

### 3. State Machine
- No explicit state machine; always invoked on request
- Each actuation request is fully handled and idempotent

### 4. Algorithms and Control Flow
- On move request:
  - If direction valid and not `motor_enabled`: enable, set direction
  - If stop request/at target: disable
  - Never allow forward & reverse active
- Checks and clears errors each step

### 5. Interfaces (APIs)
- Provided:
  - `motor_control_move(direction)`
  - `motor_control_stop(void)`
- Required:
  - GPIO/PWM HW drivers
- Error: Deactivate all motor pins if error

### 6. Error Handling
- On conflict or error: set `hw_error_flag`, disable

### 7. Resource/Timing
- Invoked per actuation request
- WCE: <1ms
- Not re-entrant

### 8. Traceability
- SWE-REQ-010, SWE-REQ-011, SWE-REQ-012, SWE-REQ-022

---

## Software Unit: Feedback Acquisition & Processing

### 1. Responsibilities
- Samples ADC, validates and filters data
- Maps ADC reading to position index [0..5]
- Passes current_position to Position Control Logic and Indication
- Excludes: No direct action on commands

### 2. Internal Data Design
- `adc_raw_value` (uint16_t)
- `position_index` (uint8_t, 0–5)
- Configuration: ADC min/max/range table

### 3. State Machine
- No explicit state machine
- Sample → Map → Publish flow

### 4. Algorithms and Control Flow
- On ADC sample:
  - Validate (in range)
  - If valid: map to index (using lookup table)
  - Else: flag error, suppress position updates

### 5. Interfaces (APIs)
- Provided:
  - `get_current_position(void)`
  - `adc_feedback_update(void)`
- Required:
  - ADC HW read

### 6. Error Handling
- Invalid ADC: flag error, do not update
- Out of range: lock system in current safe state

### 7. Resource/Timing
- Invoked on periodic or event sample
- WCE: <2ms/sample
- Not re-entrant

### 8. Traceability
- SWE-REQ-013, SWE-REQ-014, SWE-REQ-015, SWE-REQ-016, SWE-REQ-021

---

## Software Unit: Status/LED Indication

### 3. State Machine

### 6. Error Handling

### 7. Resource/Timing
- Invoked on feedback/position change
- WCE: <1ms

### 8. Traceability
- SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-023
