# 1.0 System Overview

The HVAC flap actuator system is a microcontroller-based embedded system that controls a DC motor-driven air flap in a manner similar to a car’s HVAC system. Its purpose is to allow user command-based selection of discrete air flap positions for air mixing or direction, and to provide clear position feedback via LEDs for demonstration and learning purposes. The system supports UART-based commands for flap position selection, uses potentiometer feedback for position determination, and is implemented as a proof-of-concept or prototype rather than a production automotive ECU.

---

# 2.0 Flap Position Control Requirements

**SYS-REQ-001**: The system shall allow the user to command a discrete flap position within the supported range via a UART interface.  
**SYS-REQ-002**: The system shall move the flap to the position corresponding to the latest received valid command.  
**SYS-REQ-003**: The system shall continuously compare the current flap position to the target position while the flap is moving.  
**SYS-REQ-004**: The system shall stop the flap motor when the current position matches the target position.  
**SYS-REQ-005**: The system shall hold the flap at the commanded position until a new valid command is received.  
**SYS-REQ-006**: [Implied] The system shall not react to commands requesting positions outside the supported range.

---

# 3.0 Motor Control Requirements

**SYS-REQ-007**: The system shall drive the DC motor in a direction that moves the flap towards the target position.  
**SYS-REQ-008**: The system shall control the motor direction using two dedicated GPIO outputs.  
**SYS-REQ-009**: The system shall enable or disable the motor using a PWM signal for speed control.  
**SYS-REQ-010**: The system shall disable (stop) the motor when the target position is reached or if an invalid condition is detected.  
**SYS-REQ-011**: The system shall ensure the motor is OFF immediately upon power-up and initialization.  
**SYS-REQ-012**: [Implied] The system shall avoid reversing the motor direction while the flap is still moving towards a previously commanded position.

---

# 4.0 Position Feedback Acquisition and Processing

**SYS-REQ-013**: The system shall acquire the current flap position by sampling the voltage from the potentiometer using an ADC channel.  
**SYS-REQ-014**: The system shall map ADC values to a set of discrete logical flap positions as defined in the software configuration.  
**SYS-REQ-015**: The system shall periodically update the flap position feedback by sampling the potentiometer at defined intervals.  
**SYS-REQ-016**: The system shall disregard ADC readings that fall outside the range defined for valid flap positions.  
**SYS-REQ-017**: [Implied] The system shall process and handle ADC noise or possible fluctuations in readings to avoid false position detection.

---

# 5.0 User Command Interface Requirements

**SYS-REQ-018**: The system shall accept user commands in the form of single numeric values received over UART, each representing a target flap position.  
**SYS-REQ-019**: The system shall ignore and not act upon UART commands that do not correspond to valid position values.  
**SYS-REQ-020**: The system shall not transmit any acknowledgment or error message in response to invalid commands.  
**SYS-REQ-021**: The system shall process only one user command at a time; concurrent commands shall not be processed.  
**SYS-REQ-022**: [Implied] The system shall validate received UART command data for proper format prior to interpretation.

---

# 6.0 Status Indication Requirements

**SYS-REQ-023**: The system shall use a power/status LED to indicate when the system is powered ON and initialized.  
**SYS-REQ-024**: The system shall use discrete green LEDs to indicate the current logical flap position; exactly one green LED shall be ON at a time.  
**SYS-REQ-025**: The system shall update flap position LEDs immediately upon any position change.  
**SYS-REQ-026**: [Implied] The system shall ensure that no more than one position LED is illuminated, regardless of transient states.

---

# 7.0 System Behavioral Requirements

**SYS-REQ-027**: At power-up, the system shall initialize all microcontroller peripherals required for operation (ADC, UART, GPIO, PWM).  
**SYS-REQ-028**: At power-up, the system shall read and store the current flap position using the potentiometer.  
**SYS-REQ-029**: At power-up and after initialization, the system shall ensure the motor is in the OFF state.  
**SYS-REQ-030**: While idle, the system shall wait for valid user commands and hold the flap in its current position.  
**SYS-REQ-031**: During normal operation, the system shall move the flap in response to valid user commands, monitoring progress via position feedback.  
**SYS-REQ-032**: Upon reaching the commanded position, the system shall stop the motor and indicate position status via LEDs.  
**SYS-REQ-033**: The system shall ignore invalid user commands or feedback values without generating warnings or errors.  
**SYS-REQ-034**: [Implied] If ADC feedback is out of range, the system shall stop the motor and indicate a safe state via status LEDs.

---

# 8.0 System Interface Requirements

**SYS-REQ-035**: The system shall support the following hardware interfaces:
- UART: user command input from PC
- ADC: potentiometer position sensing
- GPIO: motor control and LED outputs
- PWM: motor enable and speed control via timer  
**SYS-REQ-036**: The system shall interface with a motor driver (e.g., L298N) to drive the DC motor.  
**SYS-REQ-037**: The system shall support a USB-to-UART hardware interface for PC connectivity.  
**SYS-REQ-038**: [Implied] The system shall not implement or use CAN/LIN/vehicle network communication.

---

# 9.0 Constraints and Assumptions

**SYS-REQ-039**: Only one flap and only one motor are present and controlled by this system.  
**SYS-REQ-040**: Only a single user may command the system at any time.  
**SYS-REQ-041**: ADC calibration values for position mapping are fixed in software.  
**SYS-REQ-042**: Hardware (motor, driver, potentiometer) is assumed to be functioning correctly for this demonstration system.  
**SYS-REQ-043**: [Implied] System-level timing and execution requirements are limited to those needed for functional responsiveness (see 10.0).

---

# 10.0 Non-Functional Requirements

## 10.1 Responsiveness Expectations

**SYS-REQ-044**: The system shall process user commands and respond with observable behavior (flap movement) within a timeframe that feels immediate to a human user.  
**SYS-REQ-045**: [Implied] The system shall perform position monitoring and feedback frequently enough to ensure accurate and timely motor control.

## 10.2 Error Handling and Edge Cases

**SYS-REQ-046**: The system shall safely ignore commands that are invalid or out of range.  
**SYS-REQ-047**: If ADC readings are out of expected range, the system shall stop the motor and hold position.  
**SYS-REQ-048**: The system shall not enter fault or diagnostic modes in response to communication or hardware errors; the prototype is not required to implement recovery mechanisms.

## 10.3 Resource Constraints

**SYS-REQ-049**: The system shall avoid using dynamic memory allocation.  
**SYS-REQ-050**: The system shall not exceed the resource limitations of the STM32F407G-DISC1 platform.

## 10.4 Maintainability and Modularity

**SYS-REQ-051**: The system shall separate motor control, user command handling, position feedback, and status indication in distinct software modules to the extent reasonable.  
**SYS-REQ-052**: The system shall be designed for clarity and ease of modification by learners and engineers.

## 10.5 Testability

**SYS-REQ-053**: The system shall support manual testing using UART command injection from a PC and observation of LEDs and motor output.  
**SYS-REQ-054**: The system shall support script-based testing using UART and observable outputs.

---

# Architecture-Relevant Considerations Derived from System Requirements

- The system manages a single DC motor and a single actuator, simplifying control logic.
- All external interaction is local: UART for input, direct GPIO/ADC for hardware interfaces, and LED feedback.
- The system does not need complex concurrency, safety, or communication protocols (e.g., no CAN/LIN; no concurrent users/commands).
- System behavioral complexity is low, focusing on forward/reverse motor movement, discrete position targeting, and direct feedback.
- Expansion is possible by replicating module patterns (e.g., for more actuators), but current requirements assume only one of each hardware element.
- Modular separation of command, motor, feedback, and indication handling is encouraged to support learning/testability.

# Software Architecture – HVAC Flap Actuator System

## 1. Architecture Style Analysis

### Candidate Architecture Styles Considered

| Candidate        | Pros                                                                                  | Cons                                   | Suitability (per requirements)                                          |
|------------------|---------------------------------------------------------------------------------------|----------------------------------------|-------------------------------------------------------------------------|
| Layered          | Clear separation of concerns, supports maintainability and testability, lightweight   | Overhead may be unnecessary for simple system | Good, but adds unnecessary complexity given the monolithic nature       |
| Component-based  | Encapsulates hardware abstraction, logic, and interface; easy to maintain             | Adds extra modularity; not needed for single-function, single-flap systems | Overkill given explicit single-use/single-flap design                   |
| Monolithic (Decomposed into Logical Units) | Minimal overhead, matches simple, single-control function; responsibilities can still be separated logically in code structure | Care needed to preserve modifiability | Best fit: explicitly called for by requirements; matches ASPICE L3 separation/goals for lightweight demo |

### Evaluation and Choice

- **Complexity**: Requirements explicitly specify a single flap actuator, no concurrent activities, and a simple command-action-control pattern. No expansion, concurrent tasks, or distributed components are needed.
- **Hardware Interaction**: All interactions are direct, tightly-coupled, and local, favoring direct, simple abstractions.
- **Testability**: Requirements emphasize testability (UART, LEDs, observable motor movement); architecture should allow simple functional unit separation.
- **Maintainability**: Architecture must be easily understandable/traceable for educational purposes.
- **ASPICE L3 Alignment**: Separation of concerns, traceability, and well-documented interfaces required, but forbids unnecessary indirection.

**Chosen Architecture Style:**  
“A monolithic architecture logically decomposed into clearly separated software units (modules), where each unit maps to a set of responsibilities (command handling, position sensing, control, indication, etc.). No physically separate components/processes are introduced given the explicitly single-function, single-flap, single-thread requirements. This style provides traceability, logical separation, and maintainability without unnecessary overhead.”

### Justification

- Every alternative either does not add value (given constraints), or would contradict ASPICE L3's “no overengineering” demo philosophy for this prototype.
- This chosen style cleanly separates concerns and responsibilities, aiding testability and maintenance, while supporting educational demonstration (per requirements).

### Execution Model / Scheduling

> “No explicit execution model or scheduling policy is mandated by the requirements at this stage.”
- Requirements permit (and prototype philosophy prefers) a simple main-loop (“super-loop”) in which each software unit is called in sequence.
- No RTOS, ISRs, threads, or concurrency are needed; timing and ordering are defined by main loop, which periodically checks for UART input, evaluates position/movement, and updates LEDs.
- Any compliant single-threaded, event-driven, or polling architecture is permitted. Design remains agnostic at this level.

# Software Low-Level Design (SWE.3) – HVAC Flap Actuator System

This document provides a detailed, atomic, implementation-neutral low-level design for each software unit defined in the Software Architecture (sw-arch/sw-arch.txt, branch: new-b2) and traceable to atomic Software Requirements (sw-reqs/sw-reqs.txt, branch: new-b2). No new units, scheduling definitions, or code are introduced per workflow constraints.

## Software Unit: Command Handler

### 1. Responsibilities
- Receives and parses UART flap position commands from user.
- Validates received command format, value, and range.
- Ensures only one command is processed at a time.
- Explicitly does NOT: handle physical UART driver setup/interrupts, initiate motor movement, manage system states directly.

### 2. Internal Data Design
- Buffer for received UART characters (fixed size, statically allocated char array)
- Command-parsing state (idle/receiving/complete)
- Last valid position command (uint8_t)
- Input validation flags (bool)

### 3. State Machine (if applicable)
- Simple command-receive state: IDLE → RECEIVING → COMPLETE/ERROR → IDLE
- Transitions on UART receive events or parse/validation result.
- No concurrency, no pre-emption.

### 4. Algorithms and Control Flow
- On new UART character: store in buffer
- If buffer matches expected command format: parse numeric, validate range (against config)
- If valid and only one command in process: set last_valid_command, clear buffer, signal to State Manager
- If invalid: ignore, clear buffer, stay IDLE
- Pseudocode:
  1. On UART RX:
     - If not currently processing, append char to buffer
     - If end of command or buffer full, parse and validate
     - If valid, set last_valid_command, raise new_cmd flag
     - Else, clear buffer

### 5. Interfaces (APIs)
- Public: receive_command(void), get_last_command(void), is_command_available(void)
- Uses: UART_Rx(), Config::get_pos_thresholds(), StateManager::set_state()
- Parameters: UART char; none for getters
- Returns: command value, status flag

### 6. Error Handling
- Invalid format: ignore, clear buffer
- Out-of-range: ignore, clear buffer
- Concurrent command: ignore new until complete
- Hardware UART error: no mitigation, handled by HW Abstraction

### 7. Resource and Timing Considerations
- Event-driven: invoked on UART RX event
- Short/constant buffer parse and validation time
- Non-blocking, non-reentrant

### 8. Traceability to SWE Requirements
- SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-042, SWE-REQ-044
- Maps to architecture unit: Command Handler

---

## Software Unit: State Manager

### 1. Responsibilities
- Maintains and transitions global device states: IDLE, MOVING, STEADY
- Guards against illegal transitions or parallel activities
- Explicitly does NOT: perform position readings, control the motor, directly parse UART data

### 2. Internal Data Design
- Enum: system_state_t (IDLE, MOVING, STEADY, ERROR)
- Previous state variable
- State change flag

### 3. State Machine (if applicable)
- Explicit State Machine: See enum above
- Events: new command, position reached, error detected
- Transitions: IDLE→MOVING (on new command), MOVING→STEADY (on target reached), STEADY→MOVING (on new command), any→ERROR (on detect error)
- Entry/exit actions: clear flags, signal Control Logic, update LEDs

### 4. Algorithms and Control Flow
- On new valid command: set state MOVING, signal Control Logic
- On target reached: set state STEADY, signal Indication
- On error: set state ERROR, signal all units
- Pseudocode: State transition table based on events

### 5. Interfaces (APIs)
- Public: set_state(state), get_state(void)
- Uses: CommandHandler::is_command_available(), ControlLogic::move_to_position(), StatusIndication::update_leds()
- Params: enum state; Returns: current state

### 6. Error Handling
- If illegal transition requested: ignore, log (if possible)
- Error detected: set ERROR state
- System reset required to recover from ERROR state

### 7. Resource and Timing Considerations
- Called by other units when their key event occurs
- Enum transitions only; trivial execution
- Not reentrant

### 8. Traceability to SWE Requirements
- SWE-REQ-005, SWE-REQ-025, SWE-REQ-026, SWE-REQ-046, SWE-REQ-047
- Maps to architecture unit: State Manager

## Software Unit: Position Sensing

### 1. Responsibilities
- Reads ADC value(s) from potentiometer (through HW Abstraction)
- Maps ADC value to logical flap positions using static thresholds
- Validates position within range; filters noise
- Explicitly does NOT: directly control ADC hardware, move the motor, handle user commands

### 2. Internal Data Design
