1.0 System Overview

The HVAC Flap Actuator System is a microcontroller-based prototype designed to control the position of a vehicle air flap used in HVAC (Heating, Ventilation, and Air Conditioning) applications. The system moves the flap to discrete positions on user command, monitors flap position using a potentiometer, drives a DC motor via an H-Bridge driver, indicates status through LEDs, and communicates using UART with a PC interface. This implementation demonstrates embedded control, user-commanded actuation, status feedback, and basic error handling for learning and software process demonstration purposes.

2.0 Flap Position Control Requirements

SYS-REQ-001: The system shall allow the user to select a target flap position through a UART command interface.
SYS-REQ-002: The system shall compare the commanded target flap position to the current position at the system level.
SYS-REQ-003: The system shall actuate the flap such that the flap is moved to the selected target position.
SYS-REQ-004: The system shall hold the flap in the achieved target position after movement is complete.
SYS-REQ-005: The system shall support at least 6 discrete flap positions as defined in the high-level requirements (positions 0 to 5).
SYS-REQ-006: The system shall allow repeated position commands and respond to each valid command.
SYS-REQ-007: [Implied] If the target position matches the current position, the motor shall not be activated.

3.0 Motor Control Requirements

SYS-REQ-008: The system shall control motor direction (clockwise/counterclockwise) to increase or decrease the flap position as needed.
SYS-REQ-009: The system shall enable or disable the DC motor as required to perform flap actuation.
SYS-REQ-010: The system shall stop the motor when the target flap position is reached.
SYS-REQ-011: [Implied] The system shall stop the motor if the current position signal is invalid or out-of-range.
SYS-REQ-012: [Implied] The system shall ensure the motor starts from a stopped state at power-up.

4.0 Position Feedback Acquisition and Processing

SYS-REQ-013: The system shall acquire flap position feedback using a potentiometer connected to an ADC channel.
SYS-REQ-014: The system shall convert/quantize ADC values to logical flap positions as defined by fixed ranges in software.
SYS-REQ-015: The system shall continuously monitor and process potentiometer/ADC feedback while powered.
SYS-REQ-016: [Implied] The system shall detect and handle ADC readings outside the defined calibration ranges.
SYS-REQ-017: [Implied] The system shall not require dynamic calibration or self-learning for position mapping.

5.0 User Command Interface Requirements

SYS-REQ-018: The system shall receive and process flap position commands (numeric 0–5) from a UART interface.
SYS-REQ-019: The system shall validate UART commands and only accept numeric values corresponding to supported positions.
SYS-REQ-020: The system shall ignore and not act on invalid commands; no acknowledgment or error message shall be sent in response to invalid commands.
SYS-REQ-021: [Implied] The system shall process one command at a time.
SYS-REQ-022: [Implied] The system shall not require advanced protocol or error correction on the UART interface.

6.0 Status Indication Requirements

SYS-REQ-023: The system shall control a status LED to indicate system power ON state.
SYS-REQ-024: The system shall use dedicated LEDs to indicate the current logical flap position.
SYS-REQ-025: The system shall ensure only one green LED corresponding to the current position is ON at any one time.
SYS-REQ-026: [Implied] The system shall update LEDs to reflect the detected (not just commanded) position.

7.0 System Behavioral Requirements

SYS-REQ-027: The system shall initialize all peripherals (ADC, UART, GPIO, PWM) on power-up.
SYS-REQ-028: The flap actuator motor shall remain OFF upon system power-up/initialization.
SYS-REQ-029: The system shall read and display the current flap position on LEDs at startup.
SYS-REQ-030: During idle operation (awaiting UART command), the system shall not cause unintended flap movement.
SYS-REQ-031: On receiving a valid command, the system shall actively move the flap toward the target position until reached.
SYS-REQ-032: Upon reaching the requested target position, the system shall stop actuator movement and indicate position using LEDs.
SYS-REQ-033: If an invalid or unsupported command is received, the system shall ignore it and shall not change the current system state.
SYS-REQ-034: [Implied] The system shall use a simple, easily auditable control flow suitable for process demonstration and learning.
SYS-REQ-035: [Implied] The system shall not require explicit state machine modeling beyond described behaviors.

8.0 System Interface Requirements

SYS-REQ-036: The system shall implement a UART interface (USB-UART) to receive user input from a PC.
SYS-REQ-037: The system shall interface with a DC motor driver (L298N) via GPIO and PWM for flap movement.
SYS-REQ-038: The system shall receive position feedback from a potentiometer via an ADC channel.
SYS-REQ-039: The system shall control LED indicators using GPIO outputs.
SYS-REQ-040: [Implied] The system shall not implement CAN, LIN, or other in-vehicle network interfaces.

9.0 Constraints and Assumptions

SYS-REQ-041: The system shall be designed to control a single flap, a single motor, and accept a single user command at a time.
SYS-REQ-042: It shall be assumed that all hardware components operate within their nominal specification.
SYS-REQ-043: All position calibration values shall be pre-configured and fixed in software for this demonstration.
SYS-REQ-044: The target microcontroller shall be STM32F407G-DISC1, with STM32 HAL drivers, implemented in embedded C (MISRA-style; no dynamic memory allocation).
SYS-REQ-045: [Implied] The system shall not require or implement features outside the prototype's learning and demonstration scope.

10.0 Non-Functional Requirements
10.1 Responsiveness Expectations
SYS-REQ-046: The system shall ensure that UART commands result in actuator movement within a human-perceptible short delay.

10.2 Error Handling and Edge Cases
SYS-REQ-047: The system shall ignore invalid or out-of-range user commands and not take any action in response.
SYS-REQ-048: If a feedback (ADC) value falls outside configured ranges, the system shall stop the actuator and await further commands.
SYS-REQ-049: [Implied] The system shall not crash or enter undefined operation in case of feedback or command errors.

10.3 Resource Constraints
SYS-REQ-050: The system implementation shall be lightweight and ensure resource usage is predictable and bounded.

10.4 Maintainability and Modularity
SYS-REQ-051: The requirements and implementation shall maintain clear separation of concerns and logical modularity for learning and demonstration.

10.5 Testability
SYS-REQ-052: The system shall support testability by observation of LEDs, actuator position, and UART command handling.
SYS-REQ-053: The system shall be verifiable by manual and script-based test cases.

Architecture-Relevant Considerations Derived from System Requirements

- The system is single-responsibility and is expected to be simple and linear in control logic.
- All interactions are local: there is no vehicle network communication or concurrency with other control domains.
- Direct command-control-response: system responses are direct and observable, with minimal asynchrony.
- The use of discrete states and simple command handling means the architecture can avoid complexity related to multitasking or real-time operating systems.
- The prototype is intended to be easily expandable for demonstration, but does not require architectural extensibility for production.

# 1.0 Software Scope and Responsibility

The HVAC Flap Actuator software is responsible for receiving user commands via UART, translating these commands into flap position requests, controlling a DC motor to move the flap to the commanded positions, monitoring real-time flap position via ADC/potentiometer feedback, and driving LED indicators for mode and position. The software does not make architectural, tasking, or scheduling decisions, focusing instead on functional behavior and interface with hardware peripherals.

- SWE-REQ-003: The software shall ignore and not respond to any invalid or unsupported UART command, and shall not change system state in response. (SYS-REQ-020, SYS-REQ-033, SYS-REQ-047)

# 1.0 Architecture Style Selection

## 1.1 Candidate Architecture Styles Considered

The following software architecture styles were evaluated for the HVAC Flap Actuator System:

| Candidate Style      | System Complexity | Hardware Integration | Testability        | Maintainability   | ASPICE Alignment        |
|---------------------|-------------------|---------------------|--------------------|-------------------|-------------------------|
| Monolithic          | Low               | Direct              | Simple to test     | Hard to extend    | Meets, but not optimal  |
| Layered             | Moderate          | Clear separation    | Highly testable    | Modifiable        | Level-3 proven          |
| Component-Based     | Moderate          | Loosely coupled     | Very testable      | Highly maintainable| Level-3 proven          |


## 1.2 Evaluation and Rationale

- **Monolithic** style, while simple, does not support traceability, modularity, or future testability as strongly as required by SWE.1/SWE.2 and ASPICE Level-3.
- **Layered** architecture allows strong logical separation (input processing, control logic, hardware abstraction), ensures clear interfaces, is highly auditable, allows test hooks, and matches the modular, traceable requirement in SWE-REQs 044/050/051/033.
- **Component-Based** would increase architectural complexity unnecessarily for a single-responsibility, prototype-focused system and is not explicitly required by any SWE.1 requirement.

## 1.3 Architecture Style Selected and Justification

**The Layered Architecture is selected**. This decision is justified because:
- Requirements call for clear separation of command, control, and hardware abstraction.
- Facilitates traceability (SWE-REQ-050/051) and testability (SWE-REQ-046/047).
- Supports clear, auditable module interfaces, as suggested by implied requirements for simplicity and modularity.
- Satisfies ASPICE Level-3 expectations for modular software design while remaining lightweight, as required by SWE-REQ-044/045/050/033.

**No explicit OS, concurrency, or scheduling policies shall be defined, as none are required by the specification.**

## Software Unit: Command Handler

1. Responsibilities
- Receives and parses UART user flap position commands (0-5).
- Validates incoming commands for range and format.
- Ensures only one valid command is processed at a time (locks input until completed).
- Does NOT generate position, motor, or LED control outputs.
- Does NOT process hardware abstraction or feedback directly.

2. Internal Data Design
- Internal buffer for UART received data.
- Variable for storing most recent valid command.
- Command state flag (idle, pending, busy).
- Error flag for invalid command receipt.

3. State Machine
- States: Idle, Command Pending, Command Busy, Error
- Events: Command Received, Command Validated, Command Invalid, Command Complete
- Transitions:
  - Idle → Command Pending (on UART RX interrupt, data received)
  - Command Pending → Command Busy (on valid parse)
  - Command Pending → Error (on invalid parse)
  - Command Busy → Idle (on command completion)
  - Error → Idle (on error acknowledged)
- Entry/Exit Actions: Clear buffer on entry to Idle, store command on Pending, set error on Error.

4. Algorithms and Control Flow
- On UART RX interrupt, copy data to buffer.
- Parse buffer for single digit (0-5).
- If valid, set Command Pending → Command Busy, notify Control Logic.
- If invalid, set Error, ignore command, and set flag for error indication (if required).
- Ignore new commands until current completes.

5. Interfaces (APIs)
- Provides: command_handler_get_command(), command_handler_is_command_pending(), command_handler_clear_error().
- Uses: HAL UART receive abstraction, Control Logic notify API.
- Parameters: Command (int), Error (flag)
- Error reporting: Internal error flag, API to query error status.

6. Error Handling
- Ignores and clears buffer for invalid or out-of-range commands (SWE-REQ-002/003/037).
- Does not affect outputs or state on error.

7. Resource and Timing Considerations
- Event-driven by UART RX.
- Handles one command at a time; not re-entrant.
- Execution delay depends on user input.

8. Traceability to SWE Requirements
- SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004, SWE-REQ-024, SWE-REQ-037

---

## Software Unit: Control Logic

1. Responsibilities
- Receives validated command from Command Handler.
- Determines if flap movement is needed (target ≠ current).
- Requests actuation from Motor Driver and LED update from LED Driver.
- Is not responsible for parsing UART or direct hardware access.

2. Internal Data Design
- Target position (int)
- Current position (from Position Feedback Processor)
- Command in-progress flag
- Movement state (Idle, Moving, Finished, Error)

3. State Machine
- States: Idle, Moving, Complete, Error
- Events: Command Received, Position Update, Movement Complete, Error Detected
- Transitions:
  - Idle → Moving (on command received, if target ≠ current)
  - Moving → Complete (on position match)
  - Moving → Error (on error flag from dependencies)
  - Complete → Idle (on notification)
- Entry/Exit Actions: Request movement on Moving entry, request LED update on Complete/Idle.

4. Algorithms and Control Flow
- Wait for command_ready; fetch target position.
- If target ≠ current, request Motor Driver to move towards target.
- Poll Position Feedback Processor for current position.
- When current matches target, instruct Motor Driver OFF; update LED.
- If error from dependencies, halt and signal error.

5. Interfaces (APIs)
- Provides: control_logic_execute_cycle(), control_logic_get_state().
- Uses: command_handler_get_command(), position_feedback_get_position(), motor_driver_actuate(), led_driver_update().
- Parameters: target_position, current_position
- Error reporting: Internal error state exposed to error handler.

6. Error Handling
- If error in feedback, positions, or hardware, enter safe state and request motor stop (SWE-REQ-039/038/040).

7. Resource and Timing Considerations
- Triggered on valid command or position event.
- Linear per-cycle, not re-entrant.
- No timing assumptions enforced by design.

8. Traceability to SWE Requirements
- SWE-REQ-006, SWE-REQ-007, SWE-REQ-009, SWE-REQ-010, SWE-REQ-031, SWE-REQ-039

---

## Software Unit: Position Feedback Processor

1. Responsibilities
- Acquires analog feedback via ADC from potentiometer.
- Quantizes ADC values to known, fixed position range (0-5).
- Validates feedback against calibration table.
- Signals error if data is out of range.
- Does not control motor, parse commands, or LEDs directly.

2. Internal Data Design
- adc_value_raw (uint16_t)
- position_lookup_table[6] (ADC thresholds)
- position_valid_flag
- last_position (int)
- error_flag

3. State Machine
- No explicit state machine; operates as synchronous converter/filter.
- Control Flow: on ADC update, map value and set flags, else flag error.

4. Algorithms and Control Flow
- On ADC read, compare adc_value_raw against lookup_table.
- If within any position range, set last_position and position_valid_flag.
- If not, set error_flag, clear position_valid_flag, and notify Control Logic.

5. Interfaces (APIs)
- Provides: position_feedback_get_position(), position_feedback_is_valid().
- Uses: HAL ADC abstraction.
- Parameters: none (ADC channel configured)
- Error reporting: error_flag API/exposed to Control Logic.

6. Error Handling
- Out-of-range values signal error and prevent further actuation (safe state).

7. Resource and Timing Considerations
- Scheduled/polled or event-driven per design; not re-entrant.
- Lightweight lookup, fast per execution.

8. Traceability to SWE Requirements
- SWE-REQ-016, SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-025

---

## Software Unit: Motor Driver

1. Responsibilities
- Supplies logical direction and enable to DC motor via GPIO/PWM.
- Initializes in OFF state.
- Turns motor ON/OFF as requested by Control Logic.
- Does not accept or parse user commands or feedback directly.

2. Internal Data Design
- motor_enable (bool)
- motor_direction (enum)
- initialized_flag
- last_request (struct for diagnostic, optional)

3. State Machine
- States: Initialized, Motor OFF, Motor ON
- Events: Init, Move Request, Motor Stop
- Transitions:
  - Initialized → Motor OFF (on power-up)
  - Motor OFF → Motor ON (on actuation)
  - Motor ON → Motor OFF (on position reached or error)

4. Algorithms and Control Flow
- On actuation request, set direction based on target vs current.
- Assert motor_enable, apply direction via GPIO/PWM.
- On stop request or error, set motor_enable = false.
- Confirm state.

5. Interfaces (APIs)
- Provides: motor_driver_actuate(direction), motor_driver_stop().
- Uses: HAL GPIO/PWM abstraction.
- Parameters: direction (enum), enable (bool)
- Error reporting: optional motor_driver_get_status().

6. Error Handling
- On error or invalid request, disables motor and signals error upstream.

7. Resource and Timing Considerations
- Fast GPIO/PWM control; expected to be invoked only via Control Logic.
- Not re-entrant by design.

8. Traceability to SWE Requirements
- SWE-REQ-011, SWE-REQ-012, SWE-REQ-013, SWE-REQ-014, SWE-REQ-015, SWE-REQ-026

---

## Software Unit: LED Driver

1. Responsibilities
- Drives status LED and position indicator green LEDs.
- Ensures one LED ON matching current logical position, all others OFF.
- Is not responsible for position or command logic.

2. Internal Data Design
- led_state_array[6] (bool per LED)
- status_led (bool)
- last_position (int)

3. State Machine
- No formal state machine; mapped via logic from position.
- Control Flow: set indicator LED ON, all others OFF, per current position.

4. Algorithms and Control Flow
- On position update, turn ON LED at corresponding index, others OFF.
- Control status LED per system state (power, error).

5. Interfaces (APIs)
- Provides: led_driver_update(position), led_driver_set_status_led(state).
- Uses: HAL GPIO abstraction.
- Parameters: position (int), state (bool)
- Error reporting: Optional error state for missing or faulted LEDs.

6. Error Handling
- Invalid position results in all indicator LEDs OFF (safe default).
- Optionally, blink status LED on system error.

7. Resource and Timing Considerations
- Fast, not re-entrant; event-driven on state/position update.

8. Traceability to SWE Requirements
- SWE-REQ-021, SWE-REQ-022, SWE-REQ-023, SWE-REQ-027, SWE-REQ-046

## Software Unit: Hardware Abstraction Layer (HAL)
