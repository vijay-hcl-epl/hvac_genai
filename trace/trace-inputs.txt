1.0 System Overview
The HVAC Flap Actuator system is a microcontroller-based prototype designed to control an air flap using a DC motor, providing discrete position control for air distribution in an HVAC system. Position feedback is via a potentiometer read by an ADC, and user commands are received over UART. Visual feedback is provided using LEDs. All operations are local; no vehicle network interfaces are present.

2.0 Flap Position Control
SYS-REQ-001: The system SHALL accept user commands to set the HVAC flap to one of six discrete positions (0 to 5).
SYS-REQ-002: The system SHALL move the flap to the commanded position if the command is valid.
SYS-REQ-003: The system SHALL stop the motor once the target position is reached.
SYS-REQ-004: The system SHALL ignore invalid position commands (i.e., commands not corresponding to positions 0–5).
SYS-REQ-005: The mapping of ADC values to positions SHALL be defined in software.
[Implied] The system SHALL not act on simultaneous contradictory commands (by accepting only one command at a time).

3.0 Motor Control
SYS-REQ-006: The system SHALL control the motor direction based on the required flap movement (clockwise or anti-clockwise).
SYS-REQ-007: The system SHALL switch off (disable) the motor when the target position is reached or an error/invalid state is detected.
SYS-REQ-008: Motor start and stop SHALL be managed via GPIO and PWM as appropriate.
[Implied] The system SHALL ensure the flap is only moved upon receipt of a valid command.

4.0 Position Feedback Acquisition & Processing
SYS-REQ-009: The system SHALL read flap position using the potentiometer connected to an ADC channel.
SYS-REQ-010: The system SHALL process and map ADC readings to discrete flap positions (0–5).
SYS-REQ-011: The system SHALL stop the motor if ADC values fall outside the valid range.
[Implied] The system SHALL periodically acquire and update position feedback.

5.0 User Command Interface
SYS-REQ-012: The system SHALL receive user commands via UART.
SYS-REQ-013: The system SHALL accept only numeric commands within the allowed range (0–5).
SYS-REQ-014: The system SHALL not transmit acknowledgments or errors for invalid commands.
[Implied] Commands from only one user/source SHALL be supported at a time.

6.0 Status Indication
SYS-REQ-015: The system SHALL turn on a dedicated power/status LED when the system is powered up.
SYS-REQ-016: The system SHALL illuminate a green LED corresponding to the current flap position so that only one position LED is ON at any time.
[Implied] LED indication SHALL update if the flap position changes as a result of a command or at power-up.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)
SYS-REQ-017: On power-up, the system SHALL initialize all peripherals (ADC, UART, GPIO, PWM), leave the motor OFF, read current flap position, turn the status LED ON, and illuminate the correct position LED.
SYS-REQ-018: While idle (no user command), the system SHALL monitor UART for commands and flap position for feedback indication.
SYS-REQ-019: When moving to a new position, the system SHALL update position indication and switch off the motor once the position is achieved.
SYS-REQ-020: If an invalid command is received, the system SHALL ignore it and continue normal operation.
[Implied] System states SHALL be managed according to this behavioral logic.

8.0 Interfaces (UART, motor driver, ADC, LEDs)
SYS-REQ-021: The system SHALL communicate with a PC/user via UART for command input.
SYS-REQ-022: The system SHALL interface with the motor driver (L298N) for motor actuation using GPIO and PWM.
SYS-REQ-023: The system SHALL use an ADC channel for flap position feedback from the potentiometer.
SYS-REQ-024: The system SHALL use GPIOs to control all status and position LEDs.
[Implied] Each interface SHALL be initialized and monitored for correct operation upon system start.

9.0 Constraints & Assumptions
SYS-REQ-025: The system SHALL operate as a single-flap, single-user, local controller only.
SYS-REQ-026: Calibration/position-mapping values SHALL be fixed in software; no self-learning or run-time calibration is required.
SYS-REQ-027: The system SHALL not assume perfect hardware; invalid readings must be handled as specified; advanced diagnostics are not required.
[Implied] The hardware setup (motor, gears, potentiometer) is mechanically correct.

10.0 Non-Functional Requirements
10.1 Responsiveness
SYS-REQ-028: The system SHALL process UART commands and update position/LED indication with responsiveness suitable for interactive manual testing (typically < 1 second per action, but no strict timing).

10.2 Error Handling & Edge Cases
SYS-REQ-029: The system SHALL stop the motor for any out-of-range ADC readings or unrecognized position commands.
SYS-REQ-030: The system SHALL not hang or crash if the commanded position cannot be achieved (e.g., due to hardware limits or potentiometer fault).

10.3 Resource Constraints
SYS-REQ-031: The system SHALL operate within the memory, I/O, and processing power available on the STM32F407-Discovery platform.

10.4 Maintainability & Modularity
SYS-REQ-032: Code and configuration values for positions, calibration, interfaces, and state indication SHALL be separated and well-documented for ease of change.

10.5 Testability
SYS-REQ-033: The system SHALL support testability via user command input (UART), observable motor behavior, and LED output.
[Implied] Manual/script-based testing SHALL be feasible using listed interfaces and behaviors.

Architecture-Relevant Considerations Derived from System Requirements

- Interaction Complexity: The system has low interaction complexity; user commands are one-at-a-time, and control/feedback interfaces are direct.
- Control Complexity: The control logic is straightforward with stateful behavior tracked via software variables and simple status indication.

## 1. ARCHITECTURE STYLE SELECTION

### Candidate Styles Considered
- Layered (Presentation, Application, Hardware Abstraction)
- Component-Based (distinct modules for each function or interface)
- Monolithic (single-block with functional separation only through code structure)
- Service-Oriented / Microkernel (not suitable; out of scope per SYS/SWE.1)

### Evaluation

| Style            | System Complexity | HW Interaction | Testability       | Maintainability   | ASPICE L3 Fit           |
|------------------|------------------|----------------|-------------------|-------------------|-------------------------|
| Layered          | Moderate         | Good           | Good              | Good              | Well-suited             |
| Component-Based  | Moderate         | Very Good      | Very Good         | Very Good         | Well-suited             |
| Monolithic       | Simple           | Acceptable     | Limited           | Poor              | Not preferred           |
| Service/Micro    | Excessive        | Overkill       | Unneeded          | Overengineered    | Not justified           |

### Style Decision
**Selected:**  
**Component-based architecture** (justified below).

**Rational & Justification:**  
- System and SWE.1 both require clear interface abstraction (UART, GPIO/PWM, ADC, LEDs) with direct traceability to functional decomposition (SWE-REQ-016 thru SWE-REQ-019); these are best modularized as components.
- Testability and maintainability increased via explicit interface separation.
- System complexity is low—layered is possible, but a flat component model achieves the modularity and traceability sought by SWE.1/ASPICE.
- Monolithic design explicitly rejected for long-term maintainability and traceability reasons.
- Service/microkernel not justified due to simplicity and lack of dynamic or distributed requirements.

## Software Unit: Command Manager

1. Responsibilities
   - Handles: UART command reception, validation, decoding, and initiation of position requests.
   - Does not handle: communication protocols, hardware error recovery, or scheduling.

2. Internal Data Design
   - RX buffer: Fixed-size char array (length defined in config, ~8 chars for ASCII encoding)
   - Command variable: integer (0-5), stores decoded position
   - Error flag: Boolean, indicates invalid command
   - State: none (see below)
   - Configuration: Acceptable character set (ASCII digits '0'-'5')

3. State Machine
   - State: none (function is simple input processing, not event- or state-driven)
   - Flow: On UART receive event, buffer input, decode command, set error flag if invalid

4. Algorithms & Control Flow
   - On UART RX:
     - Buffer input
     - Validate ASCII integer value ('0'-'5')
     - If valid: set command variable and clear error flag
     - If invalid: set error flag, ignore
     - Pass valid command to Flap Control Coordinator
     - Ignore further input until completion callback from Flap Control Coordinator

5. Interfaces (APIs)
   - Provided: void Handle_UART_Command(const char *input)
     - Params: input buffer (const char*)
     - Returns: none
     - Error reporting: internal error flag
   - Required: void Request_Position(uint8_t position)
     - Params: position (0-5)
     - Returns: ACK (internal), no external reporting

6. Error Handling
   - Sets error flag and ignores invalid/duplicate commands (SWE-REQ-002, SWE-REQ-028)
   - No external error communication

7. Resource & Timing Considerations
   - Invoked only on UART RX event
   - WCET: <<1ms (command parse/decode only)
   - Not re-entrant (single command at a time)

8. Traceability
   - SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-016, SWE-REQ-028

## Software Unit: Flap Control Coordinator

1. Responsibilities
   - Handles: Main control sequencing, position tracking, high-level actions
   - Does not handle: hardware, direct input/output, or scheduling

2. Internal Data Design
   - Target position: integer (0-5)
   - Current position: integer (updated from feedback)
   - Move in progress flag: Boolean
   - Error state: Boolean
   - Configuration: movement debounce time (optional)

3. State Machine
   - States: Idle, MoveRequested, Moving, AtTarget, Error
   - Events: New command, feedback update, error detect, position complete
   - Transitions/action summary:
     - Idle → MoveRequested (new valid command)
     - MoveRequested → Moving (command accepted, motor start)
     - Moving → AtTarget (feedback = target)
     - Any → Error (error flag set)
     - AtTarget/Error → Idle (on clear/reset)

4. Algorithms & Control Flow
   - On valid position request:
     - If not moving, check validity vs current
     - If change needed, save as target, arm movement flag
     - Request Motor Control for movement
   - On feedback update:
     - Update current position
     - If reached target, request Motor Control stop
     - Update LED Management with new position
   - On error:
     - Request Motor Control stop
     - Set error state, block new commands until cleared

5. Interfaces (APIs)
   - Provided: void Process_Position_Request(uint8_t target)
   - Required:
     - void Initiate_Motor_Move(direction_t dir)
     - void Stop_Motor(void)
     - void Update_Leds(uint8_t position)
     - uint8_t Get_Feedback_Position(void)
     - void Error_Handler(void)
   - Params/returns per above, no external errors

6. Error Handling
   - Sets and blocks on error, only explicit reset clears
   - Requests error actions by Motor/LED units

7. Resource & Timing Considerations
   - Invoked on command or feedback
   - WCET: <<2ms (simple logic only)
   - Not re-entrant (one movement at a time)

8. Traceability
   - SWE-REQ-004, SWE-REQ-005, SWE-REQ-012, SWE-REQ-023, SWE-REQ-024, SWE-REQ-026

#define MAX_CMD_LEN 8

static int command_in_progress = 0;
static uint8_t command_value = 0;
static bool error_flag = false;

void Handle_UART_Command(const char *input) {
    if (command_in_progress) return;
    if (!input || strlen(input) == 0 || strlen(input) > MAX_CMD_LEN)
        goto invalid;
    if (input[1] != '\0')
        goto invalid;
    if (input[0] < CMD_MIN || input[0] > CMD_MAX)
        goto invalid;
    command_value = (uint8_t)(input[0] - '0');
    error_flag = false;
    command_in_progress = 1;
    Process_Position_Request(command_value);
    return;

    error_flag = true;
}

    if (move_in_progress || error_state) return;
    if (target > 5) return;
    if (target == current_position) return;
    target_position = target;
    move_in_progress = true;

        move_in_progress = false;
        Set_Position_LED(current_position);
        CommandManager_Complete();

}

    error_state = true;

- Mapped System Requirement ID(s): SYS-REQ-017, SYS-REQ-015, SYS-REQ-016

- Preconditions: System powered OFF, flap in a known position.

- Test Steps:
  1. Ensure the system is powered OFF and the flap is manually set to a known position (e.g., position 3).
  2. Power ON the system.
- Expected Results:
  - Status LED turns ON.
  - Only one position LED matches the actual flap position.
  - Motor remains OFF.
- Pass/Fail Criteria:
  - All results above are observed and verified during and after initialization.

### 3.2 Valid Flap Position Commands

#### SYS-TC-002: Flap Position Command Acceptance (All Valid)
- Mapped System Requirement ID(s): SYS-REQ-001, SYS-REQ-002, SYS-REQ-003, SYS-REQ-006, SYS-REQ-007, SYS-REQ-008
