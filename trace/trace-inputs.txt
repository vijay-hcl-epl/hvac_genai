SYSTEM REQUIREMENTS FOR HVAC FLAP ACTUATOR SYSTEM

1.0 System Overview
The HVAC flap actuator system is a microcontroller-based prototype designed to control an air flap's position in response to commands received from a user. The system utilizes a DC motor for repositioning the flap, potentiometer feedback for position sensing, UART for user input, and LEDs for system state and position indication. The project demonstrates embedded software processes in alignment with ASPICE Level 3 requirements.

2.0 Flap Position Control Requirements
SYS-REQ-001: The system shall allow the user to command any supported flap position via UART.
SYS-REQ-002: The system shall compare the current flap position with the requested position.
SYS-REQ-003: The system shall move the flap to the target position upon receiving a valid command.
SYS-REQ-004: The system shall stop the motor once the target position is reached.
SYS-REQ-005: The system shall continuously monitor the current position while the system is powered on.
SYS-REQ-006: The system shall map ADC readings to discrete logical positions (e.g., 0–5).
[Implied] SYS-REQ-007: The system shall reject flap commands that are not in the defined valid position range.

3.0 Motor Control Requirements
SYS-REQ-008: The system shall control the motor to rotate clockwise or anti-clockwise as required to reach the target position.
SYS-REQ-009: The system shall control motor direction using microcontroller GPIO outputs.
SYS-REQ-010: The system shall enable or disable the motor using a PWM-controlled enable signal.
SYS-REQ-011: The system shall stop the motor when the flap is at the target position.
SYS-REQ-012: The motor shall be off at system power-up and initialization.
[Implied] SYS-REQ-013: The system shall stop the motor if ADC feedback is out of expected range.

4.0 Position Feedback Acquisition and Processing Requirements
SYS-REQ-014: The system shall acquire the flap’s position via the potentiometer connected to an ADC input.
SYS-REQ-015: The system shall periodically sample the potentiometer voltage using ADC.
SYS-REQ-016: The system shall map ADC values to the defined set of flap positions (e.g., 0–5), according to calibration data.
[Implied] SYS-REQ-017: The system shall ignore changes in ADC value that do not correspond to a valid logical position.

5.0 User Command Interface Requirements
SYS-REQ-018: The system shall accept user commands via UART.
SYS-REQ-019: The system shall interpret numeric values (0–5) as target flap positions.
SYS-REQ-020: The system shall ignore invalid or out-of-range commands without acknowledgment or error response.
[Implied] SYS-REQ-021: The system shall not accept new commands while a position change is in progress.

6.0 Status Indication Requirements
SYS-REQ-022: The system shall provide a power/status LED indicating system ON state.
SYS-REQ-023: The system shall indicate flap position using green LEDs, with no more than one position LED lit at a time.
SYS-REQ-024: The LEDs shall update to represent the current logical flap position.
[Implied] SYS-REQ-025: LED indication shall be present during and after flap movement, reflecting the last valid position.

7.0 System Behavioral Requirements
SYS-REQ-026: On power-up, the system shall initialize all required peripherals (ADC, UART, GPIO, PWM).
SYS-REQ-027: On power-up, the motor shall remain off until a valid user command is received.
SYS-REQ-028: The system shall enter idle mode while awaiting commands.
SYS-REQ-029: Upon receipt of a valid flap position command, the system shall move the flap toward the target position.
SYS-REQ-030: Once the target position is reached, the system shall hold the flap in position and indicate with the relevant LED.
SYS-REQ-031: Upon receipt of an invalid command, the system shall ignore the command and maintain current operation without error.
[Implied] SYS-REQ-032: The system shall be restartable by power cycle and return to a known safe state.

8.0 System Interface Requirements
SYS-REQ-033: The system shall provide a UART interface for command and user input from a PC.
SYS-REQ-034: The system shall provide GPIO outputs for motor direction control.
SYS-REQ-035: The system shall provide a PWM-capable output for the motor driver enable signal.
SYS-REQ-036: The system shall provide an ADC input for potentiometer feedback acquisition.
SYS-REQ-037: The system shall provide GPIO outputs for LED status indication.

9.0 Constraints and Assumptions
SYS-REQ-038: The system shall operate on an STM32F407G-DISC1 microcontroller.
SYS-REQ-039: The system shall use only the specified interfaces (UART for commands, ADC for sensing, GPIOs for indication/control, PWM for motor enable).
SYS-REQ-040: The system shall not require support for CAN, LIN, or other vehicle networks.
SYS-REQ-041: The system shall use fixed calibration parameters for ADC value mapping and not support self-calibration.
[Implied] SYS-REQ-042: The system shall assume mechanical and electrical components are functioning as intended.

10.0 Non-Functional Requirements
10.1 Responsiveness Expectations:
SYS-REQ-043: The system shall process user commands and respond by moving the flap in a timeframe that is perceptibly immediate to a human operator.
[Implied] SYS-REQ-044: The system shall not provide guarantees for hard real-time deadlines since none are specified.

10.2 Error Handling and Edge Cases:
SYS-REQ-045: The system shall safely stop the motor if out-of-range ADC values are detected.
SYS-REQ-046: The system shall not crash or become unstable in the event of motor stall or missed target position.

10.3 Resource Constraints:
SYS-REQ-047: The system shall not use dynamic memory allocation.
SYS-REQ-048: The system shall be designed for a lightweight embedded environment.

10.4 Maintainability and Modularity:
SYS-REQ-049: System requirements, software, and hardware interface implementations shall be separated and clearly documented.
[Implied] SYS-REQ-050: The software architecture shall promote readability and ease of modification for educational/demo purposes.

10.5 Testability:
SYS-REQ-051: The system shall support testability through external command injection (UART) and observation of LEDs and flap position.
SYS-REQ-052: The system shall support manual and script-based test methods.

ARCHITECTURE-RELEVANT CONSIDERATIONS DERIVED FROM SYSTEM REQUIREMENTS
- The system is expected to operate in a simple, single-responsibility context (controlling one flap based on one user interface at a time).
- No concurrent or multitasking responsibilities are required/implied in the requirements.
- All hardware interactions are local/direct and do not require communication over distributed networks.
- Control logic is simple: states (idle/waiting, moving, holding/steady) transition based on direct user command or position attainment.
- System expandability (e.g., adding more flaps or new feedback types) is not assumed or required.
- The requirements allow any scheduling or execution model that meets correctness and responsiveness; no architectural constraints are imposed beyond separation and readability for learning.

# Software Requirements Specification – HVAC Flap Actuator

## 1.0 Software Scope and Responsibility
The embedded software for the HVAC flap actuator system is responsible for controlling the position of an air mixing or direction flap. The software interprets user commands received via UART, controls a DC motor through GPIO and PWM signals to adjust the flap, determines the current position via potentiometer feedback (ADC), and provides status indication through LEDs. It ensures safe, reliable, and responsive system operation while remaining implementation-agnostic regarding execution architecture.

## 2.0 Software Functional Requirements

### 2.1 User Command Handling
- SWE-REQ-001: The software shall accept user commands specifying target flap positions via UART. (SYS-REQ-001, SYS-REQ-018)
- SWE-REQ-002: The software shall interpret numeric UART values (0 to 5) as valid target flap positions. (SYS-REQ-019)
- SWE-REQ-003: The software shall validate all received user commands to confirm they fall within the defined set of allowed flap positions. (SYS-REQ-007, SYS-REQ-020)
- SWE-REQ-004: The software shall ignore or reject commands that specify invalid or out-of-range positions, without acknowledgment or error response. (SYS-REQ-020) [Implied]
- SWE-REQ-005: The software shall not accept new user commands while the flap is being repositioned. (SYS-REQ-021) [Implied]

### 2.2 Flap Position Control Logic
- SWE-REQ-006: The software shall compare the flap’s current position (as determined by ADC feedback) to the target position from the latest valid command. (SYS-REQ-002)
- SWE-REQ-007: The software shall initiate movement of the flap when a valid target position that differs from current position is commanded. (SYS-REQ-003, SYS-REQ-029)
- SWE-REQ-008: The software shall stop flap movement when the target position is reached. (SYS-REQ-004, SYS-REQ-030)
- SWE-REQ-009: The software shall map ADC readings to discrete logical flap positions according to calibration or configuration data. (SYS-REQ-006, SYS-REQ-016)
- SWE-REQ-010: The software shall ignore changes in ADC value that do not correspond to a valid logical position. (SYS-REQ-017) [Implied]

### 2.3 Motor Control Logic
- SWE-REQ-011: The software shall control motor direction via microcontroller GPIO outputs to reach the required target flap position. (SYS-REQ-008, SYS-REQ-009)
- SWE-REQ-012: The software shall enable or disable the DC motor using a PWM-controlled signal. (SYS-REQ-010, SYS-REQ-035)
- SWE-REQ-013: The software shall ensure the motor is stopped when the target position is reached or upon receiving a stop condition. (SYS-REQ-004, SYS-REQ-011, SYS-REQ-045)
- SWE-REQ-014: The software shall ensure the motor is off at system power-up and initialization. (SYS-REQ-012, SYS-REQ-027)
- SWE-REQ-015: The software shall stop the motor if ADC feedback is out of expected/calibrated range. (SYS-REQ-013, SYS-REQ-045) [Implied]

### 2.4 Position Feedback Processing
- SWE-REQ-016: The software shall acquire flap position feedback from a potentiometer via an ADC interface. (SYS-REQ-014, SYS-REQ-036)
- SWE-REQ-017: The software shall apply mapping and thresholds to translate ADC readings into logical flap positions (e.g., 0–5) according to calibration constants. (SYS-REQ-006, SYS-REQ-016, SYS-REQ-041)
- SWE-REQ-018: The software shall ignore any ADC readings that do not resolve to a defined, valid flap position. (SYS-REQ-017) [Implied]

### 2.5 Status Indication Control
- SWE-REQ-019: The software shall control a dedicated LED to indicate system power ON status. (SYS-REQ-022)
- SWE-REQ-020: The software shall control dedicated green LEDs such that no more than one position LED is on at any time, reflecting the current logical flap position. (SYS-REQ-023, SYS-REQ-024, SYS-REQ-025)

## 3.0 Software Interface Requirements
- SWE-REQ-021: The software shall utilize a UART interface to receive user commands from an external PC. (SYS-REQ-033)
- SWE-REQ-022: The software shall provide GPIO outputs to control motor direction and drive the position/power LEDs. (SYS-REQ-034, SYS-REQ-037)
- SWE-REQ-023: The software shall provide a PWM-capable output to enable or disable the DC motor. (SYS-REQ-035)
- SWE-REQ-024: The software shall acquire potentiometer position data via an ADC input, according to calibration settings. (SYS-REQ-036, SYS-REQ-015, SYS-REQ-041)

## 4.0 Software Behavioral Requirements
- SWE-REQ-025: Upon power-up, the software shall initialize all required peripherals (ADC, UART, GPIO, PWM), set the motor to OFF, and determine the initial flap position. (SYS-REQ-026, SYS-REQ-027)
- SWE-REQ-026: After initialization, the software shall maintain an IDLE state until a valid user command is received. (SYS-REQ-028)
- SWE-REQ-027: Upon receiving a valid command, the software shall move the flap toward the requested position and stop the motor when the position is attained. (SYS-REQ-003, SYS-REQ-004, SYS-REQ-029, SYS-REQ-030)
- SWE-REQ-028: After reaching the target position, the software shall hold the flap there and update the relevant indicator LED. (SYS-REQ-030)
- SWE-REQ-029: If an invalid command is received at any time, the software shall ignore it and continue current operation without error or acknowledgment. (SYS-REQ-020, SYS-REQ-031)
- SWE-REQ-030: The software shall be restartable by power cycle, and always return to an initial safe state. (SYS-REQ-032) [Implied]

## 5.0 Software Data and Configuration Requirements
- SWE-REQ-031: The software shall store fixed ADC position thresholds and mapping tables for flap positions in read-only or non-volatile memory as calibration data. (SYS-REQ-041)
- SWE-REQ-032: The software shall maintain internal state representing the current and target logical flap positions. (SYS-REQ-006)
- SWE-REQ-033: The software shall support configuration of position mappings via code constants or compile-time settings. (SYS-REQ-041)

## 6.0 Software Error Handling Requirements
- SWE-REQ-034: Upon detection of invalid UART commands, the software shall take no further motor or position action. (SYS-REQ-020, SYS-REQ-045)
- SWE-REQ-035: If ADC values are out of defined/calibrated range, the software shall stop the motor and maintain status LED indications. (SYS-REQ-045, SYS-REQ-013)
- SWE-REQ-036: Upon any motor anomaly (failure to move or missed position), the software shall avoid entering an unsafe or undefined state. (SYS-REQ-046) [Implied]

## 7.0 Software Performance and Responsiveness Requirements
- SWE-REQ-037: The software shall respond to user commands with a perceptibly immediate reaction (i.e., as fast as feasible for human interaction, but without fixed real-time deadlines). (SYS-REQ-043)
- SWE-REQ-038: The software shall periodically evaluate flap position and control motor operation, as needed for the above requirements. (SYS-REQ-005, SYS-REQ-015) [Implied]

## 8.0 Software Resource Constraint Requirements
- SWE-REQ-039: The software shall not use dynamic memory allocation. (SYS-REQ-047)
- SWE-REQ-040: The software shall be designed for operation in a resource-constrained, lightweight embedded microcontroller environment. (SYS-REQ-048)
- SWE-REQ-041: The software shall avoid unbounded or unpredictable execution times. (SYS-REQ-048) [Implied]

## 9.0 Software Testability Requirements
- SWE-REQ-042: The software shall support testability via UART command injection and allow all normal operations to be triggered by manual or scripted PC input. (SYS-REQ-051)
- SWE-REQ-043: The software shall provide observable outputs via LED indication and motor movement that can be visually checked against the commanded position. (SYS-REQ-052)
- SWE-REQ-044: The software shall support both manual and script-based test approaches, with all externally visible behaviors easily verifiable. (SYS-REQ-052)

## 10.0 Implied Software Requirements
- [Implied] SWE-REQ-045: The software shall rely on the correct functioning of hardware interfaces and components as assumed by system-level requirements. (SYS-REQ-042)
- [Implied] SWE-REQ-046: The software shall not implement architectural or scheduling assumptions—any compliant execution model is permitted. (SYS-REQ-050)
- [Implied] SWE-REQ-047: The software shall always default to a safe state (motor off, current position indicated) upon reset, error, or power loss. (SYS-REQ-032, SYS-REQ-045)

# Software Architecture – HVAC Flap Actuator System

## 1. Architecture Style Analysis

### Candidate Architecture Styles Considered

| Candidate        | Pros                                                                                  | Cons                                   | Suitability (per requirements)                                          |
|------------------|---------------------------------------------------------------------------------------|----------------------------------------|-------------------------------------------------------------------------|
| Layered          | Clear separation of concerns, supports maintainability and testability, lightweight   | Overhead may be unnecessary for simple system | Good, but adds unnecessary complexity given the monolithic nature       |
| Component-based  | Encapsulates hardware abstraction, logic, and interface; easy to maintain             | Adds extra modularity; not needed for single-function, single-flap systems | Overkill given explicit single-use/single-flap design                   |
| Monolithic (Decomposed into Logical Units) | Minimal overhead, matches simple, single-control function; responsibilities can still be separated logically in code structure | Care needed to preserve modifiability | Best fit: explicitly called for by requirements; matches ASPICE L3 separation/goals for lightweight demo |

### Evaluation and Choice

- **Complexity**: Requirements explicitly specify a single flap actuator, no concurrent activities, and a simple command-action-control pattern. No expansion, concurrent tasks, or distributed components are needed.
- **Hardware Interaction**: All interactions are direct, tightly-coupled, and local, favoring direct, simple abstractions.
- **Testability**: Requirements emphasize testability (UART, LEDs, observable motor movement); architecture should allow simple functional unit separation.
- **Maintainability**: Architecture must be easily understandable/traceable for educational purposes.
- **ASPICE L3 Alignment**: Separation of concerns, traceability, and well-documented interfaces required, but forbids unnecessary indirection.

**Chosen Architecture Style:**  
“A monolithic architecture logically decomposed into clearly separated software units (modules), where each unit maps to a set of responsibilities (command handling, position sensing, control, indication, etc.). No physically separate components/processes are introduced given the explicitly single-function, single-flap, single-thread requirements. This style provides traceability, logical separation, and maintainability without unnecessary overhead.”

### Justification

- Every alternative either does not add value (given constraints), or would contradict ASPICE L3's “no overengineering” demo philosophy for this prototype.
- This chosen style cleanly separates concerns and responsibilities, aiding testability and maintenance, while supporting educational demonstration (per requirements).

## 2. Decomposition: Software Units, Responsibilities, Interfaces

| Software Unit   | Responsibilities                                                                                                                                         | Interfaces Provided                | Interfaces Used                             |
|-----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------|---------------------------------------------|
| Command Handler | Receives, parses, and validates UART user commands. Ensures only valid and idle-safe commands are accepted.                                              | `receive_command(pos: int)`        | UART driver, State Manager                  |
| State Manager   | Maintains and transitions simple internal states (IDLE, MOVING, HOLD/STEADY). Guards that only one activity runs at a time.                              | `set_state(state)`, `get_state()`  | Command Handler, Control Logic              |
| Position Sensing| Reads ADC potentiometer, applies calibration mapping, converts to logical position. Detects out-of-range and notifies others.                            | `get_current_position()`, `is_valid_position()` | ADC driver, Control Logic         |
| Control Logic   | Determines required motor action; initiates, controls, and stops motor movement as required. Checks actual vs requested position.                        | `move_to_position(target: int)`    | Position Sensing, Motor Driver, State Manager|
| Motor Driver    | Controls GPIO direction outputs and PWM-Enable signal to drive/stop the DC motor. Ensures safe motor OFF on startup, error, or at position.              | `set_direction(dir)`, `enable()`, `disable()` | HAL (GPIO, PWM), Control Logic    |
| Status Indication| Updates power and position indicator LEDs (max 1 position LED ON). Maps logical position/state to output.                                               | `update_leds(power_on, pos_idx)`   | HAL (GPIO), State Manager, Position Sensing  |
| HW Abstraction  | Provides minimal interface to hardware peripherals (UART, ADC, GPIO, PWM), stubbed as needed for testability.                                           | Low-level drivers                  | Microcontroller hardware                    |
| Config/Constants| Stores flap ADC mapping, constants, no runtime reconfiguration.                                                   | `get_pos_thresholds()`, `init_config()` | Used by Position Sensing                |

### Execution Model / Scheduling

> “No explicit execution model or scheduling policy is mandated by the requirements at this stage.”
- Requirements permit (and prototype philosophy prefers) a simple main-loop (“super-loop”) in which each software unit is called in sequence.
- No RTOS, ISRs, threads, or concurrency are needed; timing and ordering are defined by main loop, which periodically checks for UART input, evaluates position/movement, and updates LEDs.
- Any compliant single-threaded, event-driven, or polling architecture is permitted. Design remains agnostic at this level.
