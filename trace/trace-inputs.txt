# 1.0 System Overview
The HVAC Flap Actuator system is a microcontroller-based demonstration platform for controlling a single air flap typically found in automotive HVAC systems. The system allows user selection of flap position via UART commands, moves the flap accordingly by controlling a DC motor, acquires continuous position feedback via a potentiometer, and provides status indication through LEDs. It is designed for learning, experimentation, and software process demonstration as a prototype—not as a production ECU.

# 2.0 Flap Position Control Requirements
- **SYS-REQ-001:** The system shall allow selection of discrete target flap positions in response to valid user commands.
- **SYS-REQ-002:** The system shall continuously acquire the current flap position from the potentiometer/ADC.
- **SYS-REQ-003:** The system shall determine the required direction to move the flap based on the difference between the current and target positions.
- **SYS-REQ-004:** The system shall actuate the flap to reach the selected target position.
- **SYS-REQ-005:** Once the target position is reached, the system shall stop the motor and hold the flap at that position.
- **SYS-REQ-006:** The mapping of ADC ranges to logical flap positions (e.g., 0–5) shall be defined in software and fixed for the prototype.
- **SYS-REQ-007 [Implied]:** The system shall prevent unnecessary actuation if the flap is already at the requested position.

# 3.0 Motor Control Requirements
- **SYS-REQ-008:** The system shall control the DC motor direction through dedicated GPIO pins based on the target position.
- **SYS-REQ-009:** The system shall enable or disable motor movement using a dedicated enable signal (PWM or GPIO).
- **SYS-REQ-010:** The system shall stop (de-energize) the motor when the flap has reached the target position or when an error condition is detected (e.g., invalid ADC feedback).
- **SYS-REQ-011:** The system shall not attempt to move the flap outside its defined position limits.
- **SYS-REQ-012 [Implied]:** The system shall avoid excessive motor running by stopping the motor promptly on target acquisition or error.

# 4.0 Position Feedback Acquisition and Processing
- **SYS-REQ-013:** The system shall periodically initiate ADC sampling of the potentiometer to read the flap position.
- **SYS-REQ-014:** The system shall map the analog voltage (ADC value) to a defined logical flap position in software.
- **SYS-REQ-015:** The system shall detect and ignore ADC values outside valid operating ranges (those not corresponding to any supported flap position).
- **SYS-REQ-016 [Implied]:** The system shall ensure ADC readings are obtained with sufficient resolution and filtering (if required for stability in the prototype environment).

# 5.0 User Command Interface Requirements
- **SYS-REQ-017:** The system shall receive user commands via a UART interface connected to a PC.
- **SYS-REQ-018:** The system shall interpret and validate incoming UART commands as numeric values representing flap positions.
- **SYS-REQ-019:** The system shall ignore invalid or out-of-range UART commands without sending any response or error indication.
- **SYS-REQ-020:** The system shall accept only one user command at a time; no command queuing is required.
- **SYS-REQ-021 [Implied]:** The system shall process UART commands promptly upon reception to maintain responsiveness.

# 6.0 Status Indication Requirements
- **SYS-REQ-022:** The system shall use one dedicated LED to indicate power/status.
- **SYS-REQ-023:** The system shall use dedicated green LEDs to display the currently commanded or achieved flap position (one green LED ON at a time).
- **SYS-REQ-024:** The LED status shall always match the actual logical flap position as determined from ADC readings at any time.
- **SYS-REQ-025 [Implied]:** LED indication logic shall be simple, clear, and unambiguous for all allowed positions and power states.

# 7.0 System Behavioral Requirements
- **SYS-REQ-026:** On power-up, the system shall initialize all peripherals (ADC, UART, GPIO, PWM) and leave the motor OFF.
- **SYS-REQ-027:** On power-up, the system shall immediately sample and store the current flap position.
- **SYS-REQ-028:** While idle (not moving), the system shall monitor for both user commands and flap position changes.
- **SYS-REQ-029:** During normal operation, the system shall move the flap toward the requested position and detect when the target is reached.
- **SYS-REQ-030:** After reaching the target, the system shall maintain its state and ignore redundant commands unless a new target is provided.
- **SYS-REQ-031:** The system shall safely ignore invalid input conditions (invalid UART command, out-of-range feedback, etc.).
- **SYS-REQ-032 [Implied]:** No explicit state machine or production-grade diagnostic logic is required beyond safe ignoring of errors.

# 8.0 System Interface Requirements
- **SYS-REQ-033:** The system shall use a UART interface for receiving user commands from a PC.
- **SYS-REQ-034:** The system shall use GPIO outputs to control the DC motor (direction and enable), routed through an L298N motor driver.
- **SYS-REQ-035:** The system shall use an ADC interface for potentiometer readings.
- **SYS-REQ-036:** The system shall use GPIO outputs for controlling status and position indication LEDs.
- **SYS-REQ-037 [Implied]:** No CAN, LIN, or external network interfaces shall be used by the software or exposed to users.

# 9.0 Constraints and Assumptions
- **SYS-REQ-038:** Only one actuator (flap) and motor are present and controlled in the system.
- **SYS-REQ-039:** Only one user command is handled at a time.
- **SYS-REQ-040:** Hardware (ADC, motor, potentiometer, LEDs) is assumed to function correctly unless an error is explicitly detected by software rules.
- **SYS-REQ-041:** Calibration values for the ADC (flap position mapping) are static; no dynamic calibration or auto-learning is performed.
- **SYS-REQ-042 [Implied]:** System resource usage shall be lightweight and bounded, per microcontroller learning platform norms.

# 10.0 Non-Functional Requirements
## 10.1 Responsiveness Expectations
- **SYS-REQ-043:** The system shall provide observable responsiveness to user commands (flap position changes and indicator updates occur within a time frame considered prompt by a human operator).
  - No fixed timing constraints are imposed.

## 10.2 Error Handling and Edge Cases
- **SYS-REQ-044:** The system shall safely ignore invalid user commands, out-of-range feedback, and unexpected values without crashing or undefined behavior.
- **SYS-REQ-045:** If the ADC feedback is outside defined position range, the system shall stop the motor and not attempt further movement.
- **SYS-REQ-046 [Implied]:** No advanced error handling, diagnostics, or fault recovery logic (e.g., timeouts, reset) is required for this prototype.

## 10.3 Resource Constraints
- **SYS-REQ-047:** The overall software and data resource usage (RAM, code size, variables) shall be minimized to fit easily on STM32F407G-DISC1 resources.
- **SYS-REQ-048:** No dynamic memory allocation or non-volatile storage is required.

## 10.4 Maintainability and Modularity
- **SYS-REQ-049:** The system design shall separate responsibilities for command processing, position control, feedback acquisition, motor driving, and indication.
- **SYS-REQ-050:** The system design shall support ease of modification for learning and demonstration.
- **SYS-REQ-051 [Implied]:** Software shall be modular for simple addition or adjustment of commands and positions without restructuring the system.

## 10.5 Testability
- **SYS-REQ-052:** The system shall support testability by allowing UART command injection and LED observation without special tooling.
- **SYS-REQ-053:** Manual and batch/script testing using a connected PC, observed motor response, and LEDs shall be possible for all functional requirements.
- **SYS-REQ-054 [Implied]:** No automated HIL, SIL, or remote verification infrastructure is required for this prototype.

# Architecture-Relevant Considerations Derived from System Requirements
- The system does not require explicit concurrency or multi-tasking; all responsibilities (command interface, position control, feedback acquisition, indication) can be managed in a simple cyclic or main-loop structure.
- External interactions are limited and local: PC via UART (user commands), DC motor via driver IC, potentiometer ADC, on-board LEDs. No networking or remote interfaces.
- Control is simple, with all states and event progressions determined by UART input, real-time feedback, and LED state; complex scheduling or prioritization is not required or justified.
- Design should anticipate ease of expansion (e.g., adding extra positions, refining ADC calibration, or new LED patterns) while remaining simple and modular for ease of understanding and demonstration.

# 1.0 Software Scope and Responsibility
The HVAC flap actuator software is responsible for receiving user commands via UART, validating these commands, actuating a DC motor to move a physical air flap to requested discrete positions, acquiring feedback through an ADC-connected position sensor, and reflecting current position/status through dedicated indicator LEDs. The software supports a learning/demo platform for prototyping, emphasizing modularity, clarity, and safe handling of user input, errors, and peripheral interactions.

# 2.0 Software Functional Requirements
## 2.1 User Command Handling
- SWE-REQ-001: The software shall receive user commands via UART in the form of discrete numeric flap position requests. (*SYS-REQ-017*)
- SWE-REQ-002: The software shall validate incoming UART commands to ensure they represent valid flap positions within the supported range. (*SYS-REQ-018, SYS-REQ-019*)
- SWE-REQ-003: The software shall accept and process only one user command at a time. (*SYS-REQ-020, SYS-REQ-039*)
- SWE-REQ-004: The software shall ignore invalid or out-of-range commands without generating a response or error indication. (*SYS-REQ-019*)
- SWE-REQ-005 [Implied]: The software shall process valid UART commands promptly after reception to maintain responsiveness. (*SYS-REQ-021*)

## 2.2 Flap Position Control Logic
- SWE-REQ-006: The software shall determine the required movement direction for the flap based on the current and target positions. (*SYS-REQ-003*)
- SWE-REQ-007: The software shall prevent actuation if the flap is already at the requested position. (*SYS-REQ-007*)
- SWE-REQ-008: The software shall ensure the flap does not move outside defined position limits. (*SYS-REQ-011*)
- SWE-REQ-009: The software shall stop the motor and maintain the flap at the target position when reached. (*SYS-REQ-005*)

## 2.3 Motor Control Logic
- SWE-REQ-010: The software shall control GPIO outputs to set the proper motor direction according to the target position. (*SYS-REQ-008*)
- SWE-REQ-011: The software shall enable and disable the motor using a dedicated control signal (GPIO or PWM). (*SYS-REQ-009*)
- SWE-REQ-012: The software shall de-energize (stop) the motor when the flap has reached the requested position or when an error is detected. (*SYS-REQ-010, SYS-REQ-045*)
- SWE-REQ-013 [Implied]: The software shall avoid unnecessary or excessive motor running by stopping promptly on target acquisition or error. (*SYS-REQ-012*)

## 2.4 Position Feedback Processing
- SWE-REQ-014: The software shall acquire flap position feedback using an ADC to sample the potentiometer. (*SYS-REQ-002, SYS-REQ-013*)
- SWE-REQ-015: The software shall map ADC readings to defined logical flap positions using fixed mappings in software. (*SYS-REQ-006, SYS-REQ-014, SYS-REQ-041*)
- SWE-REQ-016: The software shall ignore ADC values outside valid operating ranges mapped to supported positions. (*SYS-REQ-015, SYS-REQ-045*)
- SWE-REQ-017 [Implied]: The software shall ensure ADC resolution and filtering are sufficient for stable position detection in the demo environment. (*SYS-REQ-016*)

## 2.5 Status Indication Control
- SWE-REQ-018: The software shall use a dedicated LED to indicate power/status. (*SYS-REQ-022*)
- SWE-REQ-019: The software shall use dedicated position LEDs to reflect the current logical flap position, with one green LED ON per position. (*SYS-REQ-023, SYS-REQ-024*)
- SWE-REQ-020: The software shall update the position/status LEDs to reflect the actual position as determined from ADC feedback at all times. (*SYS-REQ-024*)
- SWE-REQ-021 [Implied]: The indication logic shall be clear and unambiguous for all allowed positions and states. (*SYS-REQ-025*)

# 3.0 Software Interface Requirements
- SWE-REQ-022: The software shall receive PC user commands via UART interface. (*SYS-REQ-033*)
- SWE-REQ-023: The software shall transmit motor direction/enable signals via GPIO to the motor driver. (*SYS-REQ-034*)
- SWE-REQ-024: The software shall acquire flap position using an ADC channel attached to the position sensor. (*SYS-REQ-035*)
- SWE-REQ-025: The software shall control dedicated GPIOs for LEDs indicating power, error, and position. (*SYS-REQ-036*)
- SWE-REQ-026 [Implied]: The software shall not use CAN, LIN, or other external networking. (*SYS-REQ-037*)

# 4.0 Software Behavioral Requirements
- SWE-REQ-027: Upon power-up, the software shall initialize all peripherals (ADC, UART, GPIO, PWM) and leave the motor OFF. (*SYS-REQ-026*)
- SWE-REQ-028: On startup, the software shall sample and store the initial flap position. (*SYS-REQ-027*)
- SWE-REQ-029: During idle, the software shall monitor for new user commands and changes in flap position. (*SYS-REQ-028*)
- SWE-REQ-030: The software shall cause the flap to move toward the requested position and detect when the target position is reached. (*SYS-REQ-029*)
- SWE-REQ-031: After reaching the target, the software shall maintain its state and ignore redundant commands unless a new target is received. (*SYS-REQ-030*)
- SWE-REQ-032: The software shall safely ignore invalid input (UART command or feedback) without undefined behavior. (*SYS-REQ-031, SYS-REQ-044*)
- SWE-REQ-033 [Implied]: No explicit state machine or production-grade diagnostics are required. (*SYS-REQ-032*)

# 5.0 Software Data and Configuration Requirements
- SWE-REQ-034: The software shall maintain a static table of ADC-to-position mappings (calibration constants) defined in code. (*SYS-REQ-006, SYS-REQ-041*)
- SWE-REQ-035: The software shall use only static calibration values for position mapping and thresholding. (*SYS-REQ-041*)
- SWE-REQ-036: The software shall not implement dynamic calibration, parameter auto-learning, or store configuration changes. (*SYS-REQ-041*)

# 6.0 Software Error Handling Requirements

- SWE-REQ-041 [Implied]: No advanced diagnostics or error recovery (timeouts, watchdog resets, or logging) are required. (*SYS-REQ-046*)

# 7.0 Software Performance and Responsiveness Requirements
- SWE-REQ-042: The software shall respond to valid user commands by changing the flap position and LED statuses promptly (in a manner observable by a human). (*SYS-REQ-043*)
- SWE-REQ-043: The software shall ensure position feedback and motor actuation updates occur without unnecessary latency, but without fixed timing constraints. (*SYS-REQ-043*)

# 8.0 Software Resource Constraint Requirements
- SWE-REQ-044: The software shall avoid dynamic memory allocation and shall use only minimal, statically allocated resources. (*SYS-REQ-048*)
- SWE-REQ-045: The software shall ensure all processing for input, control, and output is bounded and avoids unbounded execution (e.g., infinite loops, blocking waits). (*SYS-REQ-047*)
- SWE-REQ-046: The software shall maintain lightweight overall resource usage consistent with microcontroller learning platform norms. (*SYS-REQ-047*)
- SWE-REQ-047 [Implied]: The software shall not implement task-level or thread-level resource management (RTOS or concurrency). (*SYS-REQ-042*)

# 9.0 Software Testability Requirements
- SWE-REQ-048: The software shall support verification via UART control and observation of LEDs and motor motion. (*SYS-REQ-052*)
- SWE-REQ-049: Testing shall be possible via manual or batch/scripted UART command injection and visual/functional observation, with no special equipment. (*SYS-REQ-053*)
- SWE-REQ-050 [Implied]: Automated Hardware-in-the-Loop or remote verification is not required for this prototype. (*SYS-REQ-054*)

# Software Architecture – HVAC Flap Actuator Demo

## 1. Introduction / Purpose
This architectural document describes the logical structure and major software units for the HVAC Flap Actuator demonstration project (see requirements SW-REQ-001 to SWE-REQ-040). Its purpose is to:
- Ensure responsibility separation in code.
- Provide traceability for ASPICE SWE.2 standards.
- Serve as a baseline for design, implementation, and review.

No architectural choices or patterns are implied that have not been mandated by requirements. This does not prescribe execution models, scheduling, or real-time OS usage.

## 2. Candidate Architecture Styles Considered
- Monolithic C main-loop (single-file demo)
- Layered: decoupled User Cmd Handler, Position Ctrl Logic, Motor Ctrl, Feedback Acq, Status/LEDs, Config/Data
- Modular/Componentized: Each function as a unit with clear interfaces

## 3. Style Evaluation & Chosen Structure
Layered/componentized was selected, justified by:
- Clear traceability to requirements-allocated responsibilities
- Testability, maintainability, and simplicity for a learning context
- Easiest path for reviewing separation of concerns, and for demonstration
- No explicit need for RTOS/ISR/Multi-tasking — all duties can be performed in a cyclic or cooperative main loop, per reqs.

## 4. System Units and Responsibilities
| Unit                  | Responsibilities                        | Interfaces Provided        | Interfaces Used                 | Allocated SWE-REQs |
|-----------------------|-----------------------------------------|---------------------------|----------------------------------|--------------------|
| User Cmd Handler      | UART rx parsing, cmd validation, routing | CMD_IF (UART)             | DATA_IF, CTRL_IF                 | 016-019,029,037    |
| Position Ctrl Logic   | Target/actual cmp, set direction, ctrl  | CTRL_IF                   | DATA_IF, MOTOR_IF, ERR_IF        | 001-006,025-028    |
| Motor Ctrl            | Drive enable/disable, dir GPIO/PWM      | MOTOR_IF                  | CTRL_IF, GPIO/PWM_IF             | 007-012,034        |
| Feedback Acq Proc    | ADC read, map, filter, status valid      | DATA_IF                   | ADC_IF, CONF_IF, ERR_IF          | 012-015,032        |
| Status/LED Indicator  | LED logic, state display                | LED_IF                    | DATA_IF, GPIO_IF                 | 020-022,038        |
| System Config/Data    | Static cal, ranges, assignment tables    | CONF_IF                   | N/A                              | 006,032,037        |

## 6. Unit Interface Matrix
- CMD_IF: API for RX UART commands
- CTRL_IF: API for position ctrl requests and status
- MOTOR_IF: Motor drive instructions
- DATA_IF: Potentiometer value(s), logical position
- LED_IF: Current position/state to indicator logic
- CONF_IF: Static config lookups
- ERR_IF: Simple error code(s), status

## 7. Architectural Mapping to SW Requirements
- All main modules mapped to unique sets of SWE-REQs above; see table in section 4 for allocation.

## 8. Non-Selections
- No RTOS, timer interrupts, state machine patterns mandated by requirements.
- No hardware test hooks, logging, HIL, SIL, diagnostics, or networking.

## 9. Extensibility Notes (Descriptive Only)
- More positions, calibration, alternate indicator patterns, or other future learning features can be easily added by expanding table in SystemConfigData and updating logic in handlers.

# Software Low-Level Design — HVAC Flap Actuator Demo (demo-43d)

## 1. Introduction
This Software LLD documents module responsibilities and static interfaces, in direct traceability to the requirements and chosen ASPICE-compliant architecture. There is no prescribed execution or scheduling pattern. Focus is on clear separation, testability, and learnability.

## 2. Software Units and Interfaces

### 2.1 User Command Handler
- Parses and validates UART input as position commands
- Converts numeric UART data into setpoint requests
- Ignores malformed or out-of-range input (per requirements)
- API (CMD_IF): `UserCmdHandler_Process(uint8_t rx_byte)`, `UserCmdHandler_GetTarget(void)`

### 2.2 Position Control Logic
- Receives requested target, compares to actual position
- Issues direction and enable requests to Motor Controller
- Requests/coordinates feedback acquisition
- API (CTRL_IF): `PositionCtrl_Update(void)`, `PositionCtrl_GetStatus(void)`

### 2.3 Motor Controller
- Sets motor direction (GPIO) per control request
- Enables/disables drive output (GPIO/PWM)
- Stops motor on request or error state
- API (MOTOR_IF): `MotorCtrl_Set(uint8_t dir, bool enable)`, `MotorCtrl_Stop(void)`

### 2.4 Feedback Acquisition Processor
- Initiates ADC sampling
- Translates raw ADC to logical position (via config map)
- Filters/stabilizes input as needed
- API (DATA_IF): `FeedbackAcq_Trigger(void)`, `FeedbackAcq_GetPosition(void)`

### 2.5 Status/LED Indicator
- Drives status and position indication LEDs
- Reflects actual position, system state (per feedback)
- API (LED_IF): `StatusLED_Set(uint8_t pos)`, `StatusLED_ShowPower(bool on)`

### 2.6 System Config/Data
- Houses all static (const) configuration/calibration values
- Maps ADC threshold to position index, LED pin assignments, etc.
- API (CONF_IF): readonly structure reference(s)

## 3. Module Collaboration (Text Diagram)

UserCmdHandler → (CMD_IF) → PositionCtrlLogic → (CTRL_IF) → MotorCtrl
                                     ↑                   ↓
                          FeedbackAcqProc ← (DATA_IF) ←
                                     ↓
                          StatusLEDIndicator ← (LED_IF)
                          SystemConfigData (CONF_IF, structure)

## 4. Coding Outline
- Each module: one header (declares interface, types), one C file (implementation)
- Internal module data is `static`, only exposed via interface APIs
- No dynamic memory, global variables static or in `main.c` only
- All inter-module linkage via above APIs

## 6. Exclusions
- No safety, diagnostics, concurrency, interrupts, or advanced error handling beyond safe error ignores
- No RTOS, timer, or state machine pattern is coded unless needed to map requirements.
- No code for networking, vehicle comms, or automated test is included or implied.
