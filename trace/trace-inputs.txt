# 1.0 System Overview

The HVAC Flap Actuator System SHALL enable a user to command and control the position of an air flap, driven by a DC motor, with real-time feedback and visual status indication. It is intended for prototyping of automotive HVAC position control.

---

# 2.0 Flap Position Control

- SYS-REQ-001: The system SHALL allow the user to request the flap position using numeric commands corresponding to discrete positions.
- SYS-REQ-002: The system SHALL move the flap to the target position specified by each valid user command.
- SYS-REQ-003: The system SHALL stop the motor once the flap has reached the requested position.
- SYS-REQ-004: The system SHALL ignore invalid user commands.
- SYS-REQ-005: The system SHALL support a fixed number of logical flap positions, as defined in software.

---

# 3.0 Motor Control

- SYS-REQ-006: The system SHALL control a DC motor using GPIOs for clockwise and anti-clockwise rotation.
- SYS-REQ-007: The system SHALL stop the motor when the flap reaches the requested position.
- SYS-REQ-008: The system SHALL prevent the motor from running if the requested position or feedback signal is invalid.

---

# 4.0 Position Feedback Acquisition & Processing

- SYS-REQ-009: The system SHALL acquire flap position feedback using a potentiometer connected to the ADC.
- SYS-REQ-010: The system SHALL map ADC values to logical flap positions.
- SYS-REQ-011: The system SHALL update the detected flap position during operation.

---

# 5.0 User Command Interface

- SYS-REQ-012: The system SHALL receive user commands exclusively via UART.
- SYS-REQ-013: The system SHALL interpret each valid UART numeric command as a target flap position.
- SYS-REQ-014: The system SHALL not require acknowledgment or response to invalid user commands.

---

# 6.0 Status Indication

- SYS-REQ-015: The system SHALL use a power/status LED to indicate when the system is powered ON.
- SYS-REQ-016: The system SHALL use up to one green LED at a time to indicate the current flap position.
- SYS-REQ-017: The system SHALL update LED status in response to position changes and power events.

---

# 7.0 System Behavior (power-up, idle, normal, target reached, invalid input)

- SYS-REQ-018: On power-up, the system SHALL initialize all necessary peripherals (ADC, UART, GPIO, PWM).
- SYS-REQ-019: On power-up, the motor SHALL remain OFF until a valid command is received.
- SYS-REQ-020: On power-up, the system SHALL detect and indicate the current flap position.
- SYS-REQ-021: When idle, the system SHALL not move the motor until a valid command is received.
- SYS-REQ-022: The system SHALL safely ignore invalid input commands without system fault.

---

# 8.0 Interfaces (UART, motor driver, ADC, LEDs)

- SYS-REQ-023: The system SHALL interface with the user via a UART serial connection.
- SYS-REQ-024: The system SHALL interface with the DC motor via a motor driver module.
- SYS-REQ-025: The system SHALL interface with the potentiometer via an ADC channel for position feedback.
- SYS-REQ-026: The system SHALL use GPIO or PWM signals to control motor operations and LED indications.

---

# 9.0 Constraints & Assumptions

- SYS-REQ-027: The number of flap positions and associated ADC ranges SHALL be configurable in software.
- SYS-REQ-028: Only one flap actuator and one motor SHALL be controlled by the system.
- SYS-REQ-029: Only one user command SHALL be processed at a time.
- SYS-REQ-030: No attempt SHALL be made to recover from hardware failures. [Implied]
- SYS-REQ-031: No dynamic calibration SHALL be performed at runtime. [Implied]
- SYS-REQ-032: System operation SHALL assume hardware is functional unless error conditions are detected. [Implied]

---

# 10.0 Non-Functional Requirements

## 10.1 Responsiveness

- SYS-REQ-033: The system SHALL process UART commands and update flap position within a human-perceivable response time (≤ 200 ms typical). [Implied]

## 10.2 Error Handling & Edge Cases

- SYS-REQ-034: The system SHALL stop the motor if ADC readings fall outside defined ranges.
- SYS-REQ-035: The system SHALL ignore UART commands that are not recognized as valid positions.

## 10.3 Resource Constraints

- SYS-REQ-036: The system software SHALL use only available memory and resources of the target hardware, with no dynamic memory allocation.
- SYS-REQ-037: The system SHALL fit within the resource limits of the STM32F407G-DISC1 platform.

## 10.4 Maintainability & Modularity

- SYS-REQ-038: The system software design SHALL be modular to allow straightforward changes to position mapping, UI, or interfaces.

## 10.5 Testability

- SYS-REQ-039: The system SHALL facilitate testability by enabling flap movement and indication to be verified by UART commands and LED outputs.
- SYS-REQ-040: The system SHALL permit manual test cases for all major functions.

---

# Architecture-Relevant Considerations Derived from System Requirements

- The system exhibits simple control flow: commands are handled one-at-a-time (no explicit concurrency).
- Interaction complexity is low: communications are peer-to-peer—UART (user), ADC (feedback), GPIO/PWM (motor/LED).
- Control complexity is moderate: command validation, actuator/feedback mapping, and simple error handling.
- The design is expandability-friendly: additional positions, new indication styles, or new feedback mapping logic can be added with modular code changes.
- No assumptions are made regarding the underlying execution model or task scheduling.

# HVAC Flap Actuator Software Architecture (SWE.2)

## 1. Architecture Style Selection

### 1.1 Candidate Styles Considered
- Layered
- Component-based
- Monolithic

### 1.2 Evaluation
- **System Complexity:** Low to moderate (simple control, discrete commands, limited peripherals).
- **HW Interaction Needs:** High; direct interaction with UART, ADC, GPIOs.
- **Testability:** System must support unit and integration testing (SWE-REQ-048, SWE-REQ-049).
- **Maintainability:** Modularity needed for position mapping/UI/interface changes (SWE-REQ-038).
- **ASPICE L3 Expectations:** Shall trace requirements to concrete, transparent design structure, with modifiability and testability.

#### Layered Style
- + Clear separation of concerns.
- + Decouples interfaces from HW drivers and logic.
- - Unnecessary communication overhead for a simple control system.

#### Component-based Style
- + Explicit unit boundaries promote changeability/testability.
- + Matches modular design intent (SWE-REQ-038).
- + Well-matched to mapping between responsibilities and code units.

#### Monolithic Style
- + Simplicity, but lacks testability and maintainability.
- - Not suitable for ASPICE or modular/testable codebase.

### 1.3 Selected Style & Justification
- **Component-based** architecture is selected.
- It cleanly separates key concerns (command, control, feedback, indication), meets modularity/testability expectations, and aligns with ASPICE traceability and project maintainability needs.


## 2. Architecture Definition

### 2.1 Software Units & Responsibilities

A. **Command Interpreter**
   - Receive and validate UART commands (SWE-REQ-001, SWE-REQ-002, SWE-REQ-003).
   - Forward valid requests to Flap Control unit (SWE-REQ-005).

B. **Flap Control**
   - Command the Motor Control unit to reposition flap (SWE-REQ-007).
   - Ignore repeated/already achieved requests (SWE-REQ-009).
   - Block actions on invalid data (SWE-REQ-013).

C. **Motor Control**
   - Activate GPIOs to run motor in correct direction (SWE-REQ-011).
   - Stop when feedback position matches command (SWE-REQ-012, SWE-REQ-034).
   - Prevent invalid or unsafe actuation (SWE-REQ-013, SWE-REQ-014).

D. **Feedback Acquisition**
   - Read analog position from ADC (SWE-REQ-015).
   - Map ADC values to logical positions (SWE-REQ-016), per config (SWE-REQ-035).
   - Update detected state for Control & LED units (SWE-REQ-017).

E. **Status Indication**
   - Control power and position LEDs (SWE-REQ-019, SWE-REQ-020).
   - Reflect changes in state promptly (SWE-REQ-043).

F. **Hardware Interface Layer**
   - Abstract GPIO, ADC, UART driver access (SWE-REQ-022, SWE-REQ-023, SWE-REQ-024, SWE-REQ-025).

### 2.2 Software Unit Interfaces

- **Command Interpreter** exposes: [accept_command(cmd)] to Flap Control.
- **Flap Control** exposes: [set_target_position(pos)] to Motor Control.
- **Feedback Acquisition** exposes: [get_position()] to Flap Control and Status Indication.
- **Motor Control** exposes: None (actions internal, invoked by Flap Control).
- **Status Indication** exposes: [set_led_state(pos)] to Flap Control/Feedback.
- **Hardware Interface Layer** exposes: low-level drivers to above units.

### 2.3 Execution Model Statement
No explicit execution model or scheduling policy is mandated by the requirements at this stage.


## 3. Architecture Representation

### 3.1 Text-based Diagram

User UART -> [Command Interpreter] --> [Flap Control] <--> [Motor Control]
                                                      |
                                               [Feedback Acquisition]  --> [Status Indication] --> LEDs
                                                      |
                                        [Hardware Interface Layer: UART/ADC/GPIO]

### 3.2 Software Unit Table

|------------------------|-------------------------------------------------------------------------------|-----------------------------|------------------------------|

## 4. Constraints & Justifications
- All software units, data, and responsibilities are strictly derived from SWE.1/SYS-REQs. No new behavior or architectural features introduced.
- No safety/diagnostic/cybersecurity elements.
- No fixed scheduling, execution model, or concurrency is introduced, as per SWE-1/SYS-REQs (SWE-REQ-044).
- Strict separation of controller, interface, and indication logic for clarity, testability, and maintainability (SWE-REQ-038, SWE-REQ-048).

## 5. Traceability
- Each unit/responsibility is explicitly traced to SWE-REQs in brackets.
- No features present without requirement trace.

# HVAC Flap Actuator Software Low-Level Design (SWE.3)

## SWE.3 Context
- Architecture and requirements from: sw-reqs/sw-reqs.txt, sw-arch/sw-arch.txt
- Language/constraints: MISRA C; static allocation; resource, interface, and function boundaries match SWE.2

================================================================

## Software Unit: Command Interpreter

1. Responsibilities
   - Handles reception and validation of UART user commands. (SWE-REQ-001, SWE-REQ-002)
   - Forwards valid requests to Flap Control. (SWE-REQ-003, SWE-REQ-005)
   - Does not forward invalid/repeated or out-of-range commands. (SWE-REQ-003, SWE-REQ-039)

2. Internal Data Design
   - Received command buffer: statically allocated array for UART frame.
   - Command validity flag, previous command value.
   - No dynamic allocation.

3. State Machine
   - States: IDLE, WAIT_FOR_COMMAND, VALIDATE, FORWARD, IGNORE
   - Transitions on UART event or validation result; direct linear flow.

4. Algorithms & Control Flow
   - On UART RX event, store received byte.
   - Parse frame; if complete, compare to valid command list (range & format).
   - If valid and new: set flag, forward command; else clear flag, IGNORE.

5. Interfaces (APIs)
   - Provided: accept_command(cmd: uint8_t)
   - Required: UART driver (HW iface)
   - Params validated by range and protocol spec.
   - Returns: status code (OK/INVALID/REPEATED)

6. Error Handling
   - Malformed or repeated commands ignored.
   - Out-of-range or protocol errors do not propagate upstream.
   - No assertion or reset on error.

7. Resource & Timing Considerations
   - Only invoked on UART event; re-entrancy not required.
   - WCET: <10ms (single message parse/check/forward).
   - Fixed memory for buffer/flag/last_cmd.

8. Traceability
   - SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-005, SWE-REQ-039

================================================================

## Software Unit: Flap Control

1. Responsibilities
   - Handles new target position from Command Interpreter.
   - Ignores repeated/already satisfied requests. (SWE-REQ-009, SWE-REQ-031)
   - Requests actuation from Motor Control, maps position logic. (SWE-REQ-007, SWE-REQ-008)
   - Prevents commands on invalid input. (SWE-REQ-013)

2. Internal Data Design
   - Statically configured array of legal positions/thresholds.
   - Current, previous, target position variables.
   - Valid command state.

3. State Machine
   - States: WAIT_FOR_COMMAND, CHECK_POSITION, ISSUE_MOTOR_REQ, WAIT_FOR_FEEDBACK, COMPLETE
   - Transition on new command/full-feedback cycle.

4. Algorithms & Control Flow
   - On new command: check target != current.
   - If true: call Motor Control with direction.
   - Wait for feedback; if achieved, update LEDs, stop motor.

5. Interfaces (APIs)
   - Provided: set_target_position(pos: uint8_t)
   - Required: Command Interpreter, Motor Control, Feedback Acquisition, Status Indication
   - Returns: status code (BUSY/DONE)

6. Error Handling
   - Invalid or unreachable positions force request abort.
   - Bad feedback disables actuation, triggers error LED via Status Indication.

7. Resource & Timing Considerations
   - Called in sequential workflow; no async.
   - WCET: dominated by diagnostic/feedback loop (<50ms typical per iteration).

8. Traceability
   - SWE-REQ-007, SWE-REQ-008, SWE-REQ-009, SWE-REQ-013, SWE-REQ-031

================================================================

## Software Unit: Motor Control

1. Responsibilities
   - Activates/deactivates/on/off/dir signals to motor driver GPIOs under Flap Control command. (SWE-REQ-011)
   - Stops motor on position match or error. (SWE-REQ-012, SWE-REQ-034)
   - Enforces safe non-simultaneous GPIO actuation (SWE-REQ-014)

2. Internal Data Design
   - No persistent state beyond static GPIO definitions.
   - Commanded direction, activation flags.

3. State Machine
   - States: STOPPED, RUN_CW, RUN_CCW
   - Transitions based on Flap Control input; simple direct flow.

4. Algorithms & Control Flow
   - Set GPIO pin for direction.
   - Start/stop based on feedback; guard against dual activation.

5. Interfaces (APIs)
   - Required by Flap Control: motor_run(dir: enum), motor_stop()
   - Required: HW iface (GPIO), Flap Control

6. Error Handling
   - All errors (feedback/adverse event) cause motor_stop().
   - Hardware driver errors not diagnosed; no retry or escalation.

7. Resource & Timing Considerations
   - Invoked on new flap request or feedback event.
   - WCET: <5ms per actuation operation.

8. Traceability
   - SWE-REQ-011, SWE-REQ-012, SWE-REQ-014, SWE-REQ-034

================================================================

## Software Unit: Feedback Acquisition

1. Responsibilities
   - Initiates ADC read, maps analog value to logical position. (SWE-REQ-015, SWE-REQ-016)
   - Supplies stable position to Flap Control/Status Indication. (SWE-REQ-017)
   - Uses statically configured map/range. (SWE-REQ-035)

2. Internal Data Design
   - Array of threshold values; last read ADC value; last mapped position.
   - Calibration/config data static, no run-time learning.

3. State Machine
   - "None"; Event-driven call, no persistent logic beyond last-values update.

4. Algorithms & Control Flow
   - On invocation, trigger ADC, scan value, map against config.
   - Provide bounded position (range/check); ignore values outside valid window.

5. Interfaces (APIs)
   - Provided: get_position() -> pos: uint8_t
   - Required: HW iface (ADC)

6. Error Handling
   - ADC out-of-range error forces position INVALID; disables further actuation through Flap Control.

7. Resource & Timing Considerations
   - Invoked synchronously after flap request or at init.
   - WCET: <5ms per invocation.

8. Traceability
   - SWE-REQ-015, SWE-REQ-016, SWE-REQ-017, SWE-REQ-035

================================================================

## Software Unit: Status Indication

1. Responsibilities
   - Updates power and position indicator LEDs (SWE-REQ-019, SWE-REQ-020)
   - Only one position LED active at a time (SWE-REQ-021)
   - Indicates error state/feedback

2. Internal Data Design
   - Static mapping: logical position to GPIO.
   - Last state written, LED enable flags.

3. State Machine
   - "None"; synchronous update calls only.

4. Algorithms & Control Flow
   - On call: update necessary LEDs based on state, disable all non-selected LEDs.
   - Error state triggers dedicated LED or flash pattern (per config).

5. Interfaces (APIs)
   - Provided: set_led_state(pos: uint8_t, error: bool)
   - Required: HW iface (GPIO); input from Flap Control/Feedback Acquisition

6. Error Handling
   - Always reflects last known state; does not propagate failures upward.

7. Resource & Timing Considerations
   - Invoked synchronously during/after position or error event.
   - WCET: <2ms per update (one frame GPIO write).

8. Traceability
   - SWE-REQ-019, SWE-REQ-020, SWE-REQ-021

================================================================

## Software Unit: Hardware Interface Layer

1. Responsibilities
   - Statically initializes and provides APIs for UART, GPIO, ADC interaction (SWE-REQ-022, SWE-REQ-023, SWE-REQ-024, SWE-REQ-025)
   - No scheduling, buffering, or dynamic configuration.

2. Internal Data Design
   - Static memory for driver handles/config.
   - No driver state except error status.

3. State Machine
   - "None"; stateless functional calls only.

4. Algorithms & Control Flow
   - Read/write function wrappers for UART/ADC/GPIO.
   - No interrupt or DMA control logic here.

5. Interfaces (APIs)
   - Provided: uart_read(), adc_read(), gpio_set(), gpio_clear(), etc.
   - Required: Used by all above units; no unique upper-level dependency.

6. Error Handling
   - Hardware errors are status codes; no error propagation, logging, or recovery at this level.

7. Resource & Timing Considerations
   - All calls synchronous/blocking, <0.5ms/common API call.

8. Traceability
   - SWE-REQ-022, SWE-REQ-023, SWE-REQ-024, SWE-REQ-025

#include "flap_control.h"
#include "motor_control.h"
#include "feedback_acquisition.h"
#include "status_indication.h"

#define FLAP_POSITIONS  5
static uint8_t valid_positions[FLAP_POSITIONS] = {0,1,2,3,4};
static uint8_t target_position = 0;
static uint8_t current_position = 0xFF;

void flap_control_init(void) {
    // No dynamic setup required
    target_position = 0xFF;
}

void set_target_position(uint8_t pos) {
    // Check if valid position
    int found = 0;
    for (int i=0; i<FLAP_POSITIONS; ++i) {
        if (valid_positions[i] == pos) found = 1;
    }
    if (!found) {
        status_indication_set_error(true);
        return;
    }
    if (pos == current_position) return;
    // Command to motor control
    flap_dir_t dir = (pos > current_position) ? FLAP_UP : FLAP_DOWN;
    motor_run(dir);
    // Wait for feedback, simplified as direct call
    current_position = feedback_acquisition_get_position();
    if (current_position == pos) {
        motor_stop();
        status_indication_set_position(pos);
    }
}

#include "motor_control.h"
#include "hw_interface.h"

static flap_dir_t current_dir;
static int motor_active = 0;

void motor_control_init(void) {
    current_dir = FLAP_UP;
    motor_active = 0;
}

void motor_run(flap_dir_t dir) {
    // Enforce safe control: never set both directions
    gpio_clear(GPIO_MOTOR_CW);
    gpio_clear(GPIO_MOTOR_CCW);
    if (dir == FLAP_UP) gpio_set(GPIO_MOTOR_CW);
    else gpio_set(GPIO_MOTOR_CCW);
    current_dir = dir;
    motor_active = 1;
}

void motor_stop(void) {
    gpio_clear(GPIO_MOTOR_CW);
    gpio_clear(GPIO_MOTOR_CCW);
    motor_active = 0;
}

    uint16_t adc_val = adc_read();
    for (int i=0; i<FLAP_POSITIONS; ++i) {
        if (adc_val < adc_thresholds[i]) return (uint8_t)i;

void status_indication_set_position(uint8_t pos) {
    // Switch LEDs
    for (int i=0; i<NUM_POSITION_LEDS; ++i)
        gpio_clear(POSITION_LED_START+i);
    gpio_set(POSITION_LED_START+pos);
    current_led = pos;
    error_state = false;
}
void status_indication_set_error(bool err) {
    error_state = err;
    // Light a dedicated error LED; placeholder: gpio_set(9);
    if (err) gpio_set(9); else gpio_clear(9);
}
