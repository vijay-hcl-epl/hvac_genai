# 1.0 System Overview

The HVAC Flap Actuator System regulates airflow within a Heating, Ventilation, and Air Conditioning unit by controlling the position of an air inlet/outlet flap. This system reacts to user commands, acquires real-time flap position via a potentiometric feedback system, controls a DC motor for positioning, and provides user feedback via LEDs and UART, enabling learning and demonstration of automotive system engineering processes.

# 2.0 Flap Position Control Requirements

SYS-REQ-001: The system shall allow selection of a target flap position based on discrete user commands via the command interface.
SYS-REQ-002: The system shall compare actual flap position with the target position at a rate sufficient for visible responsiveness. [Implied]
SYS-REQ-003: The system shall drive the flap via the motor such that the actual position approaches the target within the physical and electrical limits of the actuator.
SYS-REQ-004: The system shall hold the flap at the most recently commanded position unless a new user command is received.

# 3.0 Motor Control Requirements

SYS-REQ-005: The system shall provide control signals for forward and reverse motion of the DC motor based on the required direction for flap positioning.
SYS-REQ-006: The system shall enable the motor only during active repositioning, disabling it when the target position is achieved or at rest.
SYS-REQ-007: The system shall stop the motor if a mechanical end-stop or positional limit is detected.

# 4.0 Position Feedback Acquisition and Processing

SYS-REQ-008: The system shall acquire analog feedback from a potentiometer connected to the flap shaft to determine its actual position.
SYS-REQ-009: The system shall use an ADC to convert the potentiometer voltage to a digital value.
SYS-REQ-010: The system shall map ADC values to logical flap positions as defined in system configuration.
SYS-REQ-011: The position acquisition and mapping shall be accurate enough to visibly reflect each position change on indicator LEDs. [Implied]

# 5.0 User Command Interface Requirements

SYS-REQ-012: The system shall receive user commands via UART.
SYS-REQ-013: The system shall validate user commands as per defined protocol.
SYS-REQ-014: The system shall reject and safely ignore invalid or out-of-sequence user commands, preserving the previous target position.

# 6.0 Status Indication Requirements

SYS-REQ-015: The system shall indicate power or status using a dedicated LED indicator.
SYS-REQ-016: The system shall use one or more LEDs to indicate the current flap position.

# 7.0 System Behavioral Requirements

SYS-REQ-017: The system shall perform initial position determination and all necessary initializations on power-up.
SYS-REQ-018: During idle state, the system shall minimize energy usage and avoid unnecessary actuator movement. [Implied]
SYS-REQ-019: The system shall accurately drive the flap to requested positions in normal operation.
SYS-REQ-020: The system shall confirm and hold the target position; any deviation shall trigger repositioning attempts or diagnostics. [Implied]
SYS-REQ-021: The system shall safely handle invalid/unrecognized inputs or failures by halting movement and providing a status indication.

# 8.0 System Interface Requirements

SYS-REQ-022: The system shall interact with a UART transceiver for command exchange with the user/test interface.
SYS-REQ-023: The system shall provide output signals suitable for the connected DC motor driver circuit.
SYS-REQ-024: The system shall receive potentiometer signals and interface with the ADC for position feedback.
SYS-REQ-025: The system shall provide drive signals for status and position indicator LEDs.

# 9.0 Constraints and Assumptions

SYS-REQ-026: The system shall operate within the input voltage, environment, and load constraints specified by the demonstration setup.
SYS-REQ-027: No external safety, cyber, or placeholder/mechanical device is assumed unless specified in the demonstration platform description. [Implied]

# 10.0 Non-Functional Requirements

## 10.1 Responsiveness Expectations
SYS-REQ-028: The system shall provide visible feedback or observable position changes to user commands within a reasonable demonstration interval, typically under 2 seconds. [Implied] (No fixed minimum or maximum timing requirements are specified unless provided by the demonstrator.)

## 10.2 Error Handling and Edge Cases
SYS-REQ-029: The system shall ignore and indicate any command or feedback outside the defined range as an error condition.
SYS-REQ-030: The system shall ensure the actuator never drives the motor past its mechanical end stops. [Implied]
SYS-REQ-031: The system shall maintain predictable, bounded behavior in the presence of unexpected conditions (e.g., power loss, miswiring). [Implied]

## 10.3 Resource Constraints
SYS-REQ-032: The implementation shall be lightweight in resource usage, reflecting an embedded learning/demonstration system. [Implied]

## 10.4 Maintainability and Modularity
SYS-REQ-033: The system shall separate the functions of position control, user interface, feedback processing, and indication to promote ease of understanding. [Implied]

## 10.5 Testability
SYS-REQ-034: The system shall provide observable behaviors (position, status indication, command interface) supporting both manual and automated testing approaches. [Implied]

# 11.0 Architecture-Relevant Considerations Derived from System Requirements

- All system responsibilities can be logically separated into position control, motor control, feedback acquisition/processing, user command handling, and user feedback/indication.
- No explicit requirement for concurrent or multi-threaded operation; responsibilities can be handled sequentially or otherwise based entirely on implementation choice.
- Control loop frequency, execution order, or background/foreground distinction is not mandated; only responsiveness and correctness of reaction must be met.
- There are no complex, real-time, or safety-critical behaviors; primary system expansion involves adding commands or feedback types, not changing the underlying control/data structure.
- All decisions regarding architecture (layering, modularity, separation of concerns) may be guided to maximize maintainability, clarity, and reuse for a learning or demo scenario, not for production safety or scalability.

# 1.0 Software Scope and Responsibility

The software for the HVAC Flap Actuator System executes on a microcontroller. It is responsible for:
- Receiving user commands to set flap position via UART interface
- Acquiring and processing position feedback from a potentiometric sensor using the ADC
- Driving a DC motor for precise movement of the flap
- Validating, interpreting, and responding to commands, errors, and statuses
- Indicating system status and flap position via LEDs

# 2.0 Software Functional Requirements

- SWE-REQ-003: The software shall reject and safely ignore invalid or out-of-sequence commands, preserving the previous target position. (SYS-REQ-014)

- SWE-REQ-006: The software shall determine and provide the required direction to reposition the flap via the motor. (SYS-REQ-003, SYS-REQ-005)
- SWE-REQ-007: The software shall hold the flap position after it reaches the target, unless a new user command is received. (SYS-REQ-004)

## 2.3 Motor Control Logic

# Software Architecture Document – HVAC Flap Actuator

## 1. Purpose and Scope
This document details the software architectural structure enabling the system and software requirements for the HVAC flap actuator system.

## 2. Architecture Overview
Selected style: Layered, componentized with explicit functional separation per requirements.
All responsibilities are implemented as separate, loosely coupled software units:

- User Command Handler
- Position Control Logic
- Motor Control Unit
- Feedback Acquisition & Processing
- Status/LED Indication
- Configuration & Data Services

No scheduling or execution model is specified – all control is driven by user commands and continuous feedback acquisition as required per requirements.


## 3. Structure

#### 3.1. Top-Level Block View (Layered)

- Application Layer
  - User Command Handler (receives & validates UART input, initiates position updates)
  - Status/LED Indication (reports current position, power, error states)
- Control Layer
  - Position Control Logic (derives movement signals from actual vs. target comparison, exposes idle/active/safe states)
- Service Layer
  - Motor Control Unit (provides forward/reverse/enable outputs; ensures limits)
  - Feedback Acquisition & Processing (periodically reads ADC, converts voltage to logical position)
  - Configuration & Data (holds all calibration, mapping, and configuration data as single accesspoint)

#### 3.2. Interfaces

| Unit                         | Interfaces Provided                       | Interfaces Used                 |
|------------------------------|-------------------------------------------|---------------------------------|
| User Command Handler         | cmd_valid, new_target_pos                 | UART driver, config/data        |
| Position Control Logic       | ctrl_signals (move fwd/rev, idle/safe), pos_status | Feedback Processing, config/data |
| Motor Control Unit           | driver_signals (fwd/rev/enable)           | ctrl_signals, config/data      |
| Feedback Acquisition         | current_pos, validity                     | ADC hardware, config/data      |
| Status/LED Indication        | led_states, error_status                  | pos_status, config/data        |
| Config/Data                  | system parameters, maps                   | N/A                            |

#### 3.3. Data Flow (Narrative)

- User input via UART triggers User Command Handler.
- Handler validates/decodes command, issues new target to Position Control Logic.
- Position Control continuously compares the actual position (from Feedback Acquisition) to the target, deriving motor direction.
- Motor Control Unit drives output pins accordingly, referencing positional/limit data.
- Feedback Acquisition regularly polls ADC, passes processed state to Position Control.
- Status/LED Indication presents real-time status through LEDs based on updates.
- All configuration/calibration data are accessed in a read-only fashion by all units.

#### 3.4. Architectural Constraints & Features

- No direct cross-unit data dependencies (all interfaces are mediated via function calls or message passing).
- Supports mock/test harness substitution of all units for demo/learning/test purposes.
- Minimal dependencies: only standard embedded C; modules implemented for static or dynamic linking.

## 4. Traceability
All architectural elements directly serve one or more software-level requirements (mapping available on request).

## 5. Exclusions
No scheduling, OS, periodicity, or explicit real-time mechanism is present at the architectural level.
No hardware abstraction layer is needed beyond direct peripheral and GPIO interfacing.

## 6. Architecture Diagram (ASCII)

```
+---------------------------+
| User Command Handler      |
+-------------+-------------+
              |
              v
+-------------+-------------+
| Position Control Logic    |
+------+------+-------------+

+------------+ +--------------+
       |                |
```

## 7. Justification
- Strict separation per requirements enables easy learning and demo of requirement tracing, code modularity, and test.
- No unnecessary layering, OS, or real-time dependency.
- Expansion (more commands, positions, error diagnoses) would require only minimal adjustment at module boundary.

# Software Low Level Design (LLD): HVAC Flap Actuator

## 1. Purpose
This LLD specifies the functional decomposition and detailed interface specification for each software unit identified in the architecture, ready for C implementation for a learning/demo project.

## 2. Unit Decomposition and API

### 2.1 User Command Handler
- Function: `void CMDH_ProcessUART(void);`
  - Parses incoming UART string, validates protocol, extracts target position.
  - Stores new valid command or ignores invalid command.
- Public API:
  - `uint8_t CMDH_GetTargetPosition(void);`
  - `bool CMDH_HasNewCommand(void);`

### 2.2 Position Control Logic
- Function: `void POSC_Update(void);`
  - Compares actual (from feedback) vs. target position, sets control state.
- Public API:
  - `void POSC_SetTarget(uint8_t pos);`
  - `uint8_t POSC_GetCurrentState(void); // enum: Idle/Moving/Error`

### 2.3 Motor Control Unit
- Function: `void MOTC_Actuate(uint8_t direction, bool enable);`
  - Drives corresponding outputs, manages enable/fault logic.
- API:
  - `void MOTC_Stop(void);`

### 2.4 Feedback Acquisition & Processing
- Function: `void FBK_Acquire(void);`
  - Reads ADC, calculates current position.
- API:
  - `uint16_t FBK_GetRawADC(void);`
  - `uint8_t FBK_GetLogicalPosition(void);`
  - `bool FBK_IsValid(void);`

### 2.5 Status/LED Indication
- Function: `void LEDI_Update(uint8_t pos, bool error);`
  - Drives GPIO/LEDs based on position, error info.
- API:
  - None; used only by main/control logic.

### 2.6 Configuration & Data
- Structure: `typedef struct {
    uint16_t adc_pos_thresholds[NUM_POSITIONS];
    uint8_t  num_positions;
    // ... any calibration/test params ...
} config_data_t;`
- API:
  - `const config_data_t* CNF_Get(void);`


## 3. Module Dependencies & Mockability
- Each module exposes its API in a header file, is compiled separately, and can be stubbed/mocked for test/demo runs.

## 4. Design Constraints
- All functions implement statically-allocated (no malloc), static state only.
- No blocking, infinite loop, or delay call in any worker function; sequencing done in main control loop/invoker.
- All interrupts, periodic mechanisms, or callbacks to be architecture configuration only, not visible in LLD.

## 5. Extensibility/Modifiability Notes
- Additional positions or commands extend only lookup/config and enum types.
- Error handling adjustable via status code returns or flags (to support learning, test).

## 6. Traceability
- All LLD elements are mapped to software requirements (mapping available upon request).
- No new functionality, hardware, or architectural mechanism is introduced.
