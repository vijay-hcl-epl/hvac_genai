1.0 System Overview

SYS-REQ-001: The system SHALL control the position of an HVAC flap actuator as commanded by the user via a defined interface.
SYS-REQ-002: The system SHALL provide real-time feedback of flap position to the user interface.
SYS-REQ-003: The system SHALL operate using power supplied via the primary system supply voltage.
[Implied]

2.0 Flap Position Control

SYS-REQ-004: The system SHALL accept user input to command the flap position between fully closed and fully open.
SYS-REQ-005: The system SHALL adjust the flap position to match the user command within the physical limits of actuator travel.
SYS-REQ-006: The system SHALL prevent motion beyond physical flap limits.
[Implied]

3.0 Motor Control

SYS-REQ-007: The system SHALL control the actuator motor to increase, decrease, or maintain the flap position.
SYS-REQ-008: The system SHALL disengage the motor when the requested flap position matches the feedback position within allowable tolerance.
SYS-REQ-009: The system SHALL detect and report motor faults (e.g., stall, open/short circuit).

4.0 Position Feedback Acquisition & Processing

SYS-REQ-010: The system SHALL acquire flap position feedback via an analog or digital sensor.
SYS-REQ-011: The system SHALL process sensor data to determine current position with a tolerance of ±3% of full scale.
SYS-REQ-012: The system SHALL detect sensor faults (out-of-range or missing signals).
[Implied]

5.0 User Command Interface

SYS-REQ-013: The system SHALL receive user flap position commands via the defined hardware/software interface (e.g., UART, buttons, etc.).
SYS-REQ-014: The system SHALL acknowledge receipt of valid commands.
SYS-REQ-015: The system SHALL reject and indicate any invalid command or out-of-range request.

6.0 Status Indication

SYS-REQ-016: The system SHALL indicate flap position and system status (e.g., movement, target reached, error, idle) via external LEDs or other defined means.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)

SYS-REQ-017: On power-up, the system SHALL initialize all internal variables, outputs, and state indication.
SYS-REQ-018: When idle, the system SHALL minimize power consumption and maintain feedback monitoring.
SYS-REQ-019: When a valid target is reached, the system SHALL maintain flap position and indicate "target reached" status.
SYS-REQ-020: Upon invalid input, the system SHALL not initiate motion and SHALL provide a clear indication of input error.

8.0 Interfaces (UART, motor driver, ADC, LEDs)

SYS-REQ-021: The system SHALL support communication via UART for receiving commands and/or providing status.
SYS-REQ-022: The system SHALL interface with the actuator motor driver.
SYS-REQ-023: The system SHALL utilize ADC channels or relevant interface to acquire analog position feedback.
SYS-REQ-024: The system SHALL control LEDs for status indication.
[Implied]

9.0 Constraints & Assumptions

SYS-REQ-025: The system SHALL operate within environmental conditions specified in the project documentation.
SYS-REQ-026: The actuator position sensor is assumed to be calibrated and linear within the usable range.
[Implied]

1.0 Software Scope & Responsibility

The software is responsible for managing all functions necessary to control and monitor the HVAC flap actuator according to user commands, feedback signals, and status indication requirements. It interprets user requests, processes sensor data, commands motor actuation, manages diagnostics, and coordinates system outputs within the context of an MCU (ADC, GPIO, UART, LEDs, timers). The software does not modify system-level requirements or physical system constraints, but implements, in a modular and testable way, the logic, interface management and data processing specified at the system level.

----------------------------
ARCHITECTURE STYLE SELECTION
----------------------------

Candidate Styles Considered:
1. Monolithic (all logic in a single unit)
2. Layered (separation: application logic, platform abstractions, I/O/HW)
3. Component-based (larger modules with clear interfaces)

Evaluation:
- System complexity is low, with logical separation between user command handling, actuator/motor control, feedback acquisition, and status indication (SWE-REQ-001, SWE-REQ-005, SWE-REQ-011, SWE-REQ-013).
- HW interaction is clearly defined at the interface level (SWE-REQ-016, SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-020).
- Testability and maintainability are explicitly demanded (SWE-REQ-020, SWE-REQ-028, SWE-REQ-037).
- ASPICE L3 requires clear unit boundaries and interfaces, not monolithic.

Selection: Layered Architecture
- The layered style allows modular implementation and separation of core logic from platform hardware interfaces, while keeping units at a maintainable granularity for ASPICE alignment.

Rejection Rationale:
- Monolithic: Rejected—requirements demand clear separation and modularity for verification and test.
- Component-based: Overly complex for current requirements, as it would partition further than traceable responsibilities warrant.

----------------------------
SOFTWARE ARCHITECTURE DEFINITION
----------------------------

Software Units & Responsibilities:

1. Command Handler
   - Responsibilities: Interpret and validate user commands (SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-004). Reject and acknowledge input.
   - Interfaces Provided: Command interface.
   - Interfaces Used: System State Manager, Status Indicator.

2. Flap Control Logic
   - Responsibilities: Calculate target position, enforce limits, idle/active transitions (SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-023, SWE-REQ-025).
   - Interfaces Provided: Target position command.
   - Interfaces Used: Command Handler, Motor Driver Interface, Position Feedback Processor.

3. Motor Driver Interface
   - Responsibilities: Command motor direction, enable/disable, fault feedback. No direct hardware layer logic. (SWE-REQ-008, SWE-REQ-009, SWE-REQ-010, SWE-REQ-018)
   - Interfaces Provided: Motor control API.
   - Interfaces Used: Flap Control Logic.

4. Position Feedback Processor
   - Responsibilities: Acquire/process position sensor data, validate signal, provide current position (SWE-REQ-011, SWE-REQ-012, SWE-REQ-017).
   - Interfaces Provided: Position data, error notification.
   - Interfaces Used: Flap Control Logic, System State Manager.

5. Status Indicator
   - Responsibilities: Manage LEDs or indicator output for system status, target reached, error (SWE-REQ-013, SWE-REQ-014, SWE-REQ-015, SWE-REQ-019).
   - Interfaces Provided: Status output API.
   - Interfaces Used: System State Manager.

6. System State Manager
   - Responsibilities: System-level state transitions: power-up init, idle, active, error (SWE-REQ-021, SWE-REQ-022, SWE-REQ-024, SWE-REQ-025, SWE-REQ-031).
   - Interfaces Provided: State transition API.
   - Interfaces Used: All units needing status/state.

7. HW Abstraction Layer (HAL)
   - Responsibilities: Platform abstraction for UART/ADC/GPIO (SWE-REQ-016, SWE-REQ-017, SWE-REQ-018, SWE-REQ-019, SWE-REQ-020). No logic beyond interface definition.
   - Interfaces Provided: Hardware APIs for UART, ADC, GPIO/LEDs.
   - Interfaces Used: Motor Driver Interface, Position Feedback Processor, Status Indicator.
