1.0 System Overview

The HVAC flap actuator system is designed as a prototype to demonstrate and validate embedded control processes. It enables user-controlled actuation of an air flap, common in automotive HVAC systems, by commanding a DC motor to rotate the flap between discrete, mapped positions. Position feedback is obtained via a potentiometer connected to an ADC, while a microcontroller coordinates the actions based on user input via UART. System states and flap position are indicated using LEDs. All system interactions are local; there is no vehicle network connectivity. The design emphasizes clarity, testability, and simplicity for learning and process demonstration purposes.

2.0 Flap Position Control Requirements

SYS-REQ-001: The system shall allow the user to select a target flap position via UART command input.
SYS-REQ-002: The system shall continuously compare the current flap position against the target position.
SYS-REQ-003: The system shall actuate the DC motor to move the flap toward the target position upon receiving a valid command.
SYS-REQ-004: The system shall stop the motor when the flap reaches the target position.
SYS-REQ-005: The system shall hold the flap in position once the target is reached.
SYS-REQ-006: The system shall support a fixed number of discrete flap positions, mapped from ADC ranges (e.g., 0 to 5 positions).
SYS-REQ-007: [Implied] The system shall define position boundaries in software using fixed ADC ranges.

3.0 Motor Control Requirements

SYS-REQ-008: The system shall control the motor direction using GPIO outputs to the motor driver.
SYS-REQ-009: The system shall enable or disable the motor via a dedicated enable signal (e.g., PWM or GPIO).
SYS-REQ-010: The motor shall stop automatically once the target flap position is detected.
SYS-REQ-011: The system shall be able to drive the motor clockwise or anti-clockwise to reach the requested flap position.
SYS-REQ-012: [Implied] The system shall prevent motor movement upon detection of invalid or out-of-range feedback values.

4.0 Position Feedback Acquisition and Processing

SYS-REQ-013: The flap position shall be measured using a potentiometer mechanically coupled to the flap.
SYS-REQ-014: The potentiometer output shall be acquired via an ADC channel of the microcontroller.
SYS-REQ-015: The system shall map the ADC readings to discrete logical flap positions.
SYS-REQ-016: The system shall periodically acquire position data to update the system state.
SYS-REQ-017: [Implied] The ADC range mapping shall be statically configured in software for each supported position.

5.0 User Command Interface Requirements

SYS-REQ-018: The system shall receive user commands as simple numeric values over UART.
SYS-REQ-019: Each received command value shall correspond to a supported flap position.
SYS-REQ-020: The system shall validate user commands for correctness and range.
SYS-REQ-021: On receipt of an invalid command, the system shall safely ignore the command and take no action or response.
SYS-REQ-022: [Implied] The system shall not transmit acknowledgment or error messages for invalid commands.

6.0 Status Indication Requirements

SYS-REQ-023: The system shall provide a visual indication of power-on/status using a dedicated LED.
SYS-REQ-024: The system shall indicate the current flap position through a distinct green LED for each possible position.
SYS-REQ-025: At most one green position LED shall be ON at any time, corresponding to the current flap position.
SYS-REQ-026: [Implied] LED indication shall be immediate and directly reflect the current detected system state.

7.0 System Behavioral Requirements

SYS-REQ-027: On power-up, the system shall initialize all necessary peripherals (ADC, UART, GPIO, PWM).
SYS-REQ-028: On power-up, the motor shall remain OFF until a valid target position command is received.
SYS-REQ-029: The system shall read flap position from the potentiometer during initialization and set initial LED indication accordingly.
SYS-REQ-030: While idle (awaiting command), the system shall maintain current flap position and status indication.
SYS-REQ-031: When moving the flap, the system shall update status indicators to reflect position changes.
SYS-REQ-032: Upon reaching the target position, the system shall stop the motor and update the LED indication.
SYS-REQ-033: Invalid input or conditions (e.g., illegal UART command, out-of-range ADC) shall be handled without resulting in system fault or crash.
SYS-REQ-034: [Implied] The system shall not require explicit user reset for recovery from invalid input.

8.0 System Interface Requirements

SYS-REQ-035: The system shall support UART as the input interface for user commands from a PC/laptop.
SYS-REQ-036: The system shall interface with a motor driver module to control a single DC motor.
SYS-REQ-037: The system shall acquire analog position feedback from the potentiometer through an ADC interface.
SYS-REQ-038: The system shall control LEDs for visual feedback using GPIO outputs.
SYS-REQ-039: [Implied] The motor enable and speed shall be controlled using a PWM-capable output or GPIO, as appropriate.

9.0 Constraints and Assumptions

SYS-REQ-040: Only one flap and one motor are used in the system.
SYS-REQ-041: Only one user command is processed at any time; concurrent user command handling is not required.
SYS-REQ-042: Hardware is assumed to operate correctly unless feedback is physically out of valid range.
SYS-REQ-043: No vehicle network integration (e.g., CAN, LIN) is required; all operations are local.
SYS-REQ-044: Dynamic calibration is not required; all configuration/calibration is fixed in software.
SYS-REQ-045: [Implied] System is designed primarily for learning and demonstration and may omit production diagnostics or safety features.

10.0 Non-Functional Requirements

10.1 Responsiveness Expectations
SYS-REQ-046: The system shall provide observable responsiveness to user input, such that commands are acted upon promptly in normal operating conditions.
SYS-REQ-047: No specific timing constraints are enforced unless explicitly stated elsewhere.

10.2 Error Handling and Edge Cases
SYS-REQ-048: The system shall safely ignore invalid UART commands.
SYS-REQ-049: If ADC feedback is out of range, the system shall stop the motor and indicate the state safely.
SYS-REQ-050: Unexpected but simple hardware or operating conditions shall not cause system crashes or require reset.

10.3 Resource Constraints
SYS-REQ-051: The system implementation shall be lightweight, using minimal embedded resources.
SYS-REQ-052: System behavior shall be predictable and bounded within normal operation.

10.4 Maintainability and Modularity
SYS-REQ-053: System software shall be organized to allow clear separation of functions (e.g., motor control, command processing, feedback mapping).
SYS-REQ-054: Implementation shall strive for clarity and ease of modification for education and demonstration.

10.5 Testability
SYS-REQ-055: The system shall support observability through both LEDs and UART.
SYS-REQ-056: The system shall support manual and script-based testing as described by the use case.


Architecture-Relevant Considerations Derived from System Requirements

The system operates a single concurrent control function (flap positioning) without external network obligations or multiple interacting subsystems. Interactions are limited to local hardware (motor, potentiometer, LEDs, UART interface). The control complexity remains low, determined primarily by mapping user commands to discrete positioning actions and updating indication status. The prototype nature enables straightforward expansion (e.g., more positions or interface sophistication), but requirements avoid prescribing execution models or periodic behavior. Software structure should remain modular to separate concerns (e.g., command input, motor logic, feedback processing), but there is no requirement for RTOS, state machines, or explicit task scheduling.

- Receiving user commands for flap position selection via UART

# Software Architecture for HVAC Flap Actuator System

## 1. Architecture Style Selection

### Candidate Architecture Styles Considered
- Layered Architecture
- Component-based Architecture
- Monolithic (Procedural) Architecture

### Evaluation
- **Layered Architecture:** Provides separation (I/O, logic, drivers), promotes maintainability/modularity, suitable for testability, maps well to ASPICE modularity, and supports future extensions. Slightly heavier than pure monolithic but justified by requirements for modularity and clear separation of concerns (see SYS-REQ-053, SYS-REQ-054).
- **Component-based Architecture:** Would define clear component boundaries, but the system does not have multiple independent, complex components—most functionality is closely coupled.
- **Monolithic Architecture:** Minimum overhead. However, it does not satisfy explicit requirements for modularity and separation of functions (see SYS-REQ-053, SWE-REQ-054).

### Chosen Style and Justification
**Layered Architecture** is selected. It directly addresses system requirements for modularity, maintainability, and clarity (see SYS-REQ-053/054, SWE-REQ-054) and aligns with ASPICE Level 3 expectations for separation of concerns without undue complexity.

## Software Unit: Command Processor

1. Responsibilities
- Parses received UART data and converts to numeric command.
- Validates command against supported positions.
- Updates target position in shared state if valid.
- Does NOT directly drive hardware or actuate motor.
- Does NOT acknowledge or reply to invalid commands (see SWE-REQ-004).

2. Internal Data Design
- `received_command`: Temporary storage for parsed UART value.
- `command_valid` (bool): Sets after command parsing/validation.

3. State Machine (if applicable)
- States: IDLE, RECEIVED_COMMAND, VALIDATED, INVALID_COMMAND.
- Events: UART RX complete, Parse error, Validation success/fail.
- Transitions: 
    - IDLE → RECEIVED_COMMAND (on UART RX)
    - RECEIVED_COMMAND → VALIDATED (on successful parse)
    - RECEIVED_COMMAND → INVALID_COMMAND (on parse fail)
    - VALIDATED → IDLE, INVALID_COMMAND → IDLE on process complete.
- No persistent state except while handling command.

4. Algorithms and Control Flow
- On UART RX event:
    1. Parse received bytes.
    2. If parse succeeds and value is in position table: set `command_valid = true` and update target position.
    3. Else, set `command_valid = false`. No outbound response.
- Pseudocode:
    - receive_uart() → parse → if valid: update_target(), else: ignore.

5. Interfaces (APIs)
- Provides: `process_u_command(data)`: Accepts UART buffer, returns status.
- Requires: `set_target_position(pos)` from Control Logic; `get_position_map()` from Feedback Mapper.

6. Error Handling
- Ignores malformed/invalid commands (SWE-REQ-003, SWE-REQ-040).
- No error is propagated externally for invalid commands.

7. Resource and Timing Considerations
- Triggered by UART RX event.
- Quick validation and update logic.
- Not re-entrant; expects sequential command processing.

8. Traceability to SWE Requirements
- SWE-REQ-001, 002, 003, 004, 040; interfaces to Control Logic (SWE-REQ-024, 025).

---

## Software Unit: Control Logic

1. Responsibilities
- Evaluates current flap position vs. target.
- Initiates/terminates motor actuation.
- Updates status for use by LED Driver.
- Does NOT directly parse commands, read ADC, or toggle GPIO.

2. Internal Data Design
- `target_position` (int, from Command Processor)
- `current_position` (int, from Feedback Mapper)
- `state`: IDLE, MOVING, AT_TARGET, ERROR
- Config: none (beyond position mapping supplied)

3. State Machine
- States: IDLE (await command), MOVING (drive motor), AT_TARGET, ERROR
- Events: command_valid, position_change, error_detected
- Entry/exit:
    - IDLE on startup or after reaching/holding position
    - MOVING after a new valid command
    - AT_TARGET after reaching final destination
    - ERROR on irrecoverable sensor/motor error

4. Algorithms and Control Flow
- On valid command: compare `target_position` to `current_position`
- If not equal: command Motor Driver to move toward `target_position` (choice of direction)
- On each ADC update: check for arrival at target. If arrived – stop Motor Driver and update status.
- If position is out of bounds or can't be reached: enter ERROR; halt movement.

5. Interfaces (APIs)
- Provides: `evaluate_position()` (called on new command or feedback update). Returns control actions.
- Requires: `get_current_position()` (Feedback Mapper), `actuate_motor(direction)` (Motor Driver), `set_led_status(state)` (LED Driver)

6. Error Handling
- If target unreachable or feedback invalid: stop motor, set status to ERROR

7. Resource and Timing Considerations
- Event-driven (by command or position change)
- Brief execution on event
- Not re-entrant but tolerant to fast sequential events

8. Traceability to SWE Requirements
- SWE-REQ-005, 006, 007, 008, 013, 042; interfaces to Motor/LED/Feedback (SWE-REQ-025, 027)

---

## Software Unit: Feedback Mapper

1. Responsibilities
- Converts ADC readings to logical position index.
- Validates raw ADC feedback against mapping/thresholds.
- Supplies position and validity state to Control Logic.
- Does NOT initiate ADC acquisition or control motor.

2. Internal Data Design
- `adc_value` (latest ADC sample)
- `position_mapping[]`: Static ADC ranges for each position
- `current_position` (int)
- `valid_feedback` (bool)

3. State Machine
- No explicit state machine; single-shot conversion logic per acquisition.
- Control flow: on ADC update, update mapping and validity flags.

4. Algorithms and Control Flow
- On ADC update:
    1. Map value to the corresponding discrete position via static mapping.
    2. If out of defined range: set `valid_feedback = false`, else update `current_position`, set `valid_feedback = true`.

5. Interfaces (APIs)
- Provides: `map_adc_to_position(adc_val)`, `is_feedback_valid()`
- Requires: `get_adc_value()` (ADC Driver)

6. Error Handling
- If ADC value is out-of-bounds: `valid_feedback = false`, reported to Control Logic (SWE-REQ-041, 042)

7. Resource and Timing Considerations
- Called event-driven per ADC update
- Minimal/quick processing, low resource

8. Traceability to SWE Requirements
- SWE-REQ-016, 017, 018, 019, 037, 041

---

## Software Unit: Motor Driver

1. Responsibilities
- Drives GPIO/PWM to control DC motor direction and enable/disable.
- Stops motor on command or on error signal.
- Does NOT evaluate position or validate commands.

2. Internal Data Design
- `motor_enable` (bool), `motor_direction` (enum)
- GPIO/PWM pins (abstracted, not enumerated here)

3. State Machine
- States: OFF, RUN_CW, RUN_CCW
- Events: enable/disable, change direction
- Entry/exit: always passes through OFF when changing direction

4. Algorithms and Control Flow
- On `actuate_motor(dir)`:
    - If enable & direction change needed: disable, set direction, enable
- On `stop_motor()`: disable outputs

5. Interfaces (APIs)
- Provides: `actuate_motor(direction)`, `stop_motor()`
- Requires: GPIO/PWM hardware interface

6. Error Handling
- On error from Control Logic: stop motor, report status if requested

7. Resource and Timing Considerations
- Direct, blocking operations; never re-entrant

8. Traceability to SWE Requirements
- SWE-REQ-011, 012, 013, 014, 015, 025

---

## Software Unit: LED Driver

1. Responsibilities
- Controls status and position indicator LEDs per Control Logic commands.
- Ensures at most one green (position) LED on at a time.
- Does NOT interpret control logic, only acts as instructed.

2. Internal Data Design
- `status_led_state`, `position_led_states[]` (one per position)

3. State Machine
- No explicit state machine: immediate action per command

4. Algorithms and Control Flow
- On `set_led_status(state)`: evaluate input state, update hardware outputs (abstracted)

5. Interfaces (APIs)
- Provides: `set_led_status(state)`
- Requires: GPIO hardware interface

6. Error Handling
- Ignores redundant/invalid states safely

7. Resource and Timing Considerations
- Called event-driven by Control Logic; no long processing

8. Traceability to SWE Requirements
- SWE-REQ-020, 021, 022, 023, 027, 032, 033, 051

## Software Unit: UART Driver

1. Responsibilities
- Low-level RX/TX handling for UART bus
- Buffers data; provides completed command to Command Processor
- Does NOT decode or interpret messages

2. Internal Data Design
- `rx_buffer[]`, `tx_buffer[]`, buffer pointers

3. State Machine
- RX/TX FSM as required by UART hardware abstraction

4. Algorithms and Control Flow
- RX complete interrupt: populate buffer, signal Command Processor

5. Interfaces (APIs)
- Provides: `uart_rx_complete(data)` event/reference
- Requires: MCU UART HW interface

6. Error Handling
- On framing/overrun: drop data, signal error status (internally only)

7. Resource and Timing Considerations
- HW-driven; not re-entrant

8. Traceability to SWE Requirements
- SWE-REQ-024, 050

## Software Unit: ADC Driver

1. Responsibilities
- Performs analog conversion on specified channel
- Provides result to Feedback Mapper
- Does NOT interpret meaning of value

2. Internal Data Design
- `latest_adc_val`, channel config

3. State Machine
- Simple: IDLE, CONVERTING; interrupt-driven

4. Algorithms and Control Flow
- On trigger: start conversion, post value to Feedback Mapper

5. Interfaces (APIs)
- Provides: `get_adc_value()`
- Requires: MCU ADC HW interface

6. Error Handling
- On hardware error: provide out-of-range value, signal invalid

7. Resource and Timing Considerations
- HW-driven; fast completion

8. Traceability to SWE Requirements
- SWE-REQ-026, 037
