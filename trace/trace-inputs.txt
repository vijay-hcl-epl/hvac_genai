SYSTEM REQUIREMENTS DOCUMENT – HVAC FLAP ACTUATOR (MOTIX™ TLE9851QXW)

1.0 System Overview
SYS-REQ-001: The system SHALL control the position of a single HVAC air flap using a DC motor and the Infineon TLE9851QXW microcontroller.
SYS-REQ-002: The system SHALL be capable of receiving and executing position commands for discrete positions 0 to 5 (fully closed to fully open) as defined in system functional mapping.
SYS-REQ-003: The system SHALL operate from an automotive supply voltage range of 5.5 V to 28 V. [Implied]

2.0 Flap Position Control
SYS-REQ-004: The system SHALL drive the flap to the commanded discrete position (0…5) received via user command interface.
SYS-REQ-005: The system SHALL support stable holding of the commanded position after movement is completed.
SYS-REQ-006: The system SHALL stop driving the motor as soon as the target position is reliably detected.

3.0 Motor Control
SYS-REQ-007: The system SHALL drive the DC motor via the microcontroller’s integrated half-bridge driver (no external driver required).
SYS-REQ-008: The system motor actuator SHALL be capable of both clockwise and counter-clockwise rotation.
SYS-REQ-009: The system SHALL stop the motor in case of detected faults or invalid ADC feedback. [Implied]
SYS-REQ-010: The system SHALL support PWM-based speed control for the actuator motor.

4.0 Position Feedback Acquisition & Processing
SYS-REQ-011: The system SHALL acquire flap position feedback via a potentiometer sampled through the TLE9851QXW ADC1 module.
SYS-REQ-012: The ADC feedback SHALL support at least 10 bits of resolution.
SYS-REQ-013: Position thresholds for logical positions (0-5) SHALL be defined in non-volatile memory (Flash).
SYS-REQ-014: The system SHALL not require dynamic calibration or runtime re-tuning for position feedback mapping.
SYS-REQ-015: Flap position SHALL be measured periodically or continuously when the system is powered.

5.0 User Command Interface
SYS-REQ-016: The system SHALL accept position commands via UART interface (UART1 or UART2) using simple numeric command protocol.
SYS-REQ-017: The system SHALL also support command reception via the LIN transceiver, acting as a LIN 2.2 slave node.
SYS-REQ-018: The system SHALL ignore invalid or out-of-range user commands without system crash or reset.

6.0 Status Indication
SYS-REQ-019: The system SHALL provide flap position indication via at least one of the following: GPIO-controlled LEDs, High-Side Switch output, UART debug messages, or LIN status frames.
SYS-REQ-020: The system SHALL allow only one position indication output to be active at any given time.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)
SYS-REQ-021: On power-up, the system SHALL initialize all voltage regulators, complete boot sequence, configure clocks, and initialize the ADC, with motor driver left disabled until initialization is complete.
SYS-REQ-022: The system SHALL read the current flap position using the ADC1 after initialization.
SYS-REQ-023: The system SHALL enter an Idle state upon completion of initialization.
SYS-REQ-024: The system SHALL not require mechanical homing at power-up. [Implied]
SYS-REQ-025: In Idle, the system SHALL wait for valid position commands and only transition to "Moving to Target" after receiving such a command.
SYS-REQ-026: When moving toward a target, the controller SHALL continuously monitor actual position feedback to determine if the target is met.
SYS-REQ-027: Upon detecting target reached (within configured thresholds), the system SHALL stop the motor and signal the new position.
SYS-REQ-028: On invalid command input, the system SHALL remain in its current state and not reset.
SYS-REQ-029: The system SHALL fail safe and stop the motor whenever a fault is detected (driver fault, open/short load, overtemperature, ADC out of range, brownout, or firmware hang).
SYS-REQ-030: Sleep or Stop modes SHALL be supported according to device capabilities but are not required for regular operation.

8.0 Interfaces (UART, motor driver, ADC, LEDs)
SYS-REQ-031: The system SHALL use UART1 or UART2 for command reception and debug.
SYS-REQ-032: The system SHALL use the integrated LIN transceiver for automotive commands (LIN slave only).
SYS-REQ-033: The system SHALL use ADC1 for position measurement (potentiometer and current sense amplifier are supported).
SYS-REQ-034: The system SHALL use up to 5 general-purpose IOs for indication outputs and external interaction as required.

9.0 Constraints & Assumptions
SYS-REQ-035: Only one flap, motor, and potentiometer are present per system instance.
SYS-REQ-036: The LIN node address, UART configuration, and ADC thresholds SHALL be stored in Flash and not change at runtime.
SYS-REQ-037: No CAN communication SHALL be present and is out of scope.
SYS-REQ-038: Hardware is assumed correct and functional for this prototype.
SYS-REQ-039: The system SHALL not attempt dynamic calibration, runtime learning, or field updates to position mapping. [Implied]

10.0 Non-Functional Requirements
10.1 Responsiveness
SYS-REQ-040: The system SHALL respond to a user command within 100 ms under normal conditions.
10.2 Error Handling & Edge Cases
SYS-REQ-041: The system SHALL detect and indicate faults in the motor driver, ADC, or supply voltage.
SYS-REQ-042: The system SHALL stop driving the motor immediately upon detection of dangerous faults (short circuit, open load, overtemperature, brownout, watchdog expiry).
SYS-REQ-043: The system SHALL never drive the motor with invalid or out-of-range ADC feedback.
10.3 Resource Constraints
SYS-REQ-044: The firmware and data SHALL not exceed 64 KB Flash and 4 KB RAM on the TLE9851QXW.
SYS-REQ-045: No runtime resource allocation or dynamic memory use SHALL be required. [Implied]
10.4 Maintainability & Modularity
SYS-REQ-046: The requirements, control algorithms, and threshold mappings SHALL be traceable and separately implemented for extensibility. [Implied]
10.5 Testability
SYS-REQ-047: The system SHALL be testable via UART commands, LIN frames, ADC value observation, motor movement, fault injection, and watchdog behavior observation.
SYS-REQ-048: Optional: Automated bench test support is recommended in design (if test infrastructure is provided).

SOFTWARE ARCHITECTURE DOCUMENT – HVAC FLAP ACTUATOR (MOTIX™ TLE9851QXW)

1.0 Architecture Style Selection

Candidate Styles Considered:
- Layered architecture
- Component-based (modular, unit-oriented)
- Monolithic single-block

Evaluation:
a) Layered: Adds complexity without clear benefit due to absence of complex middleware, application/service split, or multiple presentation/business/persistence needs. Some functional boundaries exist (command, control, feedback, IO), but layering does not reduce complexity for current scope.
b) Component-based: Matches the mapping of user commands, actuator control, feedback processing, and indication/status, which are clearly separated by both system and SWE.1 requirements. Supports maintainability, decoupling, and ASPICE L3 process goals.
c) Monolithic: Simple to implement but disfavored for maintainability, traceability, and testability, and rejected per SWE.1 explicit modular/testable requirements (SWE-REQ-040).

Selected: Component-based (modular, unit-oriented) architecture.
Justification: Chosen for direct mapping of SWE-REQ partitioning, enhanced testability/maintainability (SWE-REQ-040, 046), clear separation of concerns, and meet ASPICE traceability.

2.0 Software Architecture Definition

Software Units:
- Command Handler
- Position Control Unit
- Motor Driver Abstraction
- Feedback Acquisition & Processing Unit
- Status Indication Unit
- Persistence & Configuration Manager
- Interface Abstractions: UART Handler, LIN Handler, ADC1 Handler, GPIO Handler

Responsibilities:
- Command Handler: Accepts and validates user and LIN commands (SWE-REQ-001, 002, 017, 018).
- Position Control Unit: Interprets and closes control loop for flap positioning (SWE-REQ-004, 005, 025, 026).
- Motor Driver Abstraction: Translates movement requests to MCU driver signals – enable, direction, PWM (SWE-REQ-007, 008, 009).
- Feedback Acquisition & Processing: Samples potentiometer via ADC1, processes for position detection (SWE-REQ-010, 011, 013).
- Status Indication: Maintains reporting of position and fault status via allowed interfaces (SWE-REQ-014, 015, 019, 020).
- Persistence & Configuration Manager: Reads threshold, mapping, config data from Flash/NVM at startup (SWE-REQ-021, 030, 031).
- Interface Abstractions: Realizes hardware mapping for command input/output, feedback, and indication.

Interfaces:
- Inter-unit communication by discrete data/command/feedback structures only (no implicit shared state, implementation is out of scope).
- Position Control uses motor driver and feedback interfaces.
- Status Indication reads flap position from Feedback, signaled by Control, outputs to hardware via GPIO/LIN/UART.

Execution Model:
No explicit execution model or scheduling policy is mandated by the requirements at this stage. All triggering/events arise from hardware command inputs, ADC sampling, or command event. No OS/task/thread, polling, or cooperative scheduling is defined in SWE.1.

==== LLD for Each Software Unit ====

Software Unit: Command Handler

1. Responsibilities  
   - Handles reception and validation of user and LIN commands.  
   - Does not handle direct hardware signaling or movement logic.

2. Internal Data Design  
   - Variables: uint8_t command_received, uint8_t command_validated, uint8_t command_last
   - Command mapping table (loaded at init from Flash)

3. State Machine  
   - States: IDLE, RECEIVING, VALIDATING, DISPATCHED
   - Events: RX event, parse success, out-of-range, discarded, dispatched
   - Actions: On RX event, capture; validate against table; if valid, proceed; else ignore per SWE-REQ-002

4. Algorithms & Control Flow  
   - Wait for RX event from UART/LIN  
   - Parse byte, check range [0:5], lookup in command map table
   - If valid, set command_validated; else discard/ignore (never reset/stopper)
   - Dispatch validated command to Position Control Unit

5. Interfaces (APIs)  
   - Provided: Command_Receive(uint8_t data), Command_Validate(void): returns status code
   - Required: UART/LIN input buffers. Access to config-mapped command table
   - Error reporting: status to Status Indication Unit, error code via API return

6. Error Handling
   - Invalid commands ignored, no MCU reset. Parsing errors set error code and log to status handler as per SWE-REQ-002

7. Resource & Timing Considerations
   - Invoked per RX event (UART/LIN receive interrupt/callback)
   - WCET: <2ms per command event (input-triggered only)
   - Not re-entrant (buffered serial, single-threaded assumption)

8. Traceability
   - SWE-REQ-001, 002, 017, 018

-----------------

Software Unit: Position Control Unit

1. Responsibilities
   - Handles processing of validated command, closes position control loop
   - Does not handle command validation or direct hardware output

2. Internal Data Design  
   - Variables: uint8_t target_position, uint8_t current_position, uint8_t last_position, uint8_t movement_pending
   - Status flag for holding/idle

3. State Machine
   - States: WAIT_CMD, MOVING, HOLDING
   - Events: new valid command, actual==target, fault detected
   - Actions: Issue move request to Motor Driver; on target reached or fault, update status

4. Algorithms & Control Flow
   - On new valid command, check if position change required
   - If yes, set movement_pending flag, request motor actuation
   - Monitor feedback (current_position). When actual==target, clear movement_pending, set holding
   - No further requests until next valid command

5. Interfaces (APIs)
   - Provided: Control_Request(uint8_t new_pos), Control_Status(void): returns state/enum
   - Required: Command Handler, Feedback Acquisition, Motor Driver Abstraction
   - Error reporting: set status for Status Indication Unit

6. Error Handling
   - Fault detected by Motor Driver or Feedback propagated here, system transitions to HOLDING

7. Resource & Timing Considerations
   - Invoked on new command and by feedback/motor driver update
   - WCET: <1ms per control decision
   - Not re-entrant (single control loop)

8. Traceability
   - SWE-REQ-004, 005, 006, 025, 026

-----------------

Software Unit: Motor Driver Abstraction

1. Responsibilities
   - Handles all motor driver signals (enable, direction, PWM)
   - Does not handle command/logic or feedback directly

2. Internal Data Design
   - Variables: uint8_t enable, uint8_t dir, uint8_t pwm_value, fault_flag
   - Config struct for driver parameters loaded at init

3. State Machine
   - NONE (stateless, reacts to control requests and error status)
   - Explain flow: outputs are set atomically per invocation; any fault disables motor output immediately

4. Algorithms & Control Flow
   - On request: set enable, direction, pwm_value
   - On feedback or error: clear enable, set fault_flag

5. Interfaces (APIs)
   - Provided: Motor_Set(uint8_t dir, uint8_t pwm), Motor_Disable(void)
   - Required: Position Control signals, config struct
   - Error reporting: reports status to Position Control

6. Error Handling
   - On error signal, disables outputs, logs error

7. Resource & Timing Considerations
   - Invoked when move requested, on feedback, or on error
   - WCET: <0.2ms per update
   - Not re-entrant (driver atomic updates only)

8. Traceability
   - SWE-REQ-007, 008, 009

Software Unit: Feedback Acquisition & Processing Unit

   - Handles ADC1 sampling, maps to discrete flap position

2. Internal Data Design

3. State Machine
   - NONE (sample maps to value; periodic or event-driven by ADC interrupt)
   - Explain flow: Each sample triggers mapping algorithm, updates mapped_position

4. Algorithms & Control Flow
   - On ADC sample: compare to threshold array, map to position 0–5
   - Update mapped_position atomically

5. Interfaces (APIs)
   - Provided: Feedback_Get(void): returns mapped_position
   - Required: ADC1 Handler, Persistence & Config Manager
   - Error reporting: ADC errors flagged to Status Indication and Position Control

6. Error Handling
   - Conversion errors -> error status, ignored sample

7. Resource & Timing Considerations

   - Not re-entrant

8. Traceability

void Command_Receive(uint8_t data) {
    /* Only 0..5 are valid, per mapping table loaded from Flash */
    const uint8_t min_cmd = 0u;
    const uint8_t max_cmd = 5u;
    if (data >= min_cmd && data <= max_cmd) {
        /* Lookup in command mapping table from Flash */
        if (Config_IsValidCommand(data)) {
            command_received = data;
            command_validated = 1u;
            error_code = 0u;
        } else {
            error_code = 2u; /* invalid mapping */
            Status_SetError(error_code);
        }
    } else {
        error_code = 1u; /* out of range */
        Status_SetError(error_code);
        return; /* ignore, per SWE-REQ-002 */
    }
}

}

static uint8_t last_position = 0u;
static uint8_t movement_pending = 0u;
static uint8_t holding = 1u;

void Control_Request(uint8_t new_pos) {
    current_position = Feedback_Get();
    if (new_pos == current_position) {
        holding = 1u;
        movement_pending = 0u;
        return;
    }
    target_position = new_pos;
    movement_pending = 1u;
    holding = 0u;
    Motor_SetDirection((target_position > current_position) ? 1 : 0);
    Motor_SetPWM(128u); /* Example PWM, TBD: tune per requirement */
}

uint8_t Control_Status(void) {
    if (movement_pending) {
        current_position = Feedback_Get();
        if (current_position == target_position) {
            holding = 1u;
            movement_pending = 0u;
            Motor_Disable();
        }
    }
    return holding ? 1u : 0u;
}
