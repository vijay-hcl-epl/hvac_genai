# 1.0 System Overview
The HVAC Flap Actuator prototype is a microcontroller-based system designed to position an air flap in discrete positions for automotive HVAC use cases. The system allows user input through UART to command the flap position, drives a DC motor via GPIO/PWM to move the flap, uses a potentiometer with an ADC to sense flap position, and provides visual feedback via LEDs. The design serves as a proof-of-concept and is optimized for learning and demonstration of software engineering processes.

# 2.0 Flap Position Control Requirements
SYS-REQ-001 The system shall allow the user to select a target flap position using UART commands.
SYS-REQ-002 The system shall move the flap to the requested target position upon receiving a valid command.
SYS-REQ-003 The system shall compare the current flap position with the target position to determine movement direction.
SYS-REQ-004 The system shall maintain the flap position upon reaching the commanded position by stopping the motor.
SYS-REQ-005 The system shall continuously monitor the actual position until the target is achieved.
SYS-REQ-006 [Implied] The system shall reject and ignore commands that are not valid positional values within the supported range (0-5).

# 3.0 Motor Control Requirements
SYS-REQ-007 The system shall control a DC motor to move the flap in both clockwise and anti-clockwise directions as required.
SYS-REQ-008 The system shall control motor direction using dedicated GPIO outputs.
SYS-REQ-009 The system shall stop the motor immediately when the target position is reached or when an invalid or undefined command is detected.
SYS-REQ-010 The system shall enable or disable the motor using a PWM-controlled signal to set speed and forward power.
SYS-REQ-011 [Implied] The system shall only energize the motor while the flap is not at the target position.
SYS-REQ-012 [Implied] The motor shall be OFF at system startup and after each movement completion.

# 4.0 Position Feedback Acquisition and Processing
SYS-REQ-013 The system shall acquire the current flap position signal using a potentiometer connected to an ADC channel.
SYS-REQ-014 The system shall periodically read ADC values to determine the flap’s analog position.
SYS-REQ-015 The system shall map ADC readings to logical flap positions with fixed calibration values defined in software.
SYS-REQ-016 Out-of-range ADC values shall cause the system to halt motor movement for safety.
SYS-REQ-017 [Implied] The mapping from ADC values to logical positions shall cover at least six discrete (0–5) positions.

# 5.0 User Command Interface Requirements
SYS-REQ-018 The system shall receive simple numeric commands over UART, each representing a logical flap position (0–5).
SYS-REQ-019 The system shall validate incoming commands for proper value and format.
SYS-REQ-020 Any invalid command shall be ignored by the system with no acknowledgement or error output on UART.
SYS-REQ-021 [Implied] A command is treated as invalid if it is outside the allowed numeric range or is not parseable.

# 6.0 Status Indication Requirements
SYS-REQ-022 The system shall provide a visual indication that system power is ON using a designated LED.
SYS-REQ-023 The system shall provide visual feedback on flap position using multiple green LEDs, with at most one such indicator illuminated at a time matching the flap’s logical position.
SYS-REQ-024 [Implied] Only the green LED corresponding to the detected position shall be ON at any given instant; all others shall be OFF.

# 7.0 System Behavioral Requirements
SYS-REQ-025 On power-up, the system shall initialize all peripherals (ADC, UART, GPIO, PWM) and confirm the flap position by reading the potentiometer.
SYS-REQ-026 The motor shall be OFF at system startup.
SYS-REQ-027 During idle, the system shall maintain the flap in position and update LEDs to reflect its status.
SYS-REQ-028 When a valid command is received, the system shall actuate the flap to the new position and update LEDs accordingly.
SYS-REQ-029 If an invalid command is detected, the system shall ignore it and maintain current behavior.
SYS-REQ-030 [Implied] The system shall operate in one of the following behavioral phases: initialization, idle, moving (active), position verification, and error/invalid command ignored state.

# 8.0 System Interface Requirements
SYS-REQ-031 The system shall support UART-based serial connection with a PC for receiving user commands.
SYS-REQ-032 The system shall output GPIO/PWM signals to control a motor driver (e.g., L298N) which in turn powers the DC motor.
SYS-REQ-033 The system shall connect a potentiometer to a microcontroller ADC channel for position feedback.
SYS-REQ-034 The system shall output GPIO signals to control dedicated LEDs for status and flap position indication.

# 9.0 Constraints and Assumptions
SYS-REQ-035 Only one actuator flap, one DC motor, and one potentiometer are present in the system.
SYS-REQ-036 User interaction occurs locally via UART; there are no network interfaces (e.g., CAN, LIN).

SYS-REQ-038 No dynamic calibration or runtime learning is implemented; all calibration and configuration is static in software.

- Control logic is relatively simple (command-driven responses with explicit state transitions: initialize, idle, move, verify, error/ignore) and well-bounded for demonstration purposes.
- No requirements support for complex behaviors like multitasking, asynchronous networking, or dynamic reconfiguration/expansion.
- System expandability is intentionally constrained to encourage clarity and maintainability; adding more actuators, feedback sensor types, or sophisticated error management is explicitly excluded from this scope.

# SOFTWARE ARCHITECTURE FOR HVAC FLAP ACTUATOR

## 1. Architecture Style Identification

**Candidate Styles:**
1. Layered design (Input, Logic, Output separation)
2. Component-based (distinct components for each major function)
3. Monolithic (all SW in a unified block without separation)

**Evaluation:**
- System Complexity: Low (single actuator, localized interaction, simple logic)
- Hardware Interaction: Multiple peripherals (UART, ADC, GPIO, PWM)
- Testability: Improve by clear separation of concerns
- Maintainability: Improve by modular assignment (per requirements)
- ASPICE L3: Requires SW units and explicit interfaces (not monolithic “blob”)
- Requirements: Explicitly call for "clear separation between input handling, control logic, feedback acquisition, and status/output indication" (SYS-REQ-047)

**Selected Style:**
> **Layered/component-based architecture with the following software units:**
> - Command Handler
> - Flap Controller (Core Logic)
> - Motor Control
> - Position Feedback
> - Status Indicator

**Justification:**  
This separation matches the requirements (SYS-REQ-047), maximizes testability/maintainability, keeps units small/traceable, and aligns with ASPICE L3 expectations. Monolithic style is rejected for lack of clarity/traceability/testability. Component style (one component per function) and “layered” are nearly equivalent at this scale.

# SWE.3 Low-Level Design (LLD) for HVAC Flap Actuator

## Software Unit: Command Handler

1. Responsibilities
   - Receives UART commands, validates numeric range (0–5).
   - Forwards valid target positions to Flap Controller.
   - Ignores malformed or out-of-range commands.
   - Does NOT process motor control or ADC, nor manage system state logic.

2. Internal Data Design
   - `last_command_value` (int): Statically allocated numeric variable.
   - `command_valid` (bool): Flag set on successful validation.
   - Static buffer for UART receive (fixed-size, e.g., 8 bytes).
   - No dynamic allocation.

3. State Machine
   - Implicit (simple input/validation branch):
     - Wait for UART input → Parse → If valid [forward], else [ignore].

4. Algorithms and Control Flow
   - On UART data received:
     1. Extract ASCII data from static buffer.
     2. Parse as integer; check for range (0–5).
     3. If valid, set `last_command_value`, `command_valid` true, forward to Flap Controller.
     4. If invalid, set `command_valid` false and disregard data.

5. Interfaces (APIs)
   - Provided: `bool GetLastCommand(int* value)`
   - Used: UART interface function(s) for receiving data.
   - No direct error returns to UART.

6. Error Handling
   - Non-numeric or out-of-range input: Ignored safely, `command_valid` false.
   - No side effects; safe no-op for malformed commands.

7. Resource and Timing Considerations
   - Invoked on UART RX event (event-driven).
   - Minimal per-invocation cost; not re-entrant.

8. Traceability to SWE Requirements
   - Covers: SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-017, SWE-REQ-018, SWE-REQ-032, SWE-REQ-035, SWE-REQ-037, SWE-REQ-038

---

## Software Unit: Position Feedback

1. Responsibilities
   - Reads ADC, maps to discrete logical flap position.
   - Detects out-of-range or invalid feedback.
   - Provides position and validity information to Flap Controller.
   - Does NOT initiate movement or process user commands.

2. Internal Data Design
   - `adc_raw_value` (uint16_t): Last potentiometer reading.
   - `logical_position` (uint8_t): Resultant logical position (0–5).
   - `adc_valid` (bool): Set true only if raw value mapped to a valid position.
   - `adc_calibration_table` (static const struct): Defines min/max for each position.

3. State Machine
   - No explicit state machine; periodic read/map/validate logic.

4. Algorithms and Control Flow
   - On periodic/triggered read:
     1. Read ADC via HAL.
     2. Compare to calibration table.
     3. If within a discrete range, set logical_position and `adc_valid` true.
     4. Else, set `adc_valid` false.

5. Interfaces (APIs)
   - Provided: `bool GetPosition(uint8_t* pos)`; `bool IsFeedbackValid(void)`
   - Uses: ADC read from potentiometer.
   - Calibration constants provided as static data.

6. Error Handling
   - If ADC value out-of-bounds, set `adc_valid` false; do not map a position; Flap Controller will take fallback action.

7. Resource and Timing Considerations
   - Invoked periodically or by schedule.
   - Not re-entrant (uses exclusive static data per invocation).

8. Traceability to SWE Requirements
   - Covers: SWE-REQ-004, SWE-REQ-012, SWE-REQ-013, SWE-REQ-014, SWE-REQ-029, SWE-REQ-030, SWE-REQ-031, SWE-REQ-033, SWE-REQ-037, SWE-REQ-038

---

## Software Unit: Flap Controller

1. Responsibilities
   - Core logic: Receives validated command and position feedback.
   - Command-driven state machine: Idle, Moving, TargetReached.
   - Issues movement/stop control orders to Motor Control.
   - Does NOT interact with ADC/UART directly.

2. Internal Data Design
   - `current_target` (int): Latest valid target position.
   - `flap_state` (enum): {IDLE, MOVING, TARGET_REACHED}
   - `position_valid` (bool): Copied from Position Feedback.

3. State Machine
   - States:
     - IDLE: Waiting for valid command.
     - MOVING: Command accepted, awaits position match.
     - TARGET_REACHED: Position equals command; holding, maintain status.
   - Events:
     - Valid new command (from Command Handler)
     - Updated valid position feedback
     - Invalid feedback triggers fallback/stop
   - Entry/exit:
     - Enter MOVING: issue ControlOrder to Motor Control
     - Enter TARGET_REACHED: send stop
     - Invalid feedback: enter safe/hold state

4. Algorithms and Control Flow
   - On valid command:
     1. Store target, transition to MOVING.
   - On position match:
     1. Transition to TARGET_REACHED; order stop.
   - If feedback is invalid:
     1. Order stop, hold in safe state.

5. Interfaces (APIs)
   - Provided: `void ControlTick(void)` (invoked periodically or by driver)
   - Uses: `GetLastCommand`, `GetPosition`, `IsFeedbackValid`
   - Orders: ControlOrder_t (`MOVE_CW`, `MOVE_CCW`, `STOP`), provided to Motor Control.

6. Error Handling
   - If feedback lost/invalid, always issue stop.
   - Ignores late or repeated commands until action is complete.

7. Resource and Timing Considerations
   - Invoked cyclically or on event.
   - Not re-entrant; protected by single update phase per invocation.

8. Traceability to SWE Requirements
   - Covers: SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-007, SWE-REQ-017, SWE-REQ-022, SWE-REQ-023, SWE-REQ-025, SWE-REQ-026, SWE-REQ-028, SWE-REQ-036, SWE-REQ-038

---

## Software Unit: Motor Control

1. Responsibilities
   - Drives motor enable, direction, and stop via GPIO/PWM.
   - Receives action order from Flap Controller.
   - Does NOT interpret user commands, nor manage LED/status.

2. Internal Data Design
   - `motor_state` (enum): {STOPPED, MOVING_CW, MOVING_CCW}
   - `last_order` (ControlOrder_t): Last received action.
   - Static mapping of orders to GPIO/PWM signals.

3. State Machine
   - Implicit logic (SET/RESET GPIOs/PWM):
     - State updated on new control order; no persistent sub-states.

4. Algorithms and Control Flow
   - On control order:
     1. If different from `last_order`, update outputs accordingly.
     2. If `STOP`, disable enable pin (PWM/GPIO off).
     3. For movement, set direction GPIO, enable PWM.

5. Interfaces (APIs)
   - Provided: `void MotorControl_ApplyOrder(ControlOrder_t order)`
   - Uses: GPIO & PWM driver functions.

6. Error Handling
   - Invalid/unrecognized order: Forces STOP state.
   - Hardware error (e.g., GPIO/PWM not acknowledged): Forces STOP and signals via MotorStatus interface.

7. Resource and Timing Considerations
   - Invoked when Flap Controller changes state/order (event-driven).
   - Not re-entrant; atomic per invocation.

8. Traceability to SWE Requirements
   - Covers: SWE-REQ-008, SWE-REQ-009, SWE-REQ-010, SWE-REQ-011, SWE-REQ-037, SWE-REQ-038

---

## Software Unit: Status Indicator

1. Responsibilities
   - Controls status/power LED and position LEDs.
   - Reflects current operating state and position.
   - Does NOT make movement or control decisions.

2. Internal Data Design
   - `cur_pos_led` (uint8_t): Which position LED is ON.
   - `power_led_on` (bool): True while system powered/operational.
   - Static mapping of flap position to LED output.

3. State Machine
   - No explicit state machine. Direct mapping from data to GPIOs.

4. Algorithms and Control Flow
   - On periodic/event update:
     1. Read current logical position from Position Feedback.
     2. Illuminate appropriate position LED; ensure only one ON.
     3. Update power/status LED according to system status.

5. Interfaces (APIs)
   - Provided: `void StatusIndicator_Update(uint8_t logical_position, bool powered)`
   - Uses: GPIO driver functions for LEDs.

6. Error Handling
   - If logical_position out of range, all position LEDs off, power LED remains if powered.

7. Resource and Timing Considerations
   - Invoked periodically or on triggering system event.
   - Not re-entrant.

8. Traceability to SWE Requirements
   - Covers: SWE-REQ-015, SWE-REQ-016, SWE-REQ-025, SWE-REQ-041, SWE-REQ-038
