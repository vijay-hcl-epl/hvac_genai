1.0 System Overview 

The HVAC Flap Actuator System is a microcontroller-based prototype designed to move an air-control flap to discrete positions as commanded by a user through UART. The system controls a DC motor, acquires position feedback via a potentiometer using an ADC, and reports its status through LEDs.

2.0 Flap Position Control

SYS-REQ-001: The system SHALL allow the user to command the flap to any supported discrete position via UART.
SYS-REQ-002: The system SHALL move the flap only to the commanded positions defined in the requirements.
SYS-REQ-003: The system SHALL stop the motor upon reaching the target position.
SYS-REQ-004: The system SHALL ignore commands outside the supported position range. [Implied]

3.0 Motor Control

SYS-REQ-005: The system SHALL drive the DC motor in both clockwise and anti-clockwise directions as required to reach the target flap position.
SYS-REQ-006: The system SHALL control motor operation using GPIO and PWM signals.
SYS-REQ-007: The system SHALL ensure the motor is off when not actively moving the flap.

4.0 Position Feedback Acquisition & Processing

SYS-REQ-008: The system SHALL acquire position feedback using an ADC connected to the potentiometer.
SYS-REQ-009: The system SHALL map ADC values to logical flap positions (e.g., 0–5) according to defined software ranges.
SYS-REQ-010: The system SHALL continuously monitor actual flap position while powered on.
SYS-REQ-011: The system SHALL stop the motor if the ADC value is out of valid range. [Implied]

5.0 User Command Interface

SYS-REQ-012: The system SHALL receive user target position commands via UART as single numeric values.
SYS-REQ-013: The system SHALL ignore invalid or malformed UART commands. [Implied]

6.0 Status Indication

SYS-REQ-014: The system SHALL use one LED to indicate power status.
SYS-REQ-015: The system SHALL indicate the current flap position using up to one green LED at a time.
SYS-REQ-016: The system SHALL update the green LED indication upon position changes.

7.0 System Behavior (power-up, idle, normal, target reached, invalid input)

SYS-REQ-017: On power-up, the system SHALL initialize all required peripherals (ADC, UART, GPIO, PWM).
SYS-REQ-018: On power-up, the system SHALL ensure the motor is off.
SYS-REQ-019: On power-up, the system SHALL sample the current flap position from the potentiometer.
SYS-REQ-020: The system SHALL remain idle, with no actuator motion, until a valid user command is received.
SYS-REQ-021: Upon receiving an invalid command, the system SHALL maintain its previous state and take no action.

8.0 Interfaces (UART, motor driver, ADC, LEDs)

SYS-REQ-022: The system SHALL use UART for receiving position commands from a connected PC.
SYS-REQ-023: The system SHALL use ADC to measure potentiometer feedback for position acquisition.
SYS-REQ-024: The system SHALL use GPIO and PWM to command the motor driver.
SYS-REQ-025: The system SHALL use GPIO pins to control the power and position LEDs.

9.0 Constraints & Assumptions

SYS-REQ-026: The system SHALL operate a single flap using a single motor and a single potentiometer.
SYS-REQ-027: The system SHALL not communicate on any vehicle network such as CAN or LIN. [Implied]
SYS-REQ-028: The system SHALL assume hardware is functional and calibrated. [Implied]
SYS-REQ-029: User commands are non-concurrent and processed sequentially. [Implied]

10.0 Non-Functional Requirements
10.1 Responsiveness
SYS-REQ-030: The system SHALL process valid UART commands promptly with human-perceivable responsiveness.
10.2 Error Handling & Edge Cases
SYS-REQ-031: The system SHALL stop the motor if position feedback cannot be reliably acquired or mapped. [Implied]
SYS-REQ-032: The system SHALL ignore errors in UART communication or ADC measurement, provided safety is not compromised.
10.3 Resource Constraints
SYS-REQ-033: The system SHALL not require dynamic memory allocation at runtime.
10.4 Maintainability & Modularity
SYS-REQ-034: The system SHALL modularize functionality such that command handling, position monitoring, and indication may be independently tested. [Implied]
10.5 Testability
SYS-REQ-035: The system SHALL be testable via UART commands, LED feedback, and motor movement observable by a human or script. [Implied]

Architecture-Relevant Considerations Derived from System Requirements

Concurrency: Minimal concurrency is required, as only one command is processed at a time and no parallel motor actions occur. Data acquisition and actuation may be realized sequentially.
Interaction Complexity: Interaction is simple; input (UART) maps to motor actuation and LED output, with feedback acquired via ADC. No bidirectional or network communication is present.
Control Complexity: Position mapping, discrete position support, motor control, and error handling are straightforward; no hierarchical or distributed control.
Expandability: The architecture is easily expandable to more flap positions or additional interface types (e.g., CAN) with clear requirements separation, provided atomicity and safety are maintained.

The software for the HVAC Flap Actuator System implements user-driven control of an air flap via a DC motor, processing commands received over UART and using ADC-derived feedback from a potentiometer for precise positioning. The software is responsible for interpreting user commands, actuating the motor, acquiring position feedback, indicating status, handling errors, and ensuring bounded and robust operation on an MCU with ADC, GPIO, UART, and timer/PWM capability.

# HVAC Flap Actuator Software Architecture (ASPICE SWE.2)

## 1. Architecture Style Selection

### Candidate Styles Considered
- **Layered**: Separates I/O, application logic, and hardware abstraction for modularity.
- **Component-Based**: Allocates responsibilities to independent components with defined interfaces (often used for larger or distributed systems).
- **Monolithic**: Combines all logic into a single software block with minimal logical separation.

### Evaluation
- **System Complexity**: Low; only one main control flow, minimal parallelism, all peripheral interaction local.
- **HW Interaction Needs**: UART, ADC, GPIO, PWM; well-mapped with clear abstraction.
- **Testability**: Test points are defined at interfaces (UART handler, position monitoring, LED logic).
- **Maintainability**: Modularity is useful for change, as additional flap positions or interfaces may be added.
- **ASPICE L3**: Requires traceable, modular architecture, clear unit boundaries, explicit interfaces and responsibilities, and rationale for style choices.

### Selection 
- **Adopted Style: Layered**: 
    - Cleanly separates hardware abstraction (drivers), application logic (main control state machine), and I/O (command, feedback, indication).
    - Facilitates testability (per-unit test points via UART/LED), maintainability, and direct mapping to requirements.
- **Rejected Styles**:
    - **Component-Based**: Rejected due to system scale (single actuator, no distribution, no optional local execution).
    - **Monolithic**: Lacks maintainability and testability required by ASPICE and requirements (SWE-REQ-034, SWE-REQ-035, SWE-REQ-039).

## 2. Architecture Definition

### Software Units and Responsibilities

1. **UART Command Handler**
   - Decodes/validates incoming UART commands (SWE-REQ-001, SWE-REQ-003, SWE-REQ-017).
   - Passes valid target position to control logic.
   - Ignores spurious/invalid/malformed commands (SWE-REQ-002, SWE-REQ-003).

2. **Application Logic (Flap Actuator Controller)**
   - Sequencing and arbitration unit: receives position requests, manages target state, and controls the actuation sequence (SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-021, SWE-REQ-024).
   - Performs state machine for position control, enforces single-command processing (SWE-REQ-004, SWE-REQ-025).
   
3. **Motor Control Unit**
   - Receives actuation requests from controller, drives motor via PWM/GPIO as per command (SWE-REQ-008, SWE-REQ-009, SWE-REQ-010, SWE-REQ-019).
   - Responsible for direction, start/stop, and compliance with target/stop conditions.

4. **Position Monitoring Unit**
   - Acquires ADC and maintains logical/current/target positions (SWE-REQ-011, SWE-REQ-012, SWE-REQ-013, SWE-REQ-018, SWE-REQ-029).
   - Performs out-of-range detection, error flagging, position-to-LED mapping (SWE-REQ-013, SWE-REQ-032).

5. **LED Indication (Status and Position)**
   - Powers up and controls LEDs for power/position feedback (SWE-REQ-014, SWE-REQ-015, SWE-REQ-016, SWE-REQ-020).
   - Provides visual test/verification points (SWE-REQ-039).

6. **System Initialization**
   - One-time setup: initialize drivers, clear error state, acquire initial position (SWE-REQ-021, SWE-REQ-022).

### Interfaces Between Units
- **UART Command Handler ↔ Controller**: Delivers parsed/validated position requests.
- **Controller ↔ Motor Control**: Commands motor movement/stopping.
- **Controller ↔ Position Monitoring**: Requests current position/feedback, receives position or error.
- **Controller ↔ LED Indication**: Issues display/feedback update commands.
- **System Initialization ↔ All Units**: Startup sequencing.

### Execution Model:
No explicit execution model or scheduling policy is mandated by the requirements at this stage.

# HVAC Flap Actuator Software Low-Level Design (SWE.3)

## Introduction
This document details the Low-Level Software Design for the HVAC Flap Actuator, directly derived from the SWE.1 Software Requirements and SWE.2 Architecture. It conforms strictly to ASPICE Level 3, project, and customer rules. No new units or architecture changes are introduced. Target: MISRA-like embedded C, static allocation, single actuator, single flap, single MCU.

--------------------------------------------------------------------------------

## SOFTWARE UNITS

--------------------------------------------------------------------------------

### Software Unit: UART Command Handler

1. Responsibilities
   - Handles decoding and validation of UART commands.
   - Does not act on (ignores) malformed commands or those out of bound.
   - Passes validated command(s) to the controller.

2. Internal Data Design
   - RX buffer (fixed size, static allocation).
   - Command parsing state (e.g., enum for NONE, RECEIVING, READY_TO_PARSE).
   - Temporary buffer for parsed numeric value.

3. State Machine
   - States: WAIT_FOR_START, RECEIVE, PARSE, ERROR (parsing error), READY.
   - Events: UART RX event, buffer overrun, parse complete, invalid character.
   - Transitions: WAIT_FOR_START→RECEIVE (RX), RECEIVE→PARSE (on delimiter or max count), PARSE→READY or ERROR (success/fail), ERROR→WAIT_FOR_START (reset).
   - Actions: Accept input, parse integer, validate range, set status for controller.

4. Algorithms & Control Flow
   - On UART RX: store in buffer. If delimiter or max bytes reached, parse as integer.
   - Validate: If numeric, check against bounds. If valid, set to READY and signal controller.
   - If out of range or non-numeric, ignore and reset buffer/state.

5. Interfaces (APIs)
   - Provided: get_parsed_command(), is_command_ready()
     - Params: none
     - Returns: int (cmd); bool (ready status)
   - Required: uart_rx_callback()
     - Params: byte
     - Returns: void
   - Error reporting: status enum (e.g., OK, ERROR, OOR).

6. Error Handling
   - Command parsing error resets internal state and buffer without side effects.

7. Resource & Timing Considerations
   - Invoked only on UART RX interrupts or polling.
   - WCET per command: O(buffer size).
   - Re-entrancy: Not reentrant (one command in-progress). Locks state during parse.

8. Traceability
   - SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-017, SWE-REQ-033

--------------------------------------------------------------------------------

### Software Unit: Flap Actuator Controller

1. Responsibilities
   - Handles main sequencing, target/actual/command status, command arbitration.
   - Processes only one command at a time.
   - Invokes requests to actuator units.

2. Internal Data Design
   - State: IDLE, PROCESSING, WAIT_MOVEMENT, ERROR
   - Current position (enum/int).
   - Target position (enum/int).
   - Command in-progress flag; error flag.

3. State Machine
   - States: IDLE, ARBITRATING, MOVE, VERIFY, ERROR
   - Events: command ready, position reached, OOR, error from feedback/motor.
   - Transitions: idle to arbitrating (cmd ready), move to verify (motor reports stop), verify to idle (ok), any to error (flag/error from other units).
   - Actions: On command, validate and request to move if target ≠ current. Handle completion/error.

4. Algorithms & Control Flow
   - On command ready: if in IDLE, parse and check command. If valid and new, initiate MOVE.
   - During MOVE: monitor feedback, signal motor start/stop, verify result.
   - On error: set error flag, report to indication unit, halt sequence.

5. Interfaces (APIs)
   - Provided: process_uart_command(cmd), get_status(), clear_error()
   - Required: position_monitor_get_current(), motor_control_move(target), led_indicate_status()
   - Params: as above. Returns: flags/enums/status.
   - Error reporting: error flag, status API.

6. Error Handling
   - On feedback or command error, halts ongoing sequence, sets error, updates LEDs.

7. Resource & Timing Considerations
   - Exclusive access (no preemption).
   - WCET per event: O(state transitions), implementation bounded.
   - Not reentrant.

8. Traceability
   - SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-021, SWE-REQ-024, SWE-REQ-025, SWE-REQ-026, SWE-REQ-029, SWE-REQ-031

--------------------------------------------------------------------------------

### Software Unit: Motor Control Unit

1. Responsibilities
   - Handles low-level output for motor movement/stop.
   - Drives direction, on/off as commanded by controller only.

2. Internal Data Design
   - Direction (FORWARD/REVERSE/STOP).
   - Motor status/state.
   - Output: PWM/gpio value caches (static vars).

3. State Machine
   - State: STOPPED, MOVING, ERROR
   - Events: move command, stop command, hardware fault.
   - Actions: Set PWM, direction; stop on command or error.
   - State “none” for feedback, direct mapping from command.

4. Algorithms & Control Flow
   - On move: set direction/output, enable PWM.
   - On stop: disable PWM.
   - Fault: on command only; no diagnosis.

5. Interfaces (APIs)
   - Provided: move_to(target), stop(), get_motor_status()
   - Required: None
   - Error reporting: status enum (OK, ERROR)

6. Error Handling
   - On error/stop: output disables PWM, sets error.

7. Resource & Timing Considerations
   - Only acts when commanded. Assumes single, exclusive control.
   - WCET: O(set PWM/gpio).
   - Not reentrant.

8. Traceability
   - SWE-REQ-008, SWE-REQ-009, SWE-REQ-010, SWE-REQ-019, SWE-REQ-032

--------------------------------------------------------------------------------

### Software Unit: Position Monitoring Unit

1. Responsibilities
   - ADC acquisition, mapping logic, out-of-bounds/error detection.
   - Tracks current, target, error states for feedback.

2. Internal Data Design
   - ADC value cache (static).
   - Position mapping table or constants.
   - Error/flag field.

3. State Machine
   - State “none” (called on request, maintains last state)
   - Flow: On get_current(), samples ADC, maps to position, checks bounds.

4. Algorithms & Control Flow
   - On sample: read ADC, map value, if OOR set error.
   - APIs return last mapped position + error flag.

5. Interfaces (APIs)
   - Provided: get_current_position(), is_in_valid_range(), get_error_flag()
   - Required: adc_read()
   - Error reporting: flag (OOR, ERROR)

6. Error Handling
   - If map fails/OOR: set error, report, no C code retry.

7. Resource & Timing Considerations
   - Invoked by controller only; samples on demand.
   - WCET: O(adc sample + map).
   - Not reentrant.

8. Traceability
   - SWE-REQ-011, SWE-REQ-012, SWE-REQ-013, SWE-REQ-018, SWE-REQ-028, SWE-REQ-029, SWE-REQ-032

--------------------------------------------------------------------------------

### Software Unit: LED Indication (Status & Position)

1. Responsibilities
   - Controls all LEDs (power-on, position indication only).
   - Updates LEDs when status/position changes.

2. Internal Data Design
   - LED state cache (for each output pin, static vars).
   - Mapping array: position → LED.

3. State Machine
   - State “none” (direct mapping from logic)
   - Flow: On update, set all LED outputs per request.

4. Algorithms & Control Flow
   - update_status_led(on/off), update_position_led(position)
   - Called by controller at init/change.

5. Interfaces (APIs)
   - Provided: set_led_status(), set_led_position(pos)
   - Required: None
   - Error reporting: none if GPIO fails, update ignored.

6. Error Handling
   - Ignores physical failures; no retries; assumes working hardware.

7. Resource & Timing Considerations
   - Only set when commanded; one operation per transition.
   - WCET: O(GPIO set).
   - Not reentrant.

8. Traceability
   - SWE-REQ-014, SWE-REQ-015, SWE-REQ-016, SWE-REQ-020, SWE-REQ-039

--------------------------------------------------------------------------------

### Software Unit: System Initialization

1. Responsibilities
   - Initializes all drivers (UART, ADC, GPIO) and state.
   - Ensures safe system start and reports power-on.

2. Internal Data Design
   - Init flags (per driver/unit).
   - Initial position value/led state/data.

3. State Machine
   - State “none” (single-pass on reset/boot)
   - One-way, no recursion.

4. Algorithms & Control Flow
   - On boot: init all hardware, confirm status, request initial position, clear errors, set init LEDs.

5. Interfaces (APIs)
   - Provided: system_init()
   - Required: uart_init(), gpio_init(), adc_init(), etc.
   - Error reporting: fatal error flag if any required init fails.

6. Error Handling
   - If init failure: sets fatal error, keeps system in safe state (motor off, LEDs error).

7. Resource & Timing Considerations
   - Only runs at startup/reset.
   - WCET: O(all driver inits + position check).
   - Not reentrant.

8. Traceability
   - SWE-REQ-021, SWE-REQ-022, SWE-REQ-023

#include "uart_command_handler.h"
#include <string.h>
#include <ctype.h>

#define UART_RX_BUF_SIZE 8
static char rx_buffer[UART_RX_BUF_SIZE];
static int rx_pos = 0;
static int parsed_command = 0;
static bool command_ready = false;
static uart_cmd_status_t status = UART_CMD_OK;

void uart_command_handler_init(void) {
    rx_pos = 0;
    command_ready = false;
    status = UART_CMD_OK;
    memset(rx_buffer, 0, sizeof(rx_buffer));
}

void uart_rx_callback(unsigned char byte) {
    if (command_ready) return;
    if (byte == '\n' || byte == '\r') {
        // parse buffer
        if (rx_pos == 0) return;
        rx_buffer[rx_pos] = '\0';
        // all numeric?
        int i;
        for (i = 0; i < rx_pos; i++) {
            if (!isdigit((unsigned char)rx_buffer[i])) {
                status = UART_CMD_ERROR;
                rx_pos = 0;
                memset(rx_buffer, 0, sizeof(rx_buffer));
                return;
            }
        }
        int val = atoi(rx_buffer);
        if (val >= 0 && val <= 100) { // assume 0..100 valid
            parsed_command = val;
            command_ready = true;
            status = UART_CMD_OK;
        } else {
            status = UART_CMD_OOR;
        }
        rx_pos = 0;
        memset(rx_buffer, 0, sizeof(rx_buffer));
    } else if (rx_pos < UART_RX_BUF_SIZE-1) {
        rx_buffer[rx_pos++] = (char)byte;
    } else {
        status = UART_CMD_ERROR;
        rx_pos = 0;
        memset(rx_buffer, 0, sizeof(rx_buffer));
    }
}

bool is_command_ready(void) {
    return command_ready;
}

int get_parsed_command(void) {
    command_ready = false; // clear ready when read
    return parsed_command;
}

uart_cmd_status_t get_uart_cmd_status(void) {
    return status;
}

void uart_command_reset(void) {
    rx_pos = 0;
    command_ready = false;
    status = UART_CMD_OK;
    memset(rx_buffer, 0, sizeof(rx_buffer));
}

#include "flap_actuator_controller.h"
#include "motor_control_unit.h"
#include "position_monitoring_unit.h"
#include "led_indication.h"
#include "uart_command_handler.h"

static flap_ctrl_state_t ctrl_state = CTRL_IDLE;
static int current_position = 0;
static int target_position = 0;
static bool command_in_progress = false;
static bool error_flag = false;

void flap_actuator_controller_init(void) {
    ctrl_state = CTRL_IDLE;
    command_in_progress = false;
    error_flag = false;
    current_position = get_current_position();
    target_position = current_position;
}

void process_uart_command(int cmd) {
    if (ctrl_state == CTRL_IDLE && !command_in_progress) {
        if (cmd < 0 || cmd > 100) {
            error_flag = true;
            ctrl_state = CTRL_ERROR;
            return;
        }
        if (cmd == current_position) return; // already at position
        target_position = cmd;
        command_in_progress = true;
        ctrl_state = CTRL_PROCESSING;
    }
}

void flap_actuator_controller_task(void) {
    switch (ctrl_state) {
        case CTRL_IDLE:
            if (is_command_ready()) {
                int cmd = get_parsed_command();
                process_uart_command(cmd);
            }
            break;
        case CTRL_PROCESSING:
            // Move to target
            if (current_position < target_position) {
                move_motor_to(target_position, MOTOR_DIR_FWD);
                ctrl_state = CTRL_WAIT_MOVEMENT;
            } else if (current_position > target_position) {
                move_motor_to(target_position, MOTOR_DIR_REV);
                ctrl_state = CTRL_WAIT_MOVEMENT;
            } else {
                ctrl_state = CTRL_IDLE;
                command_in_progress = false;
            }
            break;
        case CTRL_WAIT_MOVEMENT:
            // Ask position monitor if reached
            current_position = get_current_position();
            if (current_position == target_position) {
                stop_motor();
                set_led_position(current_position);
                ctrl_state = CTRL_IDLE;
                command_in_progress = false;
            } else if (get_position_status() != POSITION_OK) {
                stop_motor();
                error_flag = true;
                ctrl_state = CTRL_ERROR;
            }
            break;
        case CTRL_ERROR:
            set_led_status(false);
            command_in_progress = false;
            // Remain in error until cleared
            break;
        default:
            break;
    }
}

flap_ctrl_state_t get_flap_ctrl_state(void) {
    return ctrl_state;
}

bool get_ctrl_error_flag(void) {
    return error_flag;
}

void clear_ctrl_error(void) {
    ctrl_state = CTRL_IDLE;
    error_flag = false;
}
