# 1.0 Architecture Style Selection

### Candidate Styles Evaluated
- Layered
- Component-Based (Module/Unit with clear interfaces)
- Monolithic

### Evaluation Against Needs
- **System Complexity:** Minimal; actuator logic is sequential, with clear input/output boundaries.
- **HW Interaction Needs:** Multiple MCU internal peripherals (ADC, PWM/CCU6, GPIOs, UART) with strong boundaries between command processing, sensor feedback, and actuator output. HW mapping arguments favor a component-based or layered style.
- **Testability:** Highest if software is modularized; grouping user interface, control kernel, and output drivers separately … matches ASPICE expectations.
- **Maintainability:** Easier with clear separation (component-based or layered). Monolithic would reduce maintainability and testability.
- **ASPICE L3:** Expects software architecture (SWE.2) to justify modularization, clear interfaces, and traceability to requirements (SWE.1). Modularity is needed.

### Selection & Justification
- **Selected Approach:** Component-Based / Modular (each logical responsibility as a separate software unit with explicit interfaces)
- **Rejected:**
  - **Monolithic:** Would not support ASPICE L3 or maintainability.
  - **Strict Layered:** Over-detailed for such a simple embedded actuator. Our architecture will permit layers-de-facto by strict module separation, but is not enforcing OSI-like stacks.

# 2.0 Software Architecture Definition (SWE.2)

## 2.1 Overview
The software is partitioned into discrete units each fulfilling an identifiable, traceable responsibility tied to SWE.1 requirements. Units communicate only via explicit interfaces – no global state (except for minimal cross-unit status needed for correct actuator function). All hardware-related information (registers, signals, constraints) is based exclusively on information present in the cited TLE985x documents (see above—no invention of electrical characteristics/values).

## 2.2 Software Units / Responsibilities / Interfaces

### 1. **User Command Interface Unit**
- Responsibilities: Receives UART commands, decodes requested position, validates user input against supported positions.
- Provided interfaces: user_command_received(command)
- Used interfaces: None (initial input source)
- Requirements: SWE-REQ-001, SWE-REQ-002, SWE-REQ-003, SWE-REQ-014

### 2. **Flap Position Control Kernel**
- Responsibilities: Core logic – compares requested position to actual (from feedback), determines if motor movement is needed, issues actuation requests.
- Provided interfaces: request_move_to(position)
- Used interfaces: get_actual_position() from Feedback Acquisition; actuate_motor(direction, enable) from Output Driver
- Requirements: SWE-REQ-004, SWE-REQ-005, SWE-REQ-021

### 3. **Feedback Acquisition Unit**
- Responsibilities: Reads ADC potentiometer channel, converts ADC to position, validates range.
- Provided interfaces: get_actual_position() => position, get_adc_value()
- Used interfaces: None (hardware ADC)
- Requirements: SWE-REQ-009, SWE-REQ-010, SWE-REQ-011, SWE-REQ-015

### 4. **Motor Driver Output Unit**
- Responsibilities: Direct GPIO and PWM/CCU6 configuration, output for motor enable/disable and direction; react to control kernel requests.
- Provided interfaces: actuate_motor(direction, enable)
- Used interfaces: None (HW access)
- Requirements: SWE-REQ-006, SWE-REQ-007, SWE-REQ-008, SWE-REQ-016

### 5. **Status Indicator Output Unit**
- Responsibilities: Drives GPIO or HS switch for Power/Position LEDs following position changes; reflects system state per requirements.
- Provided interfaces: update_leds(position)
- Used interfaces: None
- Requirements: SWE-REQ-012, SWE-REQ-013, SWE-REQ-017

### 6. **System Initialization/Reset Unit**
- Responsibilities: On power-up, initialize all peripherals (UART, GPIO, CCU6/PWM, ADC); ensure all outputs in safe state.
- Provided interfaces: initialize_system()
- Used interfaces: None
- Requirements: SWE-REQ-018, SWE-REQ-019, SWE-REQ-020

### 7. **Error Management Unit**
- Responsibilities: Detects/handles out-of-range ADC, input errors, mechanical/electrical motor faults, disables actuator when needed.
- Provided interfaces: handle_input_error(), handle_feedback_error(type), handle_motor_fault()
- Used interfaces: None (watches signals)
- Requirements: SWE-REQ-011, SWE-REQ-022, SWE-REQ-026, SWE-REQ-027, SWE-REQ-028

### 8. **Configuration/Data Definition Unit**
- Responsibilities: Stores/calibrates position ranges, channel assignments, unaffected by run-time state.
- Provided interfaces: get_position_limits()
- Used interfaces: None
- Requirements: SWE-REQ-023, SWE-REQ-024, SWE-REQ-025

## 2.3 Execution Model
No explicit execution model or scheduling policy is mandated by the requirements at this stage. All interactions may be performed using event-driven (interrupt) and polling mechanisms as long as responsibilities and interface constraints above are preserved and traceable.

SOFTWARE LOW-LEVEL DESIGN (SWE.3)
==============================

Branch: {branch}
Source Requirements: sw-reqs/sw-reqs.txt, sw-arch/sw-arch.txt

-------------------------------
ARCHITECTURE UNITS (per SWE.2):
-------------------------------
- User Command Manager
- Command Validator
- Flap Control Unit
- Motor Driver Interface
- Position Feedback Processor
- Status Indicator Control
- System Error Handler

==============================
SOFTWARE UNITS DETAILED DESIGN
==============================

----------------------
Software Unit: User Command Manager
----------------------
1. Responsibilities
   - Handles user flap position command reception via UART.
   - Does not handle validation or command application.
2. Internal Data Design
   - UART Rx buffer (fixed length array)
   - Command receive flags
   - Last received timestamp
3. State Machine
   - States: IDLE, RECEIVING, RECEIVED
   - Events: UART RX interrupt, buffer full, command transfer complete
   - Actions: Buffer data, set flags
4. Algorithms & Control Flow
   - Wait for UART RX event
   - Buffer data until end of command/message marker
   - Flag completion for validation
5. Interfaces (APIs)
   - Provided: get_next_command(buffer, len), clear_flag()
   - Required: UART HAL RX
   - Returns: Status (OK, ERROR, INCOMPLETE)
   - Error: Invalid/overflowed packet returns ERROR, buffer cleared
6. Error Handling
   - Overflow or malformed -> ERROR, clear buffer
   - No command within timeout -> IDLE
7. Resource & Timing
   - Invoked on UART RX event
   - WCET: <<1 ms per call
   - Non-reentrant
8. Traceability: SWE-REQ-001, SWE-REQ-010

----------------------
Software Unit: Command Validator
----------------------
1. Responsibilities
   - Handles command integrity, range checking; does not receive or apply commands
2. Internal Data Design
   - Last validated command struct
   - Range limits (const)
3. State Machine
   - None (stateless)
   - Each input validated in isolation
4. Algorithms & Control Flow
   - Check syntax/length
   - Check if flap position in min...max
   - Set valid/invalid flag
5. Interfaces (APIs)
   - Provided: validate_command(cmd)
   - Required: get_next_command(...)
   - Returns: Status (VALID, INVALID)
   - Error reporting: INVALID status
6. Error Handling
   - Out of range/syntax error -> INVALID
7. Resource & Timing
   - On demand per command arrival
   - WCET: <<1 ms
   - Reentrant
8. Traceability: SWE-REQ-002, SWE-REQ-003

----------------------
Software Unit: Flap Control Unit
----------------------
1. Responsibilities
   - Computes setpoints, initiates motion
2. Internal Data Design
   - Current position (volatile)
   - Target position (volatile)
   - Tolerance (const/flash)
   - Command pending flag
3. State Machine
   - States: IDLE, MOVING, TARGET_REACHED
   - Events: New valid command, feedback update
   - Actions: Update setpoint, send motion request, clear pending
4. Algorithms & Control Flow
   - If command pending, compare target/actual
   - If outside tolerance, signal motor driver
   - When within tolerance, set TARGET_REACHED
5. Interfaces (APIs)
   - Provided: set_flap_position(target), get_status()
   - Required: validate_command(), position_feedback()
   - Returns: Status, target achieved
   - Error: error codes returned for invalid input
6. Error Handling
   - On sensor fault -> error status, no motion
7. Resource & Timing
   - Invoked per command/feedback event
   - WCET: 1-2 ms per call (incl. comparison)
   - Non-reentrant
8. Traceability: SWE-REQ-004, SWE-REQ-005, SWE-REQ-006, SWE-REQ-015, SWE-REQ-016

----------------------
Software Unit: Motor Driver Interface
----------------------
1. Responsibilities
   - Handles physical actuation; does not compute target
2. Internal Data Design
   - Motor driver control flags
   - Output enable bit
3. State Machine
   - States: MOTOR_OFF, MOTOR_ON
   - Events: Drive request, stop request
   - Actions: Set or clear output
4. Algorithms & Control Flow
   - On drive request, set output enable
   - On stop, clear output
   - On error, ensure output is cleared
5. Interfaces (APIs)
   - Provided: drive_motor(enable)
   - Required: set_flap_position(), error_handler()
   - Error: Returns driver error codes
6. Error Handling
   - Fault/overcurrent: immediately clear output, report error
7. Resource & Timing
   - Invoked per control event
   - WCET: <<1 ms
   - Non-reentrant
8. Traceability: SWE-REQ-005, SWE-REQ-006, SWE-REQ-012

----------------------
Software Unit: Position Feedback Processor
----------------------
1. Responsibilities
   - Sensor data acquisition/validation; does not compute motion
2. Internal Data Design
   - ADC buffer
   - Valid/fault flags
   - Current position variable
3. State Machine
   - States: VALID, FAULT
   - Events: ADC update, self test
   - Actions: Store value, set fault if out of bounds
4. Algorithms & Control Flow
   - Sample ADC, check plausibility
   - If sensor out of range, set FAULT
   - Provide position to requester
5. Interfaces (APIs)
   - Provided: position_feedback(), get_sensor_status()
   - Required: ADC HAL
   - Error: Fault codes on sensor error
6. Error Handling
   - Sensor fault triggers FAULT state
7. Resource & Timing
   - Invoked per ADC conversion/event
   - WCET: <<1 ms
   - Reentrant
8. Traceability: SWE-REQ-007, SWE-REQ-008, SWE-REQ-011

----------------------
Software Unit: Status Indicator Control
----------------------
1. Responsibilities
   - LED output; does not determine error/state
2. Internal Data Design
   - LED state bits
   - Color/state codemap (ROM)
3. State Machine
   - States: NORMAL, MOVING, TARGET_REACHED, ERROR
   - Events: System status change
   - Actions: Update LED outputs
4. Algorithms & Control Flow
   - On event, lookup codemap, set LED outputs
5. Interfaces (APIs)
   - Provided: set_led_state(state)
   - Required: system_state_input
   - Returns: LED status
   - Error: Unreachable state returns code
6. Error Handling
   - Unmapped state triggers ERROR LED
7. Resource & Timing
   - Invoked per system status change
   - WCET: <<1 ms
   - Non-reentrant
8. Traceability: SWE-REQ-009, SWE-REQ-013, SWE-REQ-018

----------------------
Software Unit: System Error Handler
----------------------
1. Responsibilities
   - Drives error/safe state logic; does not perform recovery itself
2. Internal Data Design
   - Error status bits
   - Fault log
3. State Machine
   - States: NORMAL, ERROR, SAFE_IDLE
   - Events: Fault detected, error input, system reset
   - Actions: Log, set safe/idle
4. Algorithms & Control Flow
   - On error, transition to ERROR/SAFE_IDLE
   - On reset, clear error bits
5. Interfaces (APIs)
   - Provided: error_handler(), reset_system()
   - Required: error input, command validator, feedback proc.
   - Returns: Error status
   - Error: Codes for user
6. Error Handling
   - Any unhandled fault -> SAFE_IDLE
7. Resource & Timing
   - Event driven by input
   - WCET: 1 ms max
   - Reentrant
8. Traceability: SWE-REQ-017, SWE-REQ-018, SWE-REQ-020, SWE-REQ-021

END OF FILE -- ALL UNITS TRACEABLE TO SWE.1 and MAINTAIN STRICT ARCHITECTURE, NO CODE or ADDITIONAL UNITS.
