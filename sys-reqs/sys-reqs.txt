1.0 System Overview

The HVAC Flap Actuator system is a microcontroller-based prototype that controls the position of an air mixing flap using a DC motor, as typically found in vehicle HVAC systems. The system receives discrete position commands from a user via UART, moves the flap using a DC motor, monitors position with a potentiometer (via ADC), and provides visual status feedback using LEDs. The hardware is based on an STM32F407 platform, motor driver, and UART/ADC/LED peripherals. The design focuses on demonstrating embedded control concepts and SW process best practices.

2.0 Flap Position Control Requirements
SYS-REQ-001: The system shall allow a user to command the flap to any discrete position between 0 and 5, inclusive.
SYS-REQ-002: The system shall map each received valid command (0-5) to a unique flap position.
SYS-REQ-003: The system shall compare the current position to the target position after each command or position feedback update.
SYS-REQ-004: The system shall move the flap to the commanded target position when different from the current position.
SYS-REQ-005: The system shall stop the motor when the flap reaches the target position.
SYS-REQ-006: The system shall hold the flap at the target position after reaching it.
SYS-REQ-007: The system shall ignore commands outside the valid range (0-5) and shall leave the flap unmoved in such case.
[Implied] SYS-REQ-008: The system shall not allow fractional or undefined positions between the defined discrete states.

3.0 Motor Control Requirements
SYS-REQ-009: The system shall control the DC motor direction (clockwise or anti-clockwise) through dedicated GPIO pins.
SYS-REQ-010: The system shall enable or disable the motor using a PWM or equivalent control signal.
SYS-REQ-011: The motor shall be disabled (stopped) by default after power-up and during error or idle conditions.
SYS-REQ-012: When moving to a target, the system shall determine and execute the direction required (cw/ccw) to reach the desired position.
SYS-REQ-013: The system shall stop the motor immediately upon determining the target position has been reached.
[Implied] SYS-REQ-014: The system shall not drive the motor beyond mechanical or feedback limits defined in software.

4.0 Position Feedback Acquisition and Processing
SYS-REQ-015: The system shall acquire the potentiometer position feedback using an ADC channel.
SYS-REQ-016: The ADC shall sample the potentiometer value periodically or upon relevant events.
SYS-REQ-017: The system shall map the raw ADC value to logical flap position 0-5 based on fixed, calibrated ranges.
[Implied] SYS-REQ-018: The system shall handle ADC readings outside expected operating range as an error.
[Implied] SYS-REQ-019: No calibration or learning sequences shall be performed at runtime on this prototype.

5.0 User Command Interface Requirements
SYS-REQ-020: The system shall accept user commands via the UART interface only.
SYS-REQ-021: Each received UART command shall be parsed as a single ASCII digit ("0"-"5") corresponding to target position.
SYS-REQ-022: The system shall validate each command, accepting only values in the permitted range (0-5).
SYS-REQ-023: Upon receiving an invalid command, the system shall ignore it and not move the flap or respond on UART.

6.0 Status Indication Requirements
SYS-REQ-024: The system shall indicate power/status with one LED that is illuminated when the system is powered on and initialized.
SYS-REQ-025: The system shall use one LED to indicate the current logical flap position (0-5); only the LED corresponding to the present position shall be ON at any time.
SYS-REQ-026: Only one position LED shall be on at a time, except during initialization or error indication.
[Implied] SYS-REQ-027: LEDs used for status indication shall be GPIO-controlled outputs.

7.0 System Behavioral Requirements
SYS-REQ-028: On power-up, the system shall initialize all required peripherals (UART, ADC, GPIO, PWM) before enabling other actions.
SYS-REQ-029: After initialization, the system shall read the potentiometer and update the position indicator LEDs to reflect the initial flap position.
SYS-REQ-030: The motor shall remain OFF after system reset or power-up until a valid position command is received.
SYS-REQ-031: During idle, the system shall continue to monitor input and feedback without moving the flap.
SYS-REQ-032: When the target position is reached, the system shall stop the motor and update the LED status.
SYS-REQ-033: If invalid input or feedback is detected, the system shall stop the motor and maintain last known safe state.
[Implied] SYS-REQ-034: The system shall not require a homing sequence on power-up for this prototype.

8.0 System Interface Requirements
SYS-REQ-035: The system shall expose a UART interface for receiving user commands from a PC.
SYS-REQ-036: The system shall interface with a DC motor driver (L298N or equivalent) through GPIO and PWM outputs.
SYS-REQ-037: The system shall read potentiometer feedback via at least one ADC input channel.
SYS-REQ-038: The system shall control at least one status LED and multiple position-indicator LEDs via GPIO outputs.
[Implied] SYS-REQ-039: No vehicle network (CAN, LIN) communications shall be implemented or required.

9.0 Constraints and Assumptions
SYS-REQ-040: Only one flap actuator, motor, and user are present in the system at any time.
SYS-REQ-041: Hardware is expected to function as designed; no advanced diagnostic or recovery is implemented.
SYS-REQ-042: Flap position calibration values are pre-defined and not field-configurable.
SYS-REQ-043: Only software running on the target microcontroller is in scope for these requirements.

10.0 Non-Functional Requirements
10.1 Responsiveness Expectations
SYS-REQ-044: The system shall process valid UART commands and respond by starting flap movement with observable responsiveness to a human user (i.e., typical delay perceived as immediate but no timing guarantee).
[Implied] SYS-REQ-045: The system shall avoid unnecessary latency between command reception and actuator movement.

10.2 Error Handling and Edge Cases
SYS-REQ-046: The system shall stop the motor if ADC readings indicate position feedback outside expected ranges.
SYS-REQ-047: The system shall ignore and not act upon invalid UART commands.
SYS-REQ-048: The system shall maintain safe idle state if the flap cannot reach the requested position.
[Implied] SYS-REQ-049: No error codes or diagnostic information shall be sent to the user or PC for this prototype.

10.3 Resource Constraints
SYS-REQ-050: The system implementation shall avoid dynamic memory allocation.
SYS-REQ-051: The system shall operate with predictable, bounded stack and memory usage.
[Implied] SYS-REQ-052: Implementation shall be lightweight for learning and demonstration purposes.

10.4 Maintainability and Modularity
SYS-REQ-053: The software structure shall provide clear, modular separation between command handling, motor control, position sensing, and indication logic.
[Implied] SYS-REQ-054: All requirement-relevant code shall be understandable and modifiable for educational purposes.

10.5 Testability
SYS-REQ-055: The system shall support manual testing by allowing operators to send UART commands and observe motor and LED responses.
SYS-REQ-056: The system shall permit script-based automated command/response testing over UART.
SYS-REQ-057: The system shall provide observable status through LEDs and UART, supporting requirement verification.


Architecture-Relevant Considerations Derived from System Requirements

- The system controls only one actuator and motor in a simple command-response (single responsibility) model.
- All external interaction is local and unidirectional (UART commands in, no vehicle bus; outputs to motor/LEDs only).
- Flap movement logic is straightforward: there is no need for explicit multi-threaded or concurrent responsibilities.
- Interface complexity is low (UART for commands, ADC for feedback, GPIO/PWM for output control).
- HW/SW boundary is clear and software responsibilities are defined in terms of device drivers and command-processing logic.
- Expandability is implicit but limited by the single-flap, single-user scope and no dynamic configuration.
- Simplicity and clarity are primary design drivers, as the system is meant for demonstration and process understanding, not production scale or extensibility.
