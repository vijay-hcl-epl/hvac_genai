# 1.0 Software Scope and Responsibility
The HVAC flap actuator software is responsible for receiving user commands via UART, validating these commands, actuating a DC motor to move a physical air flap to requested discrete positions, acquiring feedback through an ADC-connected position sensor, and reflecting current position/status through dedicated indicator LEDs. The software supports a learning/demo platform for prototyping, emphasizing modularity, clarity, and safe handling of user input, errors, and peripheral interactions.

# 2.0 Software Functional Requirements
## 2.1 User Command Handling
- SWE-REQ-001: The software shall receive user commands via UART in the form of discrete numeric flap position requests. (*SYS-REQ-017*)
- SWE-REQ-002: The software shall validate incoming UART commands to ensure they represent valid flap positions within the supported range. (*SYS-REQ-018, SYS-REQ-019*)
- SWE-REQ-003: The software shall accept and process only one user command at a time. (*SYS-REQ-020, SYS-REQ-039*)
- SWE-REQ-004: The software shall ignore invalid or out-of-range commands without generating a response or error indication. (*SYS-REQ-019*)
- SWE-REQ-005 [Implied]: The software shall process valid UART commands promptly after reception to maintain responsiveness. (*SYS-REQ-021*)

## 2.2 Flap Position Control Logic
- SWE-REQ-006: The software shall determine the required movement direction for the flap based on the current and target positions. (*SYS-REQ-003*)
- SWE-REQ-007: The software shall prevent actuation if the flap is already at the requested position. (*SYS-REQ-007*)
- SWE-REQ-008: The software shall ensure the flap does not move outside defined position limits. (*SYS-REQ-011*)
- SWE-REQ-009: The software shall stop the motor and maintain the flap at the target position when reached. (*SYS-REQ-005*)

## 2.3 Motor Control Logic
- SWE-REQ-010: The software shall control GPIO outputs to set the proper motor direction according to the target position. (*SYS-REQ-008*)
- SWE-REQ-011: The software shall enable and disable the motor using a dedicated control signal (GPIO or PWM). (*SYS-REQ-009*)
- SWE-REQ-012: The software shall de-energize (stop) the motor when the flap has reached the requested position or when an error is detected. (*SYS-REQ-010, SYS-REQ-045*)
- SWE-REQ-013 [Implied]: The software shall avoid unnecessary or excessive motor running by stopping promptly on target acquisition or error. (*SYS-REQ-012*)

## 2.4 Position Feedback Processing
- SWE-REQ-014: The software shall acquire flap position feedback using an ADC to sample the potentiometer. (*SYS-REQ-002, SYS-REQ-013*)
- SWE-REQ-015: The software shall map ADC readings to defined logical flap positions using fixed mappings in software. (*SYS-REQ-006, SYS-REQ-014, SYS-REQ-041*)
- SWE-REQ-016: The software shall ignore ADC values outside valid operating ranges mapped to supported positions. (*SYS-REQ-015, SYS-REQ-045*)
- SWE-REQ-017 [Implied]: The software shall ensure ADC resolution and filtering are sufficient for stable position detection in the demo environment. (*SYS-REQ-016*)

## 2.5 Status Indication Control
- SWE-REQ-018: The software shall use a dedicated LED to indicate power/status. (*SYS-REQ-022*)
- SWE-REQ-019: The software shall use dedicated position LEDs to reflect the current logical flap position, with one green LED ON per position. (*SYS-REQ-023, SYS-REQ-024*)
- SWE-REQ-020: The software shall update the position/status LEDs to reflect the actual position as determined from ADC feedback at all times. (*SYS-REQ-024*)
- SWE-REQ-021 [Implied]: The indication logic shall be clear and unambiguous for all allowed positions and states. (*SYS-REQ-025*)

# 3.0 Software Interface Requirements
- SWE-REQ-022: The software shall receive PC user commands via UART interface. (*SYS-REQ-033*)
- SWE-REQ-023: The software shall transmit motor direction/enable signals via GPIO to the motor driver. (*SYS-REQ-034*)
- SWE-REQ-024: The software shall acquire flap position using an ADC channel attached to the position sensor. (*SYS-REQ-035*)
- SWE-REQ-025: The software shall control dedicated GPIOs for LEDs indicating power, error, and position. (*SYS-REQ-036*)
- SWE-REQ-026 [Implied]: The software shall not use CAN, LIN, or other external networking. (*SYS-REQ-037*)

# 4.0 Software Behavioral Requirements
- SWE-REQ-027: Upon power-up, the software shall initialize all peripherals (ADC, UART, GPIO, PWM) and leave the motor OFF. (*SYS-REQ-026*)
- SWE-REQ-028: On startup, the software shall sample and store the initial flap position. (*SYS-REQ-027*)
- SWE-REQ-029: During idle, the software shall monitor for new user commands and changes in flap position. (*SYS-REQ-028*)
- SWE-REQ-030: The software shall cause the flap to move toward the requested position and detect when the target position is reached. (*SYS-REQ-029*)
- SWE-REQ-031: After reaching the target, the software shall maintain its state and ignore redundant commands unless a new target is received. (*SYS-REQ-030*)
- SWE-REQ-032: The software shall safely ignore invalid input (UART command or feedback) without undefined behavior. (*SYS-REQ-031, SYS-REQ-044*)
- SWE-REQ-033 [Implied]: No explicit state machine or production-grade diagnostics are required. (*SYS-REQ-032*)

# 5.0 Software Data and Configuration Requirements
- SWE-REQ-034: The software shall maintain a static table of ADC-to-position mappings (calibration constants) defined in code. (*SYS-REQ-006, SYS-REQ-041*)
- SWE-REQ-035: The software shall use only static calibration values for position mapping and thresholding. (*SYS-REQ-041*)
- SWE-REQ-036: The software shall not implement dynamic calibration, parameter auto-learning, or store configuration changes. (*SYS-REQ-041*)
- SWE-REQ-037 [Implied]: Internal variables, constants, and mapping data shall be bounded and statically allocated only. (*SYS-REQ-042*)

# 6.0 Software Error Handling Requirements
- SWE-REQ-038: The software shall deterministically ignore and not act on any invalid user command or ADC input. (*SYS-REQ-019, SYS-REQ-015, SYS-REQ-044*)
- SWE-REQ-039: When ADC position feedback is out of range, the software shall stop the motor immediately and not attempt to move further. (*SYS-REQ-045*)
- SWE-REQ-040: The software shall safely leave motor and indicators in a known, safe state after any error. (*SYS-REQ-010, SYS-REQ-045*)
- SWE-REQ-041 [Implied]: No advanced diagnostics or error recovery (timeouts, watchdog resets, or logging) are required. (*SYS-REQ-046*)

# 7.0 Software Performance and Responsiveness Requirements
- SWE-REQ-042: The software shall respond to valid user commands by changing the flap position and LED statuses promptly (in a manner observable by a human). (*SYS-REQ-043*)
- SWE-REQ-043: The software shall ensure position feedback and motor actuation updates occur without unnecessary latency, but without fixed timing constraints. (*SYS-REQ-043*)

# 8.0 Software Resource Constraint Requirements
- SWE-REQ-044: The software shall avoid dynamic memory allocation and shall use only minimal, statically allocated resources. (*SYS-REQ-048*)
- SWE-REQ-045: The software shall ensure all processing for input, control, and output is bounded and avoids unbounded execution (e.g., infinite loops, blocking waits). (*SYS-REQ-047*)
- SWE-REQ-046: The software shall maintain lightweight overall resource usage consistent with microcontroller learning platform norms. (*SYS-REQ-047*)
- SWE-REQ-047 [Implied]: The software shall not implement task-level or thread-level resource management (RTOS or concurrency). (*SYS-REQ-042*)

# 9.0 Software Testability Requirements
- SWE-REQ-048: The software shall support verification via UART control and observation of LEDs and motor motion. (*SYS-REQ-052*)
- SWE-REQ-049: Testing shall be possible via manual or batch/scripted UART command injection and visual/functional observation, with no special equipment. (*SYS-REQ-053*)
- SWE-REQ-050 [Implied]: Automated Hardware-in-the-Loop or remote verification is not required for this prototype. (*SYS-REQ-054*)

# 10.0 Implied Software Requirements
All [Implied] requirements are explicitly marked in sections above and directly trace to their source system-level requirements.

# Explicit Exclusions
The software requirements exclude:
- RTOS, super-loop, or fixed scheduling model assumptions
- Any task/thread structure, concurrency, or prioritization
- Safety integrity levels, ISO-26262 mechanisms, or diagnostics beyond basic safe error ignoring
- Cybersecurity or external diagnostics
- Networking protocols (CAN/LIN)
- Dynamic calibration, auto-learning, non-volatile storage, or field updates
- Automated HIL/SIL or remote verification tooling
